## 三、本轮任务

### 阶段 0：环境与冒烟
1. 按 26-9-14 runbook 起 server（放开限流：`AUTH_RATE_LIMIT_MAX=1000000`）+ 起 gateway（env 从 `docker/.env.debug` 导入）+ 监测栈。

### 阶段 1：写 gateway 压测客户端（核心工作）
现有 harness 是 socket.io 的，需要实现原生 WS 压测客户端（放 perf/ 下新脚本，如 `gw-harness.mjs`），协议严格对齐 `web/src/ws/wsClient.ts` 语义：
- 连接 `ws://localhost:8090/ws?deviceId=<每连接唯一>&token=<JWT>`（token 来自 HTTP 登录，登录契约见 `perf/README.md` 的"已知限制"）。
- 可靠上行：发 `{type:'message.send', data:{clientMsgId, conversationId, content, type:'text'}}`，等 `message.ack`（按 clientMsgId 匹配）计 RTT，超时计入错误。**必须实现**：clientMsgId 幂等重发（5s 超时重发、上限 3 次）、25s 心跳帧（否则 60s presence TTL 过期被判离线）、断线重连。
- 统计口径与旧 harness 完全一致：RTT 分位 p50/p95/p99/p999、发送数、ack 数、错误分类。
- conversationId 规则：相邻用户配对 `single_<minId>_<maxId>`（见 perf/README.md）。
- 保留连接爬坡、惊群重连、扇出三类场景的 gateway 版本（可参照旧 ramp-probe/storm-reconnect/fanout-bench 改造；扇出场景 gateway 路径下由 server 落库后 publish downlink 再经网关代投）。

- S1 常规吞吐：100 连接 × 10 msg/s × 20s
- S2 连接规模：300 连接 × 2 msg/s × 15s
- S3 过载压力：150 连接 × 20 msg/s × 15s
- S4 大连接：500 连接 × 1 msg/s × 15s

- S6 连接爬坡探顶：2000 起每级 +2000 → 10000（参考 ramp-probe 的 env 参数方式）

## 四、必须遵守的公平性与方法学（来自监测计划文档）

- 同环境、同参数、同 payload、同压测机；warm-up 后取稳态窗口，每场景 ≥3 轮取中位。
- parity 已满足（gateway 已实现 ack/心跳/重连/顺序/已读/信令），**不许用"少干活"的假快路径**（如不带 ack 等待）。
- RTT 用往返（clientMsgId 关联），不信单向延迟；服务端直方图与服务内埋点用于归因。
- 记录每场景 server 与 gateway 两侧资源采样（RSS/CPU），算每连接成本。
- 明确报告基线数据来源（26-9-14）与本次数据日期。

## 五、已知坑（务必避开）

1. 登录阶段 bcrypt 12 轮极慢（1 万用户约 15 分钟），大规模压测提前批量注册并复用账号。
2. `ramp-probe.mjs` 参数是环境变量不是位置参数。
3. 过载压测（≈3000 msg/s）曾使同机 colima docker 的 PG 短暂失联（P1001）；出现时 `colima stop && colima start` 恢复，且如实记录环境波动。
4. 本机 docker 是 colima 且官方 minio 镜像拉不动：若需重启 MinIO 用 `quay.io/minio/minio` 镜像（bucket 名 our-chat，需公有读 policy，可用 server 的 aws-sdk 建）。
5. gateway 慢消费者逐出（send 缓冲打满即踢）在极端扇出场景可能影响投递成功率——被逐出连接计数记入 `gateway_evicted_total`，报告里单独归因，不要混进"消息失败"。
6. vitest 集成测试会订阅 gw:downlink 频道，压测时不要同时跑集成测试，避免 pub/sub 串扰。
