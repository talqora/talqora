## 一、背景（直接采信，无需重新调研）

- 实时链路已改造完毕并三期实测验证：客户端（Web/iOS/压测）→ **gateway(Go)** 原生 WS `/ws`（唯一对外入口，含 HTTP 反代）→ **gRPC 双向流**（`proto/ourchat/edge/v1/realtime.proto`，4 流 userId 哈希分片）→ **server(Node) 业务层**（`server/src/realtime/edgeGrpc.ts` :3008 提供 gRPC 流服务）→ PG/Redis → 下行经 Redis pub/sub `gw:downlink` 由网关代投。
- 三期实测结论（`docs/监测设施/测试报告/26-9-14`、`26-9-16`、`26-9-16-grpc`）：传输层已不是瓶颈；**当前第一瓶颈是 DB 会话 seq 发号行锁**（2500+ msg/s 时 p99 ~2s、错误率 40~80%）。
- 架构决策已定（`docs/架构/系统架构图V3.md`、`消息同步架构分析-*.md`、`26-9-16-grpc-业务层分布式化与Go重写分析.md`）：
  1. **seq 发号改 Redis 原子自增**（`INCR conv:seq:{conversationId}`，初始值从 PG `conversations.next_seq` 装载，定期 checkpoint 回 PG，Redis 不可用降级回 DB 行锁路径）——重写时必须直接落地。
  2. **业务层形态 = Go 模块化单体（多副本无状态）**，模块进程内接口化、预留拆分边界；**不做微服务拆分**。
  3. **同步三段式保持不变**：PG 真相源 + Redis pub/sub 实时扇出 + `/sync` 离线补偿；**不引入消息队列做同步主路径**。
  4. 跨副本正确性前提：所有共享状态的 read-modify-write 必须原子（已发现缺陷：Node `callSession.tryCreateSession` 忙线裁决非原子，重写时用 `SET NX` + Lua 修复）。
  5. 客户端协议**零改动**（信封 `{type,data}`、`message.ack` 按 clientMsgId、25s 心跳、5s 超时同键重发×3、断线重连）——web/src/ws/wsClient.ts 是协议权威实现。

## 七、已知坑（务必避开）

1. 压测登录 bcrypt 12 轮极慢（1 万用户 ~12-15 分钟），大规模场景提前批量注册复用账号。
2. 同机 colima：≈3000 msg/s 过载曾三次使 PG/Redis 失联（P1001/ECONNREFUSED），恢复 `colima stop && colima start` 后等容器 healthy 再跑；过载场景（tp_r30）安排在所有轻负载场景之后。
3. colima 重启后 `our-chat-minio` 容器不会自动拉起（无 restart policy），需 `docker start our-chat-minio`。
4. 本地 `npm install` 需 `strict-ssl=false`（server/.npmrc 已有）；docker compose 插件不可用，用 `docker-compose` 或直接 docker 命令。
5. 压测时不要同时跑 vitest 集成测试（会订阅 gw:downlink 造成 pub/sub 串扰）。
6. gateway 上行已切 gRPC 流（`GATEWAY_UPSTREAM=grpc`），Go 业务服务的 gRPC 流服务必须实现 `ourchat.edge.v1.Realtime/Stream`（bidi，metadata `x-gateway-token` 鉴权），否则 gateway 连不上。
7. BigInt 序列化：Node 靠全局 toJSON polyfill；Go 侧规则——**gRPC 二进制帧内 seq/server_msg_id 按 int64 原样透传（proto 定义），仅 HTTP JSON 输出层转 number**（不超 2^53），与既有客户端行为一致。
