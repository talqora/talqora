## 一、背景：架构已发生的根本变化（相对 SOP V1）

| 维度 | SOP V1 时代（26-9-16） | 现在（26-9-18 之后） |
|---|---|---|
| 业务层 | server(Node, Express+Prisma, :3007) | **biz(Go, 模块化单体, 可多副本)** `biz/cmd/biz`；Node 已不在链路中 |
| 实时链路 | gateway → HTTP-per-message → Node | gateway → **gRPC 双向流**(userId 哈希分片) → biz |
| 下行 | Redis pub/sub `gw:downlink` 全副本广播 | **定向下行**:biz 按 presence.replica 经 gRPC 下行流直发,失败回退 pub/sub(双通道) |
| 发号 | DB 行锁 | Redis INCR + Lua 装载 + checkpoint + 防回卷 |
| 存储 | messages 单表 | **messages 哈希 64 分区**(`PARTITION BY HASH (conversation_id)`) |
| 网关多后端 | 单地址 | `EDGE_GRPC_ADDR` 逗号分隔多后端 + **健康感知 failover** |
| 保护 | 仅认证限流 | + 会话热点限流(`CONV_RATE_LIMIT_MAX`,默认 500/s/会话) |
| 读路径 | 单写库 | store.RO() 只读池(25 处读已切,`PG_READONLY_URL` 未配置回退写库) |
| health | 无 | 标准 grpc.health.v1(biz 侧) |
| keepalive | 曾存在 90s 周期断连 bug(30s ping vs 5min MinTime) | 已修复(server MinTime 20s + 主动探活) |
| 消息分页 | 无 limit 全量 | `/user/messages?limit=&beforeSeq=` 游标分页 + hasMore(无参兼容全量) |

**重要**:`server/`(Node) 目录仍在仓库但**不参与任何流量**;`REALTIME_MODE=socketio` 回滚开关保留但本轮不测。

## 二、任务清单(三个交付物,依次完成)

### T1 · 新建 Grafana 权威监测面板(整个系统的实时监测权威数据)

**红线**:`docker/monitoring/grafana/dashboards/realtime-node-vs-go.json`(Realtime: Node(server) vs Go(gateway))**一字不改**。新建面板文件 `realtime-system-authority.json` 放入同目录,标题「Realtime: 系统权威监测」。

**数据源现状与缺口(先修后建)**:
1. `docker/monitoring/prometheus.yml`:job=server 抓 `host.docker.internal:3007`(现为 biz 副本 1,注释还写着"Node 业务后端"——**更新注释**,保留 job 名以兼容旧面板);**新增 biz2 抓取**(3009,双副本时第二副本;单副本部署时该 target 静默失败无碍);gateway job 不变。
2. 可选加分项(非必须):postgres_exporter/redis_exporter——PG 分区表与 Redis 发号是热路径,但加 exporter 涉及容器编排,标记为"遗留建议"即可,不阻塞交付。

**面板覆盖清单(按此组织 row,覆盖整个系统关键节点;指标名以两侧 metrics.go 实测为准)**:

| Row | 面板 | 关键指标(expr 用 rate/histogram_quantile 规范写法) |
|---|---|---|
| 连接面 | 网关连接数、握手速率、慢消费者逐出 | `gateway_connections`、`rate(gateway_handshakes_total[1m])`、`rate(gateway_evicted_total[1m])` |
| 连接面 | biz gRPC 流数、在线用户 | `sum(server_ws_connections) by (job)`、`server_online_users` |
| 上行链路 | 上行帧速率+结果分类、上行延迟分位 | `rate(gateway_uplink_total{result=~".+"}[1m])` 按 result 分线、`histogram_quantile(0.99, sum(rate(gateway_uplink_duration_seconds_bucket[1m])) by (le))` |
| 消息处理 | 消息收发速率、处理延迟 p50/p95/p99 | `rate(server_message_in_total[1m])`、`rate(server_message_out_total{result="ok"}[1m])`、`histogram_quantile(0.99, sum(rate(server_message_duration_seconds_bucket[1m])) by (le))` |
| **下行双通道(本轮新增核心)** | 定向直发 vs pub/sub 回退速率+占比、网关下行投递分类 | `rate(server_downlink_direct_total[1m])`、`rate(server_downlink_fallback_total[1m])`、`sum(server_downlink_direct_total)/sum(server_downlink_direct_total+server_downlink_fallback_total)`、`rate(gateway_downlink_total{result=~"delivered|dropped|evicted"}[1m])`、`histogram_quantile(0.99, sum(rate(gateway_downlink_duration_seconds_bucket[1m])) by (le))` |
| 保护面 | 会话热点限流拒绝、认证限流 | `rate(server_conversation_rate_limited_total[1m])` |
| 通话面 | 通话事件、活跃通话 | `rate(server_call_events_total[1m])`、`server_active_calls` |
| HTTP 面 | 请求速率+延迟、RUM 客户端打点 | `rate(http_request_duration_seconds_count[1m])`、`histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[1m])) by (le))`、`histogram_quantile(0.95, sum(rate(server_rum_web_vitals_bucket[1m])) by (le))` |
| DB 面 | 查询速率+延迟按 model 分线 | `rate(db_query_duration_seconds_count[1m])`、`histogram_quantile(0.99, sum(rate(db_query_duration_seconds_bucket[1m])) by (le, model))` |
| Go 运行时 | 双端 goroutine、GC、内存、CPU | `go_goroutines{job=~"gateway|server|biz2"}`、`rate(go_gc_duration_seconds_sum[1m])`、`process_resident_memory_bytes`、`rate(process_cpu_seconds_total[1m])` |
| 副本面 | 各 biz 副本消息分流对比(多副本均衡性) | `rate(server_message_in_total[1m]) by (job)` |

- 面板类型:趋势用 timeseries;占比/总和用 stat 或 bar gauge;legend 带单位;深色友好(系统主题自适应,Grafana 默认即可)。
- 交付验证:面板 provision 后 `curl localhost:3001` 确认加载;压测期间抓一次全面板截图作为"监测闭环"证据(压测报告引用)。

### T2 · 写《压测分析SOPV2.md》(放 `docs/监测设施/`)

以 V1 为骨架重写,重点变化:
1. 架构速览换成全 Go 拓扑(gateway → gRPC 流 → biz ×N → PG 分区表/Redis);Node 只在"回滚开关保留"一句提及。
2. 测试对象与指标全集:替换 V1 的 Node 指标(eventloop/nodejs_gc 已无意义),改为上表两侧指标;指明 eventloop 指标已不存在、goroutine 采样注意 job 标签。
3. 关键业务流程监测点(P1 上行/P2 ack/P3 下行双通道/P4 心跳/P5 断连/P6 HTTP/P7 读):每个流程写清"看哪块面板、异常形态长什么样"(如定向下行异常=fallback 陡增;限流异常=rate_limited 计数突增)。
4. runbook 更新:中间件(colima)→ **biz 构建部署**(`go build -o /tmp/biz-server ./cmd/biz`,迁移已 embed、新增迁移必须 rebuild)→ 双副本(可选)→ gateway(多后端 env)→ 监测栈 → perf 工具链。
5. 已知坑:完整吸收 `docs/监测设施/测试报告/26-9-18/26-9-18-开发踩坑记录.md`(17 类)中最关键的:colima 失联 SOP(累计 15 次,恢复流程与断点续跑)、shell env 残留(启动必须显式 export 全部关键 env,排查先 `ps eww`)、keepalive 匹配(若再调 gRPC 参数,客户端 ping 间隔必须 < server MinTime)、流建立窗口(biz 重启后等 10s 再注入负载)、限流阈值 500 会拦热点会话(压测若单会话 >500/s 需调高 `CONV_RATE_LIMIT_MAX`)。
6. 分析方法升级:归因不再有"Node vs Go"维度,改为**跨期锚定**(vs 26-9-16-grpc Node 时代数据 / vs 26-9-18 同架构上期)+ **双副本视角**(分流均衡、failover)+ **下行双通道视角**(direct/fallback 比例);保留 V1 的公平性/3 轮中位/深色模式/归档结构全部红线。

## 五、已知坑(上期 17 类坑位精选,完整版见踩坑记录)

1. **colima 宿主守护进程频繁崩溃**(开发期间累计 15 次):`docker` 报 daemon 不可达/`colima status` 报 empty value。SOP:`colima stop && colima start` → sleep 24s → `docker start our-chat-minio`(minio 不自动拉起)→ 重启 biz/gateway → 探针 → 压测断点续跑。减压手段:停掉非本任务容器(agent-* 系列大户)。
2. **shell env 残留污染**:工具 shell 环境持久化,临时实例的 `CONV_RATE_LIMIT_MAX=3` 曾残留污染主实例(980 条消息 680 条被限流拒绝)。每次启动**显式 export 全部关键 env**;行为与配置不符先 `ps eww <pid> | tr ' ' '\n' | grep -E '^(PORT|EDGE|CONV|AUTH|REPLICA)'` 查进程 env。
3. **迁移 embed 进二进制**:biz 新增/改迁移后必须重新 `go build`;迁移版本号查 `biz/migrations/` 避免重复(上次撞 0003);dirty 修复先确认事务回滚完整。
4. **gRPC 流建立窗口**:biz/gateway 重启后 5~10s 内消息会"上行流不可用"失败——重启后先 gw-probe 再压测。
5. **keepalive 匹配**:gateway 客户端 ping `Time=30s`,biz server `MinTime=20s`;若调参破坏匹配会重现 90s 周期 GOAWAY 断连(上期已修,回归时留意 gateway 日志"上行流重建"频率)。
6. **限流阈值**:`CONV_RATE_LIMIT_MAX=500`/s/会话——单会话压测(如单会话打爆实验)超 500 会 429,压测主场景每会话 ≤30/s 不受影响;要测热点限流需专门场景(单会话 500+ msg/s)。
7. bcrypt 12 轮登录慢(1 万用户 ~12-15 分钟):S6 爬坡提前批量注册复用账号;`REG_CONCURRENCY=20` 勿调高。
8. 群扇出需要 `GROUP_ID=9000002`(直写 DB 建群);HTTP bench 输出默认落到 `26-9-14/data/http_bench.json`(旧目录),跑完要拷回当期归档并还原旧目录(git show 重定向)。
9. messages 分区表已上线:迁移已执行(schema_migrations version=7),新环境若从零建库会由 biz 启动自动跑全量迁移;旧数据 359 万行已回填,勿重复执行分区迁移。
10. 深色模式与 HTML 图表基线:gen-report 的 `*_socketio.json` 命名其实装载的是"基线"数据(上期拷三期数据改名),漏拷会图表全空——**15 个基线文件一个不能少**。
