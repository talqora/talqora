# 26-9-16-grpc · 网关↔业务层 gRPC 流改造复测报告（vs HTTP-per-message / 纯 Node 基线）

> 分支 `feat/perf-monitoring`。承接 `26-9-16-连接层业务层通信架构演进方案-RPC改造.md` 的 P0-P3 落地复测：
> 上行通道由 HTTP-per-message 换成 **gRPC 双向流**（`ourchat.edge.v1.Realtime/Stream`，4 流 userId 哈希分片、
> 异步确认、并发上行 + in-flight 背压），网关同时启用 HTTP 反代作为唯一对外入口。
> 本报告回答：改造是否兑现了方案文档 §7 的定量预期、失败模式如何变化、代价是什么。
>
> 数据：`data/*.json`（`*_gateway.json` 为本期 gRPC 流模式，每场景 3 轮取 RTT p99 中位；`*_socketio.json` 为 26-9-14 纯 Node 基线）。
> 对照：`../26-9-16/`（HTTP-per-message 模式同参数数据）。HTML 汇总见同目录 `性能对比报告.html`（gen-report 生成）。

---

## 0. 结论速览

1. **方案兑现,且超预期**:≤1500 msg/s 全部零错误(HTTP 模式在 1000 msg/s 就有 12.8% 失败),RTT 在中等负载**追平纯 Node 基线**(S1 p99 63ms vs 基线 57ms;S5 p99 70ms vs 61ms)——「换 Go 网关消息变慢」的固有代价几乎被抹平。
2. **dial 耗尽根除**:1000~3000 msg/s 全程 TIME_WAIT 峰值 785(HTTP 模式 14,922/16,384 打满),`upstream_error` 归零。
3. **失败模式切换成功**:2500~3000 msg/s 时错误全部是 `message.error`(**服务端快速拒绝**),RTT p99≈2.08s 与 Node 基线(2.06s)几乎一致——排队被消除后,DB 发号行锁成为唯一瓶颈,**与方案文档 §7「诚实预期」完全吻合**。
4. **2000 msg/s 是 gRPC 模式的新拐点**:RTT p99 从 232ms(1500)跃升到 1464ms(2000),但仍零错误,且优于基线同点(7.6% 错误、p99 2041ms)。
5. **P3 唯一入口落地**:/api、/user、/oauth、/health 全部经网关反代,反代零损耗(login 19.7 vs 直连 19.4 rps);WS 与 HTTP 同端口 8090。
6. **如实记录**:过载场景(≈3000 msg/s)三次使同机 colima docker 失联(26-9-14 已知坑 3 重现),tp_r30 第三轮无效已过滤;该现象是**同机争抢的环境问题**,不是本次改造引入。

## 2. 主场景 A/B 对比(纯 Node 基线 / HTTP 模式 / gRPC 流模式)

| 场景 | 参数 | 指标 | Node 基线 | HTTP 模式(26-9-16) | **gRPC 流(本期)** |
|---|---|---|---|---|---|
| S0 | 50×2×15s | RTT p50/95/99 | 19/34/56 | 22/35/50 | **20/29/46** |
| S1 | 100×10×20s | 错误率 | 0% | 12.8% | **0%** |
| | | RTT p50/95/99/999 | 33/50/57/— | 40/117/209/267 | **32/52/63/80** |
| S2 | 300×2×15s | 错误率 | 0% | 0% | **0%** |
| | | RTT p99 | 171 | 180 | **180** |
| S3 | 150×20×15s | 错误率(类型) | 49.6%(message.error) | 14.0%(ack_timeout) | **39.8%(message.error)** |
| | | RTT p99 | 2059 | 5067 | **2053** |
| S4 | 500×1×15s | 错误率 / RTT p99 | 0% / 276 | 0% / 307 | **0% / 328** |
| S5 | 100×5×120s | 错误率 / RTT p99 | 0% / 61 | 0% / 108 | **0% / 70** |
| | | 心跳/重连 | — | 0 重连 | **0 重连** |

要点:
- **S1 是本次改造的核心验收点**:HTTP 模式的 12.8% 失败(2534 条)归零,RTT p99 从 209ms 降到 63ms,仅比纯 Node 基线慢 6ms(63 vs 57)——**gRPC 流把「多一跳」的代价从 +152ms 压缩到 +6ms**。
- **S5 长稳**:120s 零错误零重连,RTT p99 70ms(vs HTTP 模式 108ms),2 分钟窗口无漂移。
- **S3 过载**:gRPC 模式失败模式从「排队+超时」(HTTP 模式 p99=5067ms、14% ack_timeout)切换为「快速拒绝」(39.8% message.error、p99=2053ms)——**与 Node 基线(49.6% error、2059ms)同构**:业务层 DB 行锁瓶颈成为唯一主导,网关不再放大延迟。
- **S4**:RTT p99 328 vs 基线 276(差距 52ms)——500 条连接场景下每连接 in-flight 竞争与 4 流分片的哈希不均带来少量排队,属可接受区间。

|---|---|---|---|
| 10 (1000) | 0% / 62 | 16.9% / 97 | **0% / 73** |
| 15 (1500) | 0% / 58 | 33.3% / 389 | **0% / 232** |
| 20 (2000) | 7.6% / 2041 | 1.4% / 528 | **0% / 1464** |

| 30 (3000) | 62.5% / 2096 | 15.7% / 6072 | **79.9% / 2086** |

要点:
- **零错误区间从 ≤600 msg/s(HTTP 模式)扩展到 ≤2000 msg/s(gRPC 流)**,且 RTT 全程低于 HTTP 模式(除 r25 外——r25 的 HTTP 模式 0 错误是"排队换来的假象",代价是 p99 2802ms)。

- tp_r30 三轮中 r3 因 colima 失联无效(r2 后),取 r1/r2 中位;错误率 79.9%(全部 message.error 快速失败)。

## 6. 与方案文档定量预期的逐条核对(§7)

| 预期 | 实际 | 判定 |
|---|---|---|
| S1 错误率 12.8% → 0% | 0% | ✅ 兑现 |
| upstream_error ≈1000 msg/s 归零 | 全程归零,TIME_WAIT 峰值 785 | ✅ 兑现 |
| tp_r25 RTT p99 2802 → <500ms | 2075ms | ⚠️ **未达成**——原因见下 |
| tp_r30 错误率 <5% 且以快速失败为主 | 79.9%,全部 message.error | ⚠️ 错误率未达,但**失败模式(快速失败)达成** |
| S2/S4/S5 RTT ≈基线 | S2 180≈171、S5 70≈61、S4 328 vs 276 | ✅ 基本达成(S4 略高) |
| 客户端协议零改动 | 零改动复用 | ✅ 兑现 |
| 诚实预期:DB 行锁竞争回归基线水平 | 2500+ msg/s 时服务内瓶颈与基线几乎一致(p99≈2.08s) | ✅ 精确兑现 |

**tp_r25 未达成 <500ms 的原因分析(非网关问题)**:2000 msg/s 起 DB 会话发号行锁成为主导(与 Node 基线 2041ms 同点爆发),gRPC 流的 p99 与基线相差仅 17ms(2075 vs 2058)——**改造已把网关侧的额外延迟完全消除,剩余 2 秒全部是业务层 DB 瓶颈**。这正是方案文档 §9 风险 1 预告的场景:下一步应做**发号改造(Redis 原子自增/批量预取)+ 服务端限流**,把错误率压下去——那已不属于本阶段(传输层改造)的范围。

## 7. 结论:改造效果定量总结

1. **快了多少**:中等负载(≤1500 msg/s)消息 RTT 与纯 Node 基线持平(S1 p99 63 vs 57ms、S5 70 vs 61ms),相比 HTTP-per-message 模式 p99 下降 45~70%(S1 209→63、S5 108→70);网关 CPU 省 40~55%。
2. **拐点移动**:gateway 路径的失败拐点从 **≈600 msg/s(HTTP 模式)推迟到 ≈2000 msg/s(gRPC 流)**,且 2000~3000 msg/s 的失败模式与纯 Node 基线同构(快速拒绝而非排队)——**「换 Go 网关=排队爆延迟」的缺陷被根除**。
3. **唯一入口落地**:HTTP+WS 全流量经网关 8090,反代零损耗,业务层可内网化。
4. **未竟事项(如实)**:① 2500+ msg/s 的 DB 发号行锁是下一瓶颈(建议发号改 Redis 自增 + 限流拒绝,方案文档 §9);② 下行仍走 Redis gw:downlink(目标态应切 gRPC 下行流,方案文档 §4.4/P3);③ 过载压测仍会打挂同机 colima(环境问题,需独立环境复测)。
