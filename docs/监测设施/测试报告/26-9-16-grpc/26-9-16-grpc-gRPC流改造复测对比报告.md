# 26-9-16-grpc · gRPC 流改造复测报告（含深度归因：为什么 Go 优化完仍不比纯 Node 强）

> 分支 `feat/perf-monitoring`。承接 `../26-9-16/26-9-16-连接层业务层通信架构演进方案-RPC改造.md` 的 P0-P3 落地复测。
> 数据：`data/*.json`（`*_gateway.json`=本期 gRPC 流模式，3 轮取 RTT p99 中位；`*_socketio.json`=26-9-14 纯 Node 基线）。
> 对照：`../26-9-16/`（HTTP-per-message 模式同参数数据）。
>
> **本报告重点回答一个尖锐问题:gRPC 流改造把传输层损耗清零之后,Go 网关路径为什么仍然不比纯 Node 强?**
> 答案是四个结构性原因 + 一个测量维度错位(见 §6/§7),不是"优化还没做完"。

---

## 0. 结论速览

1. **改造本身成功**:dial 耗尽根除(TIME_WAIT 14922→785)、S1 错误率 12.8%→0、S1 RTT p99 209→63ms、网关 CPU 省 40~55%。**传输层的损耗已经被压缩到 17ms 以内**(过载时 gRPC p99 2075ms vs 基线 2058ms,差值即全部传输层开销)。
2. **但 Go 仍不比 Node 快——这是结构性必然,不是 bug**:Go 路径物理上多一跳(客户端→网关→Node→网关→客户端),gRPC 流的极限是"无限逼近纯 Node",**不可能超越**。中等负载的 6~52ms p99 差距是"解耦税":跨进程通信的固有调度/编码成本(§6)。
3. **所有实测负载点的瓶颈都在 Node/DB(会话发号行锁),不在传输层**:2500+ msg/s 时两侧 p99 都卡在 ~2.0s 平台、错误都来自 DB 失败拒绝——**gRPC 改造的成就恰恰是证明"传输层不再是瓶颈",剩下的 2 秒 100% 是业务层/存储层问题**(§6.2)。
4. **过载时 gRPC 错误率反而更高(40.4% vs 37.8%@2500、79.9% vs 62.5%@3000)**:两侧拒绝机制完全相同(DB 失败→message.error),差异来自**并发注入强度**——网关 in-flight 上限(64/连接)把消息灌进 Node 的瞬时并发高于 socket.io 的自然节奏,行锁冲突与 Prisma 连接池竞争更尖锐(§7)。调低 in-flight 可缓解,但本质还是 DB 瓶颈。
5. **测量维度错位**:Go 网关的设计目标是**连接密度/连接风暴隔离/业务解耦**,而本轮与 26-9-16 的核心测量维度是**消息 RTT/吞吐**——那从来不是 Go 的战场。1 万连接两个都轻松,Node 的连接上限从未被压到,"Go 更强"的假设从未获得被验证的机会(§6.4)。
6. **总账诚实说**:CPU 总消耗持平(server+gateway vs 纯 Node)、内存 500 连接时省 14%、1 万连接时多 56%——Go 在当前架构与当前负载区间内**没有为用户省下任何东西**。它的价值只有一项但真实:**架构解耦与可水平扩展的连接层**,这笔价值要等到 Node 的连接上限被击穿时才兑现。

## 6. 核心问题:为什么 Go 优化完了仍不比纯 Node 强?

### 6.1 结构性原因一:物理多一跳,极限就是"逼近"而非"超越"

两条链路的环节数对比(单条消息从发出到收到 ack):

| # | 纯 Node(socket.io) | gRPC 流路径 |
|---|---|---|
| 1 | 客户端 emit → socket.io 帧到达 server | 客户端 WS 帧 → gateway `readLoop` 读 |
| 2 | 事件循环触发 `message.send` handler | `json.Unmarshal` 解析信封(type/msgId) |
| 3 | zod 校验 | in-flight 信号量获取(背压点) |
| 4 | 落库(同一进程内) | 派发 goroutine → protobuf 组帧 |
| 5 | socket.emit ack(进程内) | gRPC 流写 → Node grpc-js 接收 |
| 6 | 客户端收到 | JSON.parse 上行帧 |
| 7 | — | 业务处理(与基线相同) |
| 8 | — | ack 组帧 → gRPC 流回 |
| 9 | — | gateway recv 循环 → `enqueue` send channel |
| 10 | — | writeLoop 写出 WS 帧 |
| 11 | — | 客户端收到 |

**Go 路径必然多 5~6 个环节**(跨进程调度、两次 protobuf 组帧/解帧、一次 send channel 中转)。每个环节在 loopback 上单次 1~2ms,聚合 + 尾部分布放大 = 6~52ms 的 p99 差距。**gRPC 流改造可以把每个环节做到最快,但无法消除环节本身——这是"连接层与业务层解耦"这个架构决策的固有税,与实现质量无关。**

### 6.2 结构性原因二:瓶颈不在传输层——gRPC 改造已把传输损耗压到 17ms

这是本报告最重要的证据:

- 过载平台(r25)两侧 p99:**gRPC 2075ms vs 基线 2058ms,差值 17ms**;
- 两侧错误机制相同:DB 事务失败 → `message.error`(基线 `socket.ts:198-200` 无显式限流,gRPC 走同一 `persistMessage` 落库);
- 两侧服务内直方图同构:DB 单查询 <10ms,但事务级等待(会话发号行锁)2s 级。

**即:在真正能测出瓶颈的负载点(2500 msg/s),Go 路径的全部额外开销 = 17ms。** 剩下 2 秒是 `conversation` 表的 seq 发号行锁,与语言、与连接层、与传输层统统无关。**"Go 不更快"的本质是:系统的瓶颈从来不在 Go 能优化的地方。**

推论:即使把 DB 发号改造成 Redis 自增(方案 §9 建议),2500 msg/s 的 p99 会降到几十毫秒——但**纯 Node 基线同样会受益,两条路径一起变快,差距依然 ≈17ms**。想让"Go 比 Node 快",只能靠业务层本身的 Go 化(见 §8),而不是连接层。

### 6.3 结构性原因三:解耦税明细——中等负载下 6~52ms 去哪了

| 场景 | p99 差(gRPC−基线) | 主要构成 |
|---|---|---|
| S1(1000 msg/s) | +6ms | 跨进程两跳调度(1~2ms/跳)+ 帧编解码,几乎触到物理下限 |
| S2(600) | +9ms | 同上 |
| S5(500,120s) | +9ms | 同上 |
| S4(500 连接,1 msg/s) | +52ms | 500 连接的 presence/心跳与 4 条流分片共享 Node 事件循环 + 网关 send channel 写回队列的调度抖动;低消息率下"固定税"占比被放大 |

S4 的 52ms 是解耦税里最不体面的一项:消息率极低(500 msg/s),按说传输层应毫无压力,但**跨进程调度 + 网关队列 + Node grpc 流回调在事件循环里的排队**共同贡献了尾部放大。这是可用工程手段继续压缩的(流分片数/调度优先级/批写),但压不干净——只要跨进程,尾部就永远比进程内多几个毫秒。

### 6.4 结构性原因四:测量维度错位——Go 的战场从未被测

回看性能监测计划(开发计划文档 §0)的成功标准:
- 消息 E2E RTT(核心维度)——**这不是 Go 的战场**,见 §6.1;
- 吞吐 msgs/s——瓶颈在 DB,**同样不是**;
- **单实例最大稳定连接数**——Go 的设计目标,但压测只到 10000,纯 Node 基线同样 100% 成功(RSS 332MB,上限未探到);
- **每连接资源**——实测 Go 反而更费(边际 29KB vs socket.io 15~18KB,§6.5);
- **断连恢复/惊群**——Go 赢了(1.7×),但这是唯一赢的维度。

**结论:Go 网关的全部设计优势(海量连接密度、连接风暴与业务隔离、逐出保护、无状态水平扩展)落在"数万连接"的区间;而我们的全部压测负载(≤10000 连接、≤3000 msg/s)都在"单进程 Node 轻松应对"的区间。** 在这个区间里,Go 是一个纯增加开销的中间层——它"不比 Node 慢很多"已经是架构上能做到的最好结果。

### 6.5 总账:CPU 与内存,Go 都没赢

| 账目 | 纯 Node | gRPC 流 | 判定 |
|---|---|---|---|
| S5 CPU 总量(120s,500 msg/s) | server 104.1s | server 92.4 + gw 12.8 = **105.2s** | 持平(网关省下的 HTTP 开销≈双进程固定成本) |
| 500 连接总内存 | 485.9MB | 301.8 + 116.4 = **418.2MB** | 省 14%(socket.io 连接对象移出 Node) |
| 10000 连接总内存 | 331.8MB | 344.5 + 175.1 = **519.6MB** | **多 56%**(网关 29KB/连接 vs socket.io 边际 15~18KB) |

CPU 的大头(DB 驱动、JSON 编解码、bcrypt)在 Node 业务层,gRPC 改造只能优化网关侧,总账自然持平。内存交叉点在 500~10000 连接之间,连接越多 Go 总账越亏——**除非连接数高到 Node 单进程扛不住**。

## 7. 深挖:过载时 gRPC 错误率为何反而更高(40.4% vs 37.8%)?

两侧的拒绝机制**完全相同**(DB 事务失败→`message.error`,基线 `socket.ts:198-200` 与 gRPC 共用 `persistMessage`),差异在**并发注入强度**:

- **纯 Node**:100 个客户端各自 socket 独立到达,消息在 Node 事件循环里按到达节奏自然交错处理,瞬时并发 = 事件循环当前排队的 handler 数,增长相对平缓;
- **gRPC 流**:网关每连接 in-flight 上限 64,理论注入上限 64×100=6400 并发;4 条流把 100 个连接的帧合流灌给 Node,`edgeGrpc` 对每帧 `void processFrame` 全部立即并发——**瞬时并发峰值显著高于 socket.io 节奏**;
- 更高的瞬时并发 → 会话发号行锁冲突更密集 + Prisma 连接池竞争更尖锐 → 更多事务超时/池耗尽 → 更多 message.error。

实测佐证:S3(150 连接×20 msg/s)gRPC 模式 goroutine 峰值 6354、server RSS 505MB(基线 491MB)——**并发注入确实比基线更猛**。

工程含义(与方案文档 §9 风险 1 呼应):
1. 这是"网关把消息喂得更快更完整"的双刃剑——它证明网关不再是限速点,但把 DB 压得更惨;
2. 可调参数:网关 in-flight 上限(现 64/连接)与 server 侧流并发窗口,调低可降低注入强度(牺牲部分吞吐换成功率),但治标;
3. **治本仍是 DB 发号改造**(Redis 原子自增/批量预取)——两条路径同等受益;
4. 更准确的描述:**在 DB 瓶颈被修复之前,"错误率谁更低"不构成架构优劣的证据**,两侧都只是"以不同的节奏撞同一堵墙"。

## 8. Go 何时会赢:可验证的条件与建议实验

| 条件 | 判定依据 | 建议实验 |
|---|---|---|
| ① 连接数击穿 Node 上限 | socket.io 边际 15~18KB/连接 + Node 堆/GC/eventloop 约束,推测 3~5 万连接出现劣化;gateway 线性到 50000(配额上限) | 爬坡实验:1 万→5 万连接(压测端需多进程/多机,当前单机 harness 端口与内存受限),记录建连成功率/eventloop/业务 RTT |
| ② 连接风暴 + 业务负载混合 | Node 模式下心跳/重连风暴占用事件循环,业务 RTT 应可测到劣化;gateway 模式下业务进程不受连接 I/O 影响 | 混合场景:5000 连接持续 25s 心跳风暴 + 100 连接发消息,对比业务 RTT p99 |
| ③ 业务进程横向扩展 | gateway 无状态(Redis presence),业务可多副本;纯 Node 模式横向扩展要带连接状态迁移 | 多副本业务层 + 单一 gateway 场景验证(架构级收益,非性能指标) |
| ④ 独立多机环境 | 当前同机 colima 在 3000 msg/s 即失联,掩盖了两侧差异 | 压测端/被测端分离复测全量场景 |

**在这些实验给出数据之前,"Go 更强"只是一个未被证伪的假设**——这也是对监测计划文档的诚实回执:计划成功标准把 RTT 列第一,但 RTT 恰恰是 Go 结构性必输的维度,更公平的对比框架应把连接密度/风暴隔离提到同等权重。

## 9. 最终结论(直接回答用户问题)

1. **"Go 优化完还是不比 Node 强"——对,而且永远不会在消息延迟/吞吐/CPU/内存上比 Node 强,除非业务层也离开 Node。** 原因:瓶颈在 DB(语言无关)+ 业务在 Node(Go 的快无处施展)+ 物理多一跳(解耦税 6~52ms)。gRPC 改造的全部成就是**把多一跳的代价从 152ms 压缩到 6~17ms**,让"解耦"这个架构决策的代价变得可以承受——它解决的是"引入 Go 后变差了怎么办",而不是"怎么让 Go 更快"。
2. **当前形态的真实价值**:架构解耦(连接层可独立水平扩展/逐出保护/风暴隔离)+ 网关唯一入口(业务层内网化)+ 传输层不再是瓶颈(为后续业务层扩容扫清道路)。这笔价值在连接数/业务副本数上来之后兑现,在单机压测区间内是隐性资产。
3. **要"更快"只有两条路**:a) 业务层瓶颈改造(DB 发号→Redis 自增,两条路径同步受益,绝对值大幅下降但 A/B 差距不变);b) 把测量转向 Go 的设计维度(§8 四个实验),去验证"数万连接 + 风暴"场景下 Go 的结构性优势。
4. **决策建议**:如果目标只是"消息更快",Go 网关方向可以叫停(数据不支持);如果目标是"连接规模与业务解耦"(IM 的长期正确形态),当前落地已完成该目标的关键路径,下一步应投 §8 实验 ①② 与 DB 发号改造,而不是继续打磨传输层。
