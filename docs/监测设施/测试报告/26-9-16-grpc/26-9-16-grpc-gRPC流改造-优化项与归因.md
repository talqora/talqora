## 0. 一句话结论

**改造本身成功**:dial 耗尽根除(TIME_WAIT 14922→785)、S1 错误率 12.8%→0、RTT p99 209→63ms,
过载平台与纯 Node 基线的传输层差值被压缩到 **17ms**——传输层从此不再是瓶颈。
但"Go 仍不比 Node 快"是**结构性必然**(物理多一跳 + 瓶颈在 DB + 测量维度错位),剩余 2 秒 p99
100% 是 DB 行锁,与语言/连接层/传输层无关——这直接引出下一轮(26-9-17-gobiz)的"发号 INCR + Go 业务层"决策。

## 3. 归因(本轮最重要的知识产出)

### 3.1 "为什么 Go 优化完仍不比纯 Node 强"——四个结构性原因

| # | 原因 | 证据 |
|---|---|---|
| 1 | **物理多一跳**:纯 Node 6 环节 vs gRPC 流 11 环节(跨进程调度/两次 protobuf 编解码/send channel 中转),每环 1~2ms,尾部聚合放大 | 中等负载 p99 差 6~52ms(解耦税) |
| 2 | **瓶颈不在传输层**:过载平台(r25)gRPC 2075ms vs 基线 2058ms,**差值 17ms**;两侧服务内直方图同构(DB 单查询 <10ms,事务级行锁等待 2s 级) | 实测平台差 17ms |
| 3 | **解耦税明细**:S1/S2/S5 +6~9ms(近物理下限);S4 +52ms(低消息率下固定税占比放大) | 分场景 p99 差 |
| 4 | **测量维度错位**:Go 的设计优势(连接密度/风暴隔离/逐出/无状态扩展)落在"数万连接"区间,而全部压测(≤1 万连接)都在 Node 舒适区 | §8 四实验至今未做 |

### 3.2 "过载时 gRPC 错误率为何反而更高(40.4% vs 37.8%)"

两侧拒绝机制完全相同(DB 事务失败→message.error),差异在**并发注入强度**:gRPC 流每连接 in-flight 64
→ 理论注入上限 64×100=6400 并发,4 条流合流灌给 Node,瞬时并发显著高于 socket.io 自然节奏 →
行锁冲突更密集 + Prisma 连接池竞争更尖锐。实测佐证:S3 gRPC 模式 goroutine 峰值 6354、server RSS 505MB。
**工程含义:网关把消息喂得更快更完整是双刃剑——传输层不再限速后,DB 被压得更惨;治本仍是 DB 发号改造。**

### 3.3 总账(诚实):CPU 持平、内存 500 连接省 14% / 1 万连接多 56%

Go 在当前架构与负载区间内没有为用户省下任何东西,其价值只有一项但真实:**架构解耦与可水平扩展的连接层**,
这笔价值要等连接数击穿 Node 上限时才兑现(§8 实验 ①,尚未验证)。

## 4. 本轮结论与遗留问题

- **结论**:传输层损耗已压缩到极限(17ms),改造的全部成就是"让解耦的代价可以承受",不是"让 Go 更快"。
- 遗留问题 1(**决定性**):DB 行锁(会话 seq 发号)是 2500+ msg/s 时 2s p99/40~80% 错误的唯一来源,
  且是业务层多副本扩展的串行化障碍——**一处代码双重阻碍**;
- 遗留问题 2:业务层仍是单进程,分布式化就绪度 ~70%(presence/下行/幂等/通话态已外置);
- 遗留问题 3:决策依据已就绪——《业务层分布式化与Go重写分析.md》结论:先做语言无关的发号改造(Redis INCR),
  重测后按"CPU 是否主导"数据决策是否 Go 重写;
- 遗留问题 4:§8 四个实验(5 万爬坡/风暴混合/多副本/独立多机)全部未做,留给后续轮次。
