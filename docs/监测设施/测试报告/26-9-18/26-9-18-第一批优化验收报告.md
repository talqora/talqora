## 0. 结论速览

1. **全部 11 主场景零错误**(史上首次):tp_r30(3000 msg/s)从三期 79.9% 错误/p99 2086ms → **0% 错误/p99 61ms**;tp_r25 p99 107ms;S3(3000 msg/s)p99 80ms。
2. **本轮 9 项优化落地,其中 4 项对主场景吞吐有直接贡献**,归因分解见 §5:分区表(写入分散+读裁剪)、定向下行(少一跳)、keepalive 修复(消除 90s 周期断连)、双副本(处理能力翻倍);failover 与内存低风险项贡献于分布式健壮性与专项;限流(未触发,保护性)、读写分离(真实副本未搭建,本轮等同回退路径)、health/分页(非热路径)不体现在本组数据。
3. **分区表对历史读路径收益巨大**:`/user/messages` p99 5919→1996ms(3×)、`/user/lastMessages` 25→274 rps(**11×**,DISTINCT ON 单分区裁剪)。
4. **分布式能力闭环**:定向下行主通道(980 帧 direct/1 fallback,流建立窗口的 1 帧,稳态 fallback≈0)、单副本故障 failover 零失败(kill 演练 1170/1170)、副本恢复自动回归。
5. **遗留**:读写分离代码就绪但**真实只读副本未搭建**(本机 colima 不稳,留待独立环境);内存高密度场景:1 万连接爬坡 biz RSS 253MB(结束档,登录期峰值 269.5MB),较上轮同口径 276MB 降 8%。

## 1. 本轮优化项清单(测试前已完成的代码变更)

| # | 优化项 | 关键实现 | 预期收益 |
|---|---|---|---|
| O-1 | 会话热点限流 | Redis INCR 1s 窗口,阈值 500/s/会话,429 message.error+clientMsgId 收敛,fail-open | 保护发号/扇出(本轮未触发) |
| O-2 | gRPC health + 多后端 | 标准 grpc.health.v1;gateway `EDGE_GRPC_ADDR` 逗号分隔多地址,每地址 4 流 | 多副本探活与连接 |
| O-3 | 消息游标分页 | `/user/messages?limit=&beforeSeq=`,hasMore,无参保持全量(旧客户端零改动) | 大会话读 |
| O-4 | messages 哈希 64 分区 | `PARTITION BY HASH (conversation_id)` 等值自动裁剪,359 万行回填+原子切换 | 写入分散+读裁剪 |
| O-5 | **定向下行** | gRPC metadata `x-replica-id`;biz 按 presence.replica 经下行流直发,失败回退 pub/sub | 少一跳+单通信面 |
| O-6 | **keepalive 修复(真实 bug)** | server MinTime 5min→20s(客户端 30s ping 曾触发 90s 周期 GOAWAY 断连) | 消除周期断连 |
| O-7 | **MultiGrpc failover(演练发现)** | IsHealthy + 目标不健康降级首个健康后端(状态全外置,任意副本可处理) | 副本故障零失败 |
| O-8 | 读写分离(代码) | store.NewRO + 25 处读查询切只读池 + 5 处写后读留写库 | 读不挤占写路径 |
| O-9 | 内存低风险项 | json.Valid 替代全量解析、MaxRecvMsgSize 1MB 对齐、流控窗口 1MB | 每帧省 any 树分配 |

## 5. 归因分解(tp_r30:425→61ms 的 364ms 去哪了)

| 贡献项 | 机制 | 证据 |
|---|---|---|
| **分区表(最大头)** | 写入从单表热点(索引/锁/WAL 竞争)分散到 64 分区 | lastMessages 11×、messages 3× 读侧裁剪;写侧每消息插入竞争面下降 |
| **定向下行** | 下行从 Redis pub/sub(JSON 两跳)改 gRPC 流直发(protobuf 一跳) | direct=980/fallback=1 指标(1 帧为流建立窗口);fanout span 2→1ms |
| **keepalive 修复** | 消除 ~90s 周期 GOAWAY 断连重建(压测窗口内的流中断与重发放大) | 修复前 gateway 日志高频"上行流重建";修复后压测全程无 |
| **双副本** | 3000 msg/s 由两副本分摊(PG 单实例仍是共享底,但业务层处理/序列化并行) | 双副本 message_in 分流计数 |
| 限流/分页/health | 未触发或非热路径 | — |

## 6. 分布式验收(多副本演练,3 轮以上实测)

| 演练 | 结果 |
|---|---|
| 双副本分流 | biz1/biz2 均处理消息(哈希分流生效) |

| 定向下行 | direct 980 / fallback 1(流建立窗口),稳态 fallback≈0 |

## 7. 遗留问题(承接后续批次)

1. **读写分离真实副本未搭建**:代码就绪+回退路径已测;PG 流复制副本留待独立环境(colima 不稳)。
2. 高密度内存:1 万连接爬坡 biz RSS 253MB(结束档;登录期峰值 269.5MB)vs Node 175MB 仍高 45%,goroutine 池化(B 组)未做。
3. messages 全量兼容路径仍在(无 limit 调用),客户端分页接入后可按数据量退役。
4. 会话热点限流阈值(500/s)未经真实热点会话验证(仅端到端语义验证)。
5. V3-P5 容量复测(2~5 万爬坡+风暴混合)仍需多机环境。
