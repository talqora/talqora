## 1. 环境类

### 1.1 colima 宿主侧守护进程频繁崩溃(本日 15 次,最严重)

- **现象**:开发/压测中 `docker` 命令间歇性报 `Cannot connect to the Docker daemon`;`colima status` 报 `error retrieving current runtime: empty value`;biz 启动报 `dial tcp 127.0.0.1:5432: connection refused`。
- **根因排查**:
  - ❌ 排除 VM OOM:`docker stats` 显示 VM 内存占用 <500MB/7.7GB(即使停了 agent-milvus/pulsar 等大户后仍复现);
  - ❌ 排除 PG 崩溃:PG 日志显示 `database system was shut down`(**干净关闭**,非 crash);
  - ✅ 定性:**宿主侧 colima 守护进程崩溃**(VM 仍活着,docker.sock 消失)。触发模式与"kill 业务进程 + 高频连接重建"相关,但无决定性证据;属环境性问题,不在代码可控范围。
- **解法(SOP)**:`colima stop && colima start && sleep 24` → `docker start our-chat-minio`(minio 不自动拉起)→ 重启 biz/gateway。
- **预防**:
  - 压测期间**避免频繁重启业务进程**(观察:失联多发于 kill biz 重启后);
  - 停掉非本任务的容器(agent-milvus/pulsar/etcd 等大户)可延长稳定窗口;
  - 压测跑批后台运行 + 定期轮询,挂了按 SOP 恢复后**从断点场景续跑**。

### 1.2 杀进程方式:lsof -ti 端口匹配有误杀风险

- **现象**:`kill -9 $(lsof -ti :3007)` 后偶发 colima 失联(与 1.1 高度相关,无法排除因果)。
- **根因**:`lsof -ti :端口` 返回**全部**持有该端口的 PID(含可能的转发/代理进程),多 PID 一起 kill 有误杀面。
- **解法**:改用精确进程匹配:`pkill -f "/tmp/biz-server"` / `pgrep -f`。
- **预防**:杀自建进程一律按二进制路径匹配,不按端口。

### 1.3 zsh 只读变量陷阱

- **现象**:shell 里 `UID=$(...)` 报 `failed to change user ID: operation not permitted`。
- **根因**:`UID` 是 zsh 只读内置变量,赋值即报错。
- **解法**:脚本变量避开 `UID`/`EUID` 等只读名(用 `USER_ID` 等)。

## 2. 配置/进程类

### 2.1 shell 环境持久化污染(限流误伤排查 680 条 error)

- **现象**:主实例冒烟 980 条消息 680 条 `message.error`,内容"会话消息频率过高,请稍后重试"——但阈值配置是 500/s,10 条并发消息不可能触发。
- **根因**:此前为验证限流起过临时实例(`CONV_RATE_LIMIT_MAX=3`),该 `export` 残留在执行工具的**持久 shell 环境**中;后续启动主实例时未显式覆盖该变量 → 继承 `=3`。
- **定位**:`ps eww <pid> | tr ' ' '\n' | grep ^CONV` 直接看进程 env,一步确诊。
- **解法**:关键 env(限流/端口/开关)**每次启动显式 export 全量关键项**,不依赖默认值。
- **预防**:新增可调阈值类 env 后,启动脚本/dev.sh 固定写出;排查"行为与配置不符"先查进程 env。

### 2.2 EDGE_GRPC_ENABLED 残留致 gRPC 静默不启动

- **现象**:biz HTTP 正常、gateway 报 `dial 3008 refused`,biz 日志无 gRPC 启动行。
- **根因**:同 2.1——会话残留 `EDGE_GRPC_ENABLED=false`(双跑对比时设置过)。
- **解法**:显式 `export EDGE_GRPC_ENABLED=true`;排查同上(ps eww)。

### 2.3 gateway 上行流建立竞争窗口

- **现象**:biz 重启后立即压测,首轮消息大量 `message.error`/`上行流不可用(建立中)`,数秒后自愈。
- **根因**:gateway 的 gRPC 流按退避重连,重建需要数秒;窗口内消息被快速失败(由客户端重试兜底)。
- **解法**:**重启业务层后等待 ~10s 再注入负载**(gw-probe 先行确认)。
- **预防**:压测编排脚本在场景前加探针前置(已在 runbook 固化)。

## 3. 数据库/迁移类

### 3.1 迁移文件版本号重复(duplicate migration file)

- **现象**:biz 启动报 `duplicate migration file: 0003_messages_partition.down.sql`。
- **根因**:新增迁移用了已存在的版本号(0003~0006 已被占用),golang-migrate 把同版本 up/down 判为重复迁移。
- **解法**:重命名为下一个空闲版本(0007);新迁移前先 `ls migrations/` 确认版本序列。

### 3.2 索引名 schema 级唯一冲突 → dirty 状态修复

- **现象**:迁移执行报 `relation "idx_messages_conv_seq" already exists`,随后 `schema_migrations` 显示 `version=7, dirty=true`。
- **根因**:PG 索引名在 schema 内全局唯一;新分区表想复用旧索引名,但旧表尚未改名(改名也不会带走索引名)。
- **解法**:
  1. 迁移内先 `ALTER INDEX ... RENAME TO ..._legacy` 释放旧名,再建新索引;
  2. 事务已回滚但 dirty 标记残留 → 手动修正:`UPDATE schema_migrations SET version=6, dirty=false WHERE version=7;`(仅当确认 DB 实际状态等于迁移前时;golang-migrate 事务回滚保证这一点)。
- **预防**:迁移里新对象命名先查 `pg_class` 全局冲突;dirty 修复前先确认回滚完整性。

### 3.3 迁移文件 embed 进二进制,新增迁移必须 rebuild

- **现象**:新增 0007 迁移后重启 biz,迁移**没有执行**(日志无迁移动作)。
- **根因**:迁移文件经 `embed.FS` 打进二进制;`/tmp/biz-server` 是旧二进制,不含 0007。
- **解法**:新增/修改迁移后 `go build -o /tmp/biz-server ./cmd/biz` 再部署。
- **预防**:部署流程固定为「build → kill → 启动」,不要省 build。

### 3.4 messages 分区表:分区键选型(认知纠正)

- **关键决策**:`PARTITION BY HASH (conversation_id)`——**text 列直接做 HASH 分区键**,等值查询自动裁剪(EXPLAIN 验证只扫 `messages_p52` 单分区),业务查询零改动。
- **反面方案**:`hashtextextended(conversation_id,0)` 表达式分区键——PG 对表达式分区键**不自动裁剪**,必须改写所有查询,弃用。
- **主键约束**:分区表主键必须含分区键 → `PRIMARY KEY (id, conversation_id)`(已核对仓库无 FK 引用 messages.id,安全)。
- **回填实测**:359 万行 INSERT SELECT 约 40s;原子切换(rename)同事务;down 可逆(旧表保留 messages_legacy)。

## 4. gRPC / 协议类

### 4.1 keepalive 参数不匹配 → 90s 周期断连(真实 bug,子代理探索发现)

- **现象**:低流量场景下 gateway↔biz 流每 ~90s 被强制断开重建。
- **根因**:gateway 客户端 `Time=30s`(空闲 30s 发 ping),biz server 默认 `KeepaliveEnforcementPolicy.MinTime=5min`;ping 间隔 < MinTime 时 `pingStrikes` 累加,>2 次即 GOAWAY `too_many_pings` 掐断连接(grpc-go `http2_server.go:923-930`)。
- **修复**:biz server 显式 `MinTime: 20s` + `PermitWithoutStream: true`;顺带加 server 主动探活(Time 60s/Timeout 20s)、`MaxRecvMsgSize 1MB`(与 gateway WS 读限对齐)、窗口 1MB。
- **预防**:引入 gRPC 时两侧 keepalive 参数必须成对核对(客户端 ping 间隔 > server MinTime)。

### 4.2 B2 误报澄清:Recv 缓冲异步持有是安全的(避免重复排查)

- **背景**:子代理提出"Recv 后 `go func` 异步处理 + 主循环立即 Recv 构成 use-after-free 式数据覆盖隐患"。
- **核实结论**:**不成立**。grpc-go v1.83 的 server Recv 走默认 codec `proto.Unmarshal`,对 `bytes` 字段**深拷贝**(`server.go:1416` → codec.Unmarshal,非 `Alias: true` 路径);`Free()` 归还的是外层 mem.BufferSlice,不影响已拷贝出的 `RawFrame` 切片。
- **留档**:本结论含源码锚点,未来若再被提"gRPC 帧缓冲覆盖",先查当前版本 codec 是否启用 aliasing 再下结论。

### 4.3 定向下行两通道帧形态一致性(实现前提)

- **关键事实**:gateway backplane 的 `gw:downlink` 载荷 `frame` 字段 = **客户端最终收到的完整 WS 帧**(`backplane.go:6-9`);`DownlinkFrame.RawFrame` 同义——两通道 payload 可复用同一 Marshal 结果,定向失败回退 pub/sub 无需二次组装。
- **replica 传递**:用 gRPC metadata `x-replica-id`(tokenAuth 注入),**不动 proto**;presence 的 `{replica}:{socketId}` 已含副本标识,biz 侧 `ReplicaOf/ReplicaOfBatch` 轻量读取(不做惰性摘除,过期数据由回退兜底)。

### 4.4 多副本演练发现:一致性哈希无 failover(真实缺陷,已修复)

- **现象**:kill 一个业务副本后,压测 **53% 消息失败**(落在该副本分片的用户全部失败)。
- **根因**:`MultiGrpc.clientFor` 按 userId 哈希**硬路由**,目标副本不可达时不会转投;而业务层状态全外置(INCR/唯一约束/通话态),任何副本都能正确处理任意用户。
- **修复**:`GrpcClient.IsHealthy()`(任一流已建立)+ `clientFor` 目标不健康时轮询降级到第一个健康后端;全部不健康回退哈希目标(启动初期由客户端重试兜底)。
- **验证**:kill 演练 1170/1170 零失败;副本恢复后自动回归分流。
- **教训**:多副本验收必须含故障演练;演练发现的"功能可用但正确性受损"比性能数据更重要。

## 5. 测试/验证类

### 5.1 限流阈值验证要端到端(不要只信单测)

- 单测(CheckConvRate Lua 逻辑)通过后仍做端到端:临时实例阈值=3 连发 4 条,第 4 条 429 `message.error` + clientMsgId 收敛——**拒绝帧语义与客户端收敛行为必须实测**,这是单测覆盖不到的契约面。

### 5.2 分页向后兼容的验收三态

- 新接口验收固定测三态:①分页(limit+hasMore 翻页);②beforeSeq 游标第二页;③**无参数旧行为**(全量升序)——分页改动最大的风险就是破坏旧客户端,第三态必测。

### 5.3 冒烟发现 980 全 error 的排查顺序

- gateway 路径消息全失败时按序排查:①手动 HTTP internal 端点(区分 gateway↔biz 流 vs 业务层);②gateway 日志(上行流重建/不可用);③biz 日志;④进程 env(限流残留,见 2.1)。本次 680 error 的根因(限流残留)用第 4 步才定位——**"行为与配置不符先查 env"应提到第 1 步**。

## 6. 运维约定(本轮新增)

| 约定 | 内容 |
|---|---|
| 重启顺序 | 先中间件(等 healthy)→ biz 双副本 → 等 ~10s → gateway → 探针 → 压测 |
