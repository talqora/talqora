一、结论速览

  • 1. 常规吞吐(S1,≈1000 msg/s)消息 RTT p99:Node 57ms → Go 209ms(267%)。
  • 错误:Node 0 条 / Go 2534 条;Go 侧超时重发 586 帧。
  • 2. 连接层(S2,300 连接):Node server RSS 峰值 300.6MB(每连接 1KB);Go gateway 仅 62.7MB / 630 goroutine(每连接 0.21KB)。gateway 路径总内存 = server + gateway 两者之和。
  • 3. 过载(S3,≈3000 msg/s)失败模式:Node 错误 22185 条(错误率 49.6%,快速失败);Go 错误 6268 条(错误率 14%)、RTT p99 5067ms(排队而非拒绝)。
  • 4. 连接容量:gateway 路径探到 10000 连接(gw RSS 315.5MB / 20012 goroutine;达到 MAX=10000(用户数 10000));Node 基线 10000 连接(达到 MAX=10000(用户数 10000))。

二、测试方法

  • A = Node(socket.io):perf/harness.mjs,socket.io-client → server /socket.io(26-9-14 基线数据)。
  • B = Go(gateway):perf/harness-gw.mjs,原生 WebSocket(query token/deviceId)→ gateway /ws → 信封帧 {type:'message.send',data:{...}} → 等 message.ack 计 RTT。
  • 编排 perf/ab-run.mjs:跑 harness + 每 2s 采样(Prometheus 连接/eventloop/goroutine/GC + ps 两进程 RSS/CPU)+ 服务内直方图分位(uplink/downlink/HTTP/GC)→ 落 JSON。
  • 场景参数与 26-9-14 基线完全一致(S0-S5、吞吐扫描、爬坡、惊群、扇出、HTTP);爬坡探顶参数走 env(同 ramp-probe)。
