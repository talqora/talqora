# 26-9-16 · Go 网关全面接入(HTTP-per-message)· 优化项与归因

> 系列定位:五轮优化测试的**第 3 轮**。web 实时层全面切换到 Go gateway(原生 WS `/ws`),
> 业务层仍为 Node;上行通信方式是 **HTTP-per-message**(每消息一次 POST)。
> 事实锚定:本目录《26-9-16-Go网关压测对比报告.md》(实测)、《26-9-16-连接层业务层通信架构演进方案-RPC改造.md》(根因+方案)、《架构分析.md》(差距清单)。

---

## 0. 一句话结论

架构解耦方向被验证正确,但**通信方式选错了**:**HTTP-per-message 的三个缺陷(dial 耗尽/每连接串行等待/重试竞态放大)使 gateway 路径在 1000 msg/s 就劣化(S1 错误率 12.8%)、2500 msg/s 时 RTT p99 2802ms**。
本轮用三条证据链把根因钉死在"通信模型"而非语言/运行时,并产出了下一轮(gRPC 流)的完整方案。

## 3. 归因(三条证据链,全部有源码锚点)

| # | 现象 | 根因锚点 | 机制 |
|---|---|---|---|
| E1 | S1 错误率 12.8%;网关日志 10,341 条 `can't assign requested address`;TIME_WAIT 达 14,922/16,384 | `upstream.go:26` 用 Go 默认 `http.Client`(**MaxIdleConnsPerHost=2**),HTTP-per-message 每秒上千次建连耗尽 loopback 临时端口 | **dial 耗尽(短连接风暴)** |
| E2 | tp_r25 客户端 RTT p99=2802ms,而网关上行服务内仅 98.3ms、下行投递 5ms | `conn.go:79-85` readLoop 每条消息**同步** dispatch→Forward 等回包才读下一帧——发送间隔(40ms)<上行耗时(p95 82ms)时队列单调增长 | **每连接串行等待** |
| E3 | S3 gateway 路径 Node 服务内仅 198.9ms(远好于基线 2483ms)但客户端 p99=5.1s、重发撞在途插入 5,396 条 unique constraint 500 | 串行上行摊平了到达 Node 的并发("保护"了 DB),代价是网关深队列 + 重发风暴 | **重试与在途竞态放大** |

**三条证据链的共同结论**:问题在"每消息一次 HTTP 请求-响应"这个通信模型,与语言无关——"即使全部用 Go 重写也无法解决"(两个 Go 进程之间 HTTP-per-message 同样会 dial 耗尽+串行等待)。

**排除项(归因的负向证据,同样重要)**:两侧 eventloop p99 全程 11~15ms、Node GC 停顿 ≤5ms、Go GC 累计 4~66ms——**运行时从来不是毛刺来源**;"Go 网关不更快"不是 Go 的问题。

## 4. 正面成果(不因通信缺陷而否定)

1. 连接层能力全面优于 socket.io:建连 2.4×、惊群 1.7×、eventloop 纹丝不动、连接 I/O 与业务进程解耦(server RSS 恒 183MB);
2. 架构范式对齐业界(Discord/Slack/微信同构)——《架构分析.md》结论:范式层已"毕业",剩余差距是规模性基础设施;
3. 过载失败模式对比(排队 vs 拒绝)的观测价值:为下一轮"异步上行"方案提供了定量靶子。

## 5. 本轮结论与遗留问题

- **结论**:解耦方向正确、通信方式错误;下一轮方案 = **gRPC 双向流**(单连接复用+异步确认+in-flight 背压),unary RPC 只能解决一半(dial 耗尽),串行排队必须靠流式+异步 ack 才能消除。
- 遗留问题 1:E1~E3 待 gRPC 流改造解决(26-9-16-grpc 轮闭环);
- 遗留问题 2:DB 行锁瓶颈在 gateway 串行上行的"保护"下被掩盖——《RPC 改造方案》§9 风险 1 预警:**上行并发恢复后 DB 行锁竞争会回归基线水平**;
- 遗留问题 3:错误帧丢 clientMsgId 导致客户端无法收敛 pending(只能等超时)——列入下一轮 P2;
- 遗留问题 4:HTTP 层 `/user/messages` 2.4 万条全量返回 3.9s,数据漂移导致两轮差异(环境性,非链路)。
