# 26-9-16 · Go gateway 全面接入后的压力与性能测试（A/B 对比纯 Node 基线）

> 分支 `feat/perf-monitoring`。web 实时层已全面切换到 Go gateway（原生 WebSocket `/ws`），业务层仍是 Node。
> 本报告对**新链路（web → gateway(Go) → server(Node) → 落库 → downlink 扇出）**做与 26-9-14 纯 Node 基线
> **同环境、同参数、同口径**的系统压力测试，回答：换 Go 网关后相对纯 Node 具体快/省多少、差异来自协议还是运行时、
> 在什么负载点拉开差距、是否达到预期。
>
> 数据来源：A = `26-9-14/data/*.json`（纯 Node 基线，socket.io 直连 server，gateway 未启动）；
> B = `data/*_gateway*.json`（本次 26-9-16，gateway 路径，每场景 ≥3 轮取 RTT p99 中位轮，原始各轮保留 `*_gateway_rN.json`）。
> HTML 自动汇总报告见同目录 `性能对比报告.html`（`perf/gen-report.mjs` 生成）。

## 0. 结论速览（TL;DR）

1. **≤600 msg/s 的中等负载：gateway 与纯 Node 完全同档**（S0/S2/S4/S5 均 0 错误，RTT 相当或略高 5~47ms p99）。gateway 多一跳（HTTP-per-message 上行），**"换 Go 让单条消息更快"不成立**。
2. **过载失败模式截然不同**：Node 在 ≈2000 msg/s 开始**快速拒绝**（tp_r20 起 7.6%→62.5% 错误，服务内 p99 达 2.48s，事务行锁竞争）；gateway **排队而非拒绝**（tp_r25 时 0 错误但 RTT p99=2.8s，tp_r30 达 6.1s）。两者都"失败"，一个丢消息、一个爆延迟。
3. **gateway 上行有独立于 Node 的新瓶颈**：≈1000 msg/s 起出现 **dial 耗尽**（`connect: can't assign requested address`，网关→Node 的 HTTP-per-message 建连把 loopback 的 16K 临时端口 + TIME_WAIT 打满，本次累计 10,341 次 upstream_error）——这是 gateway 产品层的架构问题（Go `http.Client` 默认 `MaxIdleConnsPerHost=2`），比 Node 的 DB 瓶颈**更早出现**。
4. **连接层：gateway 握手更快、更稳**。2000 条/批的突发建连 p50 134~163ms（Node 基线 318~434ms，约 2.4×）；惊群重连 p50 26ms / p99 39ms（基线 43/67ms）。10000 连接 100% 建连成功，gateway RSS 315.5MB、goroutine 20012、eventloop 11.1ms 纹丝不动；上限未探到（`GATEWAY_MAX_CONNS=50000`）。
5. **内存：连接成本从业务进程剥离，但总量更高**。gateway 边际 ≈29KB/连接（gorilla 4KB×2 缓冲 + 256 槽 send channel），socket.io 边际 ≈15~18KB/连接——**本实现下 Go 单连接内存不占优**；真正的收益是 server 在 gateway 模式下 RSS 恒为 ~183MB（10K 连接时 socket.io 模式要 332MB），连接 I/O 不再占用 Node 事件循环与堆。
6. **归因（有指标证据，非拍脑袋）**：两侧 eventloop p99 全程 11~15ms、Node GC 停顿 p99≤5ms、Go GC 单场景累计 4~66ms——**运行时（GC/事件循环）都不是毛刺来源**。差异全部来自**传输层架构**：socket.io 进程内处理 vs gateway 的「每连接串行 HTTP 上行 + 下行 pub/sub 代投」。

## 3. 归因分析（指标证据链）

### 3.1 运行时（Node 事件循环 / GC vs Go GC）——都不是差异来源

| 证据 | 数值 |
|---|---|
| Node eventloop lag p99（全部场景两侧） | 11.1~16.9ms，S3 峰值 16.9ms，从未进入危险区 |
| Node GC 停顿 p99 | 4.96~5ms（两侧一致） |
| Go GC 累计耗时/场景 | 4~66ms（S5 120s 也仅 45ms），完全可忽略 |
| gateway 下行投递 p99 | 5ms（全部场景稳定） |
| gateway 上行服务内 p99（收帧→Node ack） | 49.8~475.4ms，随场景增长但**远小于客户端 RTT** |

结论：**两侧运行时都健康，毛刺全部来自传输层架构，不来自 GC/事件循环**。

### 3.2 差异 1：协议/架构——进程内处理 vs「HTTP-per-message + 串行 readLoop」

gateway 每发一条消息要做一次独立的 `POST /internal/gateway/uplink`（`upstream.go`），且 `hub/conn.go` 的 `readLoop` 是**每连接串行**的：`Forward` 返回前不读下一帧。证据：
- S2（600 msg/s）gateway RTT p99=180ms vs 基线 171ms、S4 307 vs 276、S5 108 vs 61——固定多一跳的代价 ≈5~47ms p99。
- tp_r25（2500 msg/s）：客户端 RTT p99=2802ms，而网关上行服务内 p99 仅 98.3ms、下行 5ms——**延迟全在每连接串行队列 + 客户端重发等待里堆积**，不在 Node、不在 DB、不在 GC。
- S3 中 gateway 模式反而让 Node 服务内 p99 从基线 2483ms 降到 198.9ms：串行上行把到达 Node 的瞬时并发摊平，行锁竞争大幅缓解——**网关排队"保护"了 Node，代价是客户端延迟**。

### 3.3 差异 2：gateway 上行 dial 耗尽（本次最重要的新发现）

- 现象：S1/tp_r10 起，gateway 日志 10,341 条 `上行透传失败: dial tcp 127.0.0.1:3007: connect: can't assign requested address`（`gateway_uplink_total{result="upstream_error"}=10341`）。
- 根因链：gateway `upstream.go` 用 Go 默认 `http.Client`（`MaxIdleConnsPerHost=2`）→ HTTP-per-message 每秒上千次建连 → 每个短连接留下 TIME_WAIT → macOS loopback 临时端口 49152–65535 共 16,384 个被 TIME_WAIT 占满（压测中实测 14,922 个）。
- 定位：这是 **gateway 产品代码的连接池配置问题**（本任务约束不改产品代码，故记录为发现），不是测试脚本问题；生产跨机部署时网关侧同样会累积 TIME_WAIT，只是阈值不同。
- 影响：S1 的 12.8% 失败中相当部分由此造成（叠加 §3.6 的收尾统计口径）；错误率在扫描各档间非单调（跨轮端口池残留），RTT 曲线单调可信。

### 3.4 差异 3：重发与在途插入的幂等竞争（server 侧）

5s 超时重发命中「首个插入仍在途」的窗口时，server 的 `(conversation_id, sender_id, client_msg_id)` 唯一约束被并发插入打破，产生 5,396 条 `Unique constraint failed`（Prisma error → 500）。幂等去重只覆盖了首条先落库的场景，未覆盖并发在途竞争。这解释了部分重发后仍失败的消息。

### 3.5 差异 4：网关错误帧丢失 clientMsgId（可收敛性缺口）

网关上游失败时回投的 `errorFrame` 只有 `{type:'message.error', message:'消息发送失败'}`（`conn.go:149`），**不含 clientMsgId**，客户端无法把错误收敛到 pending，只能等 5s 超时重发兜底。harness 为此单列 `message.error_unmatched` 计数（本次运行的旧版脚本未计，该部分混在 ack_timeout 里；已修复计数逻辑）。

### 3.6 统计口径说明（诚实披露）

- ack_timeout = 3 次重发（5s×3）仍未确认 + **停发后 3s 宽限期内未收敛的在途消息**（与基线 harness 同口径）。gateway 排队场景下最后 ~3s 的消息因队列未排空而计入，S1 的 2534 条中有相当部分是此类——真实的中途失败见 tp 扫描各轮重发帧数与 `upstream_error` 指标。
- gateway 错误计数不含被逐出连接（`gateway_evicted_total=0`，本轮未发生逐出）；如发生会单列归因。

## 6. 直接回答：快多少、省多少、拐点在哪、是否达预期

**1) 快多少**
- **更快的地方（连接层）**：突发建连 2.3×（p50 134~163 vs 318~434ms）；惊群重连 1.7×（p50 26 vs 43ms）；群扇出扩散 3×（span p99 2 vs 3ms）。
- **持平的地方**：≤600 msg/s 的消息 RTT 与基线同档（多一跳固定代价 5~47ms p99）。
- **更慢的地方**：≥1000 msg/s 消息 RTT 因排队单调恶化（p99 2802ms@2500 msg/s vs 基线 2058ms——但基线同负载丢 37.8% 的消息）。

**2) 省多少**
- 每连接内存：gateway ≈29KB/连接 vs socket.io ≈15~18KB/连接（**本实现不省，甚至更高**）。
- 业务进程内存：10K 连接时 server RSS 从 332MB 降到 183MB（连接对象全部移出 Node）；但 gateway 进程另占 315.5MB，**总量 499 vs 332MB，多进程架构总内存更高**。
- CPU：S5 同负载（500 msg/s×120s）gateway 路径总 CPU 115.5s（server 93.6 + gw 21.9）vs 基线 104.1s，**+11%**（HTTP 上行跳 + 双进程 JSON 编解码）。
- 省的真正项是**耦合**：连接风暴/慢消费者逐出/心跳保活不再消耗 Node 事件循环（10K 连接时 eventloop 11.1ms 纹丝不动），业务进程可独立扩缩容。

**3) 在什么负载点开始拉开差距**
- 600→1000 msg/s：gateway 上行 dial 耗尽开始（失败率 12~17%）。
- ≈2000 msg/s：Node 开始快速拒绝（7.6%→62.5%）；gateway 仍"不丢但排队"（RTT 秒级）。
- 连接维度：10K 连接内两者都轻松；gateway 的建连吞吐优势从 2000 条/批的突发起显现。

**4) 是否达到预期**
- **部分达到**：连接层目标（握手快、事件循环零压力、逐出保护、可水平扩展）完全达成，且比预期更好（2.3× 建连、1.7× 重连）。
- **未达到**：①"Go 让消息更快"不成立——多一跳 + HTTP-per-message 让单条消息在中等负载持平、高负载变慢；②"Go 省内存"在本实现下不成立（单连接 29KB vs 15~18KB，总量更高）；③上行 HTTP-per-message 成为**比 DB 更早的新瓶颈**（≈1000 msg/s dial 耗尽），这是换网关前未充分预期的架构风险点。

---

## 7. 建议（按优先级）

1. **gateway 上行改造（最重要）**：`upstream.go` 的 `http.Client` 换成调优过的 `Transport`（`MaxIdleConnsPerHost` ≥ 上行并发度、缩短/关闭空闲回收、HTTP/2 多路复用），消除 dial 耗尽；进一步把 HTTP-per-message 改成**持久连接/批量/gRPC 流**（26-9-12 报告已提，本轮用数据证实其紧迫性：1000 msg/s 就出问题）。
2. **readLoop 串行改并发**：每连接的上行应异步并发（保留每连接有序性或按序号重组），否则 RATE>10 时串行队列直接决定尾延迟。
3. **server 幂等竞争兜底**：`persistMessage` 对 `(conversation_id, sender_id, client_msg_id)` 唯一约束冲突做捕获（视为 deduped），消除重发窗口内的 500。
4. **gateway 错误帧补 clientMsgId**：`errorFrame` 带上 clientMsgId，客户端可即时收敛，不再依赖超时重发。
5. **隔离环境复测**：压测端与被测端分离、轮间排空 TIME_WAIT，重测 S1/扫描各档，把错误率绝对值从端口池串扰中解耦；连接规模测到 2~5 万探 `GATEWAY_MAX_CONNS` 真实上限。
