# 优化项与归因(第一批:分区/定向下行/keepalive/多副本)

> 系列定位:五轮优化测试的**第 6 轮**,承接《后续优化项分析》批 1~批 3 的 9 项改动。
> 数据见同目录《第一批优化压测报告.md》;开发过程见《开发踩坑记录.md》。
> 本文按 **问题 → 手段 → 原理 → 证据** 逐项展开,并给出"425ms→61ms"的归因分解。

---

## 0. 一句话结论

这一轮把上一轮"零错误但排队"的 **tp_r30 425ms** 压到 **61ms**,同时把历史消息读路径拉回可用区间
(`/user/messages` p99 5919→1996ms、`/user/lastMessages` 25→274 rps)。四项优化各管一段:**分区表管写入热点与读放大、
定向下行管少一跳、keepalive 管稳定性、双副本管处理能力**。

---

## 1. O-4 messages 哈希 64 分区(最大头)

| 维度 | 内容 |
|---|---|
| **问题** | `messages` 单表 359 万行持续增长:①写入侧所有会话的插入都竞争同一张表的索引与 WAL;②读侧 `DISTINCT ON (conversation_id)` 与按会话分页要扫大量无关行 |
| **手段** | 新建 `messages` 按 `PARTITION BY HASH (conversation_id)` 分 **64 个分区**;`INSERT ... SELECT` 回填 **359 万行约 40s**;再在**同一事务内 rename 原子切换**;`down` 可逆(旧表保留为 `messages_legacy`) |
| **原理** | ① 哈希分区把"单表热点"打散成 64 个物理表,插入的索引分裂/锁竞争面下降;② 查询条件含 `conversation_id` 时 PG 做**分区裁剪**,只扫 1 个分区(≈1/64 数据量),`DISTINCT ON` 从"全表去重"变成"单分区去重" |
| **证据** | `/user/messages` p99 **5919→1996ms(3×)**;`/user/lastMessages` **25.4→273.6 rps(11×)** |

> 关键工程点:**回填 + 原子切换**。直接 `ALTER` 会锁表不可用;先建分区表灌数据、再事务内改名,业务无感,且保留旧表可回滚。

## 2. O-5 定向下行(少一跳)

| 维度 | 内容 |
|---|---|
| **问题** | 下行经 Redis pub/sub:业务层 publish → 网关 subscribe → 再查连接投递。多一次序列化、多一次网络跳、且与上行路径不对称(排障要看两个通信面) |
| **手段** | 网关在 gRPC 流握手时通过 metadata `x-replica-id` 上报副本标识;业务层在 presence 中记录 `userId → replica`;下行时**直接经该副本的 gRPC 流写帧**,失败(流已断/未建立)才回退 pub/sub |
| **原理** | 把"广播-过滤"模型换成"**按位置寻址**":消息只发往持有连接的那一个副本,跳数从 3 降到 2;presence 是这层寻址的唯一事实来源,因此回退必须是兜底而非主路径 |
| **证据** | direct=**980** / fallback=**1**(唯一 1 帧是流建立窗口);稳态 fallback≈0;群扇出 span p99 **2→1ms** |

## 3. O-6 keepalive 修复(真实 bug,不是调参)

| 维度 | 内容 |
|---|---|
| **问题** | 压测中每 ~90s 出现上行流重建:错误率不高但尾延迟出现规律性尖刺,长连接稳定性不可信 |
| **根因** | gRPC 服务端 keepalive `MinTime=5min` 严于客户端 `30s ping` → 服务端按 `GOAWAY` 拒绝"过于频繁"的 ping,连接被周期性掐断重建 |
| **手段** | 服务端 `MinTime` 5min→**20s**(小于客户端 ping 间隔),`PermitWithoutStream` 保持;压测全程验证无重建 |
| **原理** | keepalive 是**双端协商**:服务端 `MinTime` 表示"最短允许的 ping 间隔",客户端更频繁即判违规。参数必须满足 `客户端 ping 间隔 ≥ 服务端 MinTime`,否则正常运行会被当成攻击 |
| **证据** | 修复前 gateway 日志高频"上行流重建";修复后压测窗口内 0 次;S5 长稳 120s 无周期断连 |

## 4. O-7 多副本 + gRPC health + failover

| 维度 | 内容 |
|---|---|
| **问题** | 单副本既没有容量冗余,也无故障转移:副本重启/卡死时该副本上的全部用户断流 |
| **手段** | ① 业务层起 **2 副本**(:3007/:3009,gRPC :3008/:30081);② 实现标准 `grpc.health.v1`,网关按地址探活;③ 网关 `EDGE_GRPC_ADDR` 支持逗号分隔多地址、**每地址 4 条流**;④ `MultiGrpc` 发现目标不健康时**降级到首个健康后端** |
| **原理** | 副本可水平扩展的**前提是状态外置**(seq/幂等/通话态/presence 都在 Redis/PG),否则故障切换会丢会话内状态;健康检查把"进程活着"升级为"能服务",failover 才能在亚秒级收敛 |
| **证据** | kill 演练 **1170/1170 零失败**,副本恢复后流量自动回归;主场景 p99 全面下降(S1 59→48ms、S3 173→80ms、S4 294→140ms) |

## 5. 其余项(贡献不在主场景,但必要)

| 编号 | 手段 | 原理 / 为什么需要 | 证据 |
|---|---|---|---|
| O-1 | 会话热点限流:Redis `INCR` 1s 窗口,阈值 500/s/会话,超限回 `message.error` | 单会话被刷屏会拖垮发号与扇出,限流是**保护性措施**;**fail-open**(Redis 故障即放行)保证限流本身不会变成新的故障点 | 本轮未触发(未达阈值),属兜底 |
| O-3 | 消息游标分页 `?limit=&beforeSeq=&hasMore` | 大会话一次拉全量会把内存与 DB 都打满;游标分页把读放大变成常量;**无参保持旧行为**,老客户端零改动 | 为分区表的读收益提供入口 |
| O-8 | 读写分离:`NewRO` + 25 处纯读切只读池 + 5 处写后读留写库 | 读请求不挤占写路径;写后立刻读必须回主库,否则主从延迟会读到自己没写完的数据 | **真实副本未搭建**,本轮等同回退路径,收益未计入 |
| O-9 | `json.Valid` 替代全量反序列化、`MaxRecvMsgSize` 1MB、流控窗口 1MB | 热路径只需判断"是不是合法 JSON",全量 parse 会为每帧分配 `any` 树;1MB 对齐避免超限重传 | 内存与 GC 更稳 |

## 6. 归因分解:tp_r30 从 425ms 到 61ms,364ms 去哪了

| 贡献项 | 机制 | 证据 |
|---|---|---|
| **分区表(最大头)** | 写入从单表热点分散到 64 分区,索引/锁/WAL 竞争面下降 | 读侧 `lastMessages` 11×、`messages` 3× |
| **定向下行** | 下行少一跳(protobuf 直发替代 pub/sub JSON 两跳) | direct/fallback = 980/1,span 2→1ms |
| **keepalive 修复** | 消除 ~90s 周期断连带来的流重建与重发放大 | 压测全程无"上行流重建"日志 |
| **双副本** | 3000 msg/s 由两副本分摊处理与序列化 | message_in 分流计数;PG 仍是共享底 |

## 7. 边界与遗留

- **PG 单实例仍是共享底**:双副本只分摊业务层 CPU,写入仍落在同一 PG;3000 msg/s 已是该环境的软上限。
- **读写分离代码就绪但副本未搭**:本机 colima 内存不足,须在独立环境验证后再计入收益。
- **定向下行依赖 presence 准确**:presence 过期会造成 fallback 上升(兜底不丢帧,但延迟回到 2 跳)。
