# 26-9-16-gobiz · 业务层 Go 重写验收报告

> 分支 `feat/perf-monitoring`。对应提示词「26-9-16-Go全面重写业务层」P1~P9 全量验收。
> 实现:`biz/`(Go 模块化单体,替换 `server/` Node 业务层;客户端/web/移动端/gateway/压测工具**零改动**)。
> 数据:`data/*.json`。`*_gateway.json`=本期 Go(gateway 路径,3 轮取 RTT p99 中位);`*_socketio.json`=三期 26-9-16-grpc 基线(gen-report 命名要求,实为 Node gRPC 流模式);`opt_*`=热路径优化版重测。
> 报告全文:「实现与 Node 逐接口对齐,过载场景从 79.9% 错误率降至 0%,tp_r25 p99 2075→156ms,内存省 2.8~4 倍」。

---

## 0. 结论速览

1. **行为对齐达成**:Node↔Go 双跑字段级对比 **34/34 端点零差异**(注册/登录/好友全流程/消息收发/同步/OAuth 授权码全流程/上传秒传/内部端点),指标名与 buckets 契约对齐。**客户端零改动承诺兑现**(harness 直接跑通)。
2. **发号 INCR 改造兑现预期**:Redis INCR + Lua 原子装载 + DB 兜底,把会话发号从 PG 行锁移到 Redis。
3. **核心验收点全绿**:
   - tp_r25(2500 msg/s):三期 40.4% 错误、p99 2075ms → **Go 版 0% 错误、p99 156ms**(优化版);
   - tp_r30(3000 msg/s):三期 79.9% 错误 → **Go 版 0% 错误、p99 425ms**;
   - S1(核心):0% 错误、p99 59ms(三期 63ms,纯 Node 基线 57ms);
   - 1 万连接爬坡成功、惊群重连 p99 41ms、群扇出 span p99 130ms、HTTP 直连 11011 rps。
4. **资源收益**:**内存省 2.8~4 倍**(S1 RSS 67MB vs Node 290MB;tp_r25 171MB vs 472MB),S5 业务层 CPU 省 38%(57.6s vs 92.4s)。业务层从 8 副本分摊改为单进程直连(gRPC 流收口)。
5. **失败模式本质变化**:三期是「DB 失败→message.error 快速拒绝」,Go 版在 3000 msg/s 内**完全消除错误**;唯一残留风险是 tp_r30 量级持续过载会压挂同机 colima 的 PG/Redis(环境性风险,非代码缺陷,见 §9)。
6. **诚实边界**:tp_r30(3000 msg/s)为同机 PG 单实例能力边界附近,Go 版虽零错误但 p99 425ms 高于预期 150ms(预期基于"PG 无瓶颈"假设);压到 4000+ msg/s 时 PG 写入仍是短板,与三期「瓶颈在 DB」结论同源。

## 6. 发号 INCR 改造归因验证

三期归因「瓶颈 100% 在 DB 行锁」,本期用同一套压测工具验证解绑后结果:

| 证据 | 三期(gRPC 流,行锁) | 本期(Go,INCR) |
|---|---|---|
| tp_r25 错误率 | 40.4%(全部 message.error=DB 失败拒绝) | **0%** |
| tp_r30 错误率 | 79.9% | **0%** |
| tp_r25 p99 | 2075ms(行锁等待平台) | 156ms |
| S3(3000 msg/s) | 39.8% 错误 | **0% 错误** |
| Redis `conv:seq:*` 键 | 无 | 有(INCR 生效,checkpoint 每 60s 回写 PG) |

**结论:行锁是错误率唯一来源的假设得到反向验证——解绑后错误率直接归零,p99 脱离 2s 平台。** 余下延迟为 PG 写入与下行投递,与三期「瓶颈在 DB」同源但量级已从"拒绝"改善为"排队"。

- 内存降幅 **2.8~4.0 倍**(Node 的 Prisma 查询缓冲/对象池 vs Go 结构体流式处理);

## 9. 行为对齐验证(P7 双跑)

- **34/34 端点字段级零差异**:`biz/scripts/diff-api.mjs` 对 Node(:3007) 与 Go(:3009) 同构请求,递归比较响应键集合/值类型/时间格式/HTTP 状态,含:
  - 注册(201/409 重复/400 校验)、登录(200/400 错密码)、check-username;
  - 用户资料/更新、userConversations/conversations/messages/lastMessages/sync(含 400 非法参数)/read/mentions/readCount;
  - **好友全流程**:addFriend→getFriendReqs→replyFriendReq(accepted)→getFriendList(值骨架)→updateRemark→searchUser(已是好友);
  - **OAuth 授权码全流程**:PKCE S256 challenge→authorize 302→token→userinfo→refresh,id_token 存在性一致;
  - TURN 凭证、上传秒传、OAuth 元数据(openid-configuration/jwks.json)、RUM、内部 uplink(200/401)。
- **指标契约**:`/metrics` 指标名/buckets 对齐(含 `server_message_duration_seconds` 等 9 项契约指标;Vec 无数据不输出与 Node 行为一致)。
- 唯一结构性差异(预期内):好友列表/请求响应以动态 userId 为键,两侧注册用户 id 不同——对比脚本按值骨架比对。

## 10. 遗留问题与风险

1. **群扇出 span p99 130ms vs 三期 2ms**:单聊路径优化后,群路径(100 成员×20 条=2000 次下行投递)成为相对短板。原因:Go 版群扇出逐成员推送(每成员 2 次 Redis 命令),未做 pipeline 批量化。不影响正确性(20/20 轮全送达),但低于三期同口径。**后续优化方向:扇出 Redis pipeline 批量化 + 按连接聚合下发**。
2. **历史消息全量端点(messages)无分页**:与 Node 同语义(全量返回),大会话 p99 5.9s;数据量漂移使跨期对比失真,已在本期 HTTP bench 中注明。
3. **tp_r30 持续过载会压挂同机 colima 的 PG/Redis**:压测中发生 2 次(PG/Redis 失联,重启恢复),与三期报告「3000 msg/s 压挂中间件」同一环境性风险。**建议压测环境为中间件设置资源上限/独立部署**;代码侧已保证 PG/Redis 失联时优雅降级(发号回 DB 行锁、下行投递容错)。
4. **进程内缓存一致性**:会话/关系行/幂等/seq 初始化四级缓存均为"无删除路径"数据,多副本下靠 `ON CONFLICT DO NOTHING`/Lua 原子性兜底;若未来引入删除语义(如解散群),需同步处理缓存。
5. **golang-migrate 接管后 `schema.prisma` 仅作参考**:迁移唯一入口已切换,团队需遵守新流程(见 biz/README.md)。
