## 0. 结论速览

1. **行为对齐达成**:Node↔Go 双跑字段级对比 **34/34 端点零差异**(注册/登录/好友全流程/消息收发/同步/OAuth 授权码全流程/上传秒传/内部端点),指标名与 buckets 契约对齐。**客户端零改动承诺兑现**(harness 直接跑通)。
2. **发号 INCR 改造兑现预期**:Redis INCR + Lua 原子装载 + DB 兜底,把会话发号从 PG 行锁移到 Redis;四级进程内缓存把每消息 PG 写入从 3 次降到 1 次。
3. **核心验收点全绿**:
   - tp_r25(2500 msg/s):三期 40.4% 错误、p99 2075ms → **Go 版 0% 错误、p99 156ms**(3 轮 66/156/189ms,中位);
   - tp_r30(3000 msg/s):三期 79.9% 错误 → **Go 版 0% 错误、p99 425ms**(3 轮 425/252/537ms,中位);
   - S1(核心):0% 错误、p99 59ms(三期 63ms,纯 Node 基线 57ms);
   - 1 万连接爬坡成功(无拐点)、惊群重连 3 轮中位 p99 37ms、群扇出 3 轮中位 span p99 2ms(pipeline 修复后与三期持平)、HTTP 直连 11011 rps。
4. **内存收益分场景,不能一概而论**(见 §8,这是初版报告的结论错误):
   - **消息负载场景(≤500 连接)**:Go 业务层 RSS 67~171MB vs Node 186~472MB,**省 2.8~4 倍**;
   - **纯连接场景(1 万连接爬坡、无消息负载)**:Go 276~287MB vs Node 175MB,**反而多 58~64%**(每连接 2 个流 goroutine 栈+缓冲;Node 事件驱动无此开销)。
5. **失败模式本质变化**:三期是「DB 失败→message.error 快速拒绝」,Go 版在 3000 msg/s 内**完全消除错误**;残留风险是 tp_r30 量级持续过载会压挂同机 colima 的 PG/Redis(环境性风险,压测中恢复 5 次)。
6. **诚实边界**:tp_r30(3000 msg/s)为同机 PG 单实例能力边界附近,Go 版零错误但 p99 425ms 高于预期 150ms(预期基于"PG 无瓶颈"假设),且轮次间波动大(252~537ms,与 colima 共享资源有关)。
7. **V3 目标架构未全部完成**(见 §12):定向下行、分区表、读写分离、会话热点限流、gRPC health、多副本演练、2~5 万容量复测均未做,本报告数据均基于**单业务层副本 + Redis pub/sub 下行(过渡方案)**。

## 7. 发号 INCR 改造归因验证

三期归因「瓶颈 100% 在 DB 行锁」,本期用同一套压测工具验证解绑后结果:

| 证据 | 三期(gRPC 流,行锁) | 本期(Go,INCR) |
|---|---|---|
| tp_r25 错误率 | 40.4%(全部 message.error=DB 失败拒绝) | **0%** |
| tp_r30 错误率 | 79.9% | **0%** |
| tp_r25 p99 | 2075ms(行锁等待平台) | 156ms |
| S3(3000 msg/s) | 39.8% 错误 | **0% 错误** |
| Redis `conv:seq:*` 键 | 无 | 有(INCR 生效,checkpoint 每 60s 回写 PG) |

**结论:行锁是错误率唯一来源的假设得到反向验证——解绑后错误率直接归零,p99 脱离 2s 平台。** 余下延迟为 PG 写入与下行投递,与三期「瓶颈在 DB」同源但量级已从"拒绝"改善为"排队"。

## 8. CPU/内存收益实测(修订版:分场景、标明采样来源)

**消息负载场景(ab-run 采样,serverRss=pidOnPort(3007) 直读进程 RSS):**

| 场景 | 三期 Node serverRss 基线→峰值 | Go serverRss 基线→峰值 | CPUΔ(process_cpu_seconds)三期→Go |
|---|---|---|---|
| S1 | 186→290MB | **65→67MB** | 36.9s→25.0s(-32%) |
| S5 | 206→297MB | **90→92MB** | 92.4s→57.6s(-38%) |
| tp_r25 | 467→472MB | **170→171MB** | 55.1s→49.5s(-10%) |

**纯连接场景(gw-ramp-probe 采样,1 万连接、无消息负载):**

| 连接数 | 三期 Node serverRss | Go serverRss | 差异 |
|---|---|---|---|
| 2000 | 175.3MB | 287.4MB | +64% |
| 6000 | 175.2MB | 280.7MB | +60% |
| 10000 | 175.1MB | 276.3MB | +58% |

**归因(审查新增)**:
- Node 内存由**消息负载**驱动(Prisma 查询缓冲/对象池),纯连接时几乎不涨(175MB 平台);Go 内存由**连接数**驱动(每连接收发 2 个流 goroutine 栈 + 缓冲),1 万连接 2 万 goroutine 贡献 ~100MB。
- 结论:**"Go 内存更省"仅在消息负载场景成立(省 2.8~4 倍);纯连接高密度场景 Go 反而多 ~60%**。初版报告"内存省 2.8~4 倍"未限定场景,属结论错误,特此修正。
- 若未来场景以连接密度为主(如 10 万连接),Go 业务层需做流 goroutine 池化或 buffer 复用,否则内存会线性恶化(已列入 §12 后续计划)。
- goroutines/goGcΔ 字段采自 `job="gateway"`(网关进程),三期与本期网关相同,初版误标为业务层 goroutine(6626),已修正;eventloopP99 仅 Node 有,本期为 null 属预期。

## 10. 行为对齐验证(P7 双跑)

- **34/34 端点字段级零差异**:`biz/scripts/diff-api.mjs` 对 Node(:3007) 与 Go(:3009) 同构请求,递归比较响应键集合/值类型/时间格式/HTTP 状态,含:
  - 注册(201/409 重复/400 校验)、登录(200/400 错密码)、check-username;
  - 用户资料/更新、userConversations/conversations/messages/lastMessages/sync(含 400 非法参数)/read/mentions/readCount;
  - **好友全流程**:addFriend→getFriendReqs→replyFriendReq(accepted)→getFriendList(值骨架)→updateRemark→searchUser(已是好友);
  - **OAuth 授权码全流程**:PKCE S256 challenge→authorize 302→token→userinfo→refresh,id_token 存在性一致;
  - TURN 凭证、上传秒传、OAuth 元数据(openid-configuration/jwks.json)、RUM、内部 uplink(200/401)。
- **对比口径说明(审查补充)**:diff 为**结构级**(键集合/类型/状态码),非值级(如两侧注册用户 id、token 天然不同);好友列表/请求以动态 userId 为键,按值骨架比对。
- **指标契约**:`/metrics` 指标名/buckets 对齐(含 `server_message_duration_seconds` 等契约指标;Vec 无数据不输出与 Node 行为一致,如 call_events_total 在无通话时两侧均无序列)。
- **bcrypt 对齐已核对源码**:Node `bcrypt.hash(password, 12)`(原生库)↔ Go bcrypt cost 12,行为一致;登录耗时差异为线程池并发模型差异(§5),非 cost 不一致。

## 11. 遗留问题与风险

1. ~~群扇出 span p99 111ms vs 三期 2ms~~ **已解决(O3)**:根因是 Go 版逐成员同步串行 PUBLISH(100 次 RTT)而 Node 为异步 fire-and-forget;改用 Redis Pipeline 批量 PUBLISH 后 span p99 2ms、e2e p99 19ms,与三期持平(见附录 #10)。
2. **历史消息全量端点(messages)无分页**:与 Node 同语义(全量返回),大会话 p99 5.9s;数据量漂移使跨期对比失真,已注明。
3. **tp_r30 持续过载会压挂同机 colima 的 PG/Redis**:压测中发生 2 次(PG/Redis 失联,重启恢复),与三期报告「3000 msg/s 压挂中间件」同一环境性风险。**建议压测环境为中间件设置资源上限/独立部署**;代码侧已保证 PG/Redis 失联时优雅降级(发号回 DB 行锁、下行投递容错)。
4. **高连接密度内存无优势**:1 万连接时 Go 业务层 276~287MB > Node 175MB(§8),超大规模连接场景需 goroutine 池化优化(已列入 §12)。
5. **进程内缓存一致性**:会话/关系行/幂等/seq 初始化四级缓存均为"无删除路径"数据,多副本下靠 `ON CONFLICT DO NOTHING`/Lua 原子性兜底;若未来引入删除语义(如解散群),需同步处理缓存。
6. **Redis 键丢失灾备(审查新发现并已修复,O2)**:本部署 Redis 无持久化恢复,键丢失后发号经防回卷校验自动按 DB 实际最大值(max(seq))重新装载;恢复瞬间的 in-flight 消息可能与重装后首批 seq 重叠(窗口极小、无唯一约束冲突、客户端按 serverMsgId 幂等),已知边界,已在代码注释说明。
7. **golang-migrate 接管后 `schema.prisma` 仅作参考**:迁移唯一入口已切换,团队需遵守新流程(见 biz/README.md)。
