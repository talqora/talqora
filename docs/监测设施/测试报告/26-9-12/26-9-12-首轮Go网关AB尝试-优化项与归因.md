## 0. 一句话结论

首次把 Go gateway 接入实时链路做 A/B 对比,方向是对的,但**方法不成熟**:压测端与被测同机抢资源、
场景覆盖不全(仅 s1~s3)、无轮次取中位与资源采样——测得 S1 p99 高达 392ms(socket.io 侧),远超真实水平;
26-9-14 用严格方法论重测同参数仅 57ms,**证明本轮 392ms 是测量失真,不是系统真实性能**。

## 3. 归因:为什么本轮数据被作废

26-9-14 报告原文(证据):"**本基线显著优于旧 26-9-12 A/B 的 socketio 侧数据(同参数 S1 RTT p99 392→57ms),
旧测受同机 gateway 干扰、方法不当**"。

| 缺陷 | 后果 | 后续轮次的修正 |
|---|---|---|
| ① 同机干扰:gateway 与 server 与压测端同机抢 CPU/内存 | socket.io 侧也被拖慢(392ms 失真),两侧都测不准 | 26-9-14 起压测时 gateway **全程不启动**,确立"纯基线"概念 |
| ② 无轮次取中位 | 单次结果噪声大,不可复现 | 26-9-14 起每场景 3 轮取 RTT p99 中位,原始轮次保留 |
| ③ 无资源采样(RSS/eventloop/GC/CPU) | 无法归因"慢在哪",只能猜 | 26-9-14 起 ab-run 每 2s 采样双侧资源 + 服务内直方图 |
| ④ 场景覆盖不全(仅 3 个) | 没有过载扫描/爬坡/惊群/扇出/HTTP 层 | 26-9-14 扩到 13 场景(S0~S5/扫描/S6/S7/扇出/HTTP) |

## 4. 本轮的方法论遗产(被后续轮次固化为规矩)

1. **"纯基线"概念**:测 A 时 B 必须完全不参与流量(26-9-14 的 gateway 全程未启动,成为唯一对照基座)。
2. **同口径要求**:客户端协议语义(信封/ack 匹配/超时重发/心跳/重连)必须与真实客户端一致,不许裸发帧。
3. **3 轮取中位 + 原始轮次落盘**:承认环境噪声,用统计口径对抗。
4. **过载要警惕环境连带损坏**:本轮已出现同机中间件失联的苗头,26-9-14 正式记录为已知坑(P1001,3000 msg/s 使 colima PG 失联)。

## 5. 本轮结论

- 架构方向(Go 网关接入)保留,数据作废;
- **本轮没有可引用的性能结论**,它唯一的价值是暴露了测试方法学的问题,催生了 26-9-14 的严格基线。
- 遗留到下一轮的问题:真实性能基线缺失、"Go 网关到底快不快"尚无可靠答案。
