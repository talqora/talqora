## 四、S8 极限测试（新增）

`MODE=rate`，100 连接固定，每级 60 s 稳态。

| 级别 msg/s | p50 | p95 | p99 | 服务端 CPU | goroutine | **压测端 CPU** | 判定 |
|---|---|---|---|---|---|---|---|
| 25 | 25 | 189 | 345 | 1.37 核（7.6%） | 583 | 0.9% | Knee 前 |
| 27 | 64 | 656 | 980 | 1.73 核（9.6%） | 2,318 | 1.0% | **Knee**（p99 ×2.8） |
| 28 | 145 | 2,431 | 2,796 | 1.89 核（10.5%） | 5,809 | 1.1% | 越过 Knee |
| 30 | 2,203 | 5,604 | 6,206 | — | — | — | **Cliff**（17,974 帧超时） |

**两个点分开给**

- **性能拐点（Knee）：25–27 msg/s / 连接**，即聚合 **2500–2700 msg/s**。此后 p99 每增加 1 msg/s 就翻倍。
- **崩溃点（Cliff）：30 msg/s / 连接**（聚合 3000 msg/s），出现大面积 ack 超时。
- 二者之间（27–30）是"能跑但延迟不可接受"的区间，**报告不给单点容量**。

**关键否定证据**（这三条同时成立，才排除了"压测机不够"和"CPU 不够"两种误判）：

1. 压测端整棵进程树 CPU **≤ 1.1%**（`time -p` 实测），不是压测机打满。
2. 服务端 CPU **1.37→1.89 核**（18 核的 7.6%→10.5%），不是 CPU 打满。
3. 但 DB 查询速率从 6,000 涨到 **9,192 qps**，goroutine 从 583 涨到 **5,809**（10 倍）。

→ 吞吐上不去而 CPU 用不满、goroutine 暴涨，是**排队等固定容量资源**的典型形态。

## 五、瓶颈归因：DB 连接池

**直接证据**：在 28 msg/s × 100 连接（≈2800 msg/s）稳态下，每 3 秒采样一次 PG 连接数与 biz goroutine：

| 时刻 | PG 连接数 | biz goroutine |
|---|---|---|
| 3 s | 33 | 91 |
| 9 s | 33 | 808 |
| 12 s | 33 | 1,362 |
| 21 s | 33 | 1,374 |
| 24 s | 33 | 745 |
| 27 s（负载结束） | 33 | **20** |

- `pg_conn` 从第 3 秒起**恒定 33**（连接池 `MaxConns=32` + psql 自身 1 条），整段负载没有再涨过一条；
- goroutine 在 91–1,445 之间剧烈振荡，**负载一停立刻回落到 20**——排队中的请求全部在等连接，不是在算。

**容量算式**

| 量 | 实测值 | 来源 |
|---|---|---|
| 连接池上限 | 32 | `biz/internal/store/store.go:67` `cfg.MaxConns = 32` |
| 单条查询平均耗时 | **3.1 ms** | `db_query_duration_seconds_sum/count` |
| 每消息查询数 | ≈ 2.5 次 | `messages` 2734/s + `raw` 4267/s @ 2800 msg/s |
| 理论上限 | 32 ÷ 3.1 ms ≈ **10,300 qps** | 推算 |
| 实测峰值 | **9,192 qps**（89%） | Prometheus |
| 每连接承载 | 2800 ÷ 32 ≈ **87 msg/s** | 推算 |

结论：**连接池在 2800 msg/s 时已跑到理论容量的 89%**，进入排队区。连接数、CPU 都有余量，唯独池没有。

**为什么 DB 不是"慢"，而是"不够"**：单查询 3.1 ms 在容器网络里属正常（PG 在 colima VM 内，跨 virtiofs/docker 网桥一次往返）。要提升只有两条路——**加池容量**（受 `max_connections=100` 约束）或**减少每消息查询次数**（把 2.5 压到 1）。

## 六、连接与时延的分离现象（含一处结论更正）

S6 期间 biz CPU 曾冲到 **15.6–16.0 核**（18 核的 87%）。初判是"1 万连接烧 16 核"，**经时间线交叉验证后已更正**：

| 时刻 | biz CPU | gateway 连接数 |
|---|---|---|
| 04:29:06 | **15.6 核** | **1** |
| 04:29:36 | **16.0 核** | **1** |
| 04:30:36 | 8.4 核 | **10,001** |
| 04:31:06 | 1.0 核 | 301 |

**CPU 打满时连接数还是 1** —— 峰值对应的是探针的"注册/登录 1 万用户"阶段（日志 `登录成功 10000/10000,耗时 118.7s`），不是连接维持：

```
16 核 × 90 s ≈ 1,440 CPU·秒 ÷ 10,000 次登录 ≈ 144 ms CPU/次  ← 正是 bcrypt cost=12 的量级
```

所以本轮**无法**得出"每连接维持成本"的结论，该项需要重测（详见 `问题分析/04-连接侧CPU成本归因更正.md`）。

可以确定的是两个维度的**性质不同**：

| 维度 | 负载 | CPU 成本 | 性质 |
|---|---|---|---|
| 登录 | 1 万次 | 16 核 × 90 s | **一次性脉冲**，与连接数无关，应按 QPS 单独限流 |
| 连接维持 | 10,000 连接 | 待测（侧证：网关 290 MB / 2 goroutine 每连接） | 稳态成本，需单独测 |
| 消息 | 2,800 msg/s | 1.9 核 | 受连接池约束，与连接数无关 |

**做容量规划时这三项必须分开给数**，不能混成一个"系统能撑 N"。

S6 五级明细（每级 +2000 连接，HOLD 5 s）：

| 累计连接 | 建连成功率 | 建连 p99 | 网关 RSS | goroutine |
|---|---|---|---|---|
| 2,000 | 100% | 303 ms | 97 MB | 4,028 |
| 4,000 | 100% | 316 ms | 144 MB | 8,028 |
| 6,000 | 100% | 399 ms | 179 MB | 12,028 |
| 8,000 | 100% | 327 ms | 255 MB | 16,028 |
| 10,000 | 100% | 370 ms | 291 MB | 20,028 |

**连接上限到 1 万仍未触及**（未达 `GATEWAY_MAX_CONNS=50000`，也未见成功率下降）。故 S8 的连接维度扫描本轮未做——按 SOP §5.1 显式认领为缺口，见 §八。

## 八、正确性校验（本轮最重要的发现）

### 8.1 `seq` 唯一性被破坏

| 检查项 | 期望 | 实测 |
|---|---|---|
| `(conversation_id, seq)` 唯一 | 0 组重复 | **212,113 组重复** |
| 其中今日（本轮）新增 | 0 | **199,611 组** |
| 今日新增消息总数 | — | 1,838,365 |
| **重复占比** | 0 | **10.9%** |
| `(conversation_id, sender_id, client_msg_id)` 唯一 | 0 | **0**（幂等正常） |

分布：几乎每个 bench 会话都有约 4,500 组重复（`single_77_78` 4,571 组 / 35,072 条消息），呈**系统性**而非个例。历史上 9-14、9-17、9-18、9-20 各有一批同形态重复，说明这个问题长期存在，只是此前没做这项校验。

**证据链（矛盾点）**：

```
Redis: GET conv:seq:single_47_48 = 134865   (TTL = -1，无过期)
PG   : conversations.next_seq      = 134865
PG   : max(seq)                    = 134865
但   : 同一会话今日仍有 seq = 1,2,3,4,5 的消息被写入（84 条）
      并且 seq=128889 这一个值被 13 条不同消息共用
```

一个值被 13 条消息共用，与"并发"直接相关：`rate=28/30` 档位的重复密度显著高于低速率档位。

**运行日志已确证**：biz 日志（`/tmp/make-dev.log`）中 `seq 疑似键重建,回慢路径重新装载` 出现 **170,415 次**，与本轮 19.9 万组重复同量级；且**全时段连续分布**（每分钟 1,300–7,300 次），不是启动突发：

```
03:58  685    04:05 4,780    04:17 5,523
03:59 3,825   04:06 7,360    …持续到压测结束
```

该告警只可能来自 `seq.go:74` 那一行——即"键被重建"的判定在真实负载下被**误触发**了 17 万次。

**机制（代码级）**——`biz/internal/service/seq.go:63-76` 的快路径：

```go
if _, ok := seqInitialized.Load(convID); ok {
    seq, err := rdb.Incr(ctx, key).Result()   // 原子，每 goroutine 拿到的值互不相同
    if err == nil {
        if last, ok2 := convLastSeq.Load(convID); !ok2 || seq > last.(int64) {
            convLastSeq.Store(convID, seq); return seq, nil
        }
        // 走到这里说明 seq <= last → 判定"键被重建"
        _ = rdb.Del(ctx, key)                 // ← 删除键
        seqInitialized.Delete(convID)
    }
}
```

`convLastSeq` 是**进程级共享**的最后发号值，但 `seq > last` 这个判断在并发下不成立：goroutine A 拿到 101、goroutine B 拿到 102 并把 `last` 写成 102，A 随后比较 `101 > 102` 为假 → **把健康键误判为"被重建"并删除**。删除后走慢路径，`loadInit` 取的是 `max(seq)`（只含**已提交**的行），比刚发出但未提交的号更小 → 重新装载后从头发号 → 与已入库的 seq 重叠。

这解释了三个观测：① 重复只在高并发档出现；② 同一 seq 被 10 余条消息共用（在途并发数）；③ `Del` 后序号出现回退。

**影响**：`seq` 是增量同步的唯一定位依据（`/user/sync` 按 `seq > since` 补拉）。seq 回退 + 重复意味着**补拉会漏消息、也会重放消息**——"消息不重不乱"的核心承诺在真实并发下不成立。

**修复方向**（按优先级）：
1. 先加 **`UNIQUE (conversation_id, seq)`** 兜底——当前 `messages` 只有 `PRIMARY KEY (id, conversation_id)`，没有任何约束能拦住重复号，这是缺陷得以长期存在的前提。
2. 删掉 `seq > last` 这个并发下无效的"键重建"判据，改用**单调不回退**的检测（如记录每个会话的 `last` 只在装载后设置，或直接用 Lua 在 Redis 内做 `GREATEST` 比较）。
3. 去掉 `Del(key)` 这种破坏性恢复动作；键不存在时由 Lua 的 `SET init`（init 取 DB 最大值）自然处理。

## 十一、与上期（26-9-20）对比

**结论：本期确实退化了，但"差多少"不可靠；"为什么差"可以解释。**

| 场景 | 负载 | 9-20 p99 | 本期 p99 | 倍率 |
|---|---|---|---|---|
| S5 / S2 | 500–600 msg/s | 49 / 104 | 72 / 161 | 1.5× |
| S1 / tp_r10 | 1000 msg/s | 40 / 58 | 68 / 101 | 1.7× |
| tp_r20 | 2000 msg/s | 53 | 252 | 4.8× |
| tp_r25 | 2500 msg/s | 65 | 429 | 6.6× |
| **S3 / tp_r30** | **3000 msg/s** | **62 / 204（零错误）** | **1282 / 4763（大量超时）** | **20×** |

退化倍率随负载**单调上升**（1.5× → 23×），说明不是"机器均匀变慢"，而是**系统在临界点附近被放大的结果**。

三个叠加因素（详见 [`问题分析/07-跨期可比性与机器资源一致性.md`](./问题分析/07-跨期可比性与机器资源一致性.md)）：

1. **环境基线漂移**：本机从 11-05 起新增了另一个项目的 14 个容器；且 9-20 未做 A/A 底噪标定，本期底噪为 32%；
2. **单消息 CPU 成本上升 21%–38%**（0.92 → 1.11–1.27 ms/msg），其中一部分来自 `seq` 误判的额外查询与数据量增长（359 万 → 747 万行）；
3. **临界点放大**：池已跑到 89% 利用率，余量减少 20% 就会被排队放大成数倍延迟。

**口径限制**：两期 commit 不可比（9-20 未记录 SHA）、副本数不同（2 vs 1）、环境不同，因此**绝对 p99 不作为生产承诺**，只用于判定"是否退化"与"退化形态"。

## 十二、后续优化

后续优化: `seq` 唯一性缺陷 —— 先加 `UNIQUE (conversation_id, seq)` 约束拦截，再修 `seq.go` 的 `seq > last` 并发误判与 `Del(key)` 破坏性恢复；修复后必须重跑 L4/L16 校验，并对历史 21 万组重复做一次清洗或标注（P0）。

后续优化: DB 连接池容量 —— 当前 32 在 2800 msg/s 达 89% 利用率。先做"每消息 2.5 次查询 → 1 次"的合并（收益最大且不占 `max_connections`），再考虑把池提到 48–64 并同步调高 PG `max_connections`（P1）。

后续优化: `/user/messages` 改默认 `limit` —— **已做 A/B 实测**：同一端点不传 limit 是 7.1 rps / p99 4,474 ms，传 `limit=50` 是 3,964 rps / p99 12 ms（558×）。修复只需把默认路径指向已有的分页分支，改完按 3,964 rps 验收（P1）。

后续优化: 连接侧 CPU 成本 —— 原判"1 万连接耗 16 核"已更正为 bcrypt 登录脉冲（见分册 04），**连接维持成本本轮没有干净样本**，需按分册 04 §六 的"准备/建连/维持"三段式采样重测（P1）。

后续优化: 补齐未覆盖链路 —— L10 热点限流、L11 Redis 降级、L12 慢消费者、L15 上传、L17 通话信令，按 SOP §5.1 缺口逐项补场景；L14 OAuth/JWKS 已于本轮补测关闭（P2）。

后续优化: 观测补齐 —— 增加连接池等待指标与 Redis 命令级指标、给 Grafana 装 image-renderer 或改为面板数据导出（P2）。
`db_query_duration_seconds` 已是 `HistogramVec`（`biz/internal/metrics/metrics.go:91`，2026-09-18 起），不是 Summary：本轮取不到分位属**查询写法/抓取目标**问题（需 `sum by (le)`），不要按"改指标类型"去改代码。

后续优化: 吞吐上限的系统性提升 —— 三级台阶（省往返 2.5× → 组提交 4–7× → 扩副本线性）与分析见 `docs/IM/消息链路/2026.11/00-消息吞吐上限分析与提升技术方案.md`；每级的验收口径见分册 10。
