# 问题 09：机器真实资源——能不能查、现在查到了什么

> 严重度：**P1 分析前提**
> 状态：历史窗口不可回溯；已建立采集能力并补测参考剖面
> 关联：`07-跨期可比性与机器资源一致性.md`、`环境说明.md` §6、`perf/resmon.sh`

## 一、先回答"能不能查"

**分两种时间范围，答案不同：**

| 范围 | 能不能查 | 原因 |
|---|---|---|
| **本次压测窗口（04:03–04:45）的机器级曲线** | ❌ **不能** | macOS 不自带 `sar`（无历史采样）；当次没有埋点；Prometheus 只抓了 biz/gateway 的 `/metrics`，没有宿主机 exporter |
| **机器的当前状态与累计痕迹** | ✅ 能 | `vm_stat`（累计页数）、`sysctl vm.swapusage`、`load average`、`pmset -g log` 都保留 |
| **重新测一份参考剖面** | ✅ 能，且已做 | 新增 `perf/resmon.sh`，空载 + 受控负载各采 60 s |

所以正确做法不是"猜当时",而是**把能力建起来 + 补一份可复现的剖面**，让下一次压测自动带上。

## 二、历史痕迹里能读到的（间接证据）

`vm_stat` 的 `Pageins/Pageouts` 与 `swapusage` 是**自开机累计**的，不受压测窗口限制：

| 项 | 实测（2026-11-15 05:0x） | 含义 |
|---|---|---|
| Swap 总量 / 已用 | 47,104 MB / **45,400 MB** | 交换空间几乎用满 |
| 空闲页 | **68–231 MB** | 物理内存基本没有余量 |
| 压缩器占用 | **14.0–14.8 GB**（930,579 页 × 16 KB） | 系统在靠压缩内存续命 |
| Pageins / Pageouts（累计） | 343,198,634 / 7,391,590 | 3.4 亿次换入 |
| `memory_pressure` 报的系统空闲 | 42% | 与"空闲页 68 MB"并存——说明靠压缩/换出撑出的"可用" |

**这些数字不随压测开始/结束变化，说明内存压力是长期状态，不是压测造成的。** 也就意味着压测全程都在这台"内存已经绷紧"的机器上进行。

## 三、新建的采集能力：`perf/resmon.sh`

### 3.1 采什么

三级、每 `INTERVAL` 秒一行 JSONL：

| 层级 | 字段 |
|---|---|
| **宿主机** | `cpu_user/sys/idle`、`load1/5/15`、`mem_used_mb`、`mem_free_mb`、`compressor_mb`、`swap_used_mb`、`pageout_per_min`、`pagein_per_min`、`disk_mbs`、`net_rx_mbps`、`net_tx_mbps` |
| **colima VM** | `load1`、`mem_used_mb`、`mem_total_mb`（中间件所在的虚拟机） |
| **容器** | 其他项目容器的 **CPU 合计 / 内存合计 / 个数**（自动排除 `our-chat-*`） |
| **采样器自身** | `tick_ms`（一个采样周期耗时，用来判断采样是否构成干扰） |

### 3.2 设计上的两个细节

- **错峰采样**：`iostat -d -c 2` 要等 2 s、`docker stats` 要 2 s，全塞进每个 tick 会让采样周期变成 6 s。改成"磁盘每 3 个 tick、容器每 2 个 tick"，常规 tick 降到 1–2 s。
- **记录自身开销**：`tick_ms` 让你一眼看出采样器有没有污染数据。本轮首 tick 6,000 ms（三个重命令撞在一起），后续 1–2 s。

### 3.3 用法

```bash
# 空载基线(压测前必采)
bash perf/resmon.sh docs/监测设施/测试报告/<期>/data/resmon_idle.jsonl 60

# 负载中(与压测并行,后台跑)
bash perf/resmon.sh docs/监测设施/测试报告/<期>/data/resmon_s1_load.jsonl 70 &
CONNS=100 RATE=10 DURATION=60 node perf/harness-gw.mjs
```

## 四、补测结果：空载 vs 1000 msg/s

受控负载 = S1 参数（100 连接 × 10 msg/s × 60 s，共 59,400 条，p99 86 ms，零错误）。

| 指标（中位） | 空载 | 负载 | 负载峰值 | 解读 |
|---|---|---|---|---|
| 宿主机 CPU 忙 % | **20.1** | **37.99** | 59.98 | 空载就吃掉 **3.6 核**；负载时约 6.8 核 |
| 宿主机 CPU 空闲 % | 79.89 | 61.99 | — | — |
| load1 | 6.29 | 4.98 | 7.21 | 空载 load 6.29 却有 80% idle，说明负载主要来自**阻塞态（I/O 等待）**而非计算 |
| 内存已用 MB | 37,920 | 37,589 | 37,997 | 48 GB 中用掉 37.9 GB |
| 空闲页 MB | **231** | **80** | — | 几乎没有余量 |
| 压缩器 MB | 14,758 | 14,014 | — | 常年 14 GB |
| Swap 已用 MB | 45,317 | 45,101 | — | 基本用满 |
| **换出页/分钟** | **1,520** | **1,760** | **4,180** | **持续换页，负载下更多** |
| **磁盘 MB/s** | **1.48** | **22.41** | **48.12** | 负载把磁盘 I/O 拉高 **15 倍** |
| 网络 RX Mbps | 5.92 | 6.99 | 8.27 | 网络不是瓶颈（千兆/万兆级别余量巨大） |
| colima VM load1 | 0.36 | 0.47 | — | VM 内部（12 vCPU）并不忙 |
| 其他项目容器 CPU % | 12.3 | 17.2 | — | 占 1–2 个核 |

> 口径说明：两次采样期间 `resmon.sh` 自身都在运行（tick 1–2 s，主要成本是 `top`/`docker stats` 的等待，CPU 占用低），
> 且 IDE、浏览器等常驻应用未关闭。所以这一档代表的是「**这台工作机的典型空载**」，不是「裸机空载」——
> 真正的裸机数值需要关掉其他应用后再采一次，本轮未做。

## 五、三个关键结论

### 5.1 CPU 不是机器侧的主要问题，"空转"本身占 20%

- 空载 20.1% 的忙 = 18 核里 **3.6 核**，其中其他项目容器占 12.3%（约 2.2 核），其余是 IDE、浏览器、`com.apple.Virtualization` 等；
- 负载 1000 msg/s 时升到 38%（6.8 核），**而 biz 自身只用了约 1.2 核** → 其余 5.6 核仍然不是被测系统。

### 5.2 真正的机器侧瓶颈是内存与换页

| 证据 | 数值 |
|---|---|
| 空闲页 | 80–231 MB（48 GB 机器） |
| Swap 已用 | 45.1 GB |
| 换出页率 | 空载 1,520 /min → 负载峰值 **4,180 /min** |
| 负载期间磁盘吞吐 | 1.48 → **22.41 MB/s**（峰值 48） |

**因果链**：物理内存被 37.9 GB 常驻 + 14 GB 压缩器占满 → 空闲页接近 0 → 系统持续换出 → 压测时 DB 的 3.5 GB 表与索引无法稳定留在 page cache → 读路径命中磁盘 → 延迟抬升、磁盘 I/O 涨 15 倍。

这与本轮观察到的"低负载档 p99 也涨了 1.5–2 倍"是吻合的：**基线延迟整体抬升，正是内存不足的典型表现**。

### 5.3 `load1 = 6.29` 但 80% idle 的矛盾，说明负载是 I/O 等待型

macOS 的 load average 计入"不可中断睡眠"（等磁盘、等网络）。空载 load 6.29 却只有 20% CPU 忙，说明**大量进程卡在 I/O 上**——与 5.2 的换页结论一致。

> 这条对压测的意义：**看 CPU 利用率会以为机器很闲，看 load 才知道它很堵**。以后环境指纹必须同时记 CPU 与 load。

## 六、这修正了 `07` 篇的一个判断

`07` 篇里写"其他容器只占 6.2% 单核，不足以解释 2 倍退化"——那个数字是**某一瞬间**的 `docker stats`，且只覆盖容器、不覆盖宿主机应用。

现在有完整数据后的正确表述是：

| 因素 | 之前判断 | 现在（实测） |
|---|---|---|
| 其他容器 CPU | 6.2% 单核，可忽略 | 12.3–17.2% 单核，约占 1–2 核 |
| 宿主机整体 | 未测 | **空载已占 3.6 核**，负载 6.8 核 |
| 内存 | 未测 | **Swap 45 GB、空闲页 80 MB、持续换页** ← 真正的机器侧主因 |
| 磁盘 | 未测 | 负载下 22–48 MB/s，是空载的 15 倍 |

**结论不变（机器不是唯一原因、`seq` 与连接池是主因），但"机器侧因素"的定性要改**：不是"别的程序抢了 CPU"，而是"**整机内存不够、系统在持续换页**"。

## 七、改进建议

| 优先级 | 动作 | 收益 |
|---|---|---|
| P0 | **压测前重启 colima 与其他容器项目**，让内存回到干净状态 | 直接把 45 GB swap 清零，最便宜的一次性改善 |
| P1 | 每轮开压前采 60 s 空载基线（本脚本），写进环境说明 | 有了"这台机器此刻有多慢"的标尺 |
| P1 | 宿主机加 `node_exporter`（或 vmagent），把上述字段纳入 Prometheus | 与压测指标同时间轴，可做相关性分析 |
| P2 | 压测期间关闭 IDE / 浏览器等重应用 | 空载 3.6 核里有相当部分来自它们 |
| P2 | 长期：压测机独立 | 根治 |

## 九、一句话总结

**压测窗口的机器级数据查不回来了，但机器的"病"能查出来**：48 GB 内存里 45 GB 已换出、空闲页只剩 80 MB、负载期间磁盘 I/O 涨 15 倍。这比"别的程序抢了 CPU"更能解释为什么基线延迟整体抬升——也说明**下一轮压测前最该做的不是改代码，而是重启机器**。
