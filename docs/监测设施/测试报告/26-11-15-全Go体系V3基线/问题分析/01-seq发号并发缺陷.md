# 问题 01：`seq` 发号器在并发下自我破坏（P0）

> 严重度：**P0 数据正确性**
> 状态：已确证（SQL 实测 + 运行日志 + 代码机制三方一致）
> 关联：报告 §8.1、`biz/internal/service/seq.go`

## 一、一句话结论

会话内 `seq` 的"防回卷"守卫 `seq > last` 在并发下会**误判**,触发 `Del(key)` 破坏 Redis 计数器并从滞后的 DB 最大值重装载,导致序号回退与重号。本轮新增消息中 **10.9%** 的 seq 与他人重复,而表上**没有任何唯一约束**能拦住它。

## 二、现象

| 检查项 | 期望 | 实测 |
|---|---|---|
| `(conversation_id, seq)` 唯一 | 0 组 | **212,113 组重复** |
| 其中本轮（2026-11-15）新增 | 0 | **199,611 组** |
| 本轮新增消息总数 | — | 1,838,365 |
| **重复占比** | 0 | **10.9%** |
| `(conv, sender, client_msg_id)` 唯一 | 0 | 0 ✅（幂等本身没坏） |

分布是系统性的，不是个例：几乎每个 bench 会话都有约 4,500 组重复（`single_77_78` 4,571 组 / 35,072 条）。

历史上同形态重复也一直存在，只是此前没做过这项校验：

## 三、证据链

### 3.1 数据自相矛盾

```
Redis : GET conv:seq:single_47_48 = 134865   (TTL = -1，未过期)
PG    : conversations.next_seq     = 134865
PG    : max(messages.seq)          = 134865
但是  : 同一会话今日仍写入了 seq = 1,2,3,4,5 的消息（84 条）
       且 seq = 128889 这一个值被 13 条不同消息共用
```

一个值被 13 条消息共用，与并发度直接相关：`rate=28/30` 档位的重复密度显著高于低速率档。

### 3.2 运行日志确证

biz 日志 `seq 疑似键重建,回慢路径重新装载` 出现 **170,415 次**，且**全时段连续**（每分钟 1,300–7,300 次），不是启动突发：

```
03:58  685     04:05 4,780    04:17 5,523
03:59 3,825    04:06 7,360    ……持续到压测结束
```

该告警只可能来自 `seq.go:74`——即"键被重建"的判定在真实负载下被**误触发**了 17 万次。

### 3.3 代码机制

这段代码里有三个状态，必须先分清，否则看不懂后面为什么会互相踩：

| 状态 | 位置 / 作用域 | 含义 |
|---|---|---|
| `conv:seq:{convID}` | Redis，**跨副本全局共享** | 唯一权威计数器，所有副本、所有 goroutine 都对它 `INCR` |
| `convLastSeq` | `sync.Map`，**单进程内**共享 | 本进程"已经发出去的最大号"，每会话一个 |
| `seqInitialized` | `sync.Map`，单进程内共享 | 本进程"该会话的键可用，可以走快路径"的开关 |

`biz/internal/service/seq.go:63-87`，去掉无关行后：

```go
if _, ok := seqInitialized.Load(convID); ok {                                   // ① 快路径开关
    seq, err := rdb.Incr(ctx, key).Result()                                     // ② 原子取号
    if err == nil {
        if last, ok2 := convLastSeq.Load(convID); !ok2 || seq > last.(int64) {   // ③ 防回卷判据
            convLastSeq.Store(convID, seq)
            return seq, nil
        }
        slog.Warn("seq 疑似键重建,回慢路径重新装载", ...)                         // ④ 误判点
        _ = rdb.Del(ctx, key).Err()                                             // ⑤ 破坏性动作
    }
    seqInitialized.Delete(convID)                                               // ⑥ 关掉快路径
}
seq, err := nextSeqWith(...)   // 慢路径：GET → 查 PG 装载 → Lua「GET or SET + INCR」
```

#### 3.3.1 这个守卫原本想解决什么

本部署的 Redis **无持久化**，重启会丢键。键一丢，`INCR` 会从 0 重新开始返回 1，发号器就从 1 重新发号，与库里已有的 `1..N` 大面积重叠。

守卫的设计意图：如果键是健康的，那么"我刚 `INCR` 出来的值"必然大于"本进程此前发过的任何值"。于是 `seq <= last` 就等价于"键一定是被重建了"——此时删掉脏键，回慢路径用 DB 真实最大值重新装载。

这个推理在**串行**下是对的：只有一条执行流时，`INCR` 与比较之间没有任何别的动作插入，`last` 就是 `INCR` 之前计数器值的精确快照，比较结果可信。

#### 3.3.2 并发下判据失真：`INCR` 的原子性 ≠ 判据需要的原子性

`INCR` 是原子的，它保证的是**每个 goroutine 拿到的值互不相同**。但判据依赖的是另一件事：**"我拿到的值"与"别人登记进 `last` 的值"谁先谁后**。

而 `INCR`（在 Redis 上排队执行）与 `Store`（在 Go 进程内执行）是两个独立步骤，两者的先后由 Go 调度器和网络 RTT 决定，**与 Redis 上的取号顺序无关**。于是完全可能出现"先拿到号的人后登记"：

| 时刻 | 执行流 | Redis `conv:seq:x` | `convLastSeq[x]` | 说明 |
|---|---|---|---|---|
| T0 | — | 100 | 100 | 稳态 |
| T1 | A：`INCR` | **101** | 100 | A 拿到 101，随即被调度走（或被 GC / 网络延迟挂起） |
| T2 | B：`INCR` | **102** | 100 | B 拿到 102 |
| T3 | B：比较 + `Store` | 102 | **102** | `102 > 100`，通过，正常返回 |
| T4 | A：比较 | 102 | 102 | A 手里的 `101 > 102` 为**假** → 判定"键被重建" |
| T5 | A：`Del key` | *(键不存在)* | 102 | **健康的计数器被删除** |
| T6 | A：`seqInitialized.Delete` | — | 102 | 本进程对该会话的快路径被关闭（影响所有 goroutine，不只是 A） |

A 手里的 101 并没有"变小"，也没有任何异常：它只是**更早取到、更晚登记**。判据却把这种完全正常的现象解读成了"计数器重启"。

本质上，这是一个**用局部观察去验证全局性质**的错误。要区分"键被重置"和"我只是拿了个早号"，必须知道"我 `INCR` 之前键里是多少"——而这个信息在 `INCR` 之后已经消失。`seq > last` 拿两个执行流各自看到的局部值去反推一个全局事实，单线程下因为不存在第二个执行流而恰好成立，多 goroutine 下必然失效。

两点容易被误认为"已经防住了"，其实都没防住：

- **换成 `sync.Map` 也没用**。这不是数据竞争（race），`Load/Store` 本身是安全的；错的是**逻辑判据**，加锁只会让交错顺序更固定一点，照样误判。
- **这不是多副本问题**。多副本之间 `convLastSeq` 本就不共享，但即使只在单进程内部，两个 goroutine 就足以触发。

这也解释了为什么现有单测 `TestNextSeqKeyRebuild` 一直是绿的：它覆盖的是"键丢失"的串行恢复路径，没有覆盖"多 goroutine 同时走快路径"（见 §七 第 4 条）。

#### 3.3.3 误判的代价：重装载值必然落后于"已发出的号"

`Del` 之后走慢路径，装载值来自 `seq.go:133`：

```sql
GREATEST(c.next_seq, COALESCE((SELECT max(seq) FROM messages WHERE conversation_id = $1), 0))
```

这两个来源都只反映**已经落库**的历史，反映不了**已经发出、还在路上**的号：

| 来源 | 滞后的原因 |
|---|---|
| `conversations.next_seq` | 只由 checkpoint goroutine 每 **60s** 用 `GREATEST` 回写一次（`seq.go:210-245`），最坏滞后一整个周期 |
| `max(messages.seq)` | 只统计**已提交**的行；而发号在 `message.go:106`，INSERT 事务在 `message.go:118-136`，中间隔着 `Begin` + `INSERT` + `Commit` 三段耗时 |

所以恒有：

```
已发出的最大号  ≥  已提交的最大号  ≥  重装载值
                  └─── 差值 = 在途消息数 + checkpoint 滞后 ───┘
```

发号与落库不在同一事务，这个差值不可能为 0。重装载后计数器从更低的基线重新开始，新发出的号必然落进这个"在途窗口"，与回卷前已经发出（且随后会提交入库）的号一一撞上。

还有一个次要问题：键缺失时，多个 goroutine 会各自查一次 PG 拿到各自的 `init` 再进 Lua。Lua 里 `GET` 有值就只 `INCR`，所以只有一个 `init` 生效——**先跑进 Lua 的那个**。谁先到由调度决定，写进去的很可能是更旧的一个值。

#### 3.3.4 为什么这条链会自我维持（17 万次是全时段连续，不是启动突发）

关键在于：一旦计数器被压到 `last` 以下，它就很难再爬回去。

设重装载基线为 `R`、当前 `last` 为 `L`，且 `R < L`（正常情况 `R` 总是落后一个在途窗口）：

1. 下一个 goroutine `INCR` 得到 `R+1`；
2. `R+1 <= L` → 再次命中误判分支 → 再次 `Del` → 再次从 DB 装回 `R`；
3. 回到第 1 步。

只要 `R < L` 持续成立，每次 `INCR` 都会判失败、每次判失败都删键、每次删键都把计数器按回 `R`。这不是"偶发误判"，而是一个**自锁循环（livelock）**。

唯一的逃逸路径是：某个瞬间恰好有一批 goroutine 在别人执行 `Del` 之前连续 `INCR`，把计数器推过了 `L`，这批 goroutine 判定通过、把 `L` 抬到新的峰值。但 `L` 被抬高之后，`R`（由 DB 提交和 60s checkpoint 决定）**永远慢半拍**，所以抖动不会自愈，只会随并发度上升而更剧烈。

这条自锁链恰好解释了四个观测：

| 观测 | 解释 |
|---|---|
| 告警 17 万次且**全时段连续**（每分钟 1,300–7,300） | 自锁循环，不是启动/重连的一次性事件；频率 ≈ 在途 goroutine 数 × 每秒轮转次数 |
| 重复**只在高并发档出现**，`rate=28/30` 档密度显著更高 | 并发度既决定"推过 `L`"的概率，也决定回卷频率；并发降到 1 时 `R` 必然追上 `L`，循环自然停止 |
| 同一 seq 被 10 余条消息共用 | 每次回卷都会把 `(R, 峰值]` 这段号重新发一遍；窗口大小 ≈ 在途并发数，与观测到的 13 条量级相符 |
| 序号出现回退（库里同时存在 `seq=1,2,3,4,5` 与 `seq=128889`） | `R` 由 DB 决定，可能远低于历史已发出的最大号；回卷后从 `R+1` 重新发放 |

顺带还解释了一件事：每次 `Del` 之后，紧随其后的 goroutine 都会看到空键而走慢路径，**各自查一次 PG 的 `max(seq)`**——这正是 §七 第 1 条要求观察的"`max(seq)` 查询尖峰"的来源。

#### 3.3.5 一句话总结

**取号是原子的，但"防回卷判断"不是。** 判断把一个并发下的正常现象（早取号、晚登记）误读成异常（键被重建），再用一个不可逆的破坏性动作（`Del`）去"修复"它，而修复路径能看到的只有滞后的数据库——于是每次误判都稳定地产出一批重号。

因此修法必须同时满足两点（见 §六 方案 B）：把"比较 + 取号"合并为 Redis 内的单次原子操作（Lua），以及**彻底删掉 `Del`**——键真的丢了，也应由原子装载路径自然处理，而不是先毁掉现场再猜。

## 四、影响

`seq` 是增量同步的**唯一游标**：`/user/sync?since=<seq>` 按 `seq > since` 补拉。

| 后果 | 说明 |
|---|---|
| 漏消息 | 客户端已拉到 seq=100，服务端因回退把后续消息重新发成 90–99，`since=100` 的补拉永远取不到 |
| 重放消息 | 同一 seq 对应多条消息，客户端按 seq 去重时会丢掉其中一条 |
| 排序错乱 | 会话按 seq 排序展示时顺序与实际发送顺序不符 |
| 隐私面 | 无法从 seq 判断消息先后，审计/回溯失去依据 |

**"消息不重不乱"这个核心承诺，在真实并发下不成立。**

## 五、为什么能长期存在

`messages` 表只有主键，没有任何业务唯一约束：

```
messages_partitioned_pkey | PRIMARY KEY (id, conversation_id)
```

没有任何约束拦得住重复 `(conversation_id, seq)`，所以每次误判都静默写脏数据，直到有人主动跑聚合查询才会发现。

## 六、改进方案

### 方案 A：加唯一约束（必做，先上）

```sql
CREATE UNIQUE INDEX CONCURRENTLY uq_messages_conv_seq
  ON messages (conversation_id, seq);
```

- **收益**：把静默写脏变成显式失败，问题立刻暴露；是后续所有修复的安全网。
- **风险**：存量 21 万组重复会导致建索引失败，必须先清洗（见下）。
- **注意**：分区表上建唯一索引要求分区键包含在索引列中；当前分区键若不含 `conversation_id`，需改为在**每个分区**上建局部唯一索引，或用触发器兜底。

### 方案 B：修发号器（必做）

去掉并发下无效的判据，改为**单调不回退**语义：

| 子问题 | 改法 |
|---|---|
| `seq > last` 误判 | 不要用"与其他 goroutine 共享的 `last`"做判据。改用 Lua 在 Redis 内部完成"取当前值 → 与期望下限比较 → INCR"的原子操作，把判断放进 Redis，天然串行 |
| `Del(key)` 破坏性恢复 | 删除该动作。键不存在时由 Lua 的 `SET init` 自然处理，`init` 取 DB 最大值即可 |
| `max(seq)` 滞后于在途事务 | 装载值改为 `max(next_seq, max(seq)) + in-flight 余量`，或直接放弃"从 DB 重装载"这条路径，改为 Redis 持久化（AOF）+ 键丢失时**暂停该会话发号**并告警，人工介入 |

### 方案 C：存量清洗（修复后）

- 保留每组重复中 `id` 最小的那条的原始 seq；
- 其余按 `created_at, id` 顺序重新分配 seq（追加到 `max(seq)` 之后），保证单调；
- 清洗前先按会话导出快照，便于回滚。

**取舍**：A 是安全网、B 是根治、C 是收尾。顺序不能颠倒——先 A 会让当前代码直接报错（好事，暴露问题），但线上会开始丢消息；所以实际执行建议 **A 与 B 同批上线，C 在维护窗口做**。

## 七、验证方法（修复后怎么证明修好了）

1. 重跑 S8 速率阶梯到 `rate=30`，观察：
   - 日志中 `seq 疑似键重建` 次数应 **= 0**；
   - `pg_stat_activity` 不再出现异常的 `max(seq)` 查询尖峰。
2. 重跑正确性校验：
   ```sql
   SELECT count(*) FROM (
     SELECT conversation_id, seq FROM messages
     WHERE created_at > <本轮开始> GROUP BY 1,2 HAVING count(*)>1
   ) t;   -- 期望 0
   ```
3. 唯一索引建成即为终局证明：若有任何路径再产生重号，插入会直接失败。
4. 补一个并发单测：N 个 goroutine 并发对同一会话取 10 万次号，断言结果集合大小 = 10 万且严格递增（当前 `TestNextSeqKeyRebuild` 只覆盖了串行场景）。

## 八、附：为什么这不是"压测才有"的问题

压测只是把并发度放大到接近线上峰值。判断标准很简单：

- 线上单会话的并发发送峰值是多少？如果 ≥ 2 条消息在途，误判就可能发生；
- 触发概率随"在途消息数"和"DB 延迟"同时上升——DB 越慢，窗口越宽，误判越多。

本轮 DB 平均查询 3.1 ms，在途窗口只有几毫秒，就已触发 17 万次。**线上只要 DB 出现一次抖动，重号就会成批产生。**
