# 问题 10：吞吐提升的验收方案与压测口径

> 严重度：**P1 方法论**（没有验收口径的优化无法归因，也会被 A/A 底噪骗过去）
> 状态：待执行（配套 [`00-消息吞吐上限分析与提升技术方案.md`](../../../../IM/消息链路/2026.11/00-消息吞吐上限分析与提升技术方案.md)，11 个方向的完整分析与坑点见同目录 `01`–`11` 分册）
> 关联：本轮 §三（主跑批）、§四（S8 极限）、§五（池归因）、§8.1（正确性）

## 一、一句话结论

本轮已经把"瓶颈是连接池"钉死，但**验证"优化是否有效"比"发现瓶颈"更容易出错**：A/A 底噪 p99 相对差 **32%**，任何小于 20% 的"改善"都不可信；且本轮单副本、跨期 commit 不可比。所以优化验收必须遵守三条铁律：**单变量阶梯、三点曲线、带反证**。

## 二、三条铁律（先立规矩，再看数据）

### 2.1 单变量阶梯

一次只抬一个维度，每级 ≥60 s 稳态。禁止在同一轮里既改代码又改环境（机器、副本数、数据量）。

| 允许的变化 | 禁止的变化 |
|---|---|
| 代码改动（一个阶段一次） | 同一轮内既改代码又加副本 |
| `MODE=rate` 或 `MODE=conns` 二选一 | 混跑（本轮的 S3 与 tp_r30 是同速率不同形态，只能用来排除"连接数"假设，不能当两点曲线） |
| 参数显式 `export` | 依赖脚本默认值（本轮 `s8-limit.sh` 首版就因未 export 停止判据跑多了一级） |

### 2.2 三点曲线，不给单点容量

沿用 S8：`Knee`（p99 相对上一级 >2×）与 `Cliff`（错误率 >1%）分开报，中间只给区间。

**验收只比较"Knee 的位置"，不比较单点 p99**——因为单点 p99 受底噪支配。

### 2.3 带反证

每条优化必须预先写下"如果假设正确，应该看不到什么"。缺了反证，p99 下降可能只是机器今天比较闲。

| 优化 | 反证（若不成立即假设错误） |
|---|---|
| 池是瓶颈 | 优化后 `pg_conn` 在 28 msg/s 档**不再恒定 33**，且 `db_pool_wait_seconds` > 0 的时间占比显著下降；若池不再满但吞吐没涨 → 瓶颈另有其人 |
| `seq` 误判在放大负载 | 修复后日志 `seq 疑似键重建` = 0，且 `db_query_duration_seconds{model="raw"}` 的 QPS **下降**（少掉的正是 `max(seq)` 装载查询） |
| 批量写入突破池约束 | 优化后 **连接池利用率 < 20% 时吞吐仍能上涨**；若池利用率仍随负载线性上升 → 批量没生效（仍在逐条提交） |
| 读端点吃池 | 注入 `/user/messages`（无 limit）7 rps 后，**消息侧 p99 上升 ≥ 30%**；修完默认 limit 后同样注入应无显著影响 |

## 三、必测指标（前四项是当前硬缺口）

| # | 指标 | 现状 | 采集方式 | 为什么必须有 |
|---|---|---|---|---|
| 1 | **`db_pool_wait_seconds`**（取连接等待时长） | **无** | 自定义 collector 包装 `pgxpool.Stat()`（`AcquireDuration()` 累计等待、`AcquireCount()` 次数、`TotalConns()`/`IdleConns()`），或接第三方 `pgxpool-prometheus` | 没有它，"瓶颈是池"只能靠外部 `pg_stat_activity` 侧证（本轮就是这么做的） |
| 2 | **`db_pool_acquired / idle / max`** | **无** | 同上 | 区分"池满"与"池空转" |
| 3 | **Redis 命令级指标**（按 cmd：`eval`/`incr`/`exists`/`setnx`/`publish`） | **无** | go-redis Hook 或 redis_exporter | `seq` 修复的验证靠 `del` 归零；批量写入的验证靠 `eval` QPS 下降到 1/32 |
| 4 | `db_pool_commit_seconds`（提交耗时单独度量） | 无 | pgx tracer 已能按 SQL 打标签，`COMMIT` 会计入 `model="raw"` | 组提交的收益直接体现为"提交次数下降"，需要能单独看到 |
| 5 | `server_message_batch_size`（每批条数分布） | 无（批量后新增） | 新指标 | 批量参数是否合理（长期 <8 说明窗口太短，长期打满 64 说明窗口偏小） |
| 6 | `db_query_duration_seconds` 分位 | 代码是 Histogram（`metrics.go:91`），但本轮查不出数据 | `histogram_quantile(0.99, sum by (le) (rate(db_query_duration_seconds_bucket[1m])))` | 上一条历史结论需要复核，见方案文档 §8 附录 |

> 说明：`db_query_duration_seconds` 在代码侧一直是 `HistogramVec`（2026-09-18 起），报告 §十-1 的"是 Summary"判断与代码不符。**先按上面的正确写法复查查询语句**，不要按"改指标类型"去改代码。

## 四、分阶段验收矩阵

每阶段跑完必须同时满足"性能项"与"正确性项"，两项任一不过即回滚。

### P0：`seq` 正确性

| 项 | 场景 / 命令 | 通过标准 |
|---|---|---|
| 性能 | `OUT_SUBDIR=<本轮新目录> MODE=rate LEVELS=25,27,28,30 bash perf/s8-limit.sh` | Knee 不回退（允许 ±20%） |
| 正确性 | `SELECT count(*) FROM (SELECT conversation_id, seq FROM messages GROUP BY 1,2 HAVING count(*)>1) t` | **= 0** |
| 日志 | `grep -c 'seq 疑似键重建'` | **= 0** |
| 索引 | `\d+ messages` 含 `uq_messages_conv_seq`（每个分区都有） | 全部存在 |
| 单测 | N 个 goroutine 并发对同一会话取 10 万次号 | 结果集合大小 = 100000，严格递增 |

### P1：省往返（autocommit + 合并 Lua + presence + 默认 limit）

| 项 | 通过标准 | 反证 |
|---|---|---|
| S8 `rate=28` | 错误 0；p99 相对本轮下降 **≥ 40%** | 若 p99 下降但 `pg_conn` 仍恒定 33 → 池不是唯一瓶颈，继续查 |
| `db_query_duration_seconds` 分模型 QPS @ 2800 msg/s | `messages` 保持 ≈1 次/条（2734→≈2800）；**`raw` 从 4267/s 降到 ≈0** | `raw` 未下降 = BEGIN/COMMIT 还在，事务没去掉 |
| Redis `eval` QPS @ 2800 msg/s | 从 3 次/条降到 **1 次/条** | 未降到 1 → 合并脚本没生效 |
| `/user/messages` 无参 | 返回 `hasMore` + 默认 50 条；单请求 ≤ 20 ms | 仍返回全量 = 改错了分支 |
| HTTP 混合注入 | 7 rps 无 limit 请求不再显著拉高消息侧 p99 | — |

### P2：批量写入

| 项 | 通过标准 | 反证 |
|---|---|---|
| S8 `MODE=rate LEVELS=28,40,60,80` | **Knee 右移到 ≥ 8000 msg/s**；p50 ≤ 10 ms | 若 `pg_conn` 利用率 <20% 而吞吐仍不涨 → 瓶颈已迁移，按 §4.4 查 CPU |
| `db_pool_wait_seconds` | 稳态 p99 ≤ 1 ms | 仍高 = 批量未减少连接持有 |
| `server_message_batch_size` | 中位数 ≥ 16（64 上限、2 ms 窗口） | 中位数 ≈ 1 = 攒批没生效（队列或窗口逻辑错） |
| **提交顺序一致性** | 见 §五 S10 | 出现逆序即整批设计需返工 |
| 崩溃语义 | `kill -9` biz 后重启：已 ack 消息 100% 存在；未 ack 消息可被客户端重发 | 已 ack 丢失 = 违反红线 |

### P3：扩容与隔离

| 项 | 通过标准 |
|---|---|
| 双副本线性度 | 双副本总吞吐 ÷ 单副本 ≥ **1.85**；`max_connections` 未被打满 |
| 慢读干扰 | 注入 100 rps `/user/lastMessages`，消息侧 p99 劣化 ≤ 30% |
| 慢消费者 | 单连接不读，send buffer 打满被逐出，其它连接 p99 不受影响（对齐 L12 缺口） |

## 五、必须新增的四个场景

当前 `perf/` 覆盖 11 个主场景 + S6/S7/群扇出/HTTP，缺的是**能证明批量与隔离有效**的场景。

### S9：批量提交效率（新）

目的：证明"每条一次提交"确实变成了"每批一次提交"。

```bash
# 100 连接固定，只抬速率，观察提交次数与批大小的关系
# OUT_SUBDIR 必须显式给（脚本默认值指向 26-11-15，不覆盖会污染历史归档）
OUT_SUBDIR=<本轮新目录> MODE=rate LEVELS="28,40,60,80" DURATION=60 bash perf/s8-limit.sh
```

同时每 2 s 采一次：

```sql
SELECT xact_commit FROM pg_stat_database WHERE datname = current_database();
```

判定：`xact_commit` 增速 ÷ 消息速率 ≈ **1/批大小**。若仍 ≈ 1，说明每条消息仍独占一个事务。

### S10：提交顺序一致性（新，正确性）

目的：证明"seq 顺序 = 提交顺序"，避免 `/sync since` 跳过未提交的更小 seq（见方案文档 §5.3 决策 1）。

**为什么不能用 ack 顺序判定**：ack 按 `clientMsgId` 收敛，协议允许乱序；真正要保证的是"同会话内的下行帧 seq 单调"。而下行在 commit 之后发出，所以：

> 观察者连接（只收不发）收到的 `receiveMessage` 帧，其 `seq` 必须严格递增；出现逆序 ⇔ 提交顺序与 seq 顺序不一致。

脚本逻辑（建议独立 `perf/order-probe.mjs`，或并入 `gw-probe.mjs`）：

1. 建一个会话，1 条"观察者"连接（不发送，只记 `receiveMessage` 的 seq 序列）；
2. N=8 条发送连接并发发 5000 条（同会话），关闭会话限流：`CONV_RATE_LIMIT_MAX=0`；
3. 断言 A：观察者记录到的 seq 序列**严格递增、无重复**；
4. 断言 B：`SELECT count(*), max(seq), min(seq) FROM messages WHERE conversation_id=$1` 与 ack 集一致（无多写、无漏写）；
5. 断言 C：`SELECT count(*) FROM generate_series(min,max) s LEFT JOIN messages m ON m.seq=s WHERE m.id IS NULL` = 0（洞数登记，若 >0 必须能全部归因于崩溃/超限的跳号）。

判定：断言 A 任何一次逆序即**不通过**。

> 注意：这一项在**当前代码上大概率会随机失败**（`edge.go:136` 每帧一个 goroutine，commit 顺序与 seq 顺序无约束）。先把它作为基线缺陷记录下来，再把它当作批量写入的验收门槛——修完必须 3 轮 × 5000 条全绿。
>
> 断言 A 失败有**两个来源**：① 提交逆序（seq 小的后提交）；② 下行发送逆序（两次 `FanoutDownlink` 的 goroutine 抢跑）。二者都源于"同一会话被并发处理"，批量 writer"单分片串行"能在同一处一起解决。若只修其一，A 仍会偶发失败——这正好是它的价值。

### S11：读路径侵占写池（新，混合负载）

目的：量化 `/user/messages` 无 limit 与 `/user/lastMessages` 对写路径的影响。

```bash
# 窗 1：只跑 WS 负载（100×20=2000 msg/s）
# 窗 2：WS 负载 + 7 rps 无 limit /user/messages
# 窗 3：WS 负载 + 100 rps /user/lastMessages
```

判定：窗 2 相对窗 1，消息侧 p99 上升应 **≥30%**（证明假设成立）；修完默认 limit 后窗 2' 与窗 1 差异 ≤ 10%。

### S12：池隔离验证（新）

把 writer 池与读池拆开后，人为把读池打到 100%（慢查询注入），断言消息侧 p99 无显著变化（≤10%）。若仍耦合，说明池隔离没生效。

## 六、每轮必跑的正确性校验（与性能同权重）

性能再好也不能带病上线。以下四条每轮都跑，结果写进报告：

```sql
-- 1. seq 唯一（期望 0）
SELECT count(*) FROM (
  SELECT conversation_id, seq FROM messages
  WHERE created_at > $1 GROUP BY 1,2 HAVING count(*) > 1
) t;

-- 2. 幂等（期望 0）
SELECT count(*) FROM (
  SELECT conversation_id, sender_id, client_msg_id FROM messages
  WHERE created_at > $1 AND client_msg_id IS NOT NULL
  GROUP BY 1,2,3 HAVING count(*) > 1
) t;

-- 3. ack 与落库对账（期望差值 0；超时帧单独列出）
SELECT count(*) FROM messages WHERE created_at > $1;   -- 与 harness.ack 对比

-- 4. 定向下行命中率（期望 ≥99.5%）
-- server_downlink_direct_total / (direct + fallback)
```

## 七、环境与可比性（沿用本轮结论，不要重新踩）

| 约束 | 数值 | 对验收的影响 |
|---|---|---|
| A/A 底噪 | p99 32% / p50 2.9% / p95 1.6% | **p99 改善 < 20% 不采信**；优先看 p50 与 Knee 位置 |
| 临时端口池 | 16,383 | 单源无法建 5 万连接，连接维度上限不可测 |
| 同机抢 CPU | 18 核共享 harness + gateway + biz×2 + 5 容器 | 任何"CPU 打满"结论必须先对齐**是哪个进程、哪个阶段**（见问题 04） |
| colima 12 vCPU / 32 GiB | ≈3000 msg/s 时曾多次 PG 失联 | 压测前先确认空载；`colima stop && colima start` 恢复后再跑 |
| 数据累积 | `messages` 已 747 万行 | 读类端点跨轮不可比；用无状态端点（`/health`）做环境一致性锚 |
| commit 不可比 | 9-20 未记录 SHA | 每轮报告**必须记 `git rev-parse HEAD`** 与环境变更（见问题 07） |

- [ ] `colima list` 状态 Running，且已空载 60 s
- [ ] `ps` 确认无其它项目的重负载进程
- [ ] `SELECT count(*) FROM pg_stat_activity` ≈ 1（无残留连接）

## 八、停止判据与回滚判定

S8 的停止判据（`STOP_*`）保持不变，但**必须 export**（首版曾静默失效）：

```bash
export STOP_CONN_OK=0.95 STOP_ERR_RATE=0.01 STOP_P99_RATIO=2 \
       STOP_CPU_PCT=85 STOP_GOROUTINE_RATIO=1.5 BENCH_CPU_STOP=70 NCPU=18
```

回滚判定（任一成立即回滚该阶段，不进下一阶段）：

| 触发 | 回滚理由 |
|---|---|
| 正确性任一项不为 0（重号 / 幂等重复 / 已 ack 丢失） | 性能优化不得以正确性为代价 |
| Knee 位置相对上一阶段**左移** | 改动净负收益 |
| p50 上升 > 30%（p50 底噪仅 2.9%，比 p99 可信得多） | 批窗口或锁引入额外排队 |
| goroutine 峰值相对上一阶段增长 > 1.5× | 又出现了"排队等固定资源"的形态 |
| 混合负载下消息 p99 劣化 > 50% | 隔离没做到 |
