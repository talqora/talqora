# 问题 04：连接侧 CPU 成本——一个差点写错的结论（方法论）

> 严重度：**P1 结论正确性**（错误结论会误导容量规划）
> 状态：**已自我更正**
> 关联：报告 §六（已同步修正）、`perf/gw-ramp-probe.mjs`

## 一、结论先说

初判是"**1 万连接烧 16 核，连接维持成本高**"。用时间线交叉验证后，这个结论**站不住**：

- 16 核峰值出现在 **04:29:06–04:30:06**；
- 而连接数升到 10,001 的时刻是 **04:30:36**——**晚于** CPU 峰值；
- 峰值时段对应的是探针的"注册/登录 1 万用户"阶段（日志：`登录成功 10000/10000,耗时 118.7s`）。

**16 核是 bcrypt 登录烧的，不是连接维持烧的。** 本轮数据无法证明"1 万连接 = 16 核"，这项需要重测。

## 二、原始数据

Prometheus 采样（30 s 步长）：

| 时刻 | biz CPU | gateway 连接数 |
|---|---|---|
| 04:28:06 | 0.0 核 | 1 |
| 04:28:36 | 7.0 核 | 1 |
| 04:29:06 | **15.6 核** | 1 |
| 04:29:36 | **16.0 核** | 1 |
| 04:30:06 | **15.7 核** | 1 |
| 04:30:36 | 8.4 核 | **10,001** |
| 04:31:06 | 1.0 核 | 301 |

**注意 04:29 那一列**：CPU 已经打满，但连接数还是 1。这直接排除了"连接导致 CPU 高"。

## 三、归因算式

```
峰值 CPU ≈ 16 核，持续 ≈ 90 s        → 约 1,440 CPU·秒
同期完成 10,000 次注册/登录           → 1,440 ÷ 10,000 ≈ 144 ms CPU/次
bcrypt cost=12 单次哈希 ≈ 100–200 ms  → 量级完全吻合
```

对照：9-20 报告 §5.1 也指出 "S2/S4 CPUΔ 大头在**登录+建连阶段**(300/500 用户登录 bcrypt)"。同一现象，当时已被正确识别，本轮我一开始漏掉了。

## 四、那连接维持到底多贵

**本轮没有干净的样本可以回答**，原因：

- 探针的 10,000 次登录与建连在同一段窗口内完成，bcrypt 的 CPU 淹没了一切；
- 唯一接近"纯维持"的采样是 `04:31:06`：301 连接、1.0 核——但那是负载收尾期，且包含 GC 尾巴，不能外推。

可用的**侧证**（不能当结论）：

| 观测 | 数值 | 说明 |
|---|---|---|
| 网关 goroutine | 20,028 @ 10,000 连接 | 约 2/连接（readLoop + writer），符合预期 |
| 网关 RSS | 290 MB @ 10,000 连接 | 约 29 KB/连接，内存成本很低 |
| 建连成功率 | 100%（五级全部） | 建连本身没有压力 |
| 网关 CPU（S8 期间） | 0.44–0.48 核 @ 2,800 msg/s | **纯转发**极便宜 |

**合理推测**：连接维持的主要成本是心跳续约（每 60 s 一次 presence 写）与调度唤醒，量级应在"每万连接 ~1 核"附近，而非 16 核。但这需要实测。

## 五、对容量规划的影响

如果按错误结论做规划，会得出"加连接就要加 16 核"的荒谬产能比，从而误判：

| 错误结论的推论 | 实际应有做法 |
|---|---|
| 10 万连接需要 160 核 | 需要实测每万连接的稳态核数 |
| 连接是主要成本 | 登录（bcrypt）才是单次重成本，且可缓存/限流 |

**正确的拆分**是三个独立维度，必须分开给数：

1. **连接维持**：每万连接的稳态 CPU / 内存；
2. **建连速率**：每秒能建多少条（含 JWT 校验）；
3. **登录**：bcrypt 单次 ~150 ms CPU，是**独立的重操作**，与连接数无关，应按 QPS 单独限流。

## 六、方法改进（SOP 层面）

`perf/gw-ramp-probe.mjs` 目前把"登录 1 万用户"和"爬坡建连"写在同一个流程里，中间不打点。应改为**三段式采样**：

| 阶段 | 动作 | 采样 |
|---|---|---|
| ① 准备 | 注册/登录 N 用户 | 记录 CPUΔ、耗时，**并标注这是 bcrypt 成本** |
| ② 建连 | 爬坡到目标连接数 | 记录每秒建连数、CPUΔ/s |
| ③ 维持 | 空转 60 s（不发消息） | **记录稳态 CPUΔ/s ÷ 连接数 = 每连接维持成本** |

只有 ③ 的数值才能用于容量规划。当前缺的就是 ③。

同时，压测报告里凡出现"CPU 峰值"，必须写明**该峰值对应哪个阶段**，否则读者会把它当成稳态成本。

## 七、这条与问题 01/02 的关系

本轮真正的瓶颈链路是：

```
bcrypt 登录（一次性，16 核/90s）  ← 只影响压测准备阶段，不影响稳态
     ↓
DB 连接池 32（持续瓶颈）          ← 决定 2800 msg/s 天花板
     ↓
seq 误判带来的额外 max(seq) 查询  ← 把池推过临界点
```

三者时间尺度不同：登录是**秒级脉冲**，连接池是**稳态约束**，seq 误判是**随负载放大的正反馈**。混在一起看就会得出错误结论——这正是本文档要记录的经验。

## 八、自查清单（下次避免同类错误）

- [ ] 任何"CPU 高"的结论，先对齐**它是哪个进程、哪个时间段、哪个阶段**
- [ ] 跨数据源交叉验证（Prometheus 30 s 采样 vs 探针日志时间戳）
- [ ] 区分**一次性成本**（登录/建连/预热）与**稳态成本**（维持/转发）
- [ ] 结论写成"X 核对应 Y 负载"时，必须给出 Y 的**同期实测值**，不能用计划值
