# 26-9-14 · 纯 Node(socket.io) 性能基线 · 优化项与归因

> 系列定位:五轮优化测试的**第 2 轮**。本轮不是"性能优化"轮,而是**方法学定标轮**:
> 在无 Go 层的条件下建立完整性能基线,作为后续所有 Node vs Go 对比的唯一对照基座。
> 事实锚定:本目录 `README.md` 与 `data/*.json`(26-9-14 原始文档完整保留,本文为其"优化项与归因"档案)。

## 0. 一句话结论

用严格方法论(纯基线/gateway 全程不启动、3 轮取中位、资源采样、13 场景)建立了可信的纯 Node 基线,
并**首次精确定位了系统第一瓶颈:DB 写路径(会话发号行锁 + Prisma 连接池),拐点 1500~2000 msg/s**——
这个归因决定了后续四轮的全部方向(26-9-16 验证通信层、26-9-16-grpc 消灭传输损耗、
26-9-17-gobiz 重写业务层+发号 INCR 化,全部围绕它展开)。

## 3. 归因(本轮最重要的产出:瓶颈定位)

### 3.1 吞吐拐点根因 = DB 写路径,不是事件循环

- 证据:eventloop p99 全程仅 11~17ms、GC 停顿 ≤5ms——**运行时无压力**;而服务内 DB 直方图显示
  `db_query_duration_seconds` 单查询 <10ms,但事务级等待(会话 seq 发号行锁)随负载涨到 2s 级。
- 结论:**拐点在「会话发号行锁 + Prisma 连接池」**,与语言、与连接层无关。这条归因在 26-9-16-grpc 轮
  被再次独立验证(过载平台 gRPC 2075ms vs 基线 2058ms,差值仅 17ms)。

### 3.2 HTTP 两个独立瓶颈

| 瓶颈 | 根因 | 后续处置 |
|---|---|---|
| login 19.3 rps | bcrypt 12 轮 CPU 密集 + libuv 线程池 4 线程排队 | 与语义绑定,不优化;26-9-17-gobiz 轮 Go 版 68 rps 是并发模型差异 |
| messages 73 rps | 无 limit 全量返回历史消息 | 列入后续优化项(跨端分页,见 26-9-17-gobiz 后续优化项分析 §8) |

### 3.3 环境坑(P1001)首次记录

过载(≈3000 msg/s)使同机 colima 的 PostgreSQL 短暂失联,恢复 `colima stop && colima start`。
这条坑贯穿全部五轮,最终在 26-9-17-gobiz 轮被正式归类为"同机中间件争抢"环境风险。

## 4. 本轮结论与遗留问题

- 基线价值:成为后续 26-9-16/26-9-16-grpc/26-9-17-gobiz 三轮全部 A/B 的对照基座(数据文件被三轮引用)。
- **遗留问题 1(决定性)**:DB 行锁瓶颈——"谁能消灭它"成为后续轮次的中心命题(最终由 26-9-17-gobiz 的 Redis INCR 解决)。
- 遗留问题 2:1 万连接未探到 Node 上限,"Go 连接层更强"的假设缺乏可验证场景(26-9-16-grpc §8 实验 ①,至今未闭环)。
- 遗留问题 3:bcrypt 登录 1 万用户需 ~15 分钟,压测成本高(贯穿全系列)。
