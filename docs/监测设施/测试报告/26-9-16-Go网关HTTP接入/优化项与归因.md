# 优化项与归因（Go 网关 HTTP 接入轮）

> 系列定位:五轮优化测试的**第 3 轮**。web 实时层全面切换到 Go gateway(原生 WS `/ws`),
> 业务层仍为 Node;上行通信方式是 **HTTP-per-message**(每消息一次 POST)。
> 事实锚定:本目录《Go网关HTTP接入优化压测报告.md》(实测)、《连接层业务层通信架构演进方案-RPC改造.md》(根因+方案)、《架构分析.md》(差距清单)。

---

## 0. 一句话结论

架构解耦方向被验证正确,但**通信方式选错了**:**HTTP-per-message 的三个缺陷(dial 耗尽/每连接串行等待/重试竞态放大)使 gateway 路径在 1000 msg/s 就劣化(S1 错误率 12.8%)、2500 msg/s 时 RTT p99 2802ms**。
本轮用三条证据链把根因钉死在"通信模型"而非语言/运行时,并产出了下一轮(gRPC 流)的完整方案。

## 3. 归因(三条证据链,全部有源码锚点)

| # | 现象 | 根因锚点 | 机制 |
|---|---|---|---|
| E1 | S1 错误率 12.8%;网关日志 10,341 条 `can't assign requested address`;TIME_WAIT 达 14,922/16,384 | `upstream.go:26` 用 Go 默认 `http.Client`(**MaxIdleConnsPerHost=2**),HTTP-per-message 每秒上千次建连耗尽 loopback 临时端口 | **dial 耗尽(短连接风暴)** |
| E2 | tp_r25 客户端 RTT p99=2802ms,而网关上行服务内仅 98.3ms、下行投递 5ms | `conn.go:79-85` readLoop 每条消息**同步** dispatch→Forward 等回包才读下一帧——发送间隔(40ms)<上行耗时(p95 82ms)时队列单调增长 | **每连接串行等待** |
| E3 | S3 gateway 路径 Node 服务内仅 198.9ms(远好于基线 2483ms)但客户端 p99=5.1s、重发撞在途插入 5,396 条 unique constraint 500 | 串行上行摊平了到达 Node 的并发("保护"了 DB),代价是网关深队列 + 重发风暴 | **重试与在途竞态放大** |

**三条证据链的共同结论**:问题在"每消息一次 HTTP 请求-响应"这个通信模型,与语言无关——"即使全部用 Go 重写也无法解决"(两个 Go 进程之间 HTTP-per-message 同样会 dial 耗尽+串行等待)。

**排除项(归因的负向证据,同样重要)**:两侧 eventloop p99 全程 11~15ms、Node GC 停顿 ≤5ms、Go GC 累计 4~66ms——**运行时从来不是毛刺来源**;"Go 网关不更快"不是 Go 的问题。

## 4. 正面成果(不因通信缺陷而否定)

1. 连接层能力全面优于 socket.io:建连 2.4×、惊群 1.7×、eventloop 纹丝不动、连接 I/O 与业务进程解耦(server RSS 恒 183MB);
2. 架构范式对齐业界(Discord/Slack/微信同构)——《架构分析.md》结论:范式层已"毕业",剩余差距是规模性基础设施;
3. 过载失败模式对比(排队 vs 拒绝)的观测价值:为下一轮"异步上行"方案提供了定量靶子。

## 5. 本轮结论

- **结论**:解耦方向正确、通信方式错误;下一轮方案 = **gRPC 双向流**(单连接复用+异步确认+in-flight 背压),unary RPC 只能解决一半(dial 耗尽),串行排队必须靠流式+异步 ack 才能消除。

## 6. 后续优化

- 后续优化:E1 dial 耗尽 —— 上行换 gRPC 双向流,替代 HTTP-per-message(`26-9-16-grpc` 轮闭环)。
- 后续优化:E2 每连接串行等待 —— 上行异步并发 + in-flight 背压,消除"发送间隔 < 上行耗时"导致的队列单调增长。
- 后续优化:E3 重试与在途竞态放大 —— 同 clientMsgId 在途去重(首帧确认前不上行)+ 幂等唯一约束兜底。
- 后续优化:错误帧丢 clientMsgId —— 补 clientMsgId 让客户端即时收敛 pending,不再等超时重发。
- 后续优化:DB 行锁回归风险 —— 上行并发恢复后 DB 行锁竞争会回到基线水平,需在复测中单列观测并治本(发号 INCR 化)。
- 后续优化:`/user/messages` 全量返回 —— 2.4 万条返回 3.9s,需客户端分页接入后退役全量路径。

## 7. 补:三条根因的**原理**展开(为什么必然失败)

### 7.1 E1 短连接风暴 → 端口耗尽

- **机制**:HTTP-per-message 意味着每条消息一次 `dial`。TCP 四次挥手后主动关闭方进入 `TIME_WAIT`,默认 **60s** 后才释放四元组。
- **算术**:1000 msg/s × 60s = **6 万**个待回收端口,而 loopback 可用临时端口只有 ~2.8 万(`ip_local_port_range`),于是报 `can't assign requested address`。
- **放大器**:Go `http.Client` 默认 `MaxIdleConnsPerHost = 2`,连接池形同虚设 → 绝大多数请求都走新建连接,把"偶然失败"变成"稳定失败"。
- **手段与原理**:正确解法不是调大端口范围/调大连接池,而是**消除"每消息一次连接"这个前提**——用长连接多路复用(HTTP/2 或 gRPC 流),`dial` 次数从 O(消息数) 降到 O(连接数)。

### 7.2 E2 每连接串行等待 → 队列单调增长(排队的数学)

- **机制**:读循环"收一帧 → 同步转发 → 等回包 → 再收下一帧",单连接吞吐上限 = `1 / 上行耗时`。
- **判据**:只要**到达间隔 < 服务时间**,系统就进入不稳定区,队列长度随时间线性增长(与"服务器忙不忙"无关,是 Little 定律的必然结果)。
- **证据**:发送间隔 40ms,上行 p95 = 82ms → 40 < 82,队列必然爆;p99 因此冲到 2802ms,而网关服务内上行只有 98ms。
- **手段与原理**:① **异步上行**(发出即返回,不等回包)+ ② **in-flight 上限**做背压。异步把"串行等待"变成"流水线";上限让过载时**快速失败而非无限排队**,两者缺一不可——只有异步没有上限,会把内存和数据库一起打爆。

### 7.3 E3 重试放大 → 在途重复

- **机制**:客户端 5s 未收到 ack 就重发;而网关的深队列让"处理完成"晚于 5s → 同一 `clientMsgId` 的多份副本同时在途,撞 DB 唯一约束返回 500。
- **手段与原理**:用 `clientMsgId` 做**在途去重**(首帧确认前不上行第二帧)+ 幂等唯一约束兜底。去重解决"放大",唯一约束解决"重复",前者省资源、后者保正确性。

### 7.4 为什么"解耦"本身是正的(被数据支持)

| 指标 | 纯 Node | Go 网关 | 原理 |
|---|---|---|---|
| 建连 p50 | 318~434ms | **134~163ms** | 连接 I/O 不再与业务处理抢同一个事件循环 |
| 惊群重连 | 43/67ms | **26/39ms** | 同上;Go 的 goroutine 调度对"同时唤醒"更平滑 |
| 业务进程 RSS | 331.8MB | **恒 183MB** | 连接态从业务进程剥离,业务进程不再随连接数增长 |
| eventloop p99 | 11~15ms | 11~15ms(业务侧) | 证明"毛刺不来自运行时",排除语言背锅 |

> 结论:连接层解耦的收益是**真实的、有原理的、可复现的**;本轮失败纯属**通信模型选错**,不是架构方向错。
