# 优化项与归因(业务层 Go 重写轮)

> 系列定位:五轮优化测试的**第 5 轮**,执行 V3 目标态的业务层 Go 全域重写 + 发号 INCR 化。
> 数据与测序见同目录《业务层Go重写优化压测报告.md》(v3,含 §2 优化项清单与"数据↔代码版本"对应表)。
> 本文只回答三件事:**问题是什么(根因)→ 怎么改(手段)→ 为什么有效(原理)**,并给出可核对的收益与边界。

---

## 0. 一句话结论

把 `seq` 发号从 **PG 行锁** 换成 **Redis INCR** 后,tp_r25 由 40.4% 错误/p99 2075ms 变为 0% 错误/p99 156ms,
tp_r30 错误率 79.9%→0%——反向验证了"行锁是错误率唯一来源"的归因;随后用**四级进程内缓存**把排队性延迟
(零错误但 p99 2961ms)压回 156ms。

---

## 1. 问题分析:为什么 2500 msg/s 就开始 2 秒

### 1.1 现象与证据链

| 观察 | 数据 | 说明 |
|---|---|---|
| 错误率随速率断崖 | 2000 msg/s 0% → 2500 msg/s **40.4%** → 3000 msg/s **79.9%** | 不是线性劣化,是"排队-超时"型失败 |
| 延迟平台 | p99 稳定在 ~2075ms | 平台型,典型的"等待某个资源" |
| 服务内直方图 | **DB 单条查询 <10ms**,但**事务级等待达 2s 级** | 查询本身不慢 → 慢在拿不到执行机会 |
| 两侧对比 | gRPC 版 2075ms vs 纯 Node 基线 2058ms,**差 17ms** | 传输层已不是瓶颈,余量全在 DB |

### 1.2 根因(机制层)

发号的实现是"读-改-写"一个会话计数器:

```sql
UPDATE conversations SET next_seq = next_seq + 1 WHERE id = $1 RETURNING next_seq
```

- PG 对 `id = $1` 这一行加**排他行锁**,同会话的并发消息被迫串行;
- 持锁时间 = 语句 + 事务提交(含 WAL fsync 路径),虽然单条 <10ms,但**并发一高,队列立刻指数堆积**;
- 连接池被"持锁等待"的连接占满 → 后续请求拿不到连接 → 超时/快速失败(错误率 79.9%);
- 更关键的架构后果:**同一会话只能由一个副本推进 seq**,业务层无法多副本水平扩展。

> 一句话:瓶颈不是"SQL 慢",而是**"同一会话的写入被行锁串行化 + 连接被持锁占用"**。

## 2. 优化项逐条:手段与原理

### O0-a 发号 INCR 化(本轮核心)

| 维度 | 内容 |
|---|---|
| **手段** | Redis `INCR conv:seq:{id}`;首次装载用 **Lua 原子**完成 `GET → 不存在则读 PG → SET`,装载值取 `GREATEST(conversations.next_seq, max(messages.seq))`;每 60s **checkpoint** 批量回写 PG;Redis 失联时**降级回 DB 行锁**(保可用性);快路径做**防回卷校验**(见 O2) |
| **原理** | ① 竞争点从"磁盘行锁 + 事务"换成"**内存单线程原子自增**",O(1)、无 IO;② 一次 `INCR` 的 RTT 取代"加锁→写→提交"的多次 IO;③ 把"会话序号"这一**共享可变状态外置到 Redis**,业务副本变为无状态,同一会话的相邻消息可由不同副本处理 |
| **收益** | tp_r25:40.4% 错误 / 2075ms → **0% / 156ms**;tp_r30:79.9% 错误 → **0%** |
| **边界** | Redis 成为新的依赖点(有降级路径);键丢失会破坏单调性(由 O2 兜住);跨会话的相对顺序仍由 `seq` + 时间戳决定 |

### O0-b 幂等判定前置

| 维度 | 内容 |
|---|---|
| **问题** | 客户端 5s 未收到 ack 会原样重发(同 `clientMsgId`),若直接入库会产生重复消息 |
| **手段** | 热路径先在 Redis 用 `SET NX`(TTL 300s)占位,命中即直接回 ack;**DB 唯一约束 `uniq_msg_idem` 兜底**(缓存穿透/重启时仍不重复) |
| **原理** | 幂等键是"一次性事实",用 `SET NX` 的原子性把"判断+占位"合成一步,避免 check-then-act 竞态;唯一约束是**最终一致性防线**,保证缓存失效时语义不退让 |
| **收益** | 3000 msg/s 下零重复;重发不产生额外写放大 |

### O0-c 通话忙线裁决原子化

| 维度 | 内容 |
|---|---|
| **问题** | Node 实现是 `getSession → 判断空闲 → setSession` 的 **read-modify-write**,多副本下两个来电同时通过判断 → 双方都接通(双接竞态) |
| **手段** | 改用 **Lua 脚本单次原子执行**"判忙 + 占位 + 写状态机",返回是否抢到 |
| **原理** | 把"判断与写入"合并为一个 Redis 原子操作,消除窗口;分布式锁本质是**用单线程执行体串行化临界区** |
| **收益** | 双接竞态消除(0 复现);状态机 ringing→connected 与 12s grace 重连窗不受影响 |

### O1 四级进程内缓存(第二轮瓶颈的关键)

| 维度 | 内容 |
|---|---|
| **问题** | 行锁消除后出现**新瓶颈**:tp_r25 零错误但 p99 **2961ms**(纯排队);根因是每消息仍有 **2 次 `ON CONFLICT` 写入 + 2 次 Redis RTT**,PG 每消息写 3 次,写放大在 WAL/索引上形成新竞争 |
| **手段** | 四个进程内缓存:`convExists`(会话已建 → 跳过 `conversations` upsert)、`ucExists`(关系行已建 → 跳过 `user_conversations` upsert)、`idemLocal`(幂等键本地命中 → 免 Redis RTT)、`seqInitialized`(会话已装载 → 直接 INCR 免一次 GET) |
| **原理** | 这三类写是**状态无关的幂等 upsert**("确保存在"),只需每会话一次;用**否定缓存**(已知存在即跳过)把它们从"每消息"降为"每会话一次"。正确性不依赖缓存:缓存只做"跳过优化",DB 唯一约束仍是事实来源 |
| **收益** | PG 每消息写 **3 次 → 1 次**;tp_r25 p99 2961→**156ms**;tp_r30 错误 22.6%→**0%**、p99 7421→**425ms**;S3 场景 8.9%→**0%** |
| **边界** | 缓存是进程内的,多副本下各自重建(首次消息付一次装载成本);需设容量/TTL,避免无界增长 |

### O2 发号防回卷(正确性修复)

| 维度 | 内容 |
|---|---|
| **问题** | Redis 未开持久化,重启/清库后 `INCR` 从 0 开始 → `seq` 回卷 → 新消息与历史消息 **seq 撞车**,乱序/覆盖风险 |
| **手段** | ① 快路径校验:`INCR` 结果 ≤ 本进程已知的最后值 → 判为"键被重建",**删脏键**并走慢路径重新装载;② 装载值改为 `GREATEST(next_seq, max(messages.seq))`(走 `conv_seq` 索引,避免全表扫) |
| **原理** | `seq` 的**单调递增是跨缓存生命周期的不变量**;缓存可以丢,但"已提交的最大值"必须能从 DB 恢复。装载 + 校验共同保证 `新值 > 任何已入库值` |
| **收益** | 无性能变化;`TestNextSeqKeyRebuild` 单测覆盖键重建路径 |

> 说明:本轮之后 26-11-15 V3 基线复测发现并发下 `seq` 仍有重复,与本条"键丢失"场景不同(属**并发装载竞态**),单独跟踪,不在此处归因。

### O3 群扇出改 Pipeline(性能修复)

| 维度 | 内容 |
|---|---|
| **问题** | 100 人群扇出 span p99 **111ms**,而 Node 版是 2ms |
| **根因** | Go 实现**逐成员同步 `PUBLISH`**(N 个网络往返串行);Node 的 `publishDownlink` 是 fire-and-forget 异步,天然并行 |
| **手段** | `FanoutDownlink` 改为**单次 Redis Pipeline 批量 PUBLISH**(单聊/群聊/@mention 三处统一) |
| **原理** | 把 `O(N × RTT)` 压成 `O(RTT)`:Pipeline 只发一次系统调用批次、只等一次往返,扇出成本与人数解耦 |
| **收益** | span p99 **111ms → 1~2ms**;e2e p99 19ms;单聊冒烟 980 条零回归 |

## 3. 归因总表(哪项优化贡献了哪段延迟)

| 阶段 | 版本 | tp_r25 p99 | tp_r30 错误/ p99 | 该阶段的主要贡献 |
|---|---|---|---|---|
| 三期基线(行锁) | Node gRPC 流 | 2075ms(40.4% 错误) | 79.9% / 2086ms | — |
| Go 初版(O0) | v1 | 2961ms(0% 错误) | 22.6% / 7421ms | 行锁消除 → 失败变排队 |
| +四级缓存(O1) | v2 | **156ms** | **0% / 425ms** | 写放大 3→1 次 |
| +扇出/防回卷(O2、O3) | v3 | 156ms | 0% / 425ms | 扇出与正确性,不影响主场景 |

## 4. 边界与遗留

- **Redis 是新单点**:降级路径保证可用,但降级期间会退回行锁性能(有损可用)。
- **tp_r30 仍在 PG 单实例能力边界**:425ms 是"零错误但排队";后续靠分区表/双副本才降到 61ms(见 `26-9-18-第一批优化验收`)。
- **进程内缓存多副本各自为政**:只做否定判断,不作为事实来源。
