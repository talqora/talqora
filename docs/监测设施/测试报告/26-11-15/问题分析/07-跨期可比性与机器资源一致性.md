# 问题 07：机器是工作机——资源一致性对跨期对比的影响（P1 方法论）

> 严重度：**P1 结论正确性**
> 状态：已量化（可给出归因区间，但无法唯一归因）
> 关联：报告 §十一、`环境说明.md`、26-9-20 基线报告

## 一、先直接回答问题

**会。而且不只是"资源不一致"，更麻烦的是"不可知"——9-20 那轮没有记录背景负载，所以严格来说，那轮的绝对数字本来就不该被当作基线。**

但也不能把所有差异都推给机器。本轮实测给出的结论是：

| 因素 | 可解释的退化幅度 | 证据强度 |
|---|---|---|
| ① 环境基线漂移（同机多任务、后台容器） | **p99 ×1.5–2.1**（低负载档） | 强（低负载档整齐地对齐在 1.5–2.1 倍） |
| ② 单消息 CPU 成本上升 | **+21%～+38%** | 强（同口径 CPUΔ÷消息数） |
| ③ 系统在临界点附近的正反馈放大 | 把 ①+② 放大成 **×5–23** | 强（倍率随负载单调上升） |

**三者叠加，可以完整解释从"零错误"到"17,974 帧超时"的变化，不需要假设"有未知的代码回归"。但反过来也不能说"纯粹是机器问题"——因为 ② 本身有一部分是 `seq` 误判带来的额外查询（见问题 01）。**

## 二、证据 A：退化倍率随负载单调上升

| 场景 | 负载 | 9-20 p99 | 本轮 p99 | 倍率 |
|---|---|---|---|---|
| S5 | 500 msg/s | 49 | 72 | **1.5×** |
| S2 | 600 msg/s | 104 | 161 | **1.5×** |
| S1 | 1000 msg/s | 40 | 68 | **1.7×** |
| tp_r10 | 1000 msg/s | 58 | 101 | **1.7×** |
| S4 | 500 msg/s | 154 | 267 | **1.7×** |
| S0 | 100 msg/s | 27 | 56 | **2.1×** |
| tp_r15 | 1500 msg/s | 46 | 90 | **2.0×** |
| tp_r20 | 2000 msg/s | 53 | 252 | **4.8×** |
| tp_r25 | 2500 msg/s | 65 | 429 | **6.6×** |
| **S3** | **3000 msg/s** | **62** | **1,282** | **20.7×** |
| **tp_r30** | **3000 msg/s** | **204** | **4,763** | **23.3×** |

**这张表是整篇文档的核心。** 它说明：

- 如果只是"机器被占了 20%"，倍率应当**在所有负载档大致相同**；
- 实际是 **1.5× → 4.8× → 6.6× → 20×+**，与负载**强相关**；
- 这个形状只有一个解释：**系统本来就在 85%+ 的利用率上跑，一点点余量变化就会被排队放大**。

用排队论的语言：延迟 ≈ 1/(C − L)。`C` 掉 20%，在 `L = 0.5C` 时延迟只涨 30%，但在 `L = 0.9C` 时延迟会涨几倍。**低负载档测出的是"机器慢了多少"，高负载档测出的是"离悬崖有多近"。**

## 三、证据 B：单消息 CPU 成本（归一化后）

跨期比 p99 不可靠，但比"处理一条消息花多少 CPU"相对可靠——它不受排队影响。

| 轮次 | 场景 | 消息数 | biz CPUΔ | **每消息 CPU** |
|---|---|---|---|---|
| 9-20 | S3（3000 msg/s） | 44,709 | 41.2 s | **0.92 ms** |
| 本轮 | S3 r1 | 44,757 | 49.7 s | **1.11 ms**（+21%） |
| 本轮 | S3 r2 | 44,719 | 51.1 s | **1.14 ms**（+24%） |
| 本轮 | S3 r3 | 44,671 | 56.7 s | **1.27 ms**（+38%） |

**+21%～+38% 的单消息成本上升**，折算成容量就是"同样的 CPU 只能处理 72%–83% 的消息量"。

这 21–38% 来自哪里？两个已知来源：

1. **`seq` 误判的额外查询**：每次误判多一次 `SELECT GREATEST(next_seq, max(seq))`，本轮触发 17 万次；
2. **数据量增长**：messages 从 359 万涨到 747 万，`max(seq)` 与相关查询的成本同步上升。

**这两条都不是"机器被占用"能解释的——它们是系统自身的行为。** 所以"退化"这个结论本身是成立的，只是不能把幅度全部记在机器头上。

## 四、证据 C：环境确实变了，而且可以列清单

### 4.1 9-20 之后新增的后台容器

| 容器 | 启动时间 | 说明 |
|---|---|---|

| `elvaface-stack-ops-prometheus-1` | 2026-11-05 | 另一套 Prometheus |
| `elvaface-stack-ops-grafana-1` | 2026-11-05 | 另一套 Grafana |
| `elvaface-stack-gateway-1-1` | 2026-11-06 | |
| `elvaface-stack-python-1-1` / `-2-1` | 2026-11-10 | **空闲时占 25.6% 单核** |
| `elvaface-stack-ops-loki-1` / `tempo` / `alloy` / `otel-*` | 2026-11-05～10 | 一整套可观测栈 |
| `campus-backend` / `campus-frontend` / `campus-mysql` | — | 另一个项目 |

**9-20 那轮，这些都不存在。** 它们共享同一个 colima VM（12 vCPU / 32 GiB）。

### 4.2 但它们现在占得并不多

| 指标 | 实测值 |
|---|---|
| 其他项目容器 CPU 合计（空闲） | **6.2%（单核占比）** |
| 宿主机 CPU 空闲 | **71.86%** |
| colima VM load average | 0.61 / 1.39 / 2.85（1/5/15 分钟） |
| 宿主机 load average | 4.06 / 5.50 / **9.51**（1/5/15 分钟） |

**结论：后台容器本身不足以解释 2 倍退化。** 但注意宿主机 15 分钟 load 9.51——**这不是容器，是宿主机上的其他进程**（IDE、浏览器、我的诊断命令）。

> **⚠️ 本节结论已按 `09-机器真实资源实测与采集方法.md` 修正。**
> 上面的 6.2% 是"某一瞬间、只算容器"的数字，漏掉了宿主机应用与内存。补测后的完整画像是：
> **空载忙 3.6 核（约 20%）、Swap 已用 45 GB、空闲页仅 80–231 MB、负载期间持续换页（峰值 4,180 页/分钟）、磁盘 I/O 涨 15 倍**。
> 所以"机器侧因素"的真实性质不是"别的程序抢 CPU"，而是**整机内存不足、系统在持续换页**——这更能解释基线延迟整体抬升。详见该篇 §五。

### 4.3 一个必须承认的干扰源：我自己

本轮压测期间，我同时在同机执行诊断命令：

| 时段 | 操作 | 干扰程度 |
|---|---|---|
| 03:57 | 启动 Prometheus/Grafana | 持续抓取负载，轻微 |
| 04:03–04:22（主跑批） | 读 JSON、`git status`、`docker ps`、少量 `grep` | 轻 |
| 04:36–04:41（S8） | **`psql` 聚合查询 747 万行表**、`grep` 27 MB 日志 | **中，且与 S8 后半段重叠** |
| 04:41 之后 | 重复跑聚合 SQL、统计重复 seq | 重（但已跑完） |

**"压测机同时是分析机"是这台机器的结构性缺陷**，不是操作失误。它意味着即使关掉所有后台容器，只要我一边压一边查，数据就会有偏差。

## 五、证据 D：9-20 那轮根本没有底噪标定

| 项 | 26-9-20 | 26-11-15 |
|---|---|---|
| A/A 同参复跑 | **未做** | 做了 |
| p99 底噪 | **未知** | **32.0%** |
| p50/p95 底噪 | 未知 | 2.9% / 1.6% |

本轮 A/A 显示：**同参数、同环境、连跑两次，p99 相差 32%**。

这意味着：

- 9-20 报的 tp_r25 `p99=65ms`，其真值可能在 50–85 ms 之间；
- 本轮报的 `429ms`，真值可能在 320–560 ms 之间；
- 但 **6.6 倍的差距远大于 32% 的噪声**，所以"退化"这个定性判断仍然成立。

**教训**：没有 A/A 的轮次，其 p99 只能用于"形态判断"，不能用于"跨期比较"。9-20 的绝对数字被引用了两个月，这是方法上的欠账。

## 六、那么 9-20 的结论还算数吗

分层看：

| 9-20 的结论 | 是否仍成立 | 理由 |
|---|---|---|
| "拐点在 2500–3000 msg/s" | ⚠️ 位置可能偏乐观 | 本轮在更差的环境下测到 2500–2700，说明真实拐点**可能低于 2500**；9-20 的 3000 是"当时环境下的上限" |
| "过载时软排队、零错误" | ❌ 本轮反例 | 同样 3000 msg/s，本轮出现 17,974 帧超时。说明"零错误"依赖环境余量，不是系统性质 |
| "连接面强健（1 万连接 100%）" | ✅ 成立 | 本轮独立复现：10,000/10,000，RSS 290 MB |
| "定向下行 99.9998%" | ✅ 成立 | 本轮 99.65%（含压测初期 presence 未就绪的 fallback） |
| "DB 是吞吐瓶颈" | ✅ 成立且更精确 | 本轮直接抓到 `pg_conn` 恒定 33、goroutine 与池同相位 |

**换句话说：形态类结论稳，阈值类结论不稳。** 这和"同机噪声"的性质一致。

## 七、判定框架：以后怎么区分"环境漂移"和"真回归"

这套判断可以复用，建议进 SOP：

```
第 1 步：看均匀性
   所有负载档都退化 ≈2×  → 大概率是环境基线漂移
   只有高压档退化         → 一定是系统内部的正反馈/临界点问题

第 2 步：归一化
   用"每消息 CPU"或"每千消息 DB 查询数"做除法
   去掉排队影响后仍有差异 → 真回归（代码/数据变了）

第 3 步：看定性变化
   从"零错误"变成"有错误"     → 不是噪声，是跨过了临界点
   只是 p99 变大、错误仍为零   → 可能只是环境

第 4 步：跑一次 A/A
   差异 < 底噪 → 不要写进结论
```

本轮走完这四步的结论是：

1. 第 1 步：**不均匀**（1.5× → 23×）→ 不是纯环境；
2. 第 2 步：**每消息 CPU +21~38%** → 有一部分是真变化；
3. 第 3 步：**零错误 → 有错误** → 跨过临界点；
4. 第 4 步：差异远超 32% 底噪 → 结论可用。

## 八、怎么让下一轮的"资源一致"

### 8.1 环境说明.md 增补字段（立刻可做）

现有表缺的全是"背景负载"这一块：

| 新字段 | 取值方式 | 为什么需要 |
|---|---|---|
| 后台容器清单 | `docker ps --format '{{.Names}}\t{{.Image}}'` | 9-20 到本轮新增了 14 个容器，只有列清单才看得出来 |
| 外部容器 CPU 合计 | `docker stats --no-stream` 求和 | 判断"占了几个核" |
| 宿主机 load average | `top -l 1 \| grep "Load Avg"` | 最直接的"机器忙不忙" |
| colima VM load | `colima ssh -- uptime` | 中间件所在的 VM 是否被挤 |
| **压测期间是否同机执行其他命令** | 人工填写 | 本轮最大的隐性干扰 |
| 跑前 5 分钟空载基线 | 不压测时测 60 s 的 S0 级 p99 | 用它做"本期基线延迟"，替代"上期 p99"做对比锚点 |

### 8.2 流程约束

| 约束 | 说明 |
|---|---|
| **跑前 A/A 必做** | 已经进 SOP V3，本轮已执行（32%） |
| **跑前空载基线** | 新增：不压测时测 60 s 的 p99，作为"机器当前有多慢"的标尺 |
| **压测期间禁止同机重命令** | 分析类命令（大表聚合、日志 grep）必须等跑完；或用另一台机 |
| **固定时段** | 尽量在机器空闲时段跑（如清晨），并在环境说明里记录时段 |
| **跨期只用"同轮内相对值"** | 绝对 p99 跨期比一律标注不可比，除非两期环境说明字段逐项一致 |

### 8.3 长期：把压测搬出工作机

根本解法是**压测机与被压机分离**，或用一台干净的构建机跑固定基线。当前单机闭环的三个硬约束（CPU 争抢、macOS 端口池 16383、colima 配额）在 `压测环境与机器资源.md` 里已经写明，本轮又添了一条：**分析活动本身也是负载**。

## 九、对本期结论的影响（哪些能用、哪些不能用）

| 结论 | 是否受机器影响 | 怎么用 |
|---|---|---|
| `seq` 重号 10.9% | **不受**（数据正确性，与性能无关） | 直接采信，P0 |
| 连接池是瓶颈 | **不受**（机制性证据：`pg_conn` 恒定 + goroutine 同相位） | 直接采信 |
| `/user/messages` 7 rps | 轻微（数据量 747 万是主因） | 采信"数量级"，不采信具体 rps |
| 容量 ≈2800 msg/s | **受影响**（可能偏低） | 表述为"在这个环境下"，不给生产承诺 |
| 2500–2700 拐点 | **受影响** | 同上，并注明 9-20 在更好环境下测到 3000 |
| "1 万连接 100% 成功" | 不受 | 直接采信 |
| "绝对 p99 比 9-20 差 20 倍" | **受影响** | 只说"退化"，不说倍数；倍数仅用于说明"随负载放大"这一形态 |

## 十、一句话总结

**机器确实不够干净，这让"差多少"变得不确定；但"为什么差"仍然清楚——系统在临界点上，任何 20% 的余量变化都会被放大成 5–20 倍。** 真正该修的是把余量拿回来（修 `seq`、扩池、给 `messages` 加分页），而不是换一台更快的机器。
