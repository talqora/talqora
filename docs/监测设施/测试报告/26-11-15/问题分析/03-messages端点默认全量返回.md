# 问题 03：`/user/messages` 缺省路径返回全量，单端点吃掉半个连接池（P1）

> 严重度：**P1 性能 + 可用性**
> 状态：**9-20 已记录（遗留 2），本轮复测确认恶化**
> 关联：报告 §七、`biz/internal/api/chat_routes.go:117-134`

## 一、一句话结论

该端点**已经实现了**游标分页，但**不传 `limit` 时退化为"全量升序返回"**。压测客户端不传 limit，于是单个请求要扫描并序列化 3.5 万行——实测 **7 rps、p50 1874 ms**。更严重的是：一个请求占用 DB 连接约 2 秒，**32 条连接池里只要有 16 个这样的请求在飞，写路径就没连接可用了**。

## 二、现象与历史对比

| 轮次 | messages 表规模 | rps | p50 | p95 | p99 |
|---|---|---|---|---|---|
| 26-9-20 | 359 万行 | 9.8 | 1,676 ms | 2,717 ms | 2,746 ms |
| **26-11-15** | **747 万行** | **7.0** | **1,874 ms** | **4,121 ms** | **4,124 ms** |

同轮的其它端点（同一批请求、同一进程）：

| 端点 | rps | p50 | p99 |
|---|---|---|---|
| `/health` | 10,857 | 2 ms | 4 ms |
| `/user/mentions` | 5,474 | 4 ms | 6 ms |
| `/user/userConversations` | 5,227 | 4 ms | 9 ms |
| `/user/sync` | 3,196 | 6 ms | 12 ms |
| `/user/lastMessages` | 385 | 52 ms | 99 ms |
| **`/user/messages`** | **7** | **1,874 ms** | **4,124 ms** |

差了 **3 个数量级**，不可能是并发能力问题——同一进程的 `/health` 能跑 1 万 rps。

## 二之二、A/B 实测：只多传一个参数

同一端点、同一并发（20 × 10 s）、间隔数分钟连跑，唯一差别是**有没有 `limit=50`**：

| 调用方式 | rps | p50 | p95 | p99 | 状态 |
|---|---|---|---|---|---|
| `/user/messages?conversationId=X` | **7.1** | 1,961 ms | 4,170 ms | 4,474 ms | 200×79 |
| `/user/messages?conversationId=X&limit=50` | **3,963.9** | 5 ms | 8 ms | **12 ms** | 200×39,675 |

| 指标 | 提升 |
|---|---|
| 吞吐 | **558×** |
| p50 | **392×** |
| p99 | **373×** |

**这就是"默认值"的代价**：代码里已经写好了分页，只是没走那条路。修复不需要新增逻辑，只需要把默认路径指向已有的分页分支。

> 注意：3,963 rps 已高于 `/user/userConversations` 的 5,227 rps 同档，说明 `limit=50` 路径本身**没有性能问题**，剩余优化空间在其它地方。

## 三、代码事实

`biz/internal/api/chat_routes.go:124-134`：

```go
limitStr := c.Query("limit")
if limitStr == "" {
    // 旧行为:全量升序(零改动兼容)
    messages, err := queryMessages(c, "WHERE conversation_id = $1 ORDER BY timestamp ASC", conversationID)
    ...
    return
}
```

- `limit` 传入时：走 `seq DESC` 游标分页，`1~200` 合法，多取 1 条判 `hasMore`（`:136-158`）——**实现是完整的**。
- `limit` 不传时：走 `ORDER BY timestamp ASC` **无任何上限**。

所以问题不是"没做分页"，而是**默认值不安全**：兼容旧行为的代价放在了最危险的位置——默认路径。

## 四、为什么它比"慢"更严重

| 影响 | 机制 |
|---|---|
| 吃连接池 | 单请求耗时 1.9 s，期间独占 1 条 DB 连接。32 条池 ÷ 1.9 s ≈ **理论 16 rps**；只要有 50 个并发就会占满全池 |
| 挤占写路径 | 消息写入（2800 msg/s 时已用 89% 池）与它共用同一个池——**读慢会直接把写打死** |
| 放大现有瓶颈 | 与问题 02 叠加：池在临界点附近时，几个全量读请求就能把 p99 从 300 ms 推到秒级 |
| 内存放大 | 3.5 万行 × 每行数百字节 → 单请求几百 KB~MB 级响应体，序列化与网络写出都在占用 goroutine |
| 随数据增长恶化 | 表从 359 万涨到 747 万，rps 从 9.8 掉到 7.0——**不修就会一直变慢** |

## 五、为什么 9-20 记录过却没修

9-20 报告把它列为"遗留 2"，判断是"兼容旧行为的已知代价"。这个判断在当时成立，但**本轮有了新证据**：它现在会实质影响写路径的连接池（问题 02 是本轮才量化出来的）。两个问题叠加后，它的优先级应该从"遗留"提升到"必修"。

## 六、改进方案

### 方案 A：改默认值（推荐，改动最小）

```go
limit := 50                      // 默认一页
if s := c.Query("limit"); s != "" { limit = parse(s) }
if limit > 200 { limit = 200 }   // 硬上限，非法值不报错而是收敛
```

- **收益**：默认路径从 3.5 万行降到 50 行，rps 应直接回到千级；写路径不再被读拖垮。
- **代价**：客户端若真的依赖全量（例如桌面端首次加载要渲染全部历史），行为会变。
- **风险控制**：先确认前端调用点是否传 `limit`（Web 端 `chatApi` 需核对）；如需全量，提供显式 `?all=1` 且**仍加硬上限**（如 2000），并强制客户端改用分页。

### 方案 B：硬上限兜底（必做，可与 A 并行）

即使保留全量语义，也必须加一个不可突破的上限（如 5000 行）并在超限时返回 `hasMore`，避免单个请求无限增长。

### 方案 C：读写池分离（中长期）

见问题 02 方向 4。读路径走独立池，慢读不会饿死写入。

**取舍**：A 是根治且便宜；B 是安全网；C 解决的是"同类问题以后再出现"。建议 A+B 本轮就做。

## 七、验证方法

1. 重跑 `http-bench`（同一参数 20×10s），**改默认值后应直接复现 `limit=50` 分支的实测值**：
   - `rps ≈ 3,900`（本轮已实测该分支为 3,963.9）；
   - `p99 ≈ 12 ms`；
   - 若明显低于此，说明默认路径没真正切到分页分支（例如只改了文档没改代码）。
   - 基线锚点：修复前 7.1 rps / p99 4,474 ms，二者相差 558×，不存在"噪声内看不出差别"的可能。
2. **联动验证**（更重要）：在 messages 端点被压的同时跑 S1（1000 msg/s），观察消息 p99 是否被读到拖高。修复前预期会被拖高，修复后应无影响。
3. 前端回归：确认会话首屏仍能正常渲染（分页后首屏只加载最近 50 条，向上滚动加载更多）。

## 八、附带发现：压测脚本本身也是"不传 limit 的客户端"

`perf/http-bench.mjs` 请求 `/user/messages` 时不带任何参数，所以它精确复现了"最坏客户端"的行为。这既让问题暴露出来，也意味着**修完后要确认压测脚本仍然打到同一路径**——否则修复后的数据不可比。

建议给 http-bench 增加两档：`messages(默认)` 与 `messages?limit=50`，把"默认路径"和"分页路径"的差距长期固化在报告里。
