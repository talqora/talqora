# 问题 01：`seq` 发号器在并发下自我破坏（P0）

> 严重度：**P0 数据正确性**
> 状态：已确证（SQL 实测 + 运行日志 + 代码机制三方一致）
> 关联：报告 §8.1、`biz/internal/service/seq.go`

## 一、一句话结论

会话内 `seq` 的"防回卷"守卫 `seq > last` 在并发下会**误判**,触发 `Del(key)` 破坏 Redis 计数器并从滞后的 DB 最大值重装载,导致序号回退与重号。本轮新增消息中 **10.9%** 的 seq 与他人重复,而表上**没有任何唯一约束**能拦住它。

## 二、现象

| 检查项 | 期望 | 实测 |
|---|---|---|
| `(conversation_id, seq)` 唯一 | 0 组 | **212,113 组重复** |
| 其中本轮（2026-11-15）新增 | 0 | **199,611 组** |
| 本轮新增消息总数 | — | 1,838,365 |
| **重复占比** | 0 | **10.9%** |
| `(conv, sender, client_msg_id)` 唯一 | 0 | 0 ✅（幂等本身没坏） |

分布是系统性的，不是个例：几乎每个 bench 会话都有约 4,500 组重复（`single_77_78` 4,571 组 / 35,072 条）。

历史上同形态重复也一直存在，只是此前没做过这项校验：

| 日期 | 重复组数 |
|---|---|
| 2026-09-14 | 4,662 |
| 2026-09-17 | 120 |
| 2026-09-18 | 4,388 |
| 2026-09-20 | 5,698 |
| **2026-11-15（本轮）** | **199,611** |

## 三、证据链

### 3.1 数据自相矛盾

```
Redis : GET conv:seq:single_47_48 = 134865   (TTL = -1，未过期)
PG    : conversations.next_seq     = 134865
PG    : max(messages.seq)          = 134865
但是  : 同一会话今日仍写入了 seq = 1,2,3,4,5 的消息（84 条）
       且 seq = 128889 这一个值被 13 条不同消息共用
```

一个值被 13 条消息共用，与并发度直接相关：`rate=28/30` 档位的重复密度显著高于低速率档。

### 3.2 运行日志确证

biz 日志 `seq 疑似键重建,回慢路径重新装载` 出现 **170,415 次**，且**全时段连续**（每分钟 1,300–7,300 次），不是启动突发：

```
03:58  685     04:05 4,780    04:17 5,523
03:59 3,825    04:06 7,360    ……持续到压测结束
```

该告警只可能来自 `seq.go:74`——即"键被重建"的判定在真实负载下被**误触发**了 17 万次。

### 3.3 代码机制

`biz/internal/service/seq.go:63-78`：

```go
if _, ok := seqInitialized.Load(convID); ok {
    seq, err := rdb.Incr(ctx, key).Result()      // 原子：每个 goroutine 拿到的值互不相同
    if err == nil {
        if last, ok2 := convLastSeq.Load(convID); !ok2 || seq > last.(int64) {
            convLastSeq.Store(convID, seq); return seq, nil
        }
        slog.Warn("seq 疑似键重建,回慢路径重新装载", ...)   // ← 误判点
        _ = rdb.Del(ctx, key)                              // ← 破坏性动作
        seqInitialized.Delete(convID)
    }
}
```

`convLastSeq` 是**进程级共享**的"最后发号值"，但 `seq > last` 这个判断在并发下不成立：

1. goroutine A 执行 `INCR` 得到 101，尚未比较；
2. goroutine B 执行 `INCR` 得到 102，并把 `last` 写成 102；
3. A 恢复执行，比较 `101 > 102` → **假** → 判定"键被重建"；
4. A 执行 `Del(key)`，把**健康的计数器删掉**；
5. 慢路径 `loadInit` 取 `GREATEST(next_seq, max(messages.seq))`——而 `max(seq)` **只包含已提交的行**，比刚发出但未提交的号更小；
6. 重新 `SET` 后从更小的值继续发号 → 与已入库的 seq 重叠。

这一条链同时解释三个观测：① 重复只在高并发档出现；② 同一 seq 被 10 余条消息共用（等于在途并发数）；③ 序号出现回退。

## 四、影响

`seq` 是增量同步的**唯一游标**：`/user/sync?since=<seq>` 按 `seq > since` 补拉。

| 后果 | 说明 |
|---|---|
| 漏消息 | 客户端已拉到 seq=100，服务端因回退把后续消息重新发成 90–99，`since=100` 的补拉永远取不到 |
| 重放消息 | 同一 seq 对应多条消息，客户端按 seq 去重时会丢掉其中一条 |
| 排序错乱 | 会话按 seq 排序展示时顺序与实际发送顺序不符 |
| 隐私面 | 无法从 seq 判断消息先后，审计/回溯失去依据 |

**"消息不重不乱"这个核心承诺，在真实并发下不成立。**

## 五、为什么能长期存在

`messages` 表只有主键，没有任何业务唯一约束：

```
messages_partitioned_pkey | PRIMARY KEY (id, conversation_id)
```

没有任何约束拦得住重复 `(conversation_id, seq)`，所以每次误判都静默写脏数据，直到有人主动跑聚合查询才会发现。

## 六、改进方案

### 方案 A：加唯一约束（必做，先上）

```sql
CREATE UNIQUE INDEX CONCURRENTLY uq_messages_conv_seq
  ON messages (conversation_id, seq);
```

- **收益**：把静默写脏变成显式失败，问题立刻暴露；是后续所有修复的安全网。
- **风险**：存量 21 万组重复会导致建索引失败，必须先清洗（见下）。
- **注意**：分区表上建唯一索引要求分区键包含在索引列中；当前分区键若不含 `conversation_id`，需改为在**每个分区**上建局部唯一索引，或用触发器兜底。

### 方案 B：修发号器（必做）

去掉并发下无效的判据，改为**单调不回退**语义：

| 子问题 | 改法 |
|---|---|
| `seq > last` 误判 | 不要用"与其他 goroutine 共享的 `last`"做判据。改用 Lua 在 Redis 内部完成"取当前值 → 与期望下限比较 → INCR"的原子操作，把判断放进 Redis，天然串行 |
| `Del(key)` 破坏性恢复 | 删除该动作。键不存在时由 Lua 的 `SET init` 自然处理，`init` 取 DB 最大值即可 |
| `max(seq)` 滞后于在途事务 | 装载值改为 `max(next_seq, max(seq)) + in-flight 余量`，或直接放弃"从 DB 重装载"这条路径，改为 Redis 持久化（AOF）+ 键丢失时**暂停该会话发号**并告警，人工介入 |

### 方案 C：存量清洗（修复后）

- 保留每组重复中 `id` 最小的那条的原始 seq；
- 其余按 `created_at, id` 顺序重新分配 seq（追加到 `max(seq)` 之后），保证单调；
- 清洗前先按会话导出快照，便于回滚。

**取舍**：A 是安全网、B 是根治、C 是收尾。顺序不能颠倒——先 A 会让当前代码直接报错（好事，暴露问题），但线上会开始丢消息；所以实际执行建议 **A 与 B 同批上线，C 在维护窗口做**。

## 七、验证方法（修复后怎么证明修好了）

1. 重跑 S8 速率阶梯到 `rate=30`，观察：
   - 日志中 `seq 疑似键重建` 次数应 **= 0**；
   - `pg_stat_activity` 不再出现异常的 `max(seq)` 查询尖峰。
2. 重跑正确性校验：
   ```sql
   SELECT count(*) FROM (
     SELECT conversation_id, seq FROM messages
     WHERE created_at > <本轮开始> GROUP BY 1,2 HAVING count(*)>1
   ) t;   -- 期望 0
   ```
3. 唯一索引建成即为终局证明：若有任何路径再产生重号，插入会直接失败。
4. 补一个并发单测：N 个 goroutine 并发对同一会话取 10 万次号，断言结果集合大小 = 10 万且严格递增（当前 `TestNextSeqKeyRebuild` 只覆盖了串行场景）。

## 八、附：为什么这不是"压测才有"的问题

压测只是把并发度放大到接近线上峰值。判断标准很简单：

- 线上单会话的并发发送峰值是多少？如果 ≥ 2 条消息在途，误判就可能发生；
- 触发概率随"在途消息数"和"DB 延迟"同时上升——DB 越慢，窗口越宽，误判越多。

本轮 DB 平均查询 3.1 ms，在途窗口只有几毫秒，就已触发 17 万次。**线上只要 DB 出现一次抖动，重号就会成批产生。**
