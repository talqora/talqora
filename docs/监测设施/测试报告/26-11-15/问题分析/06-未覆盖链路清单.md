# 问题 06：核心链路覆盖缺口（P2，但会决定下一轮的可信度）

> 严重度：**P2 方法完整性**
> 状态：本轮 18 条链路中 9 条未覆盖 / 不可测
> 关联：SOP V3 §5.1 覆盖矩阵

## 一、一句话结论

18 条核心链路里，**9 条没有压测场景**（1 条因单副本无法测、1 条因架构不可测）。这不是"漏做"，而是"没有对应的压测脚本"——所以每轮都会漏。本文档把每条缺口的**补齐方式**写清楚，作为下一轮的施工清单。

## 三、逐条缺口与补齐方案

### L9 多副本分流 / 单副本故障（本轮因单副本未做）

| 项 | 内容 |
|---|---|
| 缺什么 | D1 分流均衡、D2 副本宕机 failover、D3 恢复回归 |
| 本轮为什么没做 | 只起了 1 个 biz，Prometheus `biz2` target 一直是 down |
| 怎么补 | 按 SOP §阶段 0 注释起第二副本：`PORT=3009 EDGE_GRPC_ADDR=127.0.0.1:30081 REPLICA_ID=biz-2 go run ./cmd/biz`，压测中查 `rate(server_message_in_total[1m]) by (job)` 是否 ≈1:1 |
| 判据 | 两 job 比例 1:1 ±15%；kill 一个副本后最终确认率 100% |
| 成本 | 约 20 分钟 |

### L10 会话热点限流（429 路径）

| 项 | 内容 |
|---|---|
| 缺什么 | 单会话被刷爆时是否按预期拒绝，而不是拖垮全局 |
| 现状 | `CONV_RATE_LIMIT_MAX=500`，现有场景单会话最高约 40 msg/s，**永远碰不到限流线** |
| 怎么补 | 新写 `perf/hotspot-bench.mjs`：N 个连接**全部发往同一个会话**，速率从 100 升到 800 |
| 观测 | `server_conversation_rate_limited_total` 应随速率线性上升；其它会话的 p99 不受影响（隔离性） |
| 判据 | 限流触发后，同进程内**其他会话**的 p99 抬升 < 50% |
| 风险 | 这条链路同时是"公平性"测试——如果限流失效，一个热点会拖垮所有会话 |

### L11 Redis 不可用降级

| 项 | 内容 |
|---|---|
| 缺什么 | Redis 挂掉时发号能否降级到 DB 行锁（`seq.go:142 bumpSeqDB`），下行/presence 如何退化 |
| 怎么补 | 压测中 `docker stop our-chat-redis`，持续 60 s 后 `start` |
| 观测 | ack 成功率；`server_message_out_total{result="error"}`；恢复后 seq 是否连续 |
| 判据 | 降级期间**不丢消息**（最终确认率 100%）；恢复后 seq 无回退——**注意：这条判据在问题 01 修复前必然失败** |
| 风险 | 高。可能触发 seq `Del` 路径的连锁反应，建议问题 01 修完再做 |

### L12 慢消费者逐出

| 项 | 内容 |
|---|---|
| 缺什么 | 客户端不读（TCP 窗口打满）时，网关是否正确逐出而不是无限缓冲 |
| 现状 | `GATEWAY_SEND_BUFFER=256`，`gateway_evicted_total` 计数存在但**从未被触发过** |
| 怎么补 | 改造 harness：建连后**只发不收**，持续 60 s |
| 观测 | `gateway_evicted_total` 应 > 0；同网关其它连接 p99 不应被拖高 |
| 判据 | 逐出发生且**只发生在慢消费者上**（误杀正常连接即失败） |

### L14 OAuth / OIDC 发现 / JWKS —— ✅ 已补测关闭

| 项 | 结果 |
|---|---|
| 性能 | discovery **10,968 rps / p99 3 ms**；jwks **11,000 rps / p99 4 ms**（100% 200） |
| 正确性 | 发现文档字段自洽；JWKS 的 `n` 与私钥模数**逐字节一致**（2048 bit / kid=dev / RS256 / use=sig） |
| 怎么补的 | 已把两个端点**固化进** `perf/http-bench.mjs`（新增 `ONLY` 过滤与 `OUT_NAME` 改名），下轮自动覆盖 |
| 遗留风险 | 轮转窗口（下游缓存 600 s）、`/oauth/token` 无限流、agent-server 的 `iss` 校验可被静默跳过 |
| 详见 | [`08-L14-OAuth与JWKS补测.md`](./08-L14-OAuth与JWKS补测.md) |

### L15 上传（→ S3）

| 项 | 内容 |
|---|---|
| 缺什么 | 上传并发、大小限制、S3 慢时的表现 |
| 已知风险 | 审计发现 `upload_routes.go` 先 `io.ReadAll` 再校验大小——**大文件先吃内存再拒绝** |
| 怎么补 | 分别测 1 MB / 50 MB / 200 MB 三档，x 并发 10 |
| 观测 | 进程 RSS 增量（应≈文件大小×并发）；S3 写入延迟 |
| 判据 | 超过限制的请求应在**读取前**就被拒绝（当前实现做不到，预期会暴露） |

### L17 通话信令

| 项 | 内容 |
|---|---|
| 缺什么 | `call:start/accept/reject/rejoin` 的转发速率、忙线裁决的原子性、`active_calls` 是否回落 |
| 怎么补 | 新写 `perf/call-bench.mjs`（SOP §5.2 已定义参数）：`CALLERS=50`、`DURATION=30`、`RAMP=10`，成对"发起→接听→挂断" |
| 观测 | `server_call_events_total{event}` 速率、`server_active_calls` 水位 |
| 判据 | 挂断后 `active_calls` **归零**（不归零=通话态泄漏）；忙线场景下 `call:busy` 返回率 100% |
| 注意 | 只测信令。媒体面见 SOP §5.2，不可测 |

### L18 媒体面 / TURN（不可测）

已由 SOP §5.2 定性：P2P 时服务器零媒体流量；TURN 中继受 `min-port=49160 / max-port=50159`（1000 个 relay 端口）与带宽双重限制，**只能估算不能实测**。报告中禁止把信令 QPS 换算成"支持 N 路通话"。

## 五、覆盖矩阵应长期维护

建议把 §5.1 的矩阵做成一个**随报告一起更新的表**，每轮只改状态列。这样"哪些链路从来没测过"一目了然，而不是每轮重新回忆。

判断标准很简单：**一条链路如果没有对应的 `.mjs` 脚本，它就不算被覆盖**——写在文档里不算。
