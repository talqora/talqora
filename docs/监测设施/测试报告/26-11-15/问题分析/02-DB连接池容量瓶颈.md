# 问题 02：DB 连接池（32）是吞吐天花板（P1）

> 严重度：**P1 性能容量**
> 状态：已确证（压测中同步采样 `pg_stat_activity` + goroutine 曲线）
> 关联：报告 §五、`biz/internal/store/store.go:67`

## 一、一句话结论

系统在 **~2800 msg/s** 处进入排队，而 CPU 只用 1.9/18 核、压测端只用 1%。压测中 `pg_conn` 恒定 **33（池 32 已满）**、goroutine 在 91–1,445 之间随负载振荡，负载一停立刻回落——**瓶颈是连接池，不是 CPU、不是网关、不是压测机**。

## 二、现象

S8 速率阶梯（100 连接固定，每级 60 s 稳态）：

| msg/s | p50 | p95 | p99 | 服务端 CPU | goroutine | 压测端 CPU |
|---|---|---|---|---|---|---|
| 25 | 25 | 189 | 345 | 1.37 核（7.6%） | 583 | 0.9% |
| 27 | 64 | 656 | 980 | 1.73 核（9.6%） | 2,318 | 1.0% |
| 28 | 145 | 2,431 | 2,796 | 1.89 核（10.5%） | 5,809 | 1.1% |
| 30 | 2,203 | 5,604 | 6,206 | — | — | — |

**吞吐上不去、CPU 用不满、goroutine 暴涨**——这是"排队等固定容量资源"的教科书形态。

## 三、证据链

### 3.1 压测中同步采样

在 28 msg/s × 100 连接（≈2800 msg/s）稳态下，每 3 秒采样一次 PG 连接数与 biz goroutine：

| 时刻 | PG 连接数 | biz goroutine |
|---|---|---|
| 3 s | 33 | 91 |
| 9 s | 33 | 808 |
| 12 s | 33 | 1,362 |
| 21 s | 33 | 1,374 |
| 24 s | 33 | 745 |
| 27 s（负载结束） | 33 | **20** |

- `pg_conn` 从第 3 秒起**恒定 33**，整段负载期间没有再涨过一条；
- goroutine 峰值 1,445，**负载一停 3 秒内回落到 20**——排队中的请求全在等连接，不是在算。

### 3.2 容量算式

| 量 | 实测值 | 来源 |
|---|---|---|
| 连接池上限 | **32** | `biz/internal/store/store.go:67` `cfg.MaxConns = 32` |
| 单条查询平均耗时 | **3.1 ms** | `db_query_duration_seconds_sum / _count` |
| 每消息查询数 | ≈ **2.5 次** | `messages` 2,734/s + `raw` 4,267/s @ 2800 msg/s |
| 理论上限 | 32 ÷ 3.1 ms ≈ **10,300 qps** | 推算 |
| 实测峰值 | **9,192 qps（89%）** | Prometheus |
| 每连接承载 | 2800 ÷ 32 ≈ **87 msg/s** | 推算 |
| PG `max_connections` | 100 | `SHOW max_connections` |

**池已跑到理论容量的 89%**。在 M/M/c 模型里，89% 利用率对应的平均排队长度约为服务台数的数倍——这就是 p99 从 345 ms 跳到 2,796 ms 的原因，不是任何单一查询变慢了。

### 3.3 为什么不是别的东西

| 候选嫌疑 | 排除证据 |
|---|---|
| 压测机不够 | 压测端整棵进程树 CPU ≤ 1.1%（`time -p` 实测） |
| 服务端 CPU 不够 | 1.37→1.89 核（18 核的 7.6%→10.5%），远未饱和 |
| 网关转发慢 | `gatewayCpuCores` 全程 0.44–0.48 核，纯转发 |
| DB 单查询变慢 | 平均 3.1 ms 稳定，仅个别窗口尖峰到 40 ms |
| 上行流串行化 | `edge.go:136` 是每帧一个 goroutine，非串行 |
| 慢 SQL / 缺索引 | 写路径只有 INSERT，`max(seq)` 走 `(conversation_id, seq)` 索引 |

## 四、影响

| 维度 | 影响 |
|---|---|
| 容量 | 单副本约 2800 msg/s 见顶；p99 在 2500 msg/s 起已从 345 ms 起跳 |
| 弹性 | 加副本可线性扩容（连接池是每进程 32），但单副本上限无法靠调参突破到 5000+ |
| 尾延迟 | 89% 利用率下，一次 GC 或网络抖动就会把 p99 推到秒级 |
| 放大效应 | 见问题 01：`seq` 误判每次多一次 `max(seq)` 查询，直接把池推过临界点 |

## 五、改进方案

### 方向 1：减少每消息查询次数（收益最大，优先）

当前 ≈2.5 次/消息。逐条核对可合并的点：

| 可能的查询 | 能否省 |
|---|---|
| 发号（Redis，不占池） | 已经是 Redis，不动 |
| 落库 INSERT | 必须保留 |
| 会话/成员校验 | 可进进程内缓存（已有部分缓存，需确认命中率） |
| `raw` 类查询 | 需按 SQL 文本采样定位，是降查询数的主战场 |

**目标：2.5 → 1.2 次**，等于池容量翻倍，不占用 `max_connections`。

### 方向 2：扩池（有明确上限）

- 池 32 → 48：PG `max_connections=100`，扣除运维连接与 Prometheus 探测，单副本最多约 64；
- 双副本时每个 48 就会顶到 96，**必须同时调整 PG**；
- 建议按"副本数 × 池"预留：`max_connections ≥ 副本数 × 池 + 20`。

### 方向 3：加池等待指标（前置条件）

当前**无法直接观测池等待时间**（见问题 05）。没有这个指标，方向 1 的收益无法归因，扩池也无法验证。建议先加：

```
db_pool_acquired_total / db_pool_idle / db_pool_wait_seconds
```

### 方向 4：读写分离（中长期）

读路径（`/user/messages`、`/user/sync`）与写路径争抢同一个池。把读走独立连接池/只读副本，可让写路径独占 32 条。

## 六、验证方法

1. 修复后重跑 S8 `MODE=rate LEVELS=25,27,28,30`，盯三个数：
   - `pg_conn` 在 28 msg/s 时是否**不再恒定满载**；
   - goroutine 峰值是否从 5,809 显著下降；
   - p99 曲线是否整体右移（Knee 从 25–27 抬高）。
2. 判定标准：**Knee 后移 ≥ 20% 才算有效**（A/A 底噪 p99 为 32%，低于 20% 的右移不可信）。
3. 若只扩池不做方向 1，预期 p99 改善有限——因为 89% → 70% 的利用率下降会被 `seq` 误判带来的额外查询吃掉。

## 七、附：一个容易误判的细节

`pg_conn = 33` 而不是 32，多出的 1 条是 `psql` 采样连接本身。判断"池是否打满"时不要被这个 1 干扰——关键特征是**数值恒定不变**（不再随负载增长），而不是它等于多少。
