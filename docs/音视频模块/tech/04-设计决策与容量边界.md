# 音视频模块 · 设计决策、安全边界与容量上界

> 前两篇讲"怎么做的",本篇讲"**为什么这么做**、**代价是什么**、**走到哪里就走不动了**"。面试里被追问"为什么不用 SFU""为什么要 12 秒"时,答案在这里。

## 0. TL;DR

- **不做媒体服务器**是当前阶段最关键的决策:1v1 场景下 P2P 质量最好、成本为 0,引入 SFU 等于凭空多一个高带宽、高可用的有状态服务。
- 但这条路的**天花板很低**:一旦要 3 人以上通话、要录制、要服务端转码,P2P 架构整体失效,不是加字段能解决的。
- `iceCandidatePoolSize: 0`、`reset()` 保留流与候选、12s grace、Lua 忙线裁决 —— 每一条都是**具体故障倒逼出来的**,不是拍脑袋。
- 已知安全缺口:**`call:start`/`call:accept`/`call:end`/`call:ice` 都不校验参与者身份**,`callId` 又是可预测格式。内网 demo 无碍,公网部署前必须修。
- 容量上界:relay 端口 1000 → 约 500 路双边中继;**带宽(约 1.5 Gbps)通常先于端口到顶**;P2P 成功的那部分不占服务器资源。任何"支持 N 人通话"的结论都必须带估算限定。

## 1. 六个关键决策

### D1 · 为什么用 P2P,不自研 SFU

| 维度 | P2P(当前) | 自研/自托管 SFU |
|---|---|---|
| 延迟 | 最低(通常 20-60ms,不经服务器) | +1 跳(多 30-80ms) |
| 服务器成本 | 仅信令(几乎为 0) | 每路 1-4 Mbps 出向带宽 + CPU 转发 |
| 扩展性 | **只支持 1v1** | 支持 N 方、录制、转码、混流 |
| 工程量 | 前端 800 行 + 服务端 300 行 | 引入 mediasoup/LiveKit,运维复杂度翻倍 |
| 故障面 | NAT 穿透失败(靠 TURN 兜底) | 媒体服务器本身成为单点 |

**决策**:当前是 1v1 产品,选 P2P。**判断依据不是"P2P 更先进",而是"1v1 下 SFU 的每一分成本都换不来收益"**。

**代价必须说清**:
- 无法做服务端录制(合规场景会卡住);
- 无法做服务端降码率/自适应(全靠浏览器 BWE);
- 无法做多人(见 D6);
- 质量不可观测——服务端看不到 RTP 质量,`getStats()` 只在客户端。

### D2 · 为什么 `iceCandidatePoolSize: 0`

`iceCandidatePoolSize > 0` 会让浏览器**提前**为每个 PeerConnection 分配一批 relay 候选。听起来是优化(建连更快),实操是灾难:

```text
候选池(每 PC 预分配 N 个 relay)
  × 每次 reset() 重建 PC(自适应升级、rejoin 都可能触发)
  × 单用户多标签页/多设备
  ─────────────────────────────────────
  = 短时间大量 allocation → 撞 coturn user-quota
  → 486 Allocation Quota Reached
  → 真正需要中继的通话反而分配不到
```

代码注释里写得很直白(`webrtc.ts:16-18`)。**这是"优化参数"反噬的典型案例**:预分配把"可能用到"变成"一定占用",在配额受限的中继上等于自伤。默认 0,按需收集。

### D3 · 为什么忙线裁决必须用 Lua

Node 版 `GET`-then-`SET` 在多副本下双接(见 01 篇 §4.3)。Lua 的三个收益:

1. **原子性**:检查与写入不可分割,窗口为 0;
2. **多键一致**:会话 + 两个索引要么全写要么全不写,不会出现孤儿索引;
3. **省往返**:一次 `EVAL` 代替三次命令,高并发下少两次 RTT。

代价:Lua 脚本难以单测(需要真实 Redis)、调试只能靠日志。项目里 `call_test.go` 已覆盖状态机,但 Lua 分支仍依赖集成测试。

### D4 · 为什么 grace 是 12s,客户端兜底 15s

见 03 篇 §2.3。核心规则:**内层超时 < 外层超时**。12s 覆盖浏览器 ICE 自身的重连窗口(5-8s),15s 给 `call:end` 留传输余量。

反面案例(如果反过来):客户端 10s 先结束 → 用户看到"通话结束" → 3s 后服务端的 `call:end` 到达 → 再弹一次"通话结束"。用户会认为系统有 bug。

### D5 · 为什么 `reset()` 要保留流和候选

两个都是**实测根因**,不是防御性编程:

| 保留物 | 不保留的后果 | 现象 |
|---|---|---|
| `pendingIceCandidates` | 被叫接听时重建 PC,主叫早到的 trickle 候选丢失 | **媒体单向**:能看见对方,对方看不见你 |
| `localStream` | 重协商时重新 `getUserMedia` | 权限弹窗/设备占用 → 卡住 → offer 无 answer → 12s 被 grace 挂断 |

第二条尤其隐蔽:重采媒体在桌面端通常几百毫秒完成,在移动端(摄像头被其它 App 占用)可能直接失败。**"能跑通"和"弱网/移动端能跑通"是两件事。**

### D6 · 为什么升级 relay 是"整体切换"而非"按候选挑"

理论上可以让 ICE 自己从 `all` 里挑 relay 候选,不需要 `iceTransportPolicy: 'relay'`。但实测失败场景(VPN TUN、对称 NAT)里:

- host 候选是**死地址**(198.18.x 之类),会让 ICE 检查大量超时,收敛极慢;
- srflx 候选是**代理出口的假公网地址**,对端往那发永远不通。

保留这些候选不是"多一个选择",而是**拖慢收敛、干扰选中**。所以升级时直接 `policy: 'relay'`,把垃圾候选全部丢掉。代价是失去了"其中一方其实能 P2P"的机会——但由于要求**双端同时切**,这个代价是可接受的确定性交换。

### D7 · 为什么 `callId` 由客户端生成且带双方 ID

当时的需求是:**服务端要能不看 Redis 就转发 `call:ice`**(trickle 候选量大、频率高,不想每次都读一次会话)。于是 `callId = call_<callerId>_<calleeId>_<ts>`,解析字符串即可拿到双方。

**这个优化现在变成了耦合**(见 03 篇 §5.2):

- 格式成了隐式协议,客户端改格式 → 挂断通知失效;
- ID 明文可推导,配合"不校验参与者"形成安全隐患(见 §2)。

**建议**:`callId` 改为 `call_<random128>`,`call:ice`/`call:end` 走一次 Redis 读(或加本地 LRU 缓存)。ICE 帧的频率在单通话内是每秒几个到几十个,一次 Redis GET 完全承受得起——**当初的性能顾虑被高估了**。

## 2. 安全边界(公网部署前必须处理)

当前 `callRelay.go` 的四个上行事件**都没有校验发起者是否为该通话的参与者**:

| 事件 | 缺失的校验 | 可造成的后果 | 严重度 |
|---|---|---|---|
| `call:start` | 被叫是否存在、是否为好友/可呼叫 | 向任意 userId 发起呼叫(骚扰);被叫 ID 可枚举 | 中 |
| `call:accept` | `to` 是否等于会话主叫 | 把 answer 投递给任意用户(伪造接听) | 中 |
| `call:end` | 发起者是否为双方之一 | **知道 `callId` 即可挂断他人通话**(`ClearSession` 真删会话) | **高** |
| `call:ice` | 同上 | 向他人通话注入伪造候选,可致其媒体中断 | 中 |

`callId` 格式 `call_<a>_<b>_<ms>` 是可预测的:攻击者知道自己的 ID 与目标 ID,只需枚举毫秒时间戳(几分钟窗口约几十万个值)。单帧成本极低,**足以在可接受时间内命中**。

**最小修复(按性价比排序)**:

1. `call:end`/`call:ice`/`call:accept` 进入后先 `GetCallSession(callId)`,校验 `uctx.UserID ∈ {callerId, calleeId}`;不匹配返回 404/403。一次 Redis GET,成本可忽略。
2. `call:start` 校验被叫存在且(若产品要求)为好友;被叫为黑名单直接拒绝。
3. `callId` 由客户端加 128bit 随机 nonce;或改为服务端签发。
4. 加固后把 `call:end` 的 ID 解析改为读会话,消除格式耦合。

> 这几条与压测/体检文档里"消息发送不校验会话成员"是同一类问题的两次复现:**信令面比数据面更容易被漏掉**,因为它不经过常规的 REST 鉴权中间件。

## 3. 能力边界:能做什么、做不了什么

| 能力 | 现状 | 说明 |
|---|---|---|
| 1v1 语音/视频 | ✅ | 720p 目标分辨率,`facingMode: user` |
| 静音 / 关摄像头 | ✅ | `track.enabled` 本地切换,不做信令 |
| 多端同时振铃 | ✅ | 来电扇给所有设备,接听后其它设备收 `call:handled` |
| 刷新/断网恢复 | ✅ | rejoin 重协商,12s grace |
| 弱网/严格 NAT 兜底 | ✅ | 自适应 relay-only 升级 |
| **3 人及以上通话** | ❌ | P2P 全互联在 4 人以上上行带宽爆炸;必须 SFU |
| **服务端录制** | ❌ | 媒体不经服务器 |
| **通话质量服务端可观测** | ❌ | 只有客户端 `getStats()`,无上报聚合 |
| **群聊内发起通话** | ❌ | `callRelay` 无任何 group 逻辑,只有 1v1 |
| **端到端加密保证** | ⚠️ | WebRTC 默认 DTLS-SRTP,但中继时 coturn 可见元数据(看不到内容) |

**如果要做多人**:唯一正确路径是引入 SFU(mediasoup 自托管 / LiveKit 托管)。届时信令层需要新增"房间"概念,`call:session` 从 1v1 二元组变成房间成员集合,grace/rejoin 逻辑要按成员粒度重写。**这不是增量改造,是替换。** 这也是为什么当前把 `callRelay` 的语义限制在 1v1、没有预留"多人"抽象——预留了也用不上,反而增加复杂度。

## 4. 容量上界与可测量性

### 4.1 上界估算

| 约束 | 公式 | 当前配置 |
|---|---|---|
| relay 端口 | `max-port - min-port + 1` | 1000 |
| 双边中继通话 | 端口 ÷ 2(rtcp-mux 每 allocation 占 1 端口) | ≈ 500 路 |
| 带宽 | 路数 × 码率 × 2 | 视频 1.5 Mbps/方向 → ≈ 1.5 Gbps |
| 信令 | 每通话 start/accept/end 各 1 + ICE 若干 | 远低于消息面,不是瓶颈 |

### 4.2 三条不能越过的限定

1. **这是估算,不是压测结果**。真实并发取决于 NAT 类型分布,P2P 成功部分零成本。
2. **端口段与防火墙必须一致**。当前 `turnserver.conf` 写 1000 个端口,而 compose 注释只要求放行 41 个(49160-49200)。若安全组按注释配置,第 42 路中继起就会"分配成功但媒体不通"——小规模测试完全发现不了。
3. **不能把信令 QPS 换算成通话人数**。信令是"每通电话几次事件",与媒体并发没有换算关系。

### 4.3 怎么测(与压测体系对齐)

| 层 | 可测性 | 手段 |
|---|---|---|
| 信令面 | ✅ 可压 | 按"发起→接听→挂断"成对循环,看 `server_call_events_total` 速率、`server_active_calls` 水位、信令 RTT |
| 媒体面 P2P | ❌ 压服务器无意义 | 只能真机验证(2-4 台设备) |
| 中继面 | ⚠️ 只能小规模验证 | `turnutils_uclient` 几十路;真实媒体流需大量真实端 |

对应的场景编号与判据见 [`压测分析SOPV3.md`](../../监测设施/prompts/压测分析SOPV3.md) §5.2(信令 S9)与 §10(音视频边界声明)。

## 5. 下一步优先级

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | 四个上行事件加参与者校验 | 公网可被挂断/注入,性质等同越权 |
| P0 | `callId` 加随机 nonce | 消除可预测性,顺带解耦格式 |
| P1 | 端口段与防火墙统一到单点配置 | 并发一上来就"部分无声",极难排查 |
| P1 | `call:end`/`call:ice` 改读会话拿双方 ID | 消除隐式协议 |
| P2 | `getStats()` 质量数据上报聚合 | 现在出了质量问题是瞎的 |
| P3 | 信令压测脚本(`call-bench.mjs`) | 目前完全无覆盖 |
| — | 多人通话 / SFU | **不做**,除非产品明确需要;做就是换架构 |
