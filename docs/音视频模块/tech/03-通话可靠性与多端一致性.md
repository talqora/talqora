# 音视频模块 · 通话可靠性与多端一致性

> 媒体面见 [02 篇](./02-媒体面-P2P-ICE与TURN中继设计.md)。本篇讲**网络抖了、页面刷了、开了三个标签页**时,通话凭什么还能继续。

## 0. TL;DR

- 可靠性分三层,各管一段:**媒体层**(WebRTC 自己的 ICE 重连/DTLS)、**信令层**(WS 重连 + 帧补发)、**状态层**(Redis 会话 + 12s grace)。
- 掉线**不立刻挂断**:服务端把会话置 `reconnecting` 并通知对端,12s 内重连方 `call:rejoin` 回来就恢复,超时才真结束。
- 服务端 grace **12s**,客户端兜底 **15s**。**服务端先到点**——正常情况下由服务端主动发 `call:end`,客户端 15s 定时器只是"连 `call:end` 都没收到"的最后保险。
- 重连方**永远是发 offer 的一方**,不管原先是主叫还是被叫。这条规则统一了重协商角色,避免 glare。
- 刷新恢复靠 `sessionStorage`(不是 localStorage):刷新保留、关标签页即清、按标签页天然隔离,不会多标签串话。
- 多端靠两条路由规则:来电**扇给所有设备**、已处理通知**只给其它设备**(`ExceptDeviceID`),rejoin 的 offer **只给属主设备**(`TargetDeviceID`)。
- 幂等靠两个 `Set`:同一 `callId` 的 `call:accept` 只处理一次;`call:rejoin` 的 answer 只发一次。WS 未就绪时 `send` 返回 false,靠 500ms 重试补发。

## 1. 三层可靠性:谁兜谁的底

```text
┌── 媒体层(浏览器内建)────────────────────────────────┐
│ DTLS-SRTP 加密、拥塞控制(NACK/PLI/FEC)、ICE 连通性检查  │
│ 由 Chrome/Safari 实现,我们只监听 connectionState      │
└──────────────────┬───────────────────────────────────┘
                   │ failed / disconnected
┌──────────────────▼───────────────────────────────────┐
│ 信令层:WS 重连 + call:rejoin 重协商                    │
│ 我方实现。把"媒体断了"翻译成"重来一次 offer/answer"      │
└──────────────────┬───────────────────────────────────┘
                   │ 12s 内没回来
┌──────────────────▼───────────────────────────────────┐
│ 状态层:Redis 会话 + graceEpoch 定时器                  │
│ 唯一有权判"这通电话结束了"的地方                        │
└──────────────────────────────────────────────────────┘
```

**为什么判死刑必须放在服务端**:客户端可能崩了、被系统杀了、断网了——它没有能力宣告自己退出。只有服务端能在"一段时间内没人回来"时单方面清理。

## 2. 掉线:reconnecting 与双 grace

### 2.1 服务端

```text
WS 断开
  │
  ├─ gateway 检测到连接关闭
  │    ├─ gRPC 流:frame.closed        → edge_util.go:99
  │    └─ HTTP 代理模式:/internal/gateway/disconnect → internal_routes.go:74
  │    (两条等价入口,按网关模式二选一,不会同时触发)
  ▼
biz HandleDisconnect(userID, deviceID)        callRelay.go:190
  │
  ├─ GetUserCall(userID) → 不在通话中? 直接返回(绝大多数断连走这里,O(1))
  ├─ MarkReconnecting(callID, deviceID)
  │    · 该设备不是 callerDevice/calleeDevice → 忽略(非属主设备掉线不影响通话)
  │    · 否则: resumeStatus = status(快照), status = 'reconnecting', epoch++
  ├─ PublishDownlink(peer, 'call:peer-reconnecting')  ← 让对端 UI 显示"对方网络不佳"
  └─ go { sleep 12s; 重读会话; 仍 reconnecting 且 epoch 未变 → ClearSession + 双向 call:end }
```

`epoch` 的妙处:定时器是**在 goroutine 里 `sleep`** 的,进程重启就丢了,也无法跨副本取消。但重读时比对 `epoch` 就能判断"这 12s 内有没有人 rejoin 过"——`rejoin` 会 `epoch++`,于是所有在途定时器自动作废。**用数据版本号代替分布式定时器**,是这里最值得学的一手。

### 2.2 客户端

`onConnectionStateChange`(`useCall.ts:110-126`):

| 状态 | 处置 |
|---|---|
| `connected` | `connectCall()`,起通话时长定时器 |
| `connecting` | 只打日志 |
| `failed` | ① 首次且未升级 → `escalateToRelay()`;② `reconnectingCall()`;③ 起 15s 兜底定时器 |
| `disconnected` | 只 `reconnectingCall()` + 起定时器,**不升级** |

**`failed` 与 `disconnected` 必须区别对待**:`disconnected` 是临时性中断(切网、短暂丢包),浏览器自己会尝试恢复;`failed` 是 ICE 彻底失败,只能重建。在 `disconnected` 上就升级 relay 会造成大量不必要的"明明能 P2P 却走了中继"。

### 2.3 为什么是 12s / 15s

| 值 | 位置 | 依据 |
|---|---|---|
| 12s | `service.GraceMS`(`call.go:22`) | 大于浏览器 ICE 自身的重连窗口(通常 5-8s),又小于用户耐心阈值 |
| 15s | `RECONNECT_GRACE_MS`(`useCall.ts:52`) | **故意比服务端长 3s**,留出 `call:end` 的传输时间 |

如果客户端比服务端短(比如 10s),会出现"客户端已经自己结束了,服务端的 `call:end` 5s 后才到"→ 用户看到两次"通话已结束"提示。**上下层超时必须有序**,这是分布式超时的通用规则:内层超时 < 外层超时,否则外层永远等不到内层的结论。

## 3. rejoin:刷新/断网后的重协商

### 3.1 角色规则

> **重连方永远是发 offer 的一方,无论原先是主叫还是被叫。**

这条规则(`useCall.ts:502`)是整个重连机制的地基。WebRTC 的 renegotiation 对"谁先发 offer"敏感:如果双方同时发,进入 `have-local-offer` 状态,谁也设不了 remote,协商彻底卡死(glare)。用"重连方"这个**唯一确定的角色**消除了歧义。

### 3.2 两条路径

```text
【路径 A:断网后 WS 重连 + 主动 rejoin】
  重连方(任意角色)
    ensureIceServers() → reset()(保留流与候选)
    → getUserMedia()(刷新后流必丢,必须重采)
    → createOffer()
    → ws.send('call:rejoin', { offer, relay })
        └─ send 返回 false(WS 还没连上)→ 每 500ms 重试,直到成功
  对端收到 call:rejoin
    · 若本端 status === 'ringing' → 只 updatePendingOffer,等用户接听(不自动协商)
    · 否则 → reconnectingCall() → 若 relay 标记 → setForceRelay(true)
             → reset() → handleOffer(offer) → 回 call:accept(answer)
```

**`ringing` 特例很关键**:被叫还在振铃时,主叫刷新重发 offer,被叫不能直接自动接通——用户还没点接听。此时只替换 `pendingOffer`,等真实接听时用最新的 offer 协商。

### 3.3 刷新恢复:sessionStorage 的四个理由

`web/src/utils/callPersist.ts` 只存"重建一通话所需的最小信息":`callId`/`peer`/`callType`/`role`/`status`/`startTime`/`isMuted`/`savedAt`。**不存媒体流、不存 SDP**——它们无法序列化,也不该序列化。

选 `sessionStorage` 而非 `localStorage`:

| 特性 | 收益 |
|---|---|
| 刷新保留 | 能恢复通话 |
| 关标签页即清 | 不会"过两天打开浏览器,突然复活一通早就结束的通话" |
| 按标签页隔离 | 天然规避多标签串话(两个标签页各自有独立会话) |
| 2min TTL | 即使标签页被浏览器恢复,超时也不再复活 |

`status` 字段决定恢复方式:`calling`/`connected` → 重发 offer;`ringing` → 复原来电界面等接听。

## 4. 多端与多标签

### 4.1 三条路由规则

| 下行事件 | 路由 | 实现 |
|---|---|---|
| `call:start`(来电) | 被叫**所有**在线设备 | `PublishDownlink(calleeID, ..., nil)` |
| `call:handled`(已被接/拒) | 本用户**其它**设备 | `ExceptDeviceID: uctx.DeviceID` |
| `call:rejoin`(offer) | 对端**属主**设备 | `TargetDeviceID: peerDevice` |

第三条是必要的:如果 offer 扇给对端所有设备,那么对端在手机+电脑同时登录时,两台设备都会尝试建立同一通电话的 PC,互相干扰。会话里记着 `callerDevice`/`calleeDevice`,`MarkAccepted`/`MarkRejoined` 时更新(`call.go:110-153`),重连时就能精确投递。

### 4.2 幂等的两个 Set

```ts
processedEvents  // 'accept_<callId>' —— 防止重复处理同一次接听
acceptSentIds    // 'accept_<callId>' —— 防止 answer 重复发送
```

场景:WS 抖动导致 `call:accept` 帧重传,或用户在两个标签页同时点"接听"。没有这层去重,会出现**两次 `setRemoteDescription`**,第二次抛 `InvalidStateError`,表现为"接了但黑屏"。

两个 Set 在 `cleanup()` 里清空(`:329-330`、`:409-410`),避免跨通话污染。`call:handled` 到达时也会清理——因为"别的设备已经处理了",本端不应再动作。

## 5. 竞态与账目:已知的三个坑

### 5.1 `ActiveCalls` 计数会漂

`server_active_calls` 用 `Inc()`/`Dec()` 维护,但:

- `call:start` 成功才 `Inc()`;
- `call:reject` / `call:end` 只有 `ClearSession` 返回**非 nil** 才 `Dec()`;
- `call:rejoin` 发现会话不存在时,返回 `call:end` 给重连方,但**不 `Dec()`**(因为可能已被 grace 分支清掉并减过)。

如果 grace 分支和 `call:end` 几乎同时到达,`ClearSession` 有一方会拿到 nil,于是只减一次——**这是对的**。但如果进程在 `Inc()` 之后、写 Redis 之前崩溃,计数就会永久偏高。**结论:该指标适合看趋势,不能当账本**。要精确统计应该用"Redis 里 `call:session:*` 的 key 数量"。

### 5.2 `call:end` 广播依赖 `callId` 字符串格式

```go
// callRelay.go:109-119
parts := strings.Split(callID, "_")   // call_<callerId>_<calleeId>_<ts>
id1, _ := strconv.ParseInt(parts[1], ...)
id2, _ := strconv.ParseInt(parts[2], ...)
```

`call:end` 与 `call:ice` 不读 Redis,直接解析 ID。这让客户端生成的 `callId`(`useCall.ts:431`)变成了**隐式协议**:

- 客户端换一种 `callId` 拼法 → 挂断通知发不出去 → 对方一直显示"通话中",直到 1h TTL 过期;
- `callId` 里带下划线以外的分隔符 → `parts[2]` 解析失败 → 只通知一方。

正确做法:统一从会话读 `callerId`/`calleeId`,`callId` 退回纯不透明标识。这是一处应该修的耦合。

### 5.3 重复断连通知

两条入口(gRPC `frame.closed` 与 HTTP `/internal/gateway/disconnect`)在单网关模式下只会走一条,但网络抖动时同一设备的断连可能被重复上报。`MarkReconnecting` 的幂等性由两个细节保证:

- `if s.Status != "reconnecting"` 才写 `resumeStatus`(`call.go:167`)——重复调用不会把 `resumeStatus` 覆盖成 `reconnecting`;
- 每次 `epoch++`,先起的定时器自动作废,只有最后那个生效。

所以重复通知**不会导致误挂断**,只是多一次 Redis 写和一次下行。可接受,但不该依赖"反正幂等"来掩盖重复上报。

## 6. 故障对照表

| 现象 | 根因 | 证据/定位 |
|---|---|---|
| 刷新后接不回来,12s 后被挂断 | rejoin 未发出(WS 未就绪且重试失效)或 offer 未送达 | 客户端日志 `[rejoin] 步骤4`;`server_call_events_total{event="rejoin"}` 是否为 0 |
| 接听后黑屏/无声,但状态是 connected | 候选被 reset 冲掉 / 重复 setRemoteDescription | [02 篇 §2.2](./02-媒体面-P2P-ICE与TURN中继设计.md);`processedEvents` 去重是否生效 |
| 对端一直显示"通话中" | `call:end` 广播失败(TTL 未过期) | 查 `callId` 格式是否变化;`call:session:*` key 是否残留 |
| 手机和电脑同时响,接了手机电脑还响 | `call:handled` 未送达(其它设备不在线或 `ExceptDeviceID` 判断错) | 查下行 `call:handled` 的 target 与设备表 |
| 双方都点接听,谁也没画面 | glare(双方都发 offer) | 是否破坏了"重连方发 offer"规则 |
| 频繁无故进入"重连中" | 把 `disconnected` 当 `failed` 处理 | `useCall.ts:110-126` 分支 |

## 7. 一句话总结设计哲学

**信令层负责"尽快恢复",状态层负责"最终一致",客户端只负责"如实呈现"。**

三者职责不重叠:客户端不做超时裁决(只做兜底),服务端不猜媒体状态(只看连接断没断),媒体层不关心业务(谁跟谁通话)。这条分界线一旦被打破——比如让客户端在 WS 断开时自行结束通话——就会在弱网下出现大量误挂断。
