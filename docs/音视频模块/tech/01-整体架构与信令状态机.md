# 音视频模块 · 整体架构与信令状态机

> 范围:1v1 语音/视频通话的**控制面**——谁在通话、能不能接、掉线怎么办。媒体面(P2P/ICE/TURN)见 [02 篇](./02-媒体面-P2P-ICE与TURN中继设计.md),可靠性细节见 [03 篇](./03-通话可靠性与多端一致性.md),取舍与踩坑见 [04 篇](./04-设计决策与容量边界.md)。

## 0. TL;DR

- 本模块**没有媒体服务器**。媒体走浏览器之间 P2P,coturn 只做 NAT 穿透失败时的中继兜底。服务端全程只转发信令,**不碰 RTP**。
- 信令走已有的 WebSocket 上行/下行通道,不新开连接;`biz` 侧新增 6 个上行事件、9 个下行事件(`realtime/callRelay.go`)。
- 通话的**权威状态在 Redis**,不在进程内存:`call:session:<callId>` + `call:user:<userId>` 双索引,TTL 1h。多副本部署下任意副本都能处理同一通电话。
- 忙线裁决用 **Lua 原子脚本**完成,修掉了 Node 版 `GET`-then-`SET` 的并发双接缺陷。
- 掉线不立即挂断:进入 `reconnecting`,给 12s 宽限窗(`GraceMS`),窗内 `call:rejoin` 回来就恢复;`graceEpoch` 让跨副本的在途定时器自动失效。
- **只支持 1v1**。没有 SFU/MCU、没有群通话、没有录制。这是当前架构的硬边界,见 04 篇。

## 2. 分层架构

```text
┌──────────────────────── 浏览器 A ────────────────────────┐
│ callModal / useCall.ts  ← 状态机、重协商、升级 relay      │
│   ├─ WebRTCManager (utils/webrtc.ts)  ← PC 生命周期       │
│   └─ wsClient (既有 WS 通道)          ← 信令上行           │
└───────────────┬──────────────────────────┬───────────────┘
                │  WS(call:* 帧)            │  DTLS-SRTP 媒体
                ▼                          │  (P2P 直连 / 或经 coturn 中继)
┌──────────── gateway(Go) ────────────┐    │
│ 只做连接与转发:                      │    │
│  上行帧 → gRPC bidi → biz            │    │
│  下行   ← gw:downlink ← biz          │    │
└───────────────┬──────────────────────┘    │
                ▼                            │
┌──────────────── biz(Go) ────────────────┐  │
│ realtime/callRelay.go  信令路由(无状态)  │  │
│ service/call.go        Redis 通话态      │  │
│ api/auth_routes.go     TURN 临时凭据     │  │
└───────────────┬──────────────────────────┘  │
                ▼                             │
        ┌───────────────┐         ┌───────────────────┐
        │ Redis         │         │ coturn            │
        │ call:session  │         │ 3478 / 5349       │
        │ call:user     │         │ relay 49160-50159 │
        └───────────────┘         └───────────────────┘
                                          ▲
                          媒体在这里中继 ──┘
```

三个关键事实:

1. **信令面与媒体面彻底分离**。信令走 WS(可靠、有序、可鉴权),媒体走 UDP SRTP(不可靠、低延迟、端到端加密)。任何一侧故障不会直接拖垮另一侧。
2. **biz 是无状态的**。通话状态全在 Redis,所以多副本无需粘性会话;下行靠 `PublishDownlink` 按 `userId`(+可选 `deviceId`)路由到"该用户当前连着的那台 gateway"。
3. **gateway 不知道 call 的存在**。它只认 `gw:downlink` 指令,不解析 `call:*` 语义——通话逻辑全部收敛在 biz,新增信令不需要动 gateway。

## 3. 信令事件全集

定义在 `proto/` 的 `ourchat.call.v1`,生成到 `web/src/contracts/gen/ourchat/call/v1/call.ts`。**上行 6 个、下行 9 个**:

| 方向 | 事件 | 关键字段 | 服务端行为 |
|---|---|---|---|
| ↑ | `call:start` | `callId` `to` `callType` `offer` | 原子登记会话;忙回 `call:busy`;否则下发被叫 |
| ↑ | `call:accept` | `callId` `to` `answer` | `MarkAccepted` → 转发起始时间;转发 answer;本用户其它设备收 `call:handled` |
| ↑ | `call:reject` | `callId` | 清会话;通知主叫;本用户其它设备 `call:handled` |
| ↑ | `call:end` | `callId` | 清会话;按 `callId` 解析双方并广播 `call:end` |
| ↑ | `call:rejoin` | `callId` `offer` `relay?` | 重连方回场,恢复状态;offer 定向投给对端属主设备 |
| ↑ | `call:ice` | `callId` `candidate` | 按 `callId` 解析双方,trickle 转发(排除自己) |
| ↓ | `call:start` | 原样 | 被叫所有在线设备(多端同时振铃) |
| ↓ | `call:busy` | `callId` | **只回主叫本设备**,不打扰被叫 |
| ↓ | `call:accept` / `call:reject` / `call:end` / `call:rejoin` / `call:ice` | 原样 | 对端 / 双方 |
| ↓ | `call:handled` | `callId` `status` | 同账号的**其它**设备(一排设备同时收起振铃) |
| ↓ | `call:peer-reconnecting` | `callId` | 对端(提示"对方网络不佳") |
| ↓ | `call:error` | `message` | 出错方 |

> **设计点:信令帧原样转发。** `rawJSON(data)` 把客户端 JSON 对象直接塞进下行 payload(`callRelay.go:285`),服务端不重建结构。好处是加字段不用改服务端;代价是服务端**无法校验**它不认识的字段——`relay` 标记就是靠这个机制偷偷加上的(未进 IDL),客户端用窄化类型读取(`useCall.ts:289`)。这是一个有意的"逃生口",也埋下了契约漂移的隐患。

### 3.1 指标

| 指标 | 类型 | 标签 |
|---|---|---|
| `server_call_events_total` | Counter | `event` ∈ {start, accept, reject, end, rejoin, ice, busy} |
| `server_active_calls` | Gauge | — |

`start` 成功才 `Inc()`,`reject`/`end` 清理成功才 `Dec()`。**已知偏差**:`call:rejoin` 会话不存在时直接返回 `call:end` 给重连方,但不 `Dec()`——因为原会话可能已被 grace 分支清掉并减过。这点在 03 篇的"账目"一节详述。

## 4. Redis 通话状态机

### 4.1 数据结构

```text
call:session:<callId>   → JSON,TTL 3600s
  { callId, callerId, calleeId, callType,
    status,                     // ringing | connected | reconnecting
    startTime,                  // 接入时刻(ms),ringing 时为 null
    callerDevice, calleeDevice, // 属主设备,用于定向路由
    graceEpoch,                 // 每次状态变更 +1
    resumeStatus }              // 进 reconnecting 前的状态快照

call:user:<callerId>    → <callId>,TTL 3600s    ← 忙线索引(反查"你在通话吗")
call:user:<calleeId>    → <callId>,TTL 3600s
```

双索引解决两个查询:①"这个用户现在在通话吗"(忙线判定、断连处理);②"这通电话是谁跟谁"(定向路由、`call:end` 广播)。

### 4.2 状态迁移

```text
                    call:start(原子登记成功)
          ┌──────────────────────────────────┐
          ▼                                  │
      ┌────────┐   call:accept    ┌───────────┴──┐
      │ringing │─────────────────▶│  connected   │
      └───┬────┘                  └──────┬───────┘
          │ call:reject                    │ 属主设备 WS 断
          │                                ▼
          │                        ┌──────────────┐
          │        call:rejoin     │ reconnecting │
          │      ┌─────────────────└──────┬───────┘
          │      │                        │ 12s 内无人 rejoin
          │      ▼                        ▼
          │   connected              ┌─────────┐
          └─────────────────────────▶│  已清理  │
                   call:end          └─────────┘
```

对应实现:`TryCreateSession`(`call.go:95`)、`MarkAccepted`(`:110`)、`MarkRejoined`(`:126`)、`MarkReconnecting`(`:157`)、`ClearSession`(`:176`)。

**`resumeStatus` 的作用**:`reconnecting` 会覆盖原状态,恢复时需要知道"回 ringing 还是回 connected"。`MarkReconnecting` 先存快照再覆盖(`call.go:167-170`),`MarkRejoined` 优先按快照恢复(`:136-140`)。没有这个字段,被叫在振铃期间刷新页面后回来会错误地变成"已接通"。

**`graceEpoch` 的作用**:掉线时起一个 12s 定时器;定时器到点后重读 Redis,**若 `status` 仍为 `reconnecting` 且 `epoch` 未变**,才判定真挂断(`callRelay.go:214`)。如果期间发生了 `rejoin`(epoch+1),旧定时器自然失效——这是**无锁的分布式取消**,不需要在进程间传递定时器句柄。代价:定时器本身是 `go func(){ time.Sleep(12s) }`(`:207-227`),进程重启会丢,所以只是"兜底尽早释放",不是强一致。

### 4.3 忙线裁决:为什么必须用 Lua

```text
Node 版(缺陷):
  v = GET call:user:<callee>      ← 两个副本同时读到 nil
  if v then busy
  SET call:user:<callee> ...      ← 两个都写成功 → 双接

Go 版(当前):
  Lua: GET 忙线 → 若空则 SET 会话 + SET 双索引,全部在一个原子操作里
       KEYS[1]=callee 索引  KEYS[2]=会话  KEYS[3]=caller 索引
       call.go:82-91
```

这不只是"代码更漂亮":**多副本部署下 `GET`-then-`SET` 的双接概率随并发线性上升**,而 Lua 把窗口压到 0。同一脚本还顺带保证了"会话和两个索引要么全写、要么全不写",不会出现孤儿索引。

## 5. 完整时序

### 5.1 正常接通

```text
A(主叫)            biz                    Redis              B(被叫)
  │ call:start        │                      │                  │
  ├──────────────────▶│  EVAL tryCreateLua   │                  │
  │                   ├─────────────────────▶│                  │
  │                   │◀──── 1(登记成功) ────┤                  │
  │                   │ ActiveCalls++        │                  │
  │                   │ PublishDownlink(B, call:start) ─────────▶│ 振铃
  │◀──── 204 ─────────┤                      │                  │
  │  (本地开始响铃)     │                      │  用户点接听        │
  │                   │◀──────── call:accept ───────────────────┤
  │                   │ MarkAccepted: status=connected, startTime│
  │◀── call:accept ───┤ 转发 answer          │                  │
  │                   │ PublishDownlink(A? no → B 的其它设备)    │
  │                   │                      │                  │
  │◀══════════ ICE trickle(双向,经 call:ice)══════════════════▶│
  │◀══════════════ DTLS-SRTP 媒体(不经服务端)═════════════════▶│
```

注意 `call:accept` 的转发目标是客户端自己填的 `to` 字段,**服务端不校验它等于会话主叫**。这是当前实现的真实缺口,见 04 篇"安全边界"。

### 5.2 忙线

```text
A ──call:start──▶ biz ──Lua 发现 B 的索引已被占──▶ 返回 0
A ◀── call:busy(仅投 A 本设备)── biz
```

**刻意不通知被叫**:B 正在另一通电话里,再推一条 `call:start` 会造成振铃干扰与 UI 状态错乱。所以忙线是"主叫单方面知情"的设计。

### 5.3 挂断

```text
任意一方 ──call:end──▶ biz
  ClearSession: DEL 双索引 + DEL 会话
  split(callId, "_") → [1]=id1 [2]=id2 → 分别 PublishDownlink(call:end)
```

**设计缺陷(必须知道)**:`call:end` 与 `call:ice` 不读 Redis,直接按 **`callId` 字符串格式**解析出双方 ID(`callRelay.go:109-119`、`:167-179`)。这使 `call_<callerId>_<calleeId>_<ts>`(`useCall.ts:431`)从"客户端生成的随机串"变成了**隐式协议**。任何改了 `callId` 拼法的客户端都会导致挂断通知发不出去——通话会一直挂着,直到 1h TTL 过期。正确做法是统一读会话拿 `callerId/calleeId`,`callId` 退回纯不透明 ID。

## 6. 只在服务端做的事 vs 只在客户端做的事

| 职责 | 归属 | 原因 |
|---|---|---|
| 谁能接通(忙线/已被接) | 服务端 | 需要跨设备、跨副本的全局唯一裁决 |
| 通话态存活与 grace | 服务端 | 客户端崩溃时没人执行清理 |
| 多端振铃收起(`call:handled`) | 服务端 | 需要按"同账号其它设备"扇出 |
| SDP/ICE 生成、编解码协商 | 客户端 | 服务端不解析 SDP,无状态 |
| `forceRelay` 升级决策 | 客户端 | 只有客户端看得到 ICE 失败与候选质量 |
| 媒体开关(静音/关摄像头) | 客户端 | `track.enabled` 本地生效,极低延迟 |
| 通话时长显示 | 客户端 | `startTime` 由服务端给,本地自增即可 |

这个边界的意思是:**服务端不参与媒体协商**,所以任何"服务端转码/录制/混流"的需求都等于要引入 SFU,不是加个字段能解决的。
