# RAG 服务 · 检索与生成

> 摄取见 [02 篇](./02-文档摄取与向量化.md)。本篇讲**一个问题进来,怎么找到资料、怎么拼进 prompt、怎么流式吐回去**。

## 0. TL;DR

- 检索是**单路纯向量检索**:`embed(query) → Milvus top_k → PG 回表拿原文`。没有关键词/BM25、没有混合召回、没有 rerank、没有查询改写。
- 多租户隔离**写死在唯一出口**:`MilvusVectorStore.search_by_user` 里 `filter=f"user_id == {user_id}"`。任何 router/service 都不许自己拼 filter——用代码结构杜绝漏过滤。
- **没有相似度阈值**。top_k 命中多少就传多少,哪怕最高分只有 0.1。这是当前检索质量最直接的问题。
- Prompt = `system(固定纪律 + 资料上下文) + 历史 N 条 + 本轮问题`。资料格式 `[i] (文档 <id>) <正文>`,编号就是引用号。
- 生成是**同步流式**(不经 worker),逐 token 转发 SSE;结束时把 `[n] → document_id/chunk_id` 的映射随 `done` 帧返回。
- 缺一个东西:**检索质量评测集**。没有它,任何参数调整(800/100、top_k、阈值)都是凭感觉。

## 1. 检索链路

```text
retrieve(user_id, query, top_k)                 shared/retrieval.py:43
  │
  ├─ ① embed(query)                             ← 一次 LLM 调用,~几十 ms
  │      vectors = await llm.embed(query)
  │      hits = vector.search_by_user(vectors[0], user_id, top_k)   ← :46
  │
  ├─ ② Milvus search
  │      filter  = "user_id == <id>"            ← 唯一隔离点,vector.py:137
  │      limit   = top_k
  │      output  = [user_id, document_id, chunk_id, chunk_index]
  │      metric  = COSINE
  │
  ├─ ③ PG 回表
  │      SELECT * FROM document_chunks WHERE id IN (<chunk_ids>)   ← 一条查询,不 N+1
  │
  └─ ④ 按 Milvus 顺序输出
         for hit in hits: row = by_id.get(hit.chunk_id)
                         if row is None: continue   ← PG 已删则跳过
```

### 1.1 为什么"向量库只存向量,原文回 PG 取"

- 向量库不擅长变长文本的更新与事务;PG 才是原文的权威源。
- 回表同时起到**一致性校正**作用:Milvus 里残留但 PG 已删的点被自动跳过(`retrieval.py:66`),不会把已删除文档的内容喂给 LLM。

代价是**多一次往返**(Milvus + PG)。在本地部署下这点延迟可以忽略;如果跨可用区部署,两次 RTT 会变成主要延迟。

### 1.2 为什么必须"回表保序"

`IN (...)` 查询**不保证返回顺序**,而 top_k 的顺序就是相似度排序。所以代码显式按 `hits` 顺序遍历、用 `by_id` 映射取值(`retrieval.py:64-76`)。若直接 `for row in rows`,顺序变成 PG 的主键序,**最相关的资料可能被排到最后**——LLM 对上下文位置敏感(首尾注意力更强),这会让回答质量明显下降。

### 1.3 一个没做的保护

```python
vectors = await self._llm.embed(query)
hits = await self._vector.search_by_user(vectors[0], ...)   # :46
```

`vectors[0]` 没有空列表检查。如果 embedding 服务返回空数组(部分兼容实现会这样),这里抛 `IndexError` → 500。应该在取之前判空并给出可读错误。

## 2. 当前没做的(以及为什么重要)

| 能力 | 现状 | 缺失后果 |
|---|---|---|
| **相似度阈值** | 无 | 问"今天天气"也会硬塞 6 段无关资料,LLM 被诱导"基于资料编答案" |
| **混合检索(BM25 + 向量)** | 无 | 专有名词、型号、人名等**精确匹配**场景召回很差向量模型对罕见词不敏感 |
| **RRF / 加权融合** | 无 | 无法把两路结果合成一个稳健排序 |
| **Rerank(交叉编码器)** | 无 | 向量召回只看"语义相近",不看"能否回答问题";top_k 里的噪声无法二次筛掉 |
| **查询改写 / HyDE** | 无 | 口语化短问句("这个咋用")检索效果差 |
| **文档/时间过滤** | 无(只有 `user_id`) | 无法"只在这份文档里问"或"只看最近半年" |

优先级建议:**阈值 > 混合检索 > rerank > 查询改写**。

理由:阈值是一行代码几行判断的事,收益立刻可见(不再拿噪声喂 LLM);混合检索对专有名词场景提升最大;rerank 效果最好但要多一个模型和一次推理延迟;查询改写会引入额外 LLM 调用,ROI 最低。

## 3. Prompt 组装

### 3.1 System prompt(三条纪律)

```text
你是一个个人知识助手,只能依据下方「资料」回答用户问题。
若资料不足以回答,如实说明"资料中没有相关内容",不要编造。
引用资料时用 [n] 标注来源编号(对应资料前的序号)。

资料:
[1] (文档 12) <chunk 正文>
[2] (文档 12) <chunk 正文>
```

三个设计点:

1. **先讲纪律,再给资料**。"只能依据资料"必须在看到资料之前建立,否则模型容易把资料当"参考建议"。
2. **显式允许说"不知道"**。没有这句,7B 级别模型的默认行为是硬编。
3. **`[n]` 编号与资料序号严格对应**。这是后面能把引用映射回 `document_id` 的前提。

### 3.2 空召回的退化

```python
if not chunks:
    context = "(无检索到的资料)"
```

**不跳过检索直接回答**,而是明确告诉模型"没查到"。好处是模型的行为可预测(会说不知道);坏处是对"寒暄类"问题("你好")也会走一遍完整流程并回答"资料中没有相关内容",体验略傻。

改进:加一个轻量的"是否需要检索"判断(规则或小模型),寒暄直接走普通对话。当前没做。

### 3.3 历史窗口

`history_limit = 10`(`settings.py:54`),取最近 10 条 **message**(不是 10 轮对话),即约 5 轮问答。按 `created_at desc` 取再 `reverse()` 保证升序。

**注意这是一个"条数"限制,不是 token 限制**。10 条长回答可能几千 token,叠加 top_k × 800 字符的资料,很容易超出小模型上下文。当前**没有 token 计数与截断**(`estimate_tokens` 只是 `len/3` 且仅写元数据),所以:

- `top_k=20`(接口允许上限)+ 长历史 + 长资料 → prompt 可能到 1.5 万字符以上;
- 超出模型窗口时,行为取决于推理框架(截断前半 / 报错),**不可控**。

正确做法:按 token 预算装配(资料优先、历史按近远裁剪),并在超限时降级 `top_k`。

### 3.4 引用回传

流式结束后返回 `citations`(`chat.py` 的 `done` 帧),把 `[n]` 映射到 `document_id`/`chunk_id`。前端据此渲染可点击的来源。

**这里有个隐含契约**:LLM 生成的 `[n]` 可能越界(资料只有 6 条却写了 `[8]`)。当前没有校验,前端若直接按 `n` 取数组会越界。应该在组装 `citations` 时过滤掉非法编号。

## 4. 生成与流式

```text
chat_stream(messages)                    llm.py
  ├─ AsyncOpenAI(base_url, timeout=120s)
  ├─ stream=True
  ├─ for delta in stream: yield {"type":"delta", "text": ...}
  └─ finally: 关闭上游流                  ← 客户端断开时能及时释放
```

设计点:

- **`finally` 关流**:浏览器关页面 → 后端生成器被 GC → `finally` 执行 → 上游连接释放。否则本地 Ollama 会继续算完整个回答,白烧 GPU。
- **先落用户消息,再检索**:`chat.py` 里 user message 在检索前 commit。这样即使检索失败,用户的问题也留在了历史里(不会"问了但历史里没有")。
- **回答落库**:流式结束后 `INSERT assistant message`,再把 `messageId` 放进 `done` 帧。

**没有做的事**:
- 没有 token 用量统计(成本不可观测);
- 没有 `max_tokens` 限制(模型可能生成超长回答);
- 没有并发限流(单用户可开多个并发对话,把本地 Ollama 打满)。

## 5. 端到端延迟构成

| 阶段 | 典型耗时(本地 Ollama) | 优化空间 |
|---|---|---|
| embed(query) | 20-80ms | 缓存高频 query 的向量 |
| Milvus search | 5-20ms | 已够快 |
| PG 回表 | 5-15ms | 索引已有 |
| **首 token** | **0.5-3s** | 主要受模型大小与 prompt 长度影响 |
| 生成 | 20-60 token/s | 模型/硬件决定 |

**结论:延迟几乎全部在 LLM 上**。优化 top_k、切分、向量库对"首 token 时间"影响很小;真正有效的是缩短 prompt(更少资料、更短历史)与换更快的模型。

这也是为什么 §3.3 的 token 预算很重要——**资料塞得越多,首 token 越慢,且质量未必更好**。

## 6. 怎么验证检索质量(当前缺失的一环)

现在没有任何评测集,所有参数都是默认值。最小可行方案:

| 要素 | 做法 |
|---|---|
| 语料 | 20-50 份真实文档(不要用造的数据) |
| 问题集 | 50-100 条,每条标注"答案出自哪份文档的哪一段" |
| 指标 | **Recall@k**(前 k 条里有没有正确块)、**MRR**(正确块排多前)、端到端人工评分(1-5) |
| 对照 | 改一个参数(如 chunk_size 800→1200)跑同一套,只看指标变化 |

只有有了这个,才能回答:"阈值设 0.5 合适吗""要不要加 rerank""top_k=6 够不够"。**没有评测集的调参就是玄学**——这也是当前这套实现最该补的工程基础。

## 7. 改进优先级

| 优先级 | 事项 | 收益 | 成本 |
|---|---|---|---|
| P0 | 检索评测集(50 问 + Recall@k/MRR) | 让后续所有优化可验证 | 1-2 天 |
| P0 | 相似度阈值 + 空召回走普通对话 | 立刻减少"硬编" | 半天 |
| P1 | token 预算装配(资料/历史按预算裁剪) | 避免超窗、降低首 token 延迟 | 1 天 |
| P1 | 混合检索(BM25 + 向量,RFF 融合) | 专有名词召回大幅提升 | 2-3 天 |
| P2 | rerank(小交叉编码器) | top_k 精度提升 | 2 天 + 推理延迟 |
| P2 | 引用编号合法性校验 | 修一个必然出现的越界 | 半天 |
| P3 | 查询改写 / HyDE | 口语化问题提升 | 2 天 + 额外 LLM 调用 |
