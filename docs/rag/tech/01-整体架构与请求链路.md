# RAG 服务 · 整体架构与请求链路

> 代码在独立仓库 `/Users/jaytu/agent-server`(Python + uv workspace),与主站 `talqora` 通过 JWT 与 HTTP 契约耦合。本篇讲**它由哪些进程组成、一次请求怎么流动**;摄取见 [02 篇](./02-文档摄取与向量化.md),检索见 [03 篇](./03-检索与生成.md),事件流见 [04 篇](./04-Run引擎与事件流.md),鉴权见 [05 篇](./05-鉴权多租户与配置基线.md)。

## 0. TL;DR

- **一个代码库、两个进程角色**:`rag-http`(FastAPI,:3101,对外)和 `rag-worker`(消费队列,跑重活)。同一份镜像,靠入口命令区分。
- 重活(解析 PDF、切分、批 embedding)全部走 **Pulsar → worker**,HTTP 进程只做轻量校验与入队。这是本服务最重要的架构约束:**不能让 embedding 阻塞 event loop**。
- 依赖四件套:**PostgreSQL**(元数据/事件)、**Milvus**(向量)、**Redis**(事件扇出 + 健康探活)、**Pulsar**(任务队列)。另有兼容 OpenAI 协议的 LLM。
- 事件是**事件溯源**模型:所有进度先写 `rag.run_events`(带自增序号),再通过 Redis pub/sub 扇给所有 HTTP 副本,前端用 SSE 订阅并支持 `Last-Event-ID` 断点续传。
- 与主站的契约只有两样:**JWT**(RS256,主站签、本服务验)和 **HTTP**。没有共享数据库,没有共享代码。
- 最大的结构性风险:**事件序号分配不是原子的**(读 max 再写),并发下靠唯一约束报错而非自愈。

## 2. 依赖与数据归属

| 依赖 | 存什么 | 谁写 | 一致性要求 |
|---|---|---|---|
| PostgreSQL(`rag` schema) | `documents`、`document_chunks`、`conversations`、`messages`、`runs`、`run_events`、`task_sessions`、`users` | HTTP(元数据)+ worker(chunks/runs) | 强一致,事务 |
| Milvus | `rag_knowledge_chunks`:id / vector(768) / user_id / document_id / chunk_id / chunk_index | worker 双写 | `consistency_level="Strong"` |
| Redis | 事件 pub/sub 频道、健康探活 | worker 发布,HTTP 订阅 | 尽力而为(丢了靠 PG 补发) |
| Pulsar | 摄取任务队列 | HTTP 生产,worker 消费 | 至少一次(nack 重投) |
| LLM(Ollama/兼容 OpenAI) | — | HTTP 检索 + 生成,worker embedding | 无状态 |

**为什么向量放 Milvus 而不是 pgvector**:数据量上 Milvus 的 `AUTOINDEX` 与独立扩缩容更省心;代价是**双写不一致**——PG 与 Milvus 之间没有事务,只能靠"先 PG 后 Milvus + upsert 幂等"(见 02 篇 §5)。

## 3. 三条请求链路

### 3.1 文档上传(异步)

```text
Client ──POST /api/documents (multipart)──▶ rag-http
                                              │
                                              ├─ await file.read()          ← 全量入内存
                                              ├─ 校验类型/大小(10MB)
                                              ├─ 落盘 uploads/<uuid>.<ext>
                                              ├─ INSERT documents
                                              ├─ INSERT runs(status=queued)
                                              └─ Pulsar produce(job)
                                              │
Client ◀── 202 { documentId, runId } ─────────┘
                                              │
                                       ┌──────▼───────┐
                                       │ rag-worker   │
                                       │ parse → split│
                                       │ → embed ×N   │
                                       │ → PG+Milvus  │
                                       │ → run_events │
                                       └──────┬───────┘
                                              │ Redis publish
                                              ▼
                         所有 rag-http 副本 ◀── pub/sub
                                              │
Client ◀── SSE /api/runs/{id}/stream ─────────┘
```

关键点:**上传接口不等解析完成就返回 202**。10MB 的 PDF 解析 + 上千次 embedding 可能要几十秒,同步做必然超时。

### 3.2 RAG 对话(同步流式)

```text
Client ──POST /api/conversations/{id}/messages──▶ rag-http
                                                    │
                                                    ├─ 取最近 history_limit(10) 条
                                                    ├─ embed(query)            ← 一次 LLM 调用
                                                    ├─ Milvus search(user_id, top_k=6)
                                                    ├─ PG 回表拿 chunk 原文(一条 IN 查询)
                                                    ├─ 拼 prompt(带 [i] 引用编号)
                                                    └─ LLM chat_stream → SSE 逐 token 转发
```

**对话不走 worker**。它虽然也调 LLM,但是"单次、低延迟、用户正在等"的路径,入队反而增加一次调度延迟与状态管理复杂度。

### 3.3 事件流(SSE)

```text
浏览器 ──GET /api/runs/{runId}/stream──▶ rag-http
             Header: Last-Event-ID: 42   (或 ?lastEventId=42)
                                          │
                                          ├─ ① 先订阅 Redis 频道(避免补发与实时之间丢事件)
                                          ├─ ② 从 PG 读 sequence_no > 42 的历史事件补发
                                          ├─ ③ watermark = 已发出的最大序号,实时事件只发 > watermark
                                          └─ ④ 每 15s 发 ping 保活
```

**先订阅后补发**是标准做法:反过来会丢掉"补发查询与订阅建立之间"到达的事件。watermark 再去重补发与实时重叠的那部分。

## 4. 为什么必须拆 worker

Python 的 asyncio 是**单线程协作式**调度。以下操作都会卡住整个进程:

| 操作 | 卡多久 | 影响 |
|---|---|---|
| PyMuPDF 解析 10MB PDF | 数百 ms 到数秒 | 期间所有请求排队 |
| 一次性 embedding 上千 chunk | 数十秒(网络 + 模型) | 所有对话前端超时 |
| docx 的 XML 解析 | 百 ms 级 | 抖动 |

即使把这些放到 `asyncio.to_thread`,线程池也会被少数大文档占满(**无界排队**)。所以正确解法是**进程级隔离**:HTTP 进程只做"轻活",重活滚到 worker 里,worker 崩了不影响在线对话。

代价:
- 多一个进程要部署、要监控;
- 任务状态要落库(`runs` 表),不能只放内存;
- 需要队列(Pulsar),多一个必须可用的基础设施。

**但这是 RAG 类服务的必然选择**:摄取是批量的、不可预测的,对话是在线的、延迟敏感的。两者混在一个进程里,高峰期一定互相拖死。

## 5. 部署拓扑与跨仓契约

```text
                    ┌──────────── nginx (talqora) ────────────┐
  浏览器 ──/agent/──▶│ proxy_pass → agent-rag-http:3101        │
                    └───────────────┬─────────────────────────┘
                                    │ oc-shared (docker network)
                    ┌───────────────▼─────────────────────────┐
                    │ agent-rag-http   (container_name)        │
                    │   env: OAUTH_JWKS_URI=                    │
                    │     http://our-chat-biz:3007/.well-known/jwks.json
                    └───┬──────────┬──────────┬────────────────┘
                        │          │          │
                   postgres     milvus     redis/pulsar
```

**跨仓契约只有三条,全靠环境变量表达**:

| 契约 | 值 | 改一边必须改另一边 |
|---|---|---|
| 容器名 | `agent-rag-http` | talqora 的 `nginx/conf.d/default.conf` 里 `$agent_upstream` |
| 网络 | `oc-shared`(external) | 双方 compose 都要声明 |
| JWKS 地址 | `http://our-chat-biz:3007/.well-known/jwks.json` | talqora 的 biz 容器名 |

这类"容器名即接口"的约定**没有编译期检查**,改名会静默 502。已经把这条写进两仓的注释里,但真正的保障应该是部署后的健康检查(现在 `deploy.yml` 没有)。

### 5.1 健康检查

`GET /api/health`(无鉴权)并行探活 **Postgres / Redis / Milvus**(`health/router.py:19-40`),**任一不通则 `status=degraded`——但 HTTP 仍是 200**;LLM 刻意不纳入(会浪费 token)。

这两点都要理解清楚:

- **返回 200 + degraded 是"给人看"的语义**:监控系统能读到 degraded 并告警,但不会把服务判死。好处是避免了"依赖抖动 → 容器被反复重启"的雪崩。
- **代价是它不能当编排的 readiness 探针**。K8s/compose 的 healthcheck 只看状态码,200 就等于"健康",于是 Milvus 挂了、摄取全部失败,容器依然显示 `healthy`。

所以:**监控告警要看响应体里的 `status`,编排探活要另写一个只探进程存活的端点**(或让 readiness 版本在 degraded 时返回 503)。当前只有一个 `/api/health`,两种用途混在一起。

另外,并行探活意味着**最慢的那一项决定整体探活耗时**。Milvus 慢时探活本身会变慢,需要给单次 probe 设超时(否则探活变成雪崩源)。

## 6. 失败模式速查

| 现象 | 首查 | 说明 |
|---|---|---|
| 上传后一直 `queued` | Pulsar 是否可达、worker 是否在跑 | worker 挂了不会有人消费,run 永远停在 queued |
| run 卡在 `running` | worker 日志、`run_events` 最后一条 | 无 run 超时机制(见 04 篇),卡住只能人工介入 |
| 检索结果为空但文档已 ready | Milvus 是否有该 user 的点、PG chunk 是否存在 | 双写不一致或 user_id 过滤写错 |
| SSE 断线后重连丢事件 | `Last-Event-ID` 是否被正确带上 | 前端若没保存 event id,重连会从 0 重放(前端需去重) |
| 对话 502 | `$agent_upstream` 与实际容器名 | 跨仓契约漂移 |
| 启动即退出 | Milvus load 超时(60×0.5s) | `vector.py:91-107` 加载失败直接抛,不会降级 |
