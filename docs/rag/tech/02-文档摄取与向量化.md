# RAG 服务 · 文档摄取与向量化

> 架构见 [01 篇](./01-整体架构与请求链路.md)。本篇讲**一份文件怎么变成可检索的向量**,以及每一步的取舍与坑。

## 0. TL;DR

- 摄取是**异步任务**:HTTP 只负责落盘 + 建 `documents` + 建 `runs(queued)` + 入队,解析/切分/embedding 全在 worker。
- 支持 `pdf / docx / md / markdown / txt`。**没有 html、没有 OCR**——扫描件 PDF 会被明确判失败,不会静默产出空文档。
- 切分是**递归字符切分**,分隔符层级 `\n\n → \n → 空格 → 空`,默认 `chunk_size=800`、`overlap=100`。**无标题感知、无父子块**。
- Embedding 是 `nomic-embed-text`(768 维),批大小 16,**无重试、无限流**——失败由队列重投整 job 兜底。
- 双写顺序是**先 PG 拿 `chunk_id`,再 upsert Milvus**(payload 里带 `chunk_id` 供回表)。重跑前会先删旧的 PG chunk 与 Milvus 点,**这一点做对了**,重投是幂等的。
- 代价:每个 chunk 一次独立事务插入(`N+1`),上千分片的文档会产生上千次 commit。
- 已知风险:上传接口**先 `await file.read()` 全量读进内存,再校验 10MB**,绕过大小限制就能打爆内存。

## 1. 完整链路

```text
POST /api/documents
  │
  ├─① await file.read()                    router.py:54   ← 全量入内存(风险点)
  ├─② 类型白名单 + 大小校验                  service.py:65,67
  ├─③ 落盘 <upload_dir>/<uuid>.<ext>
  ├─④ INSERT documents(status=pending)
  ├─⑤ INSERT runs(status=queued, ref_id=documentId)
  └─⑥ Pulsar produce → 返回 202

worker 消费
  │
  ├─⑦ documents.status = processing
  ├─⑧ emit step:parsing
  ├─⑨ read_bytes → parse_to_text (to_thread)     ← CPU 活,必须离开 event loop
  ├─⑩ split_text(800/100)
  ├─⑪ 空分片守卫 → 直接失败(不标 ready)
  ├─⑫ emit step:chunking {chunks: N}
  ├─⑬ delete_by_document(Milvus) + clear_chunks(PG)   ← 重试幂等
  ├─⑭ for batch in chunks(16):
  │     embed(batch) → 每 chunk INSERT(PG,拿 chunk_id) → upsert(Milvus)
  │     emit step:embedding {done, total}
  └─⑮ documents.status = ready, chunk_count = N
```

失败则 `status = failed` + `error_msg`(截断 1000 字符),异常继续上抛让队列 nack 重投。

## 2. 解析:三种格式,三种实现

| 格式 | 实现 | 位置 | 说明 |
|---|---|---|---|
| PDF | **PyMuPDF**(`fitz`) | `parser.py:39-48` | 逐页 `get_text()`,纯文本提取,不含版面结构 |
| DOCX | **zipfile + ElementTree** 自解析 XML | `parser.py:60-78` | 取 `word/document.xml` 的 `w:p` 文本,**剔除 `mc:Fallback`**(否则同一段文字会出现两遍) |
| md / txt | UTF-8 解码 | `parser.py:52` | 保留 Markdown 原文(不转 HTML、不抽标题) |

两个细节值得记:

1. **`mc:Fallback` 去重是必要的**。Word 为了兼容性会把同一个对象(如图片说明、文本框)在 `mc:Choice` 和 `mc:Fallback` 里各存一份,直接遍历所有 `w:t` 会让文本重复一倍——检索时表现为"同一段话命中两次",白白占掉 top_k 名额。
2. **声明了 `python-docx` 但没用**。`pyproject.toml:18` 有这个依赖,实际解析走原生 XML。这是依赖清单腐化,会让镜像多装一个用不到的包,也让后续维护者误以为改解析应该找 `python-docx`。

**没有 OCR** 是一个明确的能力边界:扫描件 PDF、图片型 docx 会提取到空文本 → 触发 §1-⑪ 的空分片守卫 → 明确失败。**这比"标记 ready 但检索永远为空"好得多**——后者用户会以为是模型的问题。

## 3. 切分:800 字符 / 100 重叠

### 3.1 算法

递归字符切分(`splitter.py:14`),尝试顺序:

```text
先按 "\n\n"(段落)切
  └─ 单段仍超长 → 按 "\n"(行)切
       └─ 仍超长 → 按 " "(词)切
            └─ 仍超长 → 按 ""(硬切)
每片保留尾部 100 字符作为下一片的开头(overlap)
```

这是 LangChain `RecursiveCharacterTextSplitter` 的经典策略。选它而不是语义切分/标题切分的原因:**零依赖、确定性、对任何格式都能兜底**。缺点是它只认字符,不认语义——一个 800 字符的块可能从句子中间断开,也可能横跨两个不相关的小节。

### 3.2 参数取舍

| 参数 | 当前 | 偏大 | 偏小 |
|---|---|---|---|
| `chunk_size=800` 字符 | ≈ 250-400 token(中文) | 上下文完整、块数少;但检索精度下降(一个块混多个主题),且容易超 embedding 模型有效窗口 | 检索精准;但块数暴涨(存储/检索成本线性上升),且上下文被切碎 |
| `chunk_overlap=100` | 12.5% | 跨块语义连续性更好;但存储冗余增加 | 边界句子被切断,答案恰好跨边界时检索不到 |

`800/100` 是**通用默认值**,不是针对本产品语料调出来的。真实调参应该基于评测集(见 03 篇 §6),现在没有评测集,所以只能沿用默认。

### 3.3 没有父子块(需要知道的局限)

当前架构:检索粒度 = 喂给 LLM 的粒度 = 800 字符。这意味着:

- **指代丢失**:第 2 块里的"该方法"指代第 1 块的主语,单独喂给 LLM 时无法解析;
- **表格/列表被切碎**:一张跨块的表格,命中其中一块时上下文不完整;
- **无法"小检索、大喂入"**:工业界常用"子块检索、父块喂入"(small-to-big),能用小块提高召回精度,同时给 LLM 完整上下文。当前没有这一层。

不是 bug,是**未做的优化**。要做的话需要:块之间记录 `parent_id`,`document_chunks` 加一列,`retrieve` 后按 parent 聚合去重。改动不大,但需要评测集验证收益。

## 4. Embedding

| 项 | 值 | 位置 |
|---|---|---|
| 模型 | `nomic-embed-text`(可配) | `settings.py:45` |
| 维度 | 768 | `settings.py:39` |
| 批大小 | 16 | `settings.py:33`,`ingestion.py:77-81` |
| 接口 | OpenAI 兼容 `/v1/embeddings` | `llm.py` |
| 重试 | **无显式重试** | 仅 SDK 默认行为 |
| 限流 | **无** | — |

`zip(batch, vectors, strict=True)`(`ingestion.py:93`):长度不一致立刻抛错,而不是静默截断。这是个好细节——embedding 服务返回条数不对时,静默 `zip` 会让 chunk 与向量错位,**数据从此永久错乱且无法察觉**。

**批大小 16 的取舍**:太小 → 往返次数多、吞吐低;太大 → 单次请求超时风险高、失败重试代价大。16 是保守值,在本地 Ollama 上合理。

**无重试的后果**:任一 batch 失败 → 整个 job 失败 → 队列 nack 重投 → 从头解析、重新 embedding 前面已经成功的那几百个 chunk。**重试成本随文档变大而线性上升**,这也是为什么"先删旧数据再写"(§5)必须存在。

## 5. 双写与幂等

### 5.1 顺序为什么是 PG → Milvus

```text
PG INSERT chunk  → 得到自增 chunk_id
     ↓
Milvus upsert(point_id=uuid4, payload={chunk_id, document_id, user_id, chunk_index})
```

Milvus 里的主键是 `uuid4` 生成的 `point_id`(`ingestion.py:92`),`chunk_id` 放在 payload 里。为什么不用 `chunk_id` 直接当主键?

- 用 `chunk_id` 作主键 → 重跑时同 id upsert,天然幂等,**更简单**;
- 用 `uuid4` → 每次重跑生成新点,必须显式 `delete_by_document` 才不会残留。

当前选了后者,靠 §5.2 的删除保证正确性。**代价是多一次 Milvus 删除调用,以及"若删除失败则残留脏点"的风险窗口**。这是一个可以简化的地方。

### 5.2 重试幂等:先删后写

```python
await self._vector.delete_by_document(document_id)   # Milvus
await self._clear_chunks(document_id)                # PG
```

注释写得很清楚:"重试幂等:开写前清掉本文档可能残留的两边旧数据"(`ingestion.py:72`)。**这一步做对了**,否则重投会产生重复 chunk:PG 里两份、Milvus 里两份,检索时同一段话命中两次,top_k 实际有效槽位减半。

顺序也重要:先删向量再删 PG。反过来的话,若删除 Milvus 失败,PG 已删、向量还在 → 检索命中后回表拿不到原文(代码里 `if row is None: continue` 会跳过,`retrieval.py:66`),表现为"检索结果莫名变少"。

### 5.3 代价:N+1 写入

```python
for content, vector in zip(batch, vectors):
    chunk_id = await self._create_chunk(...)   # 每 chunk 一个事务
```

`_create_chunk`(`ingestion.py:154-175`)每次独立提交。一份 10MB 文档切出 2000 片 → **2000 次 commit**。在本地 PG 上约几十毫秒到几百毫秒一次,累计几十秒到几分钟。

正确做法是批量 `INSERT ... VALUES (...),(...)` 再统一取回 id(`RETURNING`),把事务数从 N 降到 N/16。**这是当前摄取吞吐最大的单点瓶颈**,但只在"大文档"路径上才明显。

## 6. 失败与边界

| 场景 | 当前行为 | 是否合理 |
|---|---|---|
| 空文档 / 扫描件 PDF | 明确失败:"未提取到任何文本" | ✅ 好 |
| 超过 10MB | 拒绝 | ⚠️ 但已先读进内存(见下) |
| 不支持的扩展名 | 拒绝 | ✅ |
| Embedding 中途失败 | 整 job 失败 → 重投 → 先删后重写 | ⚠️ 幂等但对大文档成本高 |
| `runs` 创建失败 | **残留孤儿文件 + Document 行** | ❌ 无补偿事务 |
| worker 崩溃在双写中途 | 文档 stuck 在 `processing`,无超时自愈 | ❌ 需人工介入 |

### 6.1 上传先读全量,再校验大小

```python
data = await file.read()          # router.py:54  ← 无上限
...
if len(data) > settings.document_max_bytes:   # service.py:67  ← 才校验
```

`UploadFile` 的 `read()` 会把整个请求体读进内存(超出阈值才落临时文件,但 `read()` 仍然是一次性拿到全部字节)。攻击者发一个 2GB 的文件,进程在"校验"之前就已经 OOM。

修复方式(按侵入性排序):
1. 分块读 + 累计计数,超限立即中断并清理;
2. 用 `Content-Length` 预检(可伪造,只能当第一道);
3. 在 nginx 加 `client_max_body_size`(**当前 talqora 的 nginx 配置里没有这一项**,意味着代理层完全不设限)。

第 3 条最省事且能挡住绝大多数情况,但它不是应用层的正确性保证。**两层都该有。**

### 6.2 孤儿资源

`service.py:73-93` 的顺序是:落盘 → 建 Document → 建 Run。若建 Run 失败,前两步不回滚 → 磁盘上有文件、PG 里有一条永远 `pending` 的 Document,没有任何 run 会处理它。

修复:用一个事务包住 Document + Run(它们在同一 PG 里),失败时删文件。落盘本身无法参与事务,所以"先建记录再落盘"或"失败即删文件"必须二选一,当前两者都没做。

## 7. 可观测性缺口

现有进度事件只覆盖"阶段"(parsing/chunking/embedding),缺少:

- **每阶段的耗时**(现在只能靠日志时间戳反推);
- **embedding 的实际吞吐**(chunks/s)与失败次数;
- **文档总字符数 vs 分片数**,看不出切分是否合理;
- **Milvus 写入耗时**,双写里最慢的一步常常是它。

这些指标在"大文档摄取慢"的问题上几乎是唯一的定位依据。当前只能:①看 `run_events` 的 `created_at` 间隔;②worker 日志。够用,但不够快。

## 8. 改进优先级

| 优先级 | 事项 | 收益 |
|---|---|---|
| P0 | 上传分块读 + nginx `client_max_body_size` | 消除 OOM 面 |
| P1 | chunk 批量插入(单事务 + RETURNING) | 大文档摄取从分钟级降到十秒级 |
| P1 | Milvus 主键改 `chunk_id` | 去掉 delete-then-write 的窗口 |
| P2 | embedding 失败按 batch 重试(指数退避) | 避免整文档重跑 |
| P2 | Document + Run 同事务 + 失败删文件 | 消除孤儿 |
| P3 | 父子块(small-to-big) | 检索精度与上下文完整性同时提升,**需先有评测集** |
| P3 | 标题感知切分(Markdown 按 `#` 分节) | 对 md 语料明显更好 |
