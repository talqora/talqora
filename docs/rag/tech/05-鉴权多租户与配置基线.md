# RAG 服务 · 鉴权、多租户与配置基线

> 架构见 [01 篇](./01-整体架构与请求链路.md)。本篇讲**谁在调用、数据怎么隔离、哪些配置一旦写错就是事故**。

## 0. TL;DR

- 本服务**不是 IdP**,只验签:主站(biz)签发 RS256 token,本服务用其 JWKS 验签。`audience="agent-server"`。
- 但保留了 **HS256 兜底**分支(本地注册/登录签发的 token),按 `header.alg` 分发。**这条兜底路径不校验 `iss`/`aud`**——只要拿到 `JWT_SECRET` 就能自签任意 `sub` 冒充他人。生产靠一个"弱密钥拒绝"校验兜住,而该校验**只在 `env == "production"` 时生效**,`env` 默认却是 `development`。
- 多租户靠**一个字段 `user_id`** 贯穿三层:JWT → 每个查询 → Milvus filter。向量层把 filter **写死在唯一出口**(`vector.py:137`),这是最有效的防漏方式。
- token 允许走 `?access_token=`:不是偷懒,是 **EventSource 无法设置请求头**。
- 配置里最危险的三项:`JWT_SECRET`(默认 `dev-secret`)、`ENV`(默认 development)、`CORS_ORIGINS`(留空时 dev 反射任意 origin)。

## 1. 双模 JWT:为什么有两个,风险在哪

### 1.1 分发逻辑

```python
header = jwt.get_unverified_header(token)      # auth.py:74
alg = header.get("alg")
if   alg == "RS256": payload = self._verify_rs256(token)
elif alg == "HS256": payload = self._verify_hs256(token)
else:                raise UnauthorizedError(f"不支持的 alg: {alg}")
```

**先看未验签的 header 决定用哪套校验**,这是 JWT 库的标准做法(必须这么做,否则不知道该用哪个密钥)。风险在于:**`alg` 由攻击者控制**。这里虽然写死了白名单(只接受两种,不会退化成 `none`),但两条路径的严格程度不同:

| | RS256(主路径) | HS256(兜底) |
|---|---|---|
| 密钥 | JWKS 公钥(主站私钥签) | 共享 `JWT_SECRET` |
| `audience` | ✅ 校验 `agent-server` | ❌ **不校验** |
| `issuer` | ✅ 校验 | ❌ **不校验** |
| `exp` / `sub` | ✅ require | ✅ require |
| 时钟容差 | 30s | 30s |

后果:任何**知道 `JWT_SECRET`** 的人,都能自签一个 `{"sub": "任意用户", "exp": ...}` 的 HS256 token,直接访问任意用户的知识库。而 RS256 路径看起来完全正常,**问题只在被利用时暴露**。

### 1.2 为什么会存在这条路径

本地开发/单机部署时没有完整的 OAuth 体系,`/api/auth/register` 与 `/api/auth/login` 直接签发 HS256 token,让人能跑起来。这个需求是合理的,但它把"共享密钥"这一弱环节带进了生产架构。

### 1.3 生产环境的护栏(以及它的漏洞)

```python
if self.env != "production":
    return self                     # ← 关键:非 production 直接放行
if len(secret) < 32 or secret in _DEV_JWT_SECRETS:
    raise ValueError("生产环境 JWT_SECRET 缺失或过弱...")
```

护栏本身写得不错(长度 + 已知弱值黑名单,并给出 `openssl rand -hex 32` 的指引)。**漏洞在于 `env` 默认是 `development`**:

> 部署时忘了设 `ENV=production` → 护栏静默失效 → `dev-secret` 照用 → 任何人都能自签 token。

这类"安全开关默认为关"的设计是典型的 fail-open。**应该反过来**:不认识的环境名一律按 production 处理,只有显式 `ENV=development` 才放行。或者干脆去掉 HS256 分支(生产只留 RS256),把本地登录也改成签 RS256(用同一把私钥)。

### 1.4 建议

| 优先级 | 措施 |
|---|---|
| P0 | HS256 分支补齐 `audience`/`issuer` 校验(与 RS256 一致) |
| P0 | `env` 的默认值改为 `production`,或对未知值按 production 处理 |
| P1 | 生产构建里直接移除 `/api/auth/register`、`/api/auth/login`(只需要验签,不需要自己发 token) |
| P2 | 记录/告警 HS256 路径的使用量:生产里它应该恒为 0 |

## 2. token 怎么传:为什么允许 query

```python
Authorization: Bearer <token>     ← 常规
?access_token=<token>             ← SSE / EventSource
```

`deps.py:43-51` 两种都收。第二种的必要性:**浏览器原生 `EventSource` 不能设置请求头**。SSE 端点(`/api/runs/{id}/stream`)只能把 token 放 URL。

代价必须知道:

- token 会出现在**访问日志、浏览器历史、Referer、代理日志**里;
- 有效期 2h(`jwt_expire_seconds=7200`),泄漏窗口不小。

缓解措施(当前都没有):

1. 对 `access_token` 这类查询参数在日志里打码;
2. 为 SSE 单独签发**短时效(1-5 分钟)、单用途(仅 stream)**的 token;
3. 或者改用 fetch + ReadableStream 消费 SSE(可以带 header),代价是自己实现重连与 `Last-Event-ID`。

## 3. 联邦身份:外部 issuer 怎么映射到本地用户

token 里的 `iss` 决定身份归属:

```text
iss == 本服务配置的 issuer   → 本地用户(sub 即 user_id)
iss 为其它受信 issuer        → 联邦身份:(issuer, subject) → 查/建本地用户
```

`federated.py:48-66` 的处理值得一记:**并发首见靠唯一约束 + 回滚回查**。

```text
两个并发请求同时首次见到 (iss, sub)
  → 都尝试 INSERT
  → 一个成功,一个 IntegrityError
  → 捕获后回查已存在的行
```

这是"用数据库约束解决并发去重"的标准写法,比先查后插更可靠(先查后插在并发下会双建)。**代价是必须捕获特定异常并回查**,不能简单吞掉。

## 4. 多租户:三道闸

```text
① 入口:JWT 验签 → TokenClaims.sub → user_id
        ↓
② 业务层:每个 service 显式带 user_id 条件
   documents/service.py:112   doc.user_id != user_id → 拒绝
   conversations/service.py:43 ensure_owned
        ↓
③ 向量层:filter 写死在唯一出口
   vector.py:137  filter=f"user_id == {user_id}"
```

**第 ③ 道是关键设计**。`retrieval.py` 开头的注释把纪律写死了:

> 检索只能走这里,且只经 `vector.search_by_user(user_id 过滤写死在 agent-core 那一层)。禁止任何 router/service 自己拼 Milvus filter——从代码结构上杜绝漏过滤导致的越权泄露。

这种"把安全检查下沉到唯一出口、让上层**没有能力**写错"的模式,比"每个调用点记得加条件"可靠得多。同类的成功案例还有:系统里 `IsConversationMember` 的集中校验(虽然它在消息链路上漏用了,见体检文档)。

**但要注意第 ② 道的不一致**:PG 侧靠每个 service 自己记得加条件,没有统一拦截。任何新写的 service 忘了带 `user_id`,就是一个越权。改进方向:在 repository 基类里强制 `user_id` 参数,或引入行级安全(RLS)。

### 4.1 免鉴权端点

| 端点 | 为什么可以公开 |
|---|---|
| `GET /api/health` | 探活,不含数据 |
| `POST /api/auth/register` | 注册入口 |
| `POST /api/auth/login` | 登录入口 |

除这三个,所有 router 都挂了鉴权依赖。**新增端点时必须显式声明**——FastAPI 的依赖是逐路由声明的,漏写就是公开端点。建议加一条测试:遍历 `app.routes`,断言除白名单外全部需要鉴权。这类测试比人工 review 可靠。

## 5. 配置基线

### 5.1 必填与关键项

| 配置 | 默认 | 说明 |
|---|---|---|
| `DATABASE_URL` | **必填** | `postgresql+asyncpg://` |
| `REDIS_URL` | `redis://localhost:6380` | 注意不是 6379 |
| `PULSAR_URL` | `pulsar://localhost:6650` | |
| `MILVUS_ADDRESS` | `localhost:19530` | 无 scheme 会自动补 `http://` |
| `MILVUS_COLLECTION` | `rag_knowledge_chunks` | |
| `MILVUS_VECTOR_SIZE` | 768 | **改 embedding 模型必须同步改**,否则写入报维度错误 |
| `OAUTH_ISSUER` / `OAUTH_JWKS_URI` | `""` | 空则 RS256 不可用 |
| `JWT_SECRET` | **`dev-secret`** | ⚠️ 危险默认 |
| `ENV` | **`development`** | ⚠️ 决定上面那个护栏是否生效 |
| `CORS_ORIGINS` | `""` | 空:dev 反射任意 origin,生产拒绝所有跨源 |

### 5.2 业务参数

| 配置 | 默认 | 调大 | 调小 |
|---|---|---|---|
| `CHUNK_SIZE` | 800 | 上下文完整,检索精度下降 | 精度高,块数暴涨 |
| `CHUNK_OVERLAP` | 100 | 跨块连续性好,冗余高 | 边界断句 |
| `EMBED_BATCH` | 16 | 吞吐高,单请求超时风险高 | 往返多 |
| `RAG_TOP_K` | 6(接口允许 1-20) | 召回高,噪声与 prompt 长度上升 | 可能漏 |
| `HISTORY_LIMIT` | 10(条数,非轮次) | 上下文完整,token 压力大 | 多轮指代丢失 |
| `AGENT_MAX_ITERATIONS` | 8 | 复杂任务更强,成本与延迟上升 | 复杂任务被截断 |
| `LLM_TIMEOUT_SECONDS` | 120 | 慢模型可用 | 快速失败 |
| `DOCUMENT_MAX_BYTES` | 10MB | 大文档可传,内存压力 | — |

### 5.3 连接与超时

| 项 | 现状 | 风险 |
|---|---|---|
| PG 连接池 | **只设了 `pool_pre_ping=True`**,未设 `pool_size`/`max_overflow` | 走默认 5+10,高并发下排队;无 `statement_timeout`,慢查询可长期占连接 |
| Redis | 仅 pub/sub 与健康探活 | 无连接池配置需求 |
| Milvus | 启动时 `load_collection` 轮询 60×0.5s,超时抛错 | **不可达则启动失败**,无降级 |
| LLM | `AsyncOpenAI(timeout=120s)`,未设 `max_retries` | 用 SDK 默认 2 次重试,无 fallback 模型 |

## 6. 生产部署 checklist

- [ ] `ENV=production`(把护栏打开)
- [ ] `JWT_SECRET` ≥32 字符且与 biz 一致(`openssl rand -hex 32`)
- [ ] `OAUTH_ISSUER` / `OAUTH_JWKS_URI` 指向 `http://our-chat-biz:3007`,且 `/api/health` 之外能实际验过一枚真实 token
- [ ] `CORS_ORIGINS` 显式列出前端 origin(不要留空)
- [ ] 确认 `/api/auth/register`、`/api/auth/login` 已下线或不可达
- [ ] `MILVUS_VECTOR_SIZE` 与实际 embedding 模型维度一致
- [ ] nginx 侧 `/agent/` 的 `client_max_body_size` 已设置(当前 talqora 侧**没有**这一项)
- [ ] PG 连接池与 `statement_timeout` 已按并发量显式配置
- [ ] 日志里已对 `access_token` 查询参数打码

## 7. 跨仓契约(改一边必须改另一边)

| 契约 | 本仓取值 | 对端位置 |
|---|---|---|
| 容器名 | `agent-rag-http` | talqora `nginx/conf.d/default.conf` 的 `$agent_upstream` |
| 网络 | `oc-shared`(external) | 双方 compose 声明 |
| JWKS 地址 | `http://our-chat-biz:3007/.well-known/jwks.json` | talqora 的 biz 容器名 |
| JWT `audience` | `agent-server` | biz 签发时的 `aud` |
| JWT `JWT_SECRET` | 环境变量 | biz 的同一变量 |

前三项**没有任何编译期或运行期校验**,改名会在运行时表现为 401/502。唯一可靠的防线是部署后的端到端冒烟:拿一枚真实 token 打 `/api/conversations`,而不是只看 `/api/health`(健康检查不验鉴权链路)。

---

## 8. 一句话总结

**鉴权的强度不取决于"有没有验签",而取决于最弱的那条分支。** RS256 + JWKS 做得再规范,只要 HS256 兜底还留着 `dev-secret`、且护栏靠一个默认值兜底,整体安全性就等于 `dev-secret`。
