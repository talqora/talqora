# 直播模块分析：为什么做成独立微服务

> 本文回答三个问题：
> 1. 直播功能由哪些部分组成，哪些值得自己做、哪些应该用现成组件？
> 2. 为什么把它做成独立的 live 服务，而不是放进 biz？代价是什么？
> 3. 对项目和面试有什么价值，范围怎么控制？
>
> 架构设计、协议、任务与实验见 [02-规划-架构设计与开发计划](./02-规划-架构设计与开发计划.md)。

## 0 一段话讲清

直播是「一个人推流、很多人观看、观众实时互动」的功能，技术上分成两个面：

- **媒体面**：把主播的音视频推上来、再分发给观众。
- **互动面**：直播间状态、弹幕、在线人数、礼物、榜单、PK。

媒体面是音视频工程的专业领域，用成熟的开源媒体服务器即可，不值得自研。后端能力集中体现在互动面：一个热门直播间可能有 5 万观众，每秒 5000 条弹幕；礼物涉及真实的扣费；PK 的分数与倒计时是常驻内存的状态，服务节点挂掉也不能丢。

这些特征与 IM 正好相反：IM 是一对一、小群，每条消息必达，业务层无状态。把两种负载混在一个服务里，限流、降级、背压策略会互相干扰。所以直播做成独立的 live 服务：它通过钱包接口扣费，通过网关推送，用租约管理房间归属。

对面试来说，它补齐了 IM 项目里没有的三件事：**热点一对多扇出、可覆盖语义、跨服务的资金一致性**。

## 1 直播功能拆解

| 子功能 | 技术本质 | 自己做还是用现成 | 理由 |
|---|---|---|---|
| 推流（主播端上传音视频） | 音视频采集、编码、传输协议（RTMP、WebRTC 的 WHIP） | 用现成：OBS 或浏览器 WHIP，加开源媒体服务器 | 编解码与传输是专门领域；自研没有后端展示价值，调试成本极高 |
| 分发与播放 | 转封装、分发协议（HTTP-FLV、HLS、WebRTC 的 WHEP）、CDN | 用现成：媒体服务器直出，web 端用 hls.js 或 mpegts.js 播放 | 同上 |
| 开播鉴权 | 推流密钥校验、开播与下播状态 | **自己做**：媒体服务器回调 live 服务 | 业务规则：谁能开播、直播间状态归谁管 |
| 直播间与进房 | 房间生命周期、首屏数据、订阅关系 | **自己做** | 有状态服务与订阅路由 |
| 弹幕 | 高频上行、聚合、抽样、热点扇出 | **自己做** | 本模块的核心技术点 |
| 在线人数与热度 | 近似计数、周期上报 | **自己做** | 分布式计数，允许近似 |
| 礼物 | 扣费、计分、播报 | **自己做**，钱只在钱包 | 跨服务的资金一致性 |
| 贡献榜 | 排行榜 | **自己做**（Redis 有序集合） | 派生数据，可以从账本重建 |
| PK | 两个直播间的计分对决、倒计时结算 | **自己做** | 有状态，节点故障下不能丢分 |
| 连麦（主播之间的视频合流） | 媒体合流、SFU（选择性转发单元，只转发、不转码的多方媒体服务器） | **不做** | 媒体面工作量巨大，PK 只做计分对决 |
| 转码集群、CDN、美颜、推荐 | 媒体处理与推荐算法 | **不做** | 不在后端求职的能力范围内 |

## 2 直播与 IM 的负载对比

把两种负载放在一起比较，就能看出为什么不能共用一套策略：

| 维度 | IM（现有 biz） | 直播互动（live） |
|---|---|---|
| 流量形态 | 一对一、小群；扇出范围小 | 一对多热点：一个房间 5 万观众 |
| 下行语义 | **可靠消息**：每条都要送达、持久化、有序，断线后按 seq 补拉 | **可覆盖状态**：每 200 毫秒一帧房间快照，新帧覆盖旧帧，慢观众丢帧无害 |
| 上行处理 | 每条消息落库、发号、去重 | 弹幕高频且允许抽样：每秒 5000 条进来，每个观众每秒只需看到十几条 |
| 状态模型 | 无状态多副本，状态外置到 PG 与 Redis | 有状态：房间的在线人数、热度、PK 分数与倒计时常驻某个节点的内存 |
| 慢连接策略 | 只能限流或断开重连，不能丢消息 | 跳过旧帧即可，不应因为跟不上就被踢掉 |
| 一致性要求 | 消息不重不丢 | 弹幕允许丢；礼物与 PK 分数必须精确，且以钱包为准 |
| 扩缩容维度 | 消息量、会话数 | 热门房间数、单房间观众数 |
| 故障影响 | 影响所有用户的基础通信 | 影响正在看直播的用户 |

**下行语义的差别最根本。** 网关现在给每个连接配了一条容量 256 的有界下行队列，写满就把连接当慢消费者踢掉。这对 IM 是对的：可靠消息宁可断开重连、再按 seq 补拉，也不能悄悄丢掉。但对直播是错的：热门房间的观众只要网络稍慢，几秒内就会攒满 256 帧被踢，重连后再被踢，形成振荡。直播需要的是「每个连接只保留最新一帧」的覆盖槽位。

## 3 为什么做成独立服务

### 3.1 四个理由

1. **故障隔离（舱壁）。** 热门直播的弹幕洪峰会占满 CPU、Redis 和连接，不应拖垮 IM 的发消息主链路。独立服务有独立的进程、资源上限和限流。洪峰最坏只影响直播，聊天照常可用。
2. **独立扩缩容。** 直播的负载由热门房间决定，波动大、峰值集中在开播时段；IM 的负载由日常消息量决定，相对平稳。拆开后，可以只为直播加实例。
3. **状态模型不同。** biz 是无状态多副本，任意副本处理任意请求；live 的房间是有状态的，每个房间同一时刻只能由一个实例持有。如果让同一个服务同时承担两种模型，部署、发布、故障接管的策略都要分两套，复杂度不降反升。
4. **发布节奏独立。** 直播功能迭代快，而 IM 主链路要求稳定。拆开后，发布 live 不需要重启 biz，也不影响长连接。

### 3.2 代价

| 代价 | 具体表现 | 应对 |
|---|---|---|
| 跨服务鉴权 | live 要识别用户身份 | WebSocket 帧经网关转发，网关已验签并附上 user_id；HTTP 接口用业务层 IdP 签发、aud 为 live 的 RS256 令牌，live 用 JWKS 公钥验签，与 agent-server 的做法一致 |
| 跨服务一致性 | 送礼的扣费在钱包，计分在 live | 钱的事实只在钱包；live 的分数是从钱包事实派生的计算结果，宕机后从账本重放（02 规划 5.6 节） |
| 运维复杂度 | 多一个服务、一个媒体服务器、一套部署与监控 | 复用现有的 compose、Prometheus 与告警体系；live 的指标纳入权威面板 |
| 网络跳数 | 弹幕上行多经过一次路由 | 网关按帧类型直接路由到 live，不经过 biz 中转 |
| 开发量 | 约 48 小时（3 月前 22 小时，其余在面试季） | 分期交付，每期都可独立演示（02 规划第 7 节） |

### 3.3 方案对比

| 维度 | A：放进 biz 作为模块 | **B：独立 live 服务（推荐）** | C：用云直播加 IM SDK | D：每个房间一个进程 |
|---|---|---|---|---|
| 故障隔离 | 差：洪峰直接冲击 IM | 好 | 好，由厂商负责 | 最好 |
| 扩缩容 | 只能整体扩 | 按直播负载单独扩 | 厂商负责 | 按房间扩，需要调度系统 |
| 状态与归属 | 与无状态模型冲突 | 房间租约，复用发号模块的租约包 | 无 | 进程即归属，需要 Agones 这类房间调度 |
| 资金一致性 | 同库事务，最简单 | 钱包接口加派生计算 | 厂商的打赏系统，看不到内部 | 同 B |
| 开发量 | 小 | 中 | 最小，但要付费 | 大 |
| 面试价值 | 低：只是又一个业务模块 | **高**：服务边界、热点扇出、有状态归属、跨服务资金一致性 | 很低：调用 SDK | 高，但超出时间预算 |
| 选错的代价 | 一场热门直播拖垮聊天；两种状态模型缠在一起，后续难拆 | 多维护一个服务 | 没有可讲的后端工作；按量付费 | 时间预算翻倍，主线模块被挤掉 |

选 B。A 看似省事，但「直播洪峰拖垮聊天」恰恰是面试官会追问的故障场景，而 A 回答不了；D 是游戏房间服的做法，对直播间这种生命周期长、数量多的房间来说过重。

## 4 边界划分

数据和职责各归一处，是微服务不变成「分布式单体」的前提：

| 组件 | 负责 | 不负责 | 持有的数据 |
|---|---|---|---|
| 媒体服务器 | 收推流、转封装、分发播放流 | 任何业务规则；开播与否通过回调问 live | 无持久业务数据 |
| live 服务 | 直播间与场次、推流密钥、房间状态（在线人数、热度、PK）、弹幕处理、礼物下单与播报、贡献榜 | 钱；用户资料；长连接 | PG 的 `live` schema；Redis 的 `live:` 前缀 |
| biz（钱包） | 扣费、入账、礼物支付记录、钱包事件 | 直播间状态与计分 | 钱包账本（唯一事实来源） |
| 网关 | 长连接、验签、按帧类型路由上行、按房间扇出下行 | 弹幕内容的业务处理 | 只有内存里的连接与房间订阅表 |

禁止跨服务读表：live 需要礼物支付记录时，调用钱包的 ListGiftPayments 接口，而不是直接查 biz 的库。

## 5 媒体服务器选型

| 维度 | **SRS（推荐）** | MediaMTX | LiveKit | 云直播服务 |
|---|---|---|---|---|
| 语言与许可证 | C++，MIT（待复核） | Go，MIT（待复核） | Go，Apache-2.0（待复核） | 商业 |
| 推流 | RTMP、WebRTC（WHIP）、SRT | RTMP、RTSP、WebRTC、SRT | WebRTC；RTMP 与 WHIP 需要单独的 ingress 组件 | RTMP 等 |
| 播放 | HTTP-FLV、HLS、WebRTC | HLS、WebRTC、RTSP | WebRTC | CDN 分发 |
| 业务回调 | on_publish、on_unpublish、on_play 等 HTTP 回调 | HTTP 鉴权钩子 | Webhook | 控制台加回调 |
| 适合的场景 | 一对多直播，国内资料多 | 轻量部署、协议转换 | 互动连麦、多人会议 | 不想运维 |
| 选错的代价 | — | 回调与集群能力较弱，直播间多起来后要换 | 为一对多直播引入 SFU 与房间模型，组件多、调试重 | 按量付费，后端工作被厂商吃掉 |

选 SRS，因为它原生支持「主播 RTMP 或 WHIP 推流、观众 HTTP-FLV 或 HLS 播放」这条一对多链路，并且用 HTTP 回调把开播鉴权交给业务服务，正好让 live 掌握直播间状态。播放协议默认用 HTTP-FLV（典型延迟约 1–3 秒），HLS 作为兼容兜底（典型延迟 5 秒以上），WebRTC 播放作为低延迟的可选项。延迟数字是常见量级，以实测为准（待复核）。

为什么不复用现有的通话链路：现有音视频通话是 WebRTC 点对点，加 coturn 中继。点对点在多人观看时要退化成网状结构，主播的上行带宽随观众数线性增长，不可能支撑一对多。

## 7 面试效果

这个模块能支撑的面试故事，每一个都对应一组可测量的证据：

| 故事 | 面试官可能的追问 | 用什么证据回答 |
|---|---|---|
| 热点直播间的扇出 | 5 万人的房间怎么推？带宽算过吗？慢观众怎么办？ | 两级扇出加按房间订阅；先算带宽再压测；覆盖槽位与逐条推送的对照数据 |
| 可覆盖与可靠两种语义 | IM 为什么不能丢、弹幕为什么能丢？两者在网关里怎么共存？ | 两条下行通道的设计与实验 |
| 有状态房间的归属 | 持有房间的节点挂了怎么办？两个节点都以为自己持有房间怎么办？ | 租约加两层隔离；kill 属主的实验数据 |
| 跨服务的资金一致性 | 扣了钱但没计分怎么办？计分重复怎么办？为什么不用分布式事务？ | 钱只在钱包；按订单号幂等；从账本重放；故障注入后三方对账为零 |
| 服务边界 | 为什么拆？拆的代价是什么？什么情况下不该拆？ | 本文第 3 节的对比与取舍 |

大多数学生项目只有「无状态服务加缓存」。同时拿出「有状态归属、资金一致性、热点扇出」三件事并有实验数据，在后端面试里区分度很高。

## 8 范围控制与风险

**3 月 7 日前只做 L0 到 L2**：房间与播放、弹幕与在线人数、礼物与贡献榜，共 22 小时。PK、房间高可用、排空与完整压测放到面试季（02 规划第 7 节）。

| 风险 | 应对 |
|---|---|
| 时间被直播挤占，主线模块做不完 | 直播排在发号、可观测、红包之后；进度落后时整个直播模块顺延到面试季，不影响其他模块 |
| 媒体调试耗时：推流协议、HTTPS、防火墙、UDP 端口 | 先用 OBS 推 RTMP、web 播 HTTP-FLV 打通最短链路；WHIP 与 WebRTC 播放作为可选项 |
| 压测带宽不够 | 只压互动面，媒体面只做功能验证；压测前先算带宽，规模按测试网络能承受的上限定，再用容量模型外推（02 规划 8.1 节） |
| 范围膨胀：连麦、美颜、回放 | 第 1 节「不做」清单写死 |

## ★ 关键理解点

- **正向：直播的后端价值在互动面，不在媒体面。** 媒体服务器负责「把视频送到」，live 服务负责「直播间里发生的一切」。前者用现成组件，后者自己做，并用实验证明。
- **反向：用 IM 的策略对待直播会出事。** 用有界可靠队列推弹幕，慢观众会被反复踢掉；每条弹幕都落库，数据库会被洪峰打满；把 PK 分数只放在内存里，节点一挂分数就没了。
- **边界：live 不碰钱。** 礼物扣费的事实只在钱包，live 的分数和榜单都是派生数据，可以随时从账本重建。这条边界让跨服务的一致性问题退化成「按订单号幂等加重放」，不需要分布式事务。
- **对比：拆服务与拆模块。** 如果两种负载的语义、状态模型、扩缩容维度都一样，拆成服务只会增加网络跳数和运维成本；正因为直播与 IM 在这三点上都相反，拆开才有收益。判断要不要拆，看的是负载性质是否不同，而不是功能是否不同。
