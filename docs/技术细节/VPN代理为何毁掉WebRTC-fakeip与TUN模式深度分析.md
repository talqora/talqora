# VPN / 代理为什么会毁掉 WebRTC 音视频(fake-ip / TUN 模式深度分析)

> 背景:自建 coturn 三层配置问题(配额 486 / 黑名单 403 / 端口段 508)全部修完、服务端 verbose 日志确认干净后,异网络通话**仍**建不起来、媒体严格单向。进一步看两端交换的 ICE 候选,发现里面全是 `198.18.0.1`、`10.0.0.5` 这类"死地址"——**测试机开着 VPN/科学上网(TUN + fake-ip 模式),它从根上搞坏了 WebRTC**。
>
> 本文解释这个机制、给出判定与规避方法。排障全过程见 [`docs/debug/音视频异网络打不通-WebRTC与自建TURN完整排障复盘.md`](../debug/音视频异网络打不通-WebRTC与自建TURN完整排障复盘.md)。

---

## 0. 摘要(TL;DR)

- **现象**:服务端 TURN 已完全正常,通话仍不通、媒体单向。
- **根因**:测试机在跑 VPN/代理(Clash/Surge/Shadowrocket 之类)的 **TUN + fake-ip 模式**。
- **三条致命机制**:
  1. **垃圾 host 候选**:TUN 虚拟网卡的 IP(`198.18.x`、`10.x`)被浏览器当 host 候选塞给对端 → 全是不可路由的死地址。
  2. **srflx 失真**:发往 STUN 的探测包经代理出口 → 反射回来的"公网地址"是代理的,不是你真实网络出口 → 对端按它发,发不到你。
  3. **UDP 媒体被 TUN 吞掉(最致命)**:WebRTC 媒体是持续 UDP 流,被灌进 TUN 后,代理对 UDP 的转发普遍残缺 → 媒体半通/断流。
- **判定**:`chrome://webrtc-internals` 里出现 `198.18.x`/`10.x` 候选、或 STUN 反射地址不是你真实公网 → 有 VPN 在作祟。
- **规避**:**测 WebRTC 一律两端都关 VPN/系统代理/TUN**(含手机端代理 App)。

## 1. 触发场景与证据

排 coturn 时,verbose 日志里某端为对端候选建的 permission 是:

```
peer 169.254.254.95   ← 链路本地(APIPA / iOS)
peer 172.16.212.77    ← 运营商私网
peer 198.18.0.1       ← ⚠ VPN/代理 fake-ip
peer 10.0.0.5         ← ⚠ 私网(虚拟网卡 / 可能 coturn 同段)
peer 106.37.222.98    ← 唯一可路由的公网 srflx
```

外加一个旁证:更早从本机直接探测 coturn 的 STUN(`stun:tujiang.tech:3478`),**响应源地址是 `198.18.3.113`**——不是 coturn 的真实公网 `115.159.224.210`,说明这台机器的流量被代理接管、经 fake-ip 回来了。

> `198.18.0.0/15` 是 RFC 2544 定义的**基准测试专用段**,公网上不会出现;Clash/Surge 等代理的 **fake-ip 模式**正是借用 `198.18.0.0/16` 给域名发假 IP。看到它 = 有代理。

## 2. 前置概念(读者不必另开搜索)

### 2.1 ICE 候选是怎么"收集"出来的

WebRTC 建连前,浏览器要凑齐三类**候选地址(candidate)**:

- **host**:**枚举本机所有网络接口,每个接口的 IP 各生成一个 host 候选**。有线网卡、WiFi、**以及 VPN 建的虚拟网卡(TUN/TAP)**,统统算进去。
- **srflx**(server-reflexive):向 STUN 服务器发探测,STUN 把"它看到的你的公网 IP:端口"回给你。
- **relay**:向 TURN 申请一个中继地址。

> 关键:**host 候选来自"本机网卡列表",VPN 一开就多出虚拟网卡,它的 IP 就被当成一条 host 候选塞进 SDP、发给对端**。浏览器不知道这块网卡是"假的"。

### 2.2 代理的三种工作方式(重点是第三种)

| 方式 | 怎么工作 | 对 WebRTC 的影响 |
|---|---|---|
| 系统 HTTP 代理 | 只代理 HTTP(S),应用需显式走它 | 一般不碰 WebRTC 的 UDP,影响小 |
| SOCKS5 | 可代理 TCP,UDP 靠 `UDP ASSOCIATE`(很多客户端/节点不完整支持) | UDP 常半残 |
| **TUN + fake-ip**(现在主流"全局模式") | **建一块虚拟网卡接管默认路由**,DNS 用 fake-ip 拦截,所有流量灌进 TUN 再由代理转发 | **从根上影响 WebRTC:多虚拟网卡候选 + srflx 失真 + UDP 被吞** |

### 2.3 fake-ip DNS 是什么

代理拦截你的 DNS 查询,对每个域名**不返回真实 IP,而是返回一个 `198.18.x.x` 的假 IP**,再把发往这个假 IP 的流量按域名规则路由到代理节点。好处是无需等真实解析、分流灵活;副作用是**本机凭空多了一张 `198.18.x` 的虚拟网卡与一堆假地址**。

### 2.4 WebRTC 媒体是 UDP,而代理最不擅长 UDP

信令(SDP/ICE 交换)走你的 Socket.io(TCP/WebSocket),**不受影响**;但**媒体(RTP 音视频流)是持续的 UDP**,TURN 的 relay 分配与中继也主要走 UDP。代理体系(尤其 TCP 型节点、或 UDP 支持残缺的实现)**转发 UDP 时丢包、乱序、甚至完全不通**——这正好砸在 WebRTC 最依赖的那条路上。

## 3. 三条致命机制(逐条剖析)

### 3.1 垃圾 host 候选:把死地址塞进 ICE

- TUN 虚拟网卡 IP(`198.18.0.1`)、代理/容器虚拟段(`10.x`)被浏览器枚举成 host 候选。
- 通过信令发给对端后,对端老老实实对每个候选做**连通性检查(STUN Binding)**。这些地址**在公网不可路由**,检查必然超时失败。
- 后果:不仅浪费,还**拖慢/扰乱 ICE 收敛**,挤占真正有用候选的检查节奏。

### 3.2 srflx 失真:反射的是代理,不是你

- 正常:你发 UDP 给 STUN,STUN 看到你 NAT 的公网映射 → srflx = 你真实出口。
- 走代理:发往 STUN 的包**先进代理、从代理节点出去** → STUN 看到的是**代理节点的地址**。
- 于是你的 srflx 指向代理出口。对端按这个 srflx 发媒体,发到的是代理、且回程对不上 → **打洞失败**。

### 3.3 UDP 媒体被 TUN 吞掉:最致命的一条

- TUN 接管默认路由后,WebRTC 到 TURN 的 relay 分配包、以及后续媒体 UDP,**全被灌进 TUN → 交给代理转发**。
- 代理对 UDP 的支持普遍残缺:轻则大量丢包、重则完全不转。
- 现象学表现(和我们看到的**完全吻合**):
  - **少量 STUN 控制包**(Allocate/Refresh/Binding)偶尔能挤过去 → coturn 侧 **allocation 成功、`peer usage` 有零星单向字节**;
  - **持续的媒体 UDP 流被吞** → **双向媒体永远建不起来 → `peer usage` 从不是双向(`rp>0 且 sp>0`)**。

## 4. 为什么正好解释"relay 能分配、媒体却单向"

把上面三条合起来,就能一一对上 coturn verbose 里的观测:

| 观测 | 解释 |
|---|---|
| allocation 成功、无 486/403/508 | 服务端已修好;分配是少量控制包,能挤过代理 |
| `peer usage` 有非 0 但**单向**(`sp>0,rp=0`) | 少量包偶尔单向漏过;真正的双向媒体 UDP 被 TUN/代理吞掉 |
| 对端候选里 `198.18.0.1`/`10.0.0.5` | 测试机 TUN 虚拟网卡 IP 被当 host 候选 |
| STUN 反射来自 `198.18.x` | 探测包经代理出口,srflx 失真 |
| 同 WiFi 能通、异网络不通 | 同 WiFi 走 host 直连、路径短,偶尔能绕过代理影响;异网络必须靠 srflx/relay 的 UDP,正好被代理砸死 |

## 5. 如何确认(诊断清单)

1. **`chrome://webrtc-internals`**:通话中看 ICE candidate 列表,**出现 `198.18.x` / `10.x` / 其它陌生虚拟网段** → 有 VPN/虚拟网卡在污染候选。
2. **核对 srflx**:candidate 里 `typ srflx` 的地址,和你在 ip138/whatismyip 看到的真实公网**对不上** → 走了代理。
3. **前后对比**:**关掉代理**再抓一次候选,`198.18.x` 消失、srflx 变成真实公网 → 实锤。
4. **服务端佐证**:coturn verbose 里 `peer <ip>` permission 出现 `198.18.x`/内网段。

---

## 6. 规避 / 正确测试姿势

- **测 WebRTC 一律两端都关**:VPN、系统代理、TUN/增强模式、手机端代理 App(Shadowrocket/Clash for Android 等)统统退出到"直连"。
- **若必须共存**(平时挂着代理开发):
  - 把代理切到"规则模式"而非"全局/TUN 全局",并给 WebRTC 相关目标(你的 TURN 域名/IP、STUN)加 **direct 直连规则**;
  - 或改用**系统 HTTP 代理**模式(不接管 UDP),而非 TUN;
  - 关掉 **fake-ip**(改 real-ip / redir-host)能消掉 `198.18.x` 候选,但 UDP 被代理转发的问题仍在。
- **注意**:`iceTransportPolicy: 'relay'`(强制只用 relay)**救不了**这种情况——媒体照样是 UDP,照样被 TUN 吞。根子是"UDP 走了代理",只能让 WebRTC 的 UDP 直连。

## 8. 延伸:哪些网络环境会共性地干扰 WebRTC

| 环境 | 影响 | 对策 |
|---|---|---|
| VPN/代理(TUN/fake-ip) | 垃圾候选 + srflx 失真 + UDP 被吞 | 关掉;或直连分流 |
| 对称 NAT / CGNAT(手机流量) | srflx 无效,必须 TURN relay | 自建/托管 TURN(本项目已做) |
| 企业防火墙只放行 443 | UDP 全封,STUN/常规 TURN 不通 | TURNS over TCP/443(TLS) |
| 浏览器 mDNS 隐私(未授权媒体时) | host 候选变 `.local`,拿到媒体权限后恢复真实 IP | 通话已授权,通常不受影响 |
