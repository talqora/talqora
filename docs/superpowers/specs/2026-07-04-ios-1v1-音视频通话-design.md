# iOS 端 1:1 音视频通话 · 设计文档(Phase 1)

> 目标:把 web 已有的 1:1 语音/视频通话能力搬到 iOS 原生端,做到 **iOS ↔ web 端到端互通**。复用现有 `call:*` Socket.io 信令、coturn TURN、`/api/turn-credentials`,新代码集中在 iOS 侧的媒体引擎、通话状态机与 UI。
>
> 关联:web 实现见 `web/src/utils/webrtc.ts` + `web/src/hooks/useCall.ts`;信令契约见 `proto/ourchat/call/v1/call.proto`;服务端信令见 `server/src/utils/socket.ts`;WebRTC/TURN 背景见 `docs/技术方案/`、`docs/技术细节/`、`docs/debug/` 三篇音视频文档。

---

## 1. 背景与目标

- **现状**:web 有完整 1:1 语音/视频(WebRTC P2P + 自建 coturn,Socket.io `call:*` 信令,断线 `call:rejoin` 重连)。**iOS 端零音视频**——`Features/` 无 Call,`ServerEvent` 仅接了 message/friend 事件(但已留 `call:*` 扩展注释),`SocketClient` 是可用的 actor 化 Socket.io 长连接。
- **本次目标(Phase 1)**:iOS 实现 1:1 语音+视频通话,与 web 互通,不依赖 Apple VoIP 推送证书。
- **成功标准(可测)**:
  1. iOS 发起语音/视频呼叫 → web 接听 → **双向音频/视频通**(能听到、看到;coturn `peer usage` 双向非 0)。
  2. web 发起 → iOS 接听 → 双向通。
  3. 通话内:静音、免提(听筒/扬声器切换)、关/开摄像头、前后置翻转,均即时生效。
  4. 一端断网 → grace 窗内自动 `call:rejoin` 重连恢复;超时则双方收到 `call:end`。
  5. 拒接 / 挂断 / 忙线(被叫在另一通)行为与 web 一致。
  6. 麦克风/摄像头权限被拒时给人话引导,不崩、不白屏。

## 2. 范围

**做(Phase 1)**:
- iOS `WebRTCSession`(封装 `stasel/WebRTC` 的 `RTCPeerConnection`)。
- `CallFeature`(TCA)通话状态机 + `CallView` 语音/视频两态 UI。
- `SocketClient` 扩展 `call:*` 收发 + `ServerEvent` 新 case + 解析器。
- 麦克风/摄像头权限、`AVAudioSession` 配置、后台 audio 模式。
- Tuist 接入 `stasel/WebRTC` 依赖。
- 服务端:**零改动**(复用现有 `call:*` 信令与 TURN 凭据端点)。

**不做(Phase 2,外部依赖阻塞)**:
- **CallKit + PushKit VoIP 推送**(App 被杀/后台系统级来电、进系统通话记录)。阻塞点=**Apple Developer VoIP 推送证书 + APNs VoIP 配置 + 服务端 VoIP 推送服务**,非音视频本体。本次把状态机设计成 **CallKit-ready**(§13),证书就绪后独立迭代接入。
- 群组(多人)通话、屏幕共享、录制、美颜。

## 3. 复用盘点(为什么新代码几乎只在 iOS)

| 层 | 现状 | 本次动作 |
|---|---|---|
| 信令事件 | 服务端 `call:start/accept/reject/end/ice/rejoin/busy/handled/peer-reconnecting` 全在,web 在用 | iOS 作为"另一个说同样话的客户端"接入,**服务端不改** |
| 信令传输 | iOS `SocketClient`(actor 化 Socket.io,握手 auth 已对齐) | 扩展 `call:*` 收发 |
| 契约 | `proto/ourchat/call/v1/call.proto` 定义全部消息 | iOS 按现有约定**手写 Codable/字典解析**镜像形状(与 `SocketMessageParser` 同范式,不引 protobuf codegen) |
| NAT 穿透 | coturn + `/api/turn-credentials` 短期 HMAC 凭据 | iOS 复用同一端点拉 iceServers |

## 4. 架构总览

```
                 ┌─────────────────────────── CallFeature (TCA Reducer) ───────────────────────────┐
                 │  状态机: idle→outgoing/incoming→connecting→connected→(reconnecting)→ended        │
   CallView ◀───▶│  订阅两条事件流,单向驱动 State,发 Action                                        │
 (语音/视频 UI)   │     ▲ signaling events (call:*)          ▲ media events (ice/track/state)         │
                 └─────┼──────────────────────────────────────┼────────────────────────────────────┘
                       │                                        │
             SocketClient.callEvents()              WebRTCSession.events()  ← 新增 Dependency
             (扩展现有 actor)                        (actor 隔离 RTCPeerConnection)
                       │                                        │
             Socket.io  call:*  ───► server ───► 对端            RTCPeerConnection ──媒体RTP──► 对端
                       │                                        │
                 /api/turn-credentials ──► iceServers(coturn STUN/TURN)─┘
```

- **两条输入流**:①信令(`call:*`,谁打给谁 / SDP / ICE)②媒体(本地 ICE 候选生成、远端轨道到达、连接状态)。`CallFeature` 是唯一"缝合点",把两条流按状态机编排:收到 offer→喂给 `WebRTCSession`→产出 answer→经信令回发;`WebRTCSession` 吐本地候选→经信令发对端;收到对端候选→喂回 `WebRTCSession`。
- **完全对齐 web `useCall`** 的编排顺序,包括**接听前暂存对端早到 ICE 候选、`setRemoteDescription` 后再灌入**(web 侧刚修的候选丢失 bug,iOS 从一开始就按正确顺序做,见 §9)。

## 5. 组件设计

### 5.1 `WebRTCSession`(新 Dependency,actor 封装)

镜像 `SocketConnection` 的范式:`@DependencyClient` 结构体 + 私有 `actor` 持有非 Sendable 的 `RTCPeerConnection`,delegate 回调在边界处转成 Sendable 领域事件后经 `AsyncStream` 扇出。

```swift
// 对外:Sendable 领域事件(不泄漏任何 WebRTC 类型)
enum WebRTCEvent: Sendable {
    case localCandidate(IceCandidateDTO)          // 本地生成候选 → 上层经信令发对端
    case remoteVideoTrackAdded                     // 远端视频轨到达 → UI 渲染
    case connectionState(RTCState)                 // new/connecting/connected/failed/closed(自映射枚举)
}

@DependencyClient
struct WebRTCSession: Sendable {
    var configure: @Sendable (_ iceServers: [IceServerDTO], _ relayOnly: Bool) async -> Void
    var createOffer: @Sendable () async throws -> SessionDescriptionDTO
    var createAnswer: @Sendable (_ remoteOffer: SessionDescriptionDTO) async throws -> SessionDescriptionDTO
    var setRemoteAnswer: @Sendable (_ answer: SessionDescriptionDTO) async throws -> Void
    var addRemoteCandidate: @Sendable (_ c: IceCandidateDTO) async -> Void   // 内部按 remoteDescription 是否就绪暂存/直加
    var startLocalMedia: @Sendable (_ video: Bool) async throws -> Void       // getUserMedia 等价:麦克风(+摄像头)
    var setMuted: @Sendable (_ muted: Bool) async -> Void
    var setCameraEnabled: @Sendable (_ on: Bool) async -> Void
    var switchCamera: @Sendable () async -> Void
    var setSpeaker: @Sendable (_ on: Bool) async -> Void                       // AVAudioSession 路由
    var localVideoTrack: @Sendable () async -> RTCVideoTrackHandle?            // 供 UI 拿轨道渲染(不透 WebRTC 类型,给包装句柄)
    var remoteVideoTrack: @Sendable () async -> RTCVideoTrackHandle?
    var reset: @Sendable () async -> Void                                      // 重建 PC(保留暂存候选,见 §9)
    var close: @Sendable () async -> Void
    var events: @Sendable () -> AsyncStream<WebRTCEvent> = { .finished }
}
```

- **视频渲染**:`RTCVideoTrackHandle` 是对 `RTCVideoTrack` 的薄封装;`CallView` 里用一个 `UIViewRepresentable` 包 `RTCMTLVideoView`(Metal 渲染)挂轨道。这是唯一必须触碰 UIKit 的地方(SwiftUI 无原生 WebRTC 视图),范围最小、隔离在一个 View 文件里。
- **DTO**:`SessionDescriptionDTO{type,sdp}`、`IceCandidateDTO{candidate,sdpMLineIndex?,sdpMid?}`、`IceServerDTO{urls,username?,credential?}`——全 Sendable、与 proto 形状一致。

### 5.2 TURN 凭据拉取(复用)

新增一个轻量 API 调用(走现有 `APIClient`)命中 `/api/turn-credentials`,返回 `{iceServers, ttl}`。iOS 在**每次建连前**拉一次(与 web 同策略),交给 `WebRTCSession.configure`。

### 5.3 `SocketClient` 扩展 `call:*`

在现有 `SocketClient`/`SocketConnection` 上加:
- **出站方法**:`sendCallStart / sendCallAccept / sendCallReject / sendCallEnd / sendCallIce / sendCallRejoin`,各自 `socket.emit("call:xxx", payload)`,payload 字典镜像 proto 形状。
- **入站注册**:`SocketConnection.connect` 里补 `socket.on("call:start"/"call:accept"/"call:reject"/"call:end"/"call:ice"/"call:rejoin"/"call:busy"/"call:handled"/"call:peer-reconnecting")`,各自解析 → `emit(.callXxx(...))`。
- **`ServerEvent` 新 case**:`.callIncoming / .callAccepted / .callRejected / .callEnded / .callIce / .callRejoin / .callBusy / .callHandled / .callPeerReconnecting`。
- **解析器**:`SocketCall*Parser` 纯函数(可单测),镜像 proto。**必须处理契约不对称**:`call:start`/`call:rejoin` 的 `from/to` 是 CallUser 对象;`call:accept` 的 `from/to` 是 user id(int)。

### 5.4 `CallFeature`(TCA Reducer)

对齐 web `useCall` + `callStore`:

- **State**(`@ObservableState`):
  - `phase: CallPhase`(见 §8 状态机)
  - `callId: String`、`callType: .voice|.video`、`peer: CallUser`、`role: .caller|.callee`
  - `pendingOffer: SessionDescriptionDTO?`(被叫接听前暂存的 offer;刷新/重启后为 nil → 走 rejoin)
  - `isMuted / isSpeakerOn / isCameraOn / isFrontCamera: Bool`
  - `hasRemoteVideo: Bool`、`durationSeconds: Int`、`errorMessage: String?`
- **Action**:UI 意图(`acceptTapped/rejectTapped/hangupTapped/toggleMute/...`)+ 信令入站(`incomingCall/remoteAccepted/remoteIce/...`)+ 媒体事件(`localCandidate/remoteTrackAdded/connectionStateChanged`)+ 计时器 tick。
- **Effects**:订阅 `socketClient.callEvents()` 与 `webRTCSession.events()`(两条 `.run` 长效 effect,随通话结束取消);发起/接听是 async effect 串起 `configure→startLocalMedia→createOffer/Answer→emit signaling`。

### 5.5 `CallView`(SwiftUI,遵守 mobile-swift UX 硬规范)

- **两态复用一壳**:语音态(头像+计时+按钮排)/ 视频态(远端全屏 + 本地小窗 PiP + 悬浮按钮),按 `callType`/`hasRemoteVideo` 切换渲染面,**共享同一状态机与控制条**(呼应仓库根 CLAUDE.md「按变化维度解耦,不 if(type) 散落」)。
- 强制项(mobile-swift CLAUDE.md §6):**先加载 `mobile-ios-design`+`swiftui-pro` skill**;可点元素 ≥44pt + `PressableButtonStyle` 按下反馈;颜色/字号走 `WeChatTheme`/`WeChatFont` 令牌;权限拒绝/连接失败三态化(`AsyncStateView` 思路);明暗两套实测;`.sensoryFeedback` 给接听/挂断触觉。
- 呈现方式:全屏 `fullScreenCover`(来电/通话中),由根级 `CallFeature` 驱动(scope 到 App root,任意页都能弹)。

### 5.6 权限、音频会话、后台

- `Project.swift` 的 `infoPlist` 补:`NSMicrophoneUsageDescription`、`NSCameraUsageDescription`(人话文案)。
- `UIBackgroundModes: ["audio"]`(通话切后台音频不断;Phase 2 再加 `"voip"`)。
- `AVAudioSession`:通话开始 `setCategory(.playAndRecord, mode: .voiceChat, options: [.allowBluetooth])` + 免提切 `.defaultToSpeaker`;结束还原。处理来电/闹钟**中断**(`AVAudioSession.interruptionNotification` → 暂停/恢复)。

## 6. 信令契约映射(iOS ↔ server ↔ 对端)

| iOS 出站 | emit 事件 | 关键载荷 | 服务端路由 |
|---|---|---|---|
| 发起 | `call:start` | callId, from(CallUser), to(CallUser), offer, callType | 忙线→回 `call:busy`;否则 → 被叫 |
| 接听 | `call:accept` | callId, from(id), to(id), answer | → 主叫;并 `call:handled` 通知被叫其它端 |
| 拒接 | `call:reject` | callId | → 主叫 |
| 挂断 | `call:end` | callId | → 双方 |
| 候选 | `call:ice` | callId, candidate | → 对端 |
| 重连 | `call:rejoin` | callId, from(CallUser), to(CallUser), offer | → 对端(优先对端设备房) |

- `callId` 规则沿用 web:`call_{fromId}_{toId}_{timestamp}`。
- 入站对称监听同名事件(§5.3)。

## 7. 数据流(时序)

**A 发起 → B 接听(A=iOS,B=web,反之对称):**
```
A: configure(iceServers) → startLocalMedia → createOffer → setLocalDescription
A: emit call:start(offer) ─────────────────────────► server ──► B (振铃, 暂存 offer)
A: (ICE 生成) emit call:ice ×N ─────────────────────► server ──► B (B 暂存: 无 remoteDescription)
B: 用户点接听 → configure → startLocalMedia → setRemoteDescription(offer)
                → createAnswer → setLocalDescription → 灌入暂存候选
B: emit call:accept(answer) ────────────────────────► server ──► A: setRemoteAnswer
B: (ICE 生成) emit call:ice ×N ─────────────────────► server ──► A: addRemoteCandidate
→ 双方 connectionState=connected,媒体流通
```

**断线重连**:某端 socket 掉 → 服务端 grace 窗内广播 `call:peer-reconnecting`;重连方 `pendingOffer==nil` → 新建 PC、发 `call:rejoin(新 offer)` → 对端重协商;超时未回 → 双方 `call:end`。

## 8. 状态机(对齐 web)

```
idle ──start──► outgoing ──remoteAccepted──► connecting ──connected──► connected
idle ──incomingCall──► incoming ──acceptTapped──► connecting ──connected──► connected
                          └─rejectTapped─► ended        connected ──peerReconnecting──► reconnecting
outgoing/incoming/connecting/connected ──hangup/remoteEnd/reject/busy/failed──► ended
reconnecting ──rejoin成功──► connected ; ──grace超时──► ended
ended ──► (清理: close WebRTCSession, 停计时, dismiss)
```

## 9. 关键正确性:ICE 候选早到暂存(从一开始就做对)

web 曾因被叫接听时重建 PC 清空了主叫早到候选导致媒体单向(见 `docs/debug/音视频被叫接受打不通-reset清空ICE候选缓冲复盘.md`)。iOS **内建规避**:`WebRTCSession.addRemoteCandidate` 在 `remoteDescription` 未设时把候选存入内部 `pendingCandidates`,`createAnswer`/`setRemoteAnswer` 完成后统一灌入;`reset()` 跨重建**保留** `pendingCandidates`。单测覆盖此路径(§11)。

## 10. 错误处理与边界

- **权限拒绝**:`AVCaptureDevice.requestAccess` 被拒 → `phase=ended` + 文案「需要麦克风/摄像头权限」+ 跳设置引导,不发起。
- **无 TURN / 凭据拉取失败**:退化为仅 STUN(同网可用),记录并提示;不静默卡死。
- **忙线**:收 `call:busy` → 主叫直接 `ended("对方忙线中")`。
- **对端离线/无应答**:发起后 N 秒无 `call:accept/reject` → 超时 `ended`。
- **多设备**:`call:handled` 到达 → 本设备若在振铃则停止(已在别处接听/拒绝)。
- **中断**:音频被系统中断(来电)→ 暂停轨道,恢复后续传。

## 11. Swift 6 严格并发处理

- `RTCPeerConnection` 及其 delegate 回调类型(`RTCIceCandidate`/`RTCSessionDescription`/`RTCVideoTrack`)**非 Sendable**。全部由 `WebRTCSession` 内部 actor 独占持有,**绝不跨 actor 边界传出**。
- delegate(`RTCPeerConnectionDelegate`,回调在 WebRTC 信令线程)用一个 `nonisolated` 转发器:回调里**立即把 WebRTC 类型转成 Sendable DTO**,再 `Task { await actor.ingest(...) }` 或直接 `continuation.yield(dto)`。Sendable 边界卡在"转 DTO"这一步。
- 对 UI:视频轨道不作为 Sendable 传递,`CallView` 通过 `@MainActor` 的 `RTCMTLVideoView` 包装在渲染点直接向 actor 取句柄绑定(在主线程完成 attach)。

## 12. 风险与依赖

| 风险 | 说明 | 缓解 |
|---|---|---|
| Tuist × 二进制 SPM | `stasel/WebRTC` 是 xcframework 二进制包,Tuist 对 binary target 偶有坑 | 先小步验证 `tuist generate` 能拉入并链接;不行则回退用 `Package.swift` 直接声明 binaryTarget |

## 13. Phase 2 预留(CallKit-ready)

`CallFeature` 的状态迁移(incoming/connected/ended)设计为**可被外部驱动**:Phase 2 加一个 `CallKitClient`(`CXProvider`/`CXCallController`)把系统事件映射成同一批 Action,并在服务端 `call:start` 时发 APNs VoIP 推送唤醒 App。届时 `CallView` 的自定义来电页降级为"App 内已连时"的 fallback,系统来电走 CallKit。**本次不写这些,只保证 Action 边界不与 CallKit 冲突。**

## 15. 交付顺序(里程碑)

1. **依赖与骨架**:Tuist 接入 WebRTC + 权限 + `WebRTCSession` 空壳 + DTO,能 build。
2. **信令打通**:`SocketClient` `call:*` 收发 + 解析器 + 单测;`CallFeature` 状态机 + reducer 单测(不含真实媒体)。
3. **语音互通**:`WebRTCSession` 音频路径 + `CallView` 语音态 → iOS↔web 语音互拨(成功标准 1/2 语音部分)。
4. **视频互通**:视频轨道 + `RTCVideoView` + 视频态 UI → 双向视频。
5. **控制与鲁棒**:静音/免提/摄像头/翻转 + 断线 `call:rejoin` 重连 + 忙线/拒接/权限边界 + UX 硬规范自检。
6. **验收**:两真机 / 一真机一 web 全 §1 成功标准过一遍。

每步"代码 + 测试同提交",reducer/解析器高覆盖单测,媒体路径靠协议抽象 + mock 单测 + 手动互通验收(见 mobile-swift 测试约定)。
