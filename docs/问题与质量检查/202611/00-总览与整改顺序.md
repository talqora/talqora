## 0 一段话总评

这套系统的**架构演进是成功的，工程质量没有跟上**。

成功的地方值得先说清楚，否则下面的清单会失真：业务层从 Node 迁到 Go（`biz/`，约 8.5k 行）后，模块边界（`api` / `service` / `store` / `realtime`）切得比原来干净，SQL 全部参数化，Redis 用 Lua 收敛了原子性，gRPC 双向流替代了每消息一次 HTTP POST，`go vet` 与现有单测全绿；agent-server 的多租户隔离把 `user_id` 过滤下沉到了向量检索的唯一出口，SSE 断线补发实现了「先订阅后补发 + watermark 去重」，这两处是真正做对的细节。

没跟上的地方集中在三类：

1. **鉴权只做了一半。** 三个「按会话读取」的端点（`/user/messages`、`/user/conversations`、`/user/lastMessages`）一个都没校验成员归属；而 `sync`、`read`、`readCount` 都校验了。实时通道反过来：`read.report` 校验了成员，`message.send` 没校验。结果是任意登录用户能读到任意会话的全部消息、也能往任意会话里发消息。
2. **双实现漂移产生了真实故障。** Web 按 OpenAPI 发数字 `userId`，Go 业务层把它绑成 `string` 并用 `_ = c.ShouldBindJSON` 吞掉错误，于是「加好友 / 改备注 / 回复好友请求 / 建会话」四个功能在 Web 端正恒返回 403。已在本地用最小程序复现绑定行为（见 02 分册 BZ-S2）。
3. **没有任何自动关卡能拦住上面两类问题。** 两个仓库的 CI 都是「推送即部署」，没有 build、没有 vet、没有测试、没有 lint；`biz/internal/api` 的语句覆盖率是 **3.8%**，测试只覆盖纯函数，没有一个 HTTP 处理器被执行过。同时 `server/`（Node 旧业务层）仍被部署脚本 scp 到生产机、仍被 `buf.gen.yaml` 当作生成目标、仍被 README 描述为「业务层」，它自带的 CI 放在嵌套 `.github/` 里从未执行过。

按影响排优先级：**先修越权（BZ-S1/S2/S3），再修部署阻断（01 分册 DP-S1/S2），最后补门禁（07 分册）。** 前两类是「线上真的会出错」，第三类是「以后不再出错」。合计约 40 小时，可以在 11 月底前完成，正好落在校招计划 W1–W2 的「代码体检」窗口里。

### 3.2 本轮新发现并已修复的三个缺陷

1. **biz 收到 SIGTERM 后永久挂起。** `edgeSrv.GracefulStop()` 会等 gateway 的 4 条长驻双向流自然结束，而它们不会结束；于是 `httpSrv.Shutdown` 与 `FinalCheckpoint`（seq 终检）永远执行不到，最终被编排层 SIGKILL，**每次部署都丢最后一次发号位点**。修法：先停 HTTP，再对 `GracefulStop` 加 1s 超时兜底 `Stop()`；compose 加 `stop_grace_period: 15s`。
2. **网关误用业务层的副本号。** dev 下两者共用 `.env.debug`，`REPLICA_ID=biz-1` 被网关读走，多网关副本时会互相覆盖 `presence:meta`、把定向下行路由到错误副本。修法：网关改用 `GATEWAY_REPLICA_ID`。
3. **MinIO 官方镜像已从 Docker Hub 下架**（`minio/minio` 与 `quay.io/minio/minio` 均不可拉），导致 `make middleware` 在任何机器上都失败。修法：dev 编排改用 LocalStack 的 S3（对外仍映射 9000，业务侧 minio-go 与 `S3_*` 配置零改动），桶与匿名读策略由容器内 ready 钩子创建。

## ★ 关键理解点

- **正向：鉴权要成对检查。** 一个业务动作总是包含「读」与「写」两侧，两侧必须用同一条授权规则。本项目里 `read`/`sync` 校验了、`messages` 没校验，`message.send` 没校验、`read.report` 校验了——不是某一次疏忽，而是缺少一个统一的「会话访问控制」入口，让每个 handler 各自决定要不要检查。修法不是补四个 `if`，而是抽一个 `RequireConversationMember(convID, userID)` 中间件或服务函数，所有涉及会话的端点一律经过它。
- **反向：契约漂移最贵的形态是「两端都能编译、运行时静默失败」。** `userId` 在 OpenAPI 里一处写 `integer`、一处写 `string`，Go 侧照 string 写，Web 侧照 number 发，两边类型检查都通过，错误被 `_ =` 吞掉，最终表现为「按钮点了没反应」。这类问题只能靠跨层契约测试发现——单测、类型检查、code review 都抓不到。
- **边界：测试覆盖率的数字本身不重要，重要的是覆盖了哪条路径。** 28.7% 的 `service` 覆盖率看起来还行，但覆盖的全是纯函数（`parseNonneg`、`singleConvID`、`randomUUID`）；真正出问题的处理器层是 3.8%。判断标准应当是「每个对外端点至少有一条端到端用例」，而不是一个百分比。
- **对比：安全缺陷与可靠性缺陷的修复成本不对称。** 越权读取只需要改三个 handler（1.5 小时），但它造成的后果是「全站消息可被任意用户读取」，属于不可接受级别；而发号竞态（BZ-I1）修复成本高、当前触发概率低。所以顺序上先修安全，再修可靠性，不要被「哪个技术更有意思」带偏。
