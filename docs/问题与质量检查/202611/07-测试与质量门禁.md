# 测试与质量门禁

> 范围：talqora（`biz`、`gateway`、`web`）、agent-server 的测试资产与 CI 门禁，以及压测/实验资产的可用性。
>
> 证据来源：**实际执行** `go vet ./...`、`go test ./... -cover`、`go test -race`；只读核对 `Makefile`、`.github/workflows/*`、`vitest.config.ts`、`pyproject.toml`。覆盖率数字均为本次运行输出，不是历史记录。
>
> 本文是 [02](./02-talqora业务层.md) / [03](./03-talqora网关与基础设施.md) / [04](./04-agent-server.md) 三册的「为什么这些问题没被拦住」的总结。

## 0 一段话总评

**没有一个仓库在合并前跑测试。**

talqora 三条 workflow：`deploy.yml`（推送即部署，无任何检查）、`proto.yml`（只校验 proto 生成物）、`perf.yml`（只跑前端体积与 Lighthouse）。没有 `go build`、没有 `go vet`、没有 `go test`、没有 `pnpm lint`、没有 `pnpm test`。agent-server 三条 workflow：部署、proto、私有包发布，`pytest|ruff|mypy` 零命中。

测试本身的分布也错位了。看这张表（本次实测）：

| 模块 | 语句覆盖率 | 该模块里的严重缺陷 |
|---|---|---|
| `biz/internal/api` | **3.8%** | BZ-S1（越权读）、BZ-S2（`userId` 绑定） |
| `biz/internal/realtime` | **0.0%** | BZ-S3（注入消息）、BZ-S4（通话鉴权） |
| `biz/internal/store` | **0.0%** | BZ-I6（`sslmode`/连接池） |
| `gateway/internal/presence` | **0.0%** | GW-I2（meta 丢失） |
| `gateway/internal/backplane` | **0.0%** | — |
| `gateway/internal/hub` | 10.9% | GW-I3（配额 O(n)）、GW-I4（不排空） |
| `gateway/internal/upstream` | 7.2% | GW-S1（并发 Send）、GW-I1（panic 窗口） |
| `biz/internal/service` | 28.7% | BZ-I1（发号竞态） |
| `gateway/internal/ws` | 82.0% | — |
| `gateway/internal/config` | 80.0% | — |

规律很清楚：**覆盖率高的两个包恰好是问题最少的；所有 S 级缺陷都落在 0%–4% 的包里。** 现有 690 行 biz 测试 + 613 行 gateway 测试（共 1303 行）测的全是纯函数——`parseNonneg`、`singleConvID`、`randomUUID`、`parseStringArray`、`backoffDelay`。`go test -race` 全绿，但它跑的是这些纯函数，与 GW-S1 的并发路径完全无关。

这就是「有测试」和「测试有效」的区别。

## 1 问题清单

### 严重

#### QA-S1 三个仓库都没有合并前质量门禁（已核实）

**证据。**

| 仓库 | workflow | 触发 | 做了什么 | 没做什么 |
|---|---|---|---|---|
| talqora | `deploy.yml:24-32` | push `main`（任意路径） | 预检 Secrets → scp → 服务器 build+up | build / vet / test / lint / 镜像验证 |
| talqora | `proto.yml:6-16` | PR 改 `proto/**` 等 | buf lint + 生成物新鲜度 | 任何代码测试 |
| talqora | `perf.yml:5-12` | PR/push 改 `web/**` | size-limit + Lighthouse | `pnpm lint` / `pnpm test` |
| agent-server | `deploy.yml` | push `master` | 预检 → scp → 远程 build+up | `pytest` / `ruff` / `mypy` |
| agent-server | `proto.yml` / `publish-contracts.yml` | — | 契约校验 / npm 发布 | 同上 |

**原理。** 门禁的价值在于「用便宜的自动检查拦住机器能发现的问题」。本报告里的 DP-S1（Go 版本与 go.mod 不符、Dockerfile 缺 `ENTRYPOINT`）、AS-I5（事件序号竞态）、BZ-S2（`userId` 类型）都**只需一次 build 或一条用例**就能发现，却全部进了主干。这不是某一次粗心，而是流程里根本没有这道关卡。

**后果。** 任何改动都可能静默上线。最典型的是 01 分册记录的 DP-S1：`main` 分支当前按配置根本部署不起来，而 CI 会一路绿灯跑到最后一步。

**修复。** 两个仓库都改成「检查作业 → 部署作业」，部署 job `needs: [check]`。检查清单见第 2 节。

#### QA-S2 测试结构失衡：只覆盖纯函数，处理器与并发路径为零（已核实）

**证据。** 现有测试清单（`find biz gateway -name "*_test.go"`，共 14 个文件 1303 行）：

| 文件 | 行数 | 测的是什么 |
|---|---|---|
| `biz/internal/oauth/oauth_test.go` | 179 | 密钥装载、JWKS 结构、JWT 往返 |
| `biz/internal/service/seq_test.go` | 157 | `nextSeq` 的依赖注入版（用 fake Redis） |
| `biz/internal/service/call_test.go` | 136 | 通话会话结构 |
| `biz/internal/api/auth_test.go` | 74 | 密码哈希、token 解析 |
| `biz/internal/service/auth_test.go` | 60 | 同上 |
| `biz/internal/api/friend_test.go` | 45 | **仅** `singleConvID`/`parseNonneg`/`randomUUID`/`parseStringArray` |
| `biz/internal/service/ratelimit_test.go` | 39 | 限流窗口计算 |
| `gateway/test/smoke_test.go` | 153 | 端到端冒烟（需要真实 Redis） |
| `gateway/internal/ws/server_test.go` | 147 | 握手验签与 Origin 校验 |
| `gateway/test/backpressure_test.go` | 99 | 背压逐出 |
| `gateway/internal/hub/hub_test.go` | 81 | 注册/注销/路由 |
| `gateway/internal/upstream/upstream_test.go` | 67 | fake upstream |

**没有一个测试启动过 `gin.Engine` 并打一次 HTTP 请求**（`api` 包 3.8% 就是证据：那 3.8% 来自 `auth_test.go` 直接调用 `service.HashPassword` 之类的函数，而不是走路由）。

**后果（具体到本次报告的四条 S 级业务层问题）。**

| 缺陷 | 本可以拦住它的最小用例 |
|---|---|
| BZ-S1 越权读 | 用非成员账号打 `GET /user/messages?conversationId=...`，断言 403 |
| BZ-S2 `userId` 绑定 | 用 Web 的真实 payload（数字）打 `PUT /user/addFriend`，断言 200 |
| BZ-S3 注入消息 | 非成员发 `message.send`，断言 403 且消息表行数不变 |
| BZ-S4 通话鉴权 | 非被叫发 `call:accept`，断言主叫收不到 |

四条用例，合计不到 200 行。**它们的缺失不是因为难写，而是因为没有地方强制要求写。**

**修复。** 见第 2 节的「最小可用测试集」。

### 重要

#### QA-I1 没有 `-race` 门禁（已核实）

**证据。** 三个 workflow 里没有 `go test -race`。本地跑 `go test -race ./internal/hub/... ./internal/upstream/...` 全绿——但如 [03 分册](./03-talqora网关与基础设施.md) 所述，现有用例根本不触发并发 `Send` 路径。

**原理与后果。** race detector 只在**代码真的并发执行到**时才报告。没有「并发跑同一路径」的用例，`-race` 就是摆设。项目的并发风险点集中在三处（gRPC 流多写者、presence 摘除、ack channel 关闭），都没有并发用例。

**修复。** CI 加 `-race`；同时补三条并发用例（每条约 40 行）：同一 shard 并发 100 次 `forward`、`deliverAck` 与 `failAll` 并发、同 deviceID 重连与旧连接关闭并发。

#### QA-I2 没有集成测试基础设施（已核实）

**证据。** 全仓搜不到 `sqlmock`、`testcontainers`、`dockertest`。`biz` 侧的测试全部依赖 `store.SetRedisForTest`（`biz/internal/store/store.go:118`，仅供测试注入 Redis）或纯函数；`biz/internal/service/seq_test.go` 用的是接口注入版 `nextSeq(ctx, rdb, ...)`（`seq.go:57`），这是好设计，但只覆盖了发号、没覆盖「发号 + 落库 + 幂等」这条真实链路。

**后果。** 「消息恰好落库一次」「重复 clientMsgId 不产生两条」「seq 单调」这些**最需要被验证的语义**，一个都没有可执行的断言。校招计划证据线三要做的「正确性检查器」，本质上就是把这套断言工程化——现在连基础都没有。

**修复。** 引入 `testcontainers-go`（或 `dockertest`）起一次性的 PG + Redis，把 `biz` 的集成测试挂在 `//go:build integration` tag 下，CI 里跑一个 job。这一步同时是「正确性检查器」的前置工程。

#### QA-I3 压测资产与现状脱节（已核实）

**证据。**

- `perf/README.md:3`：「只压 `server/`（Express + Socket.io,基址 `http://localhost:3007`）」。
- `perf/node-run.mjs:158`：`mode: 'socketio'`。
- `perf/storm-reconnect.mjs:15`、`http-bench.mjs:14`、`ramp-probe.mjs:16`：`BASE=http://localhost:3007`。
- 同时 `perf/` 下也有 `harness-gw.mjs`、`gw-fanout-bench.mjs`、`gw-ramp-probe.mjs` 等面向 gateway 的脚本。

**原理与后果。** 一半脚本压的是已下线的 Node 服务，一半压的是 gateway。跑出来的数字无法直接比较，也无法支撑「每核能承载多少连接」的容量模型。而校招计划证据线二的核心产出就是这个模型。

另外 `perf/node_modules` 被提交进了工作区（未 gitignore 的部分见 `perf/package-lock.json`），进一步说明这块缺治理。

**修复。** 统一到一个 harness：`perf/harness-gw.mjs` 作为唯一上行入口（已存在），删掉 socketio 模式；每次压测输出机器可读的基线文件（JSON），并规定「基线文件必须与代码版本一起提交」。这也是校招计划里「实验报告五要素」中「环境 + 方法 + 原始数据」的落地方式。

#### QA-I4 缺少正确性检查器与故障注入脚本（已核实）

**证据。** `perf/` 下 18 个脚本全部是负载生成与探针，没有一个是「读数据库 + 读客户端日志 + 校验不变式」的检查器；也没有任何脚本做故障注入（kill -9、网络分区、Redis 主从切换）。

已有的 `gw-storm-reconnect.mjs`、`storm-reconnect.mjs` 是**客户端行为模拟**（重连风暴），不是故障注入。

**原理与后果。** 校招计划把「正确性检查器」标为**区分度最高的一件东西**（★ 标记），并定义四条不变式：seq 唯一递增、已确认消息恰好持久化一次、在线成员都能同步到、账本借贷之和为零。当前这四条一条都没有可执行的判定方式——也就是说，即使现在做实验，也拿不出「差异为 0」这个结论。

**修复。** 这是一个独立小工具，不需要大改架构：

1. 输入：一个会话 ID + 时间窗口；
2. 读 PG：`SELECT seq, count(*) FROM messages WHERE conversation_id=$1 AND timestamp BETWEEN ... GROUP BY seq HAVING count(*)>1`（查重复）、`SELECT max(seq), count(*)`（查空洞是否合理）；
3. 读客户端日志（压测 harness 输出的 ack 记录）：比对「已 ack 的 clientMsgId 集合」与「库里存在的 clientMsgId 集合」的差集；
4. 输出：`{duplicates: n, missing: n, ok: bool}`，非零退出码。

约 200 行，半天到一天。这正是「E8：100 万条消息、20 次故障、差异为 0」的前置。

### 一般

| 编号 | 问题 | 证据 | 修复 |
|---|---|---|---|
| QA-N1 | 没有覆盖率阈值，覆盖率只作为一次性数字存在 | 无 `-coverprofile` 配置、无 `coverageThreshold` | CI 里设「不得低于上次」的基线（`biz/internal/api` 允许先设 5%，只许升） |

## 2 建议的门禁设计

### 2.1 talqora `ci.yml`

```yaml
name: ci
on:
  pull_request:
  push: { branches: [main] }

jobs:
  go:
    strategy: { matrix: { module: [biz, gateway] } }
    steps:
      - checkout
      - setup-go（版本从该模块 go.mod 读取，不要写死）
      - run: go build ./...
      - run: go vet ./...
      - run: go test -race -coverprofile=cover.out ./...
      - run: go tool cover -func=cover.out   # 打印，供人工看趋势

  web:
    steps:
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm test
      - run: pnpm build

  images:            # 只构建，不推送；目的是发现 Dockerfile 与 go.mod 不一致
    steps:
      - run: docker build biz
      - run: docker build gateway
      - run: docker build web
      - run: docker run --rm --entrypoint= biz  # 验证镜像里有可执行入口

  nginx:
    steps:
      - run: docker run --rm -v $PWD/docker/nginx:/etc/nginx:ro nginx:alpine nginx -t

  secrets:
    steps:
      - uses: gitleaks/gitleaks-action

  contracts:
    steps:
      - run: ./scripts/check-openapi-coverage.sh   # web 调用的 URL ⊆ openapi paths
```

`deploy.yml` 增加 `needs: [go, web, images, nginx, secrets]`。

**注意 `images` job 里的 `docker run --entrypoint= biz`**：01 分册的 DP-S1 第 ③ 处（biz 镜像没有 `ENTRYPOINT`）就是「镜像能构建、容器起不来」，只 build 不 run 是发现不了的。

### 2.3 最小可用测试集（优先级从高到低）

不追求覆盖率数字，只补「会真的出错」的路径：

| # | 用例 | 覆盖 | 行数 |
|---|---|---|---|
| 1 | 非成员读 `GET /user/messages` → 403 | BZ-S1 | 40 |
| 2 | Web 真实 payload 打 `PUT /user/addFriend` → 200 | BZ-S2 | 40 |
| 3 | 非成员发 `message.send` → 403 且不落库 | BZ-S3 | 50 |
| 4 | 非被叫发 `call:accept` → 主叫收不到 | BZ-S4 | 40 |
| 5 | 同一 shard 并发 100 次 `forward`（`-race`） | GW-S1 | 40 |
| 6 | `deliverAck` 与 `failAll` 并发（`-race`） | GW-I1 | 30 |
| 7 | 同 deviceID 重连与旧连接关闭并发 | GW-I2 | 40 |
| 8 | 重复 `clientMsgId` 只落一条（需 testcontainers） | ID 幂等 | 60 |
| 9 | 事件序号并发 emit 不撞唯一约束 | AS-I1 | 40 |

合计约 380 行，一天到一天半。**这 9 条用例的价值高于把覆盖率从 16% 提到 60%**——因为它们对应的正是本次体检发现的全部 S 级问题。

## 3 整改顺序

| 顺序 | 事项 | 关联 | 工时 |
|---|---|---|---|
| 1 | talqora `ci.yml`（go build/vet/test + web lint/test + 镜像构建 + nginx -t） | QA-S1 | 3h |
| 2 | agent-server `ci.yml`（ruff/mypy/pytest） | QA-S1 | 2h |
| 3 | 两仓 `deploy.yml` 加 `needs` | QA-S1 | 0.5h |
| 4 | 用例 1–4（业务层四个 S） | QA-S2 | 3h |
| 5 | 用例 5–7（网关三个并发） | QA-I1 | 2.5h |
| 6 | 引入 testcontainers，用例 8–9 | QA-I2 | 4h |
| 7 | 压测资产统一到 gateway + 基线文件规范 | QA-I3 | 3h |
| 8 | 正确性检查器（四条不变式） | QA-I4 | 8h |

第 1–5 项合计 11 小时，一周内可以做完。做完之后，「本次体检发现的全部 S 级问题」都有回归用例，「下一次同类问题」在 PR 阶段就会被拦住。

第 8 项（正确性检查器）虽然是校招计划里的重头戏，但它**依赖第 1–6 项的工程基础**——没有 CI、没有 testcontainers、没有基线文件规范，检查器写出来也只能在本地手工跑。

## ★ 关键理解点

- **正向：门禁的意义是「让错误发生在便宜的地方」。** 同一个 bug，在 PR 阶段发现成本是「改一行 + 重跑 3 分钟」，在生产发现成本是「用户投诉 + SSH 排查 + 回滚 + 好久不能合代码」。CI 的全部价值就是把发现点往前挪。
- **反向：覆盖率高不等于测得好，覆盖率低一定意味着有盲区。** `gateway/internal/ws` 82% 覆盖、零缺陷；`biz/internal/realtime` 0% 覆盖、两个 S 级缺陷。覆盖率不能证明质量，但它能精确定位「哪些代码从来没被执行过」——而那正是缺陷最容易积累的地方。
- **边界：单元测试的边界是「函数」，端到端测试的边界是「契约」。** BZ-S2 这类前后端类型不一致的问题，在单元测试层永远测不出来（Go 侧认为 `string` 正确、TS 侧认为 `number` 正确），只有「用对方的真实 payload 打自己的真实接口」才能发现。所以契约测试是独立的一层，不能用单测替代。
- **对比：有测试 vs 有门禁。** 本项目已经有 1303 行测试，但它在合并前不执行。这两件事的区别，就是「写了作业」和「交了作业」——后者才有人批改。
