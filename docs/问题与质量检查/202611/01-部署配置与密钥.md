# 部署、配置与密钥（跨仓）

> 范围：talqora 与 agent-server 两个仓库的部署链路、跨仓配置、密钥与 CI 门禁。网关、业务层、agent-server 内部的代码问题分别见 [03-talqora网关与基础设施](./03-talqora网关与基础设施.md)、[02-talqora业务层](./02-talqora业务层.md)、[04-agent-server](./04-agent-server.md)。
>
> 证据来源：只读代码、配置、脚本与 git 历史，没有参考任何现有文档。每条问题标明核实状态：「已核实」指仓库里的代码与配置能直接证明；「待确认」指结论依赖服务器上的实际状态，需要登录生产环境确认。
>
> 编号规则：DP 表示部署、配置与密钥；S 严重，I 重要，N 一般。

> **整改状态**：本文记录的是审计当时（2026-11-15）的代码状态，不代表当前状态。已完成的整改项与改动后的实测结果，统一见 [00-总览与整改顺序](./00-总览与整改顺序.md) 第 3 节。

## 0 一段话总评

这一组问题的共同点是：**代码已经演进了，部署配置没有跟上，而 CI 里没有任何一道关卡能把这种不一致拦下来。**

9 月 30 日的两次提交把生产编排里的 Node 业务层（`server`）换成了 Go 业务层（`biz`），但以下几处都没有同步：

- CI 的拷贝清单；
- Dockerfile 的 Go 版本；
- nginx 的反代目标；
- agent-server 的 JWKS 地址。

结果是：按 main 分支当前的配置部署，Go 业务层构建不出来，nginx 起不来，AI 助手的两个方向都断了，而部署脚本仍会报告「成功」。另外，官方账号的明文口令写在了仓库文件里。

这些问题单个都不难修，合计约一个工作日。但它们说明部署链路缺一道「配置与代码一致」的自动检查，这才是要补的根本。

## 1 问题清单

### 严重

#### DP-S1 main 分支当前无法部署（已核实三处，一处待确认）

**现象。** 推送到 main 会触发部署，但有三处已核实的独立阻断，任何一处都足以让 Go 业务层无法按新代码上线。

**证据。**

| 阻断 | 证据 | 说明 |
|---|---|---|
| ① CI 不拷贝 biz 源码 | `.github/workflows/deploy.yml:75` 写的是 `source: 'server,gateway,web,docker'` | 生产编排却从 `../biz` 构建业务层（`docker/docker-compose.prod.yml:54-55`）。服务器上的 biz 目录要么不存在、构建直接失败，要么是某次手工拷贝的旧版本，悄悄跑着旧代码 |
| ② Go 版本不匹配 | `gateway/Dockerfile:2` 和 `biz/Dockerfile:2` 都是 `FROM golang:1.22-alpine`；`gateway/go.mod:3` 要求 `go 1.25.0`，`biz/go.mod:3` 要求 `go 1.26.5` | 从 Go 1.21 起，go.mod 里的 go 版本是最低要求。官方 golang 镜像默认设置 `GOTOOLCHAIN=local`，即不自动下载新工具链（待复核），于是构建报错，提示 go.mod 需要更高版本 |
| ③ biz 镜像没有启动命令 | `biz/Dockerfile` 共 20 行，运行阶段到 `EXPOSE 3007 3008` 结束，没有 `ENTRYPOINT` 或 `CMD`；对照 `gateway/Dockerfile` 末行有 `ENTRYPOINT ["/usr/local/bin/gateway"]`；生产编排的 biz 服务也没有 `command:` | 容器会执行基础镜像 alpine 的默认命令 `/bin/sh`。非交互环境下 shell 立即退出，容器按 `restart: unless-stopped` 反复重启，健康检查永远不通过，网关因依赖 biz 健康而一并起不来 |
| ④ 私有包令牌未注入（待确认） | web 构建参数 `NODE_AUTH_TOKEN: ${NODE_AUTH_TOKEN:-}`（`docker/docker-compose.prod.yml` 的 web 服务） | 用于拉取 `@talqora/agent-contracts` 私有包；两条工作流都没注入这个变量。如果服务器上的 .env 也没有，web 镜像构建会因拉不到包而失败 |

**原理。** 这里的 CI 走的是「runner 上 checkout 源码 → scp 到服务器 → 服务器上 `docker compose build`」。所以服务器能构建什么，完全取决于 scp 的清单。新增一个服务目录却没加进清单，这类遗漏在本地开发时永远发现不了：本地仓库里什么都有。

**后果。** 每次推送都可能出现两种结果：构建失败，生产停在旧版本；或者 biz 用旧源码构建成功，生产与仓库不一致却没人知道。第二种更危险。

**修复。**
1. scp 清单改为 `biz,gateway,web,docker`。`server` 是否继续拷贝，取决于 [01-业务层Go统一](../模块开发计划/01-业务层Go统一/02-开发计划-收尾与下线Node.md) 的下线进度；下线后删掉。
2. 两个 Dockerfile 的构建镜像升到与 go.mod 一致的版本，例如 `golang:1.26-alpine`。同时在 CI 里固定一条规则：go.mod 的 go 版本不得高于构建镜像的版本。
3. biz/Dockerfile 末尾补上 `ENTRYPOINT ["/usr/local/bin/biz"]`，并仿照网关加上 `HEALTHCHECK`。
4. 在部署工作流里注入 `NODE_AUTH_TOKEN`（来自 GitHub Secret）。
5. 根本修复是 DP-I1：部署之前先在 CI 里把三个镜像各构建一次，并真的把 biz 容器启动起来、等健康检查通过。只构建不启动，发现不了第 ③ 处那种「镜像能构建、容器起不来」的问题。

**验证。** 在一个干净目录里只放 scp 清单中的目录，执行 `docker compose -f docker-compose.prod.yml up -d --build`，biz、gateway、web 三个容器都应进入 healthy 状态。

#### DP-S2 nginx 仍把 API 反代到已删除的 server 服务（已核实）

**现象。** 生产入口 nginx 的五个 location 仍指向 `server:3007`，而生产编排里已经没有名为 `server` 的服务。

**证据。**
- `docker/nginx/conf.d/default.conf:32、39、46、55、79`：`/api/`、`/oauth/`、`/user/`、`/socket.io/`、`/.well-known/` 都是 `proxy_pass http://server:3007;`。
- `docker/docker-compose.prod.yml` 的服务只有 postgres、redis、biz、gateway、web、coturn。biz 的网络是 `[our-chat, oc-shared]`，没有配置名为 `server` 的网络别名。
- `docker/deploy-build.sh:14-15`：`nginx -t && nginx -s reload || echo "nginx reload 跳过…"`。校验失败只打印一行提示，脚本照样以成功结束。

**原理：为什么 nginx 会直接起不来。** nginx 在加载配置时，就要把 `proxy_pass` 里写死的主机名解析成 IP（相当于启动时查一次 DNS）。在 Docker 网络里，这个查询由内置 DNS（127.0.0.11）回答；不存在的服务名会被回答「查无此名」，nginx 随即报 `host not found in upstream` 并拒绝启动。

同一个文件里 `/agent/` 用的是另一种写法：`resolver` 加变量形式的 `proxy_pass`。它把解析推迟到请求到来时，所以上游不在线时 nginx 仍能启动，只是请求返回 502。

**后果。** 有两种情况，取决于 web 容器这次是否被重建：

| 情况 | 结果 |
|---|---|
| web 镜像有变化，容器被重建 | nginx 启动失败；容器按 `restart: unless-stopped` 反复重启，80/443 全站不可用 |
| 容器没有重建 | 旧 nginx 进程里缓存的是旧 server 容器的 IP，而旧容器已被 `--remove-orphans` 删除，所以 /api、/oauth、/user 全部 502，登录不可用 |

两种情况下，部署脚本都报告成功。

**修复：有两种改法。**

| 维度 | A：HTTP 直连 biz | B：全部经网关转发 |
|---|---|---|
| 做法 | `/api/`、`/oauth/`、`/user/`、`/.well-known/` 改为 `proxy_pass http://biz:3007;`，`/ws` 仍到网关 | 除静态资源外全部转发到 `gateway:8090`，由网关的 PROXY_API 反代到 biz |
| 跳数 | 1 跳 | 2 跳 |
| 故障耦合 | 网关重启只影响长连接，HTTP 不受影响 | 网关重启时 HTTP 一起中断 |
| 网关职责 | 只管长连接 | 兼做 HTTP 反向代理 |
| 额外配置 | 无 | 必须给网关设置 `UPSTREAM_BASE_URL=http://biz:3007`（现在缺省是 127.0.0.1，见 GW 质检文档），并补上超时配置 |

**选 A。** nginx 本来就是反向代理，没有理由再让网关重复做一遍；而且网关的发布频率和故障面应当与 HTTP 解耦。同时：
- 删掉已经无效的 `/socket.io/` location：biz 与 web 都已不再使用 Socket.io；
- 把 deploy-build.sh 改成 `nginx -t` 失败即退出非零，让部署失败显式可见；
- 生产网关关闭 PROXY_API。

**验证。** 部署后的冒烟脚本至少请求四个地址：`/api/health`、`/.well-known/jwks.json`、一次登录、一次 `/ws` 握手，任何一个失败都判定部署失败。

#### DP-S3 AI 助手的跨仓配置两头都断了（已核实配置，生产状态待确认）

**现象。** AI 助手调用链上有两处配置写的是改名前的容器名。

**证据。**

| 方向 | 配置 | 实际容器名 |
|---|---|---|
| 浏览器 → agent-server | talqora `docker/nginx/conf.d/default.conf:105`：`set $agent_upstream agent-node-server:3101;` | agent-server 生产容器已改名为 `agent-rag-http`（agent-server `docker/docker-compose.prod.yml:162`） |
| agent-server → talqora（取 JWKS 公钥） | agent-server `docker/docker-compose.prod.yml:43`：默认值 `http://our-chat-server:3007/.well-known/jwks.json` | talqora 业务层容器名是 `our-chat-biz`（talqora `docker/docker-compose.prod.yml:59`） |

**原理。** 两个仓库各自用 compose 部署，经共享网络 `oc-shared` 按容器名互访，所以容器名在这里就是跨仓接口。一边改了名，另一边的配置就失效了。而两边的部署脚本都带 `--remove-orphans`，旧名字的容器会被删掉，不会「碰巧还活着」。

**后果。**
- `/agent/` 请求返回 502：上游名解析不到；
- 即使请求能到达 agent-server，用 RS256 签名的令牌也会因为取不到 JWKS 公钥而验签失败，返回 401。
- AI 助手整体不可用。

**修复。**
1. 两个名字都改对：talqora 的 nginx 上游改为 `agent-rag-http:3101`；agent-server 的 `OAUTH_JWKS_URI` 默认值改为 `http://our-chat-biz:3007/.well-known/jwks.json`，并由 CI 显式注入。
2. 消除「容器名即接口」的脆弱性：在 oc-shared 网络上给两边的服务配稳定的网络别名，例如 `talqora-idp` 和 `agent-api`，跨仓配置只引用别名，内部改名不再波及对方。
3. 跨仓冒烟测试：talqora 部署后，用一枚刚签发的 agent 令牌请求 `/agent/api/health` 和一个需要鉴权的接口。

#### DP-S4 官方账号的明文口令写在仓库文件里（已核实）

**现象。** 一个「所有用户都自动成为其好友」的官方账号，其明文登录口令出现在仓库文件中。本文不复述口令本身。

**证据。**
- `perf/call-rejoin-probe.mjs` 第 3 行注释，以及第 12–13 行的登录调用，含官方账号和一个测试账号的明文口令。
- `biz/migrations/0006_seed_official_account_tujiang.up.sql` 第 3 行注释写明了该账号的明文口令；数据库里存的是 bcrypt 哈希（第 4 行注释，以及插入语句）。
- 同一迁移的第 1 行注释说明，所有用户（含未来注册者）都会自动成为该账号的好友。biz 启动时会自动执行迁移。

**原理。** 数据库里存 bcrypt 哈希，是为了让数据库泄露时攻击者也拿不到口令。可一旦口令以明文出现在仓库里，哈希的保护就被绕开了：任何能读到仓库的人都能直接登录。git 的历史记录还意味着，即使现在删掉文件，旧提交里的口令依然可读。

**后果。** 能读到仓库的人可以冒充官方账号，给全部用户发消息，而这个账号天然与所有人互为好友。仓库是否公开待确认：如果公开，应当按已泄露处理。

**修复。** 按顺序执行：
1. 立即在生产上修改该账号的口令；测试账号同样处理，或确认生产库里不存在测试账号。
2. 从文件中删除口令。探针脚本改为从环境变量读取账号口令；迁移的注释里删掉口令。迁移文件一旦执行过就不应修改其 SQL 逻辑，这里只改注释，校验和是否受影响要看迁移工具的规则（待确认）。
3. 如果仓库公开或曾经共享，用 git filter-repo 一类工具清理历史，并通知所有克隆者重新克隆。
4. 在 CI 里加入密钥扫描（例如 gitleaks），阻止类似内容再次合入。

**验证。** 对全部历史执行一次密钥扫描，结果为零；旧口令在生产登录失败。

### 重要

#### DP-I1 两个仓库的 CI 都没有质量门禁（已核实）

**现象。**
- talqora：`deploy.yml` 在推送到 main（任意路径）时直接部署，之前没有 Go 的构建、`go vet`、测试、lint，也没有镜像构建验证。另外两条工作流里，`proto.yml` 只做契约校验，`perf.yml` 只检查 web 前端。
- agent-server：推送到 master 直接部署，没有测试和 lint 关卡；而 `make test`（在仓库根运行有 5 个测试失败）和 `make lint`（tools/ 目录有格式问题）本身就是坏的。

**原理。** 门禁的作用是：在部署前用便宜的自动检查，拦住能被机器发现的错误。DP-S1、DP-S2 这两类错误，一次 `docker compose build` 加一次 `nginx -t` 就能发现，却一路进了生产。这不是哪一次粗心，而是流程里根本没有这道关。

**修复。** 两个仓库都改成「检查作业 → 部署作业」，部署作业声明依赖检查作业：

| 仓库 | 检查内容 |
|---|---|
| talqora | Go：build、vet、`test -race`（gateway 与 biz）；三个镜像的 `docker compose build`；用 nginx 官方镜像对 default.conf 跑 `nginx -t`；密钥扫描；go.mod 版本与构建镜像版本一致性检查 |
| agent-server | 在子包目录运行 pytest；ruff check 与 ruff format --check；mypy strict；镜像构建；先修好 Makefile 里的测试入口 |

具体任务与工时见 [07-部署与交付](../模块开发计划/07-部署与交付/开发计划.md)。

#### DP-I2 没有回滚能力（已核实）

**现象。** 镜像只打 `:local` 一个标签；deploy.yml 传入了 `GIT_SHA`（:82）但没有使用；部署末尾执行 image prune 删除旧镜像；容器名固定。

**后果。** 发现坏版本时，唯一的办法是对旧提交重新走一遍完整构建，耗时是分钟级，期间服务处于坏版本。

**修复。** 镜像按 git SHA 打标签，并保留最近 3 个版本；部署脚本记录「上一个成功版本」；冒烟测试失败时自动切回上一版本的标签重新 `up`。

## ★ 关键理解点

- **正向：部署配置也是代码，也会和代码不一致。** 服务改名、目录新增、语言版本升级，都会在部署配置里留下需要同步的地方。保证一致性的手段，是在 CI 里真的把镜像构建一遍、真的跑一次 `nginx -t`、真的发一次冒烟请求。
- **反向：「部署成功」不等于「服务可用」。** deploy-build.sh 吞掉了 nginx 的校验失败，`up -d` 只关心容器有没有起来；判断部署是否成功，必须用面向用户的冒烟请求，而不是看脚本的退出码。
- **边界：跨仓接口不只有 API。** 容器名、网络名、JWKS 地址、令牌的 aud 与 iss，都是两个仓库之间的契约。它们不在 proto 里，所以 buf 的校验管不到，需要用稳定别名加跨仓冒烟测试来守护。
- **对比：bcrypt 哈希与明文口令。** 哈希防的是「数据库泄露」，防不了「口令写进仓库」。一旦明文进了 git 历史，删除文件不等于删除泄露，只有改口令才真正止损。
