# 问题 07：`CACHE 1` 并不是"每次 nextval 都写 WAL"——据此调参是伪优化

> 严重度：**P3（认知纠偏）**——不改任何代码，避免团队做一次没有收益、还要承担跳号风险的变更
> 状态：已核实（PG 序列预写机制）
> 关联：[方向 H · 索引瘦身与序列优化](../08-索引瘦身与序列优化.md)

---

## 一、一句话结论

流传很广的一句"`BIGSERIAL` 默认 `CACHE 1`，所以每次 `nextval` 都写一次 WAL，改成 `CACHE 200` 能显著提升插入吞吐"——**前半句是错的**。PostgreSQL 对序列有固定的预写批量（源码里的 `SEQ_LOG_VALS`，值为 **32**）：即使 `CACHE 1`，也是**每 32 次 `nextval` 才落一条 WAL 记录**。

所以：

> **`CACHE` 几乎不影响 WAL 量，它影响的是"序列页的加锁次数"。** 在本项目当前的写入速率下，这个锁不是瓶颈。

---

## 二、现象：这个说法在哪里出现

- 各类"PG 高并发插入优化"博客的标准套路：`BIGSERIAL` → `CACHE 1` → "每次写 WAL" → 改 `CACHE 1000`；
- 我们自己的排查过程中也一度把它列为"批量写入后的潜在串行点"（[分册 08](../08-索引瘦身与序列优化.md) 已改为"低优先级、需实测"）。

如果不纠正，团队可能在上批量写入（方向 E）之后顺手做一次 `ALTER SEQUENCE ... CACHE 200`，然后**把吞吐的提升错误归因给它**——这会掩盖真正的收益来源，也会让后续容量模型失真。

---

## 三、真实机制

### 3.1 序列的 WAL 预写

序列值存在一个特殊的堆页（`pg_sequence` 对应的 relation）里。`nextval` 流程：

```
取序列页 → 读 seq 值 → +1 → 写回页 → 返回
```

为了减少 WAL，PG 在写序列页时会把"预写配额"一起记进去（`seq->log_cnt`）：

| 参数 | 行为 |
|---|---|
| `CACHE 1` | 每 32 次 `nextval` 落一次 WAL，其余 31 次只改内存页 |
| `CACHE 200` | 每个 backend 一次预取 200 个值，落 WAL 时预写 200×32 = 6400 个 |

也就是说：**`CACHE` 影响的是"跨 backend 的分配粒度"，不是"每次调用是否写 WAL"。**

### 3.2 那么 `nextval` 的成本是什么

| 成本项 | 量级 | 是否受 `CACHE` 影响 |
|---|---|---|
| 序列页的 LWLock 获取/释放 | 亚微秒 | ✅ 受影响（`CACHE` 大 → 同一页的争用减少，但每 backend 仍需取锁） |
| 页内自增（内存操作） | 纳秒 | ❌ |
| WAL 记录 | 每 32 次一条 | ⚠️ 影响很小（32 → 6400 才落一条，但本来就不是每次） |
| 网络往返 | 已经是 INSERT 语句的一部分 | ❌ |

**结论：在 2 万 INSERT/s 的量级、批次内一次调用多次 `nextval` 的场景下，序列锁几乎不可能成为瓶颈。**

### 3.3 什么时候 `CACHE` 真的有用

| 场景 | 是否适用 |
|---|---|
| 单条 INSERT 一个事务、几十个 backend 抢同一个序列、10 万+/s | ✅ 有收益 |
| 批量 INSERT（一个语句内多次 nextval，同一个 backend） | ❌ 无收益（锁本来就在同一个 backend 内串行） |
| 序列被用作"业务计数器"（如订单号） | ✅ 但这时更该考虑号段/雪花 |

本项目属于第二种——**批量写入上线后更不属于第一种**。

## 四、怎么验证（用数据说话，而不是信博客）

### 4.1 看 WAL 记录增速

```sql
-- 压测前后各取一次
SELECT wal_records, wal_bytes FROM pg_stat_wal;
```

对比：

```
wal_records 增量 ÷ 插入行数
```

- 若 ≈ 1（每行一条），说明 WAL 主要来自**索引与堆**，不是序列；
- 序列的贡献 = 插入行数 ÷ 32（`CACHE 1`），占比极小。

### 4.2 看序列页的等待事件

```sql
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE state = 'active'
GROUP BY 1,2 ORDER BY 3 DESC;
```

如果序列是瓶颈，会看到与 `LWLock` / `buffer_content` 相关的等待集中在少数 backend 上。**本项目历史压测（V3 报告）从未观察到这类等待**，瓶颈是连接池。

### 4.3 A/B 对比

```sql
-- 记录基线（同一压测参数、同一轮内）
ALTER SEQUENCE messages_id_seq CACHE 200;
-- 重跑同一场景
```

判定标准沿用压测口径：**Knee 右移 ≥ 20% 才算有效**（A/A 底噪 p99 为 32%，更小的差异不可信）。

## 五、坑点

### 坑 1：`CACHE` 会放大 id 空洞

每个 backend 各自缓存一段序列值。崩溃/重启时未用完的部分丢失：

| `CACHE` | 单次崩溃最大空洞 |
|---|---|
| 1 | ~31 |
| 200 | ~199 |
| 1000 | ~999 |

`id` 在本项目里只作唯一标识（对外是 `serverMsgId`），空洞无害。**但任何"按 id 连续"的假设都会被打断**——目前没有这种假设（分页与同步都用 `seq`）。

### 坑 2：`id` 不能当"消息顺序"用

`seq` 才是会话内单调的游标；`id` 是全局自增，跨会话交错，且受 `CACHE` 影响会跳号。**不要用 `id` 排序或做游标**。

### 坑 3：改 `CACHE` 不会改变已分配的值

`ALTER SEQUENCE ... CACHE n` 只影响之后的分配，不会重排历史。可以随时回滚（改回 1）。

### 坑 4：真正的优化方向是"去掉 nextval"

如果将来确实需要，正确做法不是调 `CACHE`，而是**应用侧生成 id**（雪花 / UUIDv7）：

- 彻底移除序列页访问；
- 但要改 `id` 的生成语义、迁移历史数据、并确认所有消费方（`serverMsgId` 是字符串对外，兼容）；
- 属于结构性改动，与本轮性能目标无关。

### 坑 5：别把"批量写入的收益"归因到序列

批量写入（方向 E）的收益来自 **fsync 次数下降 + 往返摊薄**，与序列完全无关。做 A/B 实验时如果同时改了 `CACHE`，就分不清收益来源了——**单变量原则**。

## 六、验证

| 项 | 方法 | 通过标准 |
|---|---|---|
| WAL 主要来源 | `pg_stat_wal` 增量 ÷ 插入行数 | ≈1（说明来自堆与索引） |
| 序列不是瓶颈 | `pg_stat_activity` 等待事件 | 无集中的 sequence/LWLock 等待 |
| A/B 无差异 | 同参 S8 跑 `CACHE 1` vs `CACHE 200` | Knee 位置差异 < 20%（即无效） |
| 空洞可接受 | 重启后查 `max(id) - count(*)` | 空洞存在但不影响任何功能 |
