# 问题 08：读消息接口只做认证、不做授权（越权读取 / IDOR）

> 严重度：**P0（安全）**——任何登录用户都能读取任意会话的消息
> 状态：已确证（路由有 `AuthenticateToken`，处理器内无成员校验）
> 关联：[方向 G · 读端点治理](../07-读端点分页与慢查询治理.md)

---

## 一、一句话结论

`/user/messages`、`/user/lastMessages`、`/user/conversations` 三个读接口**都有登录校验（认证）**，但**都没有"你是不是这个会话的成员"的校验（授权）**。而 `conversationId` 是可预测的（`single_<uid1>_<uid2>`、`group_<id>`），所以任何登录用户只要改一下 ID，就能读到别人的私聊与群聊内容。

> 准确表述：不是"没有鉴权"，而是**认证到位、授权缺失**（IDOR，Insecure Direct Object Reference）。

---

## 二、证据

### 2.1 路由层：三个接口都挂了认证中间件

`biz/internal/api/chat_routes.go:17-25`：

```go
func mountChatRoutes(r *gin.Engine) {
    g := r.Group("/user")
    g.GET("/userConversations", AuthenticateToken(), handleUserConversations)
    g.GET("/conversations",      AuthenticateToken(), handleConversations)
    g.GET("/messages",           AuthenticateToken(), handleMessages)      // ← 认证有
    g.POST("/updateConversationTime", AuthenticateToken(), handleUpdateConversationTime)
    g.GET("/lastMessages",       AuthenticateToken(), handleLastMessages)  // ← 认证有
}
```

### 2.2 处理器内：没有任何"成员/属主"判断

**`handleMessages`**（`chat_routes.go:71-121`）：只校验 `conversationId` 非空，随后直接查库。

```go
conversationID := c.Query("conversationId")
if conversationID == "" { ...400... }
// ← 这里应该有一次 IsConversationMember
messages, err := chatSvc.Messages(ctx, conversationID, before, limit)
```

**`handleLastMessages`**（`chat_routes.go:144-179`）：直接把入参当会话 ID 列表查。

```go
ids := parseStringArray(c.Query("userConversationIds"))   // 参数名叫 userConversationIds，实际当 conversation_id 用
msgs, err := chatSvc.LastMessages(ctx, ids)               // ← 无属主过滤
```

**`handleConversations`**（`chat_routes.go:49-65`）：按 ID 集合返回会话详情，同样没有属主校验。

### 2.3 对比：其他接口是做了的

| 接口 | 授权检查 | 位置 |
|---|---|---|
| `/user/sync` | ✅ `IsConversationMember` | `sync_routes.go:72-80` |
| `/user/read` | ✅ 同上 | `sync_routes.go:136-144` |
| `/user/readCount` | ✅ 同上 | `sync_routes.go:175-183` |
| `/user/userConversations` | ✅ `userId == currentUser` | `chat_routes.go:36-39` |
| `/user/updateConversationTime` | ✅ `userId == currentUser` | `chat_routes.go:130-133` |
| **`/user/messages`** | ❌ | — |
| **`/user/lastMessages`** | ❌ | — |
| **`/user/conversations`** | ❌ | — |

同一个模块里两套标准，说明不是"设计如此"，而是遗漏。

### 2.4 `conversationId` 完全可以猜

会话 ID 是业务拼出来的，不含任何随机成分：

| 形态 | 生成规则 | 可枚举性 |
|---|---|---|
| 单聊 | `single_<minUserId>_<maxUserId>` | **用户 ID 是自增的**，从 1 开始遍历即可 |
| 群聊 | `group_<groupId>` | 自增，同样可遍历 |

```bash
# 攻击示例（仅需一个合法账号）
curl -b 'token=<自己的token>' 'http://host/user/messages?conversationId=single_1_2&limit=50'
curl -b 'token=<自己的token>' 'http://host/user/messages?conversationId=group_9000002&limit=50'
```

## 三、根因

### 3.1 授权逻辑被"写在了错误的地方"

`IsConversationMember` 已经存在（`service/read.go:15-24`），也在 `/user/sync` 里被正确使用。`/user/messages` 漏掉它，最可能的原因是：**该接口最早是按"数据访问"实现的，鉴权被默认成"前端只会拿自己的会话 ID 来请求"**——把客户端的善意当成了安全边界。

### 3.2 `userConversationIds` 参数名加深了误解

`/user/lastMessages` 的参数叫 `userConversationIds`，但 repo 里当 `conversation_id` 用（`chat.go:92-95`）。名字暗示"这些是当前用户的会话行 ID"，从而让人误以为"能列出这些 ID 就说明是本人"——**实际上服务端从未验证过这些 ID 属于谁**。

---

## 四、影响

| 维度 | 影响 |
|---|---|
| 隐私 | 任意登录用户可读任意私聊/群聊的**全部历史消息**（`/user/messages` 无 limit 时是全量） |
| 规模 | 用自增 ID 遍历即可批量拉取，不需要任何特殊权限 |
| 合规 | 属于典型的越权访问漏洞，若涉及真实用户数据，是必须披露与整改的级别 |
| 与性能的关系 | **无**。它不是吞吐问题，但在做读接口改造（方向 G）时是顺手必须补上的一道门 |

---

## 五、方案

### 5.1 单聊：从 ID 直接推导，零成本

```go
// 必须先按前缀分流：DeriveParticipants 对非 single_ 前缀会回落成 [senderID]，
// 直接用它做鉴权会把群聊误判为"有权"。
if strings.HasPrefix(convID, "single_") {
    parts := service.DeriveParticipants(convID, currentUserID)
    // 只有成功解析出双方（len==2）且包含当前用户才放行；
    // 解析失败时它返回 [senderID]，长度不足 2 → 拒绝
    if len(parts) != 2 || !slices.Contains(parts, currentUserID) {
        forbidden(c); return
    }
} else if gid, ok := service.ParseGroupConvID(convID); ok {
    // 群聊走成员表（带缓存，见 5.2）
    if !isMemberCached(ctx, gid, currentUserID) { forbidden(c); return }
} else {
    forbidden(c); return   // 未知形态一律拒绝
}
```

对 `single_<u1>_<u2>`，`DeriveParticipants` 返回两个 ID；判断当前用户是否在其中即可，**不需要任何 DB 查询**。这是绝大多数流量（单聊）的路径。

> **边界必须显式处理**：`DeriveParticipants` 的契约是"异常情况回落到 `[senderID]`"（`message.go:241-256`），所以**不能**用"当前用户是否在返回列表里"作为唯一判据——否则群聊或畸形 ID 会被误判为有权。必须先判断 `len(parts) == 2`。
>
> 另外 `single_5_5`（自聊）会返回 `[5,5]`，长度 2，属于合法；`single_x_1` 返回 `[senderID]`，长度 1，应拒绝。

### 5.2 群聊：查成员表 + 缓存

```go
member, err := groupRepo.IsMember(ctx, groupID, currentUserID)   // RO 池
```

`IsMember` 已经存在（`repo/group.go:171-179`），走只读池。为避免每条消息多一次查询，加一层进程内缓存：

| 缓存 | TTL | 失效 |
|---|---|---|
| `memberCache[userID:groupID]` | 60 s | 退群/被踢时主动删（若暂无该功能，TTL 到期自然失效） |

> **不要复用 `ucExistsCache`**（`message.go:51-54`）：那是"写路径已确认存在"的缓存，语义是"这行我写过"，不是"这个用户可以读"。

### 5.3 `/user/lastMessages` 与 `/user/conversations` 的批量授权

这两个接口收的是 ID 列表，逐个检查会比查询本身还贵。推荐**反过来做**：从"当前用户的会话列表"出发过滤。

```sql
-- 一次查询拿到"当前用户有权的会话 ID 集合"，再与入参求交集
SELECT conversation_id FROM user_conversations WHERE user_id = $1
  AND conversation_id = ANY($2::text[]);
```

- 索引：`user_conversations (user_id, conversation_id)` 上的唯一约束（`user_id, conversation_id`）刚好可裁剪；
- 若单用户会话数很大（数千），可改为"只对入参里的 ID 逐个 EXISTS"（N 次点查，走唯一索引，很快）。

**判定原则**：入参里任何一个 ID 不在允许集合中，就**过滤掉**（而不是整请求 403），因为 `lastMessages` 是"给我这些会话的最后一条"，部分无权应当返回部分结果。而 `/user/messages` 是单一对象，无权即 403。

### 5.4 返回码语义

| 接口 | 无权时 | 理由 |
|---|---|---|
| `/user/messages` | 403 `{"message":"无权访问该会话"}` | 与 `/user/sync` 一致（`sync_routes.go:78`） |
| `/user/lastMessages` | 200 + 过滤后的结果 | 列表语义，部分成功 |
| `/user/conversations` | 200 + 过滤后的结果 | 同上 |

> 不建议统一返回 404：会话 ID 本身可枚举，404 并不隐藏存在性，反而增加排查成本。

## 六、坑点

### 坑 1：加校验会让"慢请求"变成"两个慢请求"

`/user/messages` 单请求 1.8 s（无 limit），再加一次成员校验并无所谓；但**修完分页（方向 G）后单请求只有 5 ms**，此时多一次 DB 查询会占 40% 的时间。

**所以必须用 §5.1 的"单聊零查询推导"**，只有群聊才查库（且带缓存）。顺序上建议：**先修方向 G 的分页，再加授权**，否则两个慢查询叠加。

### 坑 2：不要在授权失败时暴露"会话是否存在"

直接返回 403 即可，不要区分"会话不存在"与"你不是成员"——虽然 ID 可枚举，但少一个信号总是好的。

### 坑 3：群成员缓存的失效

如果实现了"退群/踢人"，缓存必须主动失效，否则被踢的人 60 s 内仍可读。**当前若无该功能，TTL 就够；一旦加退群，必须同步改缓存失效路径。**

### 坑 4：单聊 ID 的规范化

`single_1_2` 与 `single_2_1` 可能同时存在（历史上未强制排序）。校验时**两种顺序都要认**，否则会误判合法用户无权：

```go
parts := service.DeriveParticipants(convID, currentUserID)  // 已处理两种顺序
```

### 坑 5：HTTP 与 WS 两条路径都要覆盖

`read.report` 走 WS（`handleReadReport`），已经有 `IsConversationMember`（`handleUplink.go:220`）。但 `message.send` 的**群成员校验只校验发送者**（`message.go:82-90`），没有校验"这个会话是否存在/是否合法"。这不是本次问题，但改造时别把两者搞混。

### 坑 6：压测与内部调用

如果压测脚本或运维工具用"跨用户读取"来校验数据（例如 `perf/` 里的对账），加授权后会 403。需要给内部调用留一条路径（内部 token）或改用直连 DB 校验。**上线前 grep 一遍 `perf/` 与 `biz/scripts/`。**

## 七、验证

| 项 | 方法 | 通过标准 |
|---|---|---|
| 越权被拒 | 用户 A 请求 `single_<B>_<C>` | 403 |
| 正常可读 | 用户 A 请求 `single_<A>_<B>` | 200 |
| 群越权 | 非群成员请求 `group_<id>` | 403 |
| 列表过滤 | `/user/lastMessages` 混入无权 ID | 200，只返回有权会话 |
| 性能 | 单聊读取 p50 | 不高于改造前 115%（推导路径应几乎无开销） |
| 回归 | 全量 e2e（web 首屏、翻页、群聊） | 无 403 误伤 |

```bash
# 越权回归脚本（两账号）
A_TOKEN=... B_TOKEN=... CONV_B_C=single_<B>_<C> \
  bash -c 'curl -s -o /dev/null -w "%{http_code}\n" -b "token=$A_TOKEN" "http://localhost:3007/user/messages?conversationId=$CONV_B_C"'
# 期望 403
```
