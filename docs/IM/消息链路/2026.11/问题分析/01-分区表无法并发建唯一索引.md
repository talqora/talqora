# 问题 01：分区表无法并发建唯一索引（方向 A 的落地障碍）

> 严重度：**P0（阻塞项）**——不是现网故障，而是"修 seq 缺陷"绕不过去的一道坎
> 状态：已确证（PG 版本行为 + 现有迁移文件）
> 关联：[方向 A · seq 修复](../01-seq发号器并发缺陷修复.md)

---

## 一、一句话结论

`messages` 是按 `conversation_id` HASH 分区的分区表，而 **PostgreSQL 不支持在分区表上使用 `CREATE INDEX CONCURRENTLY`**（PG 16 仍然如此）。这意味着"加唯一索引拦截重号"这件事**没法用常规的零阻塞方式做**——要么接受一次写入阻塞，要么走"逐分区并发建 + `ATTACH PARTITION`"的绕行方案。

---

## 二、现象

### 2.1 直接执行会报错

```sql
CREATE UNIQUE INDEX CONCURRENTLY uq_messages_conv_seq
  ON messages (conversation_id, seq);
```

```
ERROR:  cannot create index on partitioned table "messages" concurrently
```

同样的限制也适用于 **`DROP INDEX CONCURRENTLY`**：

```sql
DROP INDEX CONCURRENTLY idx_messages_conv_ts;
-- ERROR: cannot drop index on partitioned table "messages" concurrently
```

### 2.2 但非并发的建索引是"能建"的

`migrations/0007_messages_partition.up.sql:102-105` 就是这么做的：建表时表是空的，直接 `CREATE INDEX` 秒级完成，不构成问题。

**问题只出现在"表里已有 747 万行"的现在。**

### 2.3 最容易误判的一点

`messages` 是分区**父表**，真正存数据的是 `messages_p00 … messages_p63`。有人会想"那我建在父表上、让它自己传播不就行了"——传播是有的，但**传播过程不是一个事务**：父表 DDL 会对所有分区逐一加锁建索引，整个过程持 `SHARE` 锁，期间所有 `INSERT` 被阻塞。

---

## 三、根因

### 3.1 为什么 `CONCURRENTLY` 不能用于分区表

`CONCURRENTLY` 的实现要求：

| 要求 | 分区表的现实 |
|---|---|
| 索引构建必须跨多个短事务（而不是一个长事务） | 分区表的索引是"一个父索引 + N 个子索引"的树，`ATTACH` 关系必须在**单个事务**里维护一致性 |
| 构建期间允许并发写 | 每个分区可以做到，但"父索引对所有子索引可见"这个状态没有中间态可表示 |

PG 选择直接禁用，而不是提供一个"每个分区并发、父索引稍后生效"的隐式流程——后者需要用户显式 `ATTACH`，也就是下面 §四的方案 B。

### 3.2 阻塞的真实代价

非并发建索引对写入持 `SHARE` 锁（与 `INSERT` 冲突）：

```
747 万行 / 64 分区 ≈ 每分区 11.7 万行
单分区建 B-tree ≈ 数十毫秒到数百毫秒（视 buffer 命中）
父表逐个分区执行 → 总时长 ≈ 数秒到数十秒
```

这几十秒内：**所有 `message.send` 都会卡在 INSERT 上**，客户端 5 s 超时后会重发，形成重发风暴；重发又撞在同一把锁上。**这是必须避免的**。

---

## 四、方案对比

| 方案 | 阻塞 | 复杂度 | 适用 |
|---|---|---|---|
| A. 维护窗口直接建 | 数十秒写阻塞 | 低 | 可停机 / 可接受短暂写入失败 |
| B. 逐分区 `CONCURRENTLY` + `ATTACH` | **零阻塞** | 中（脚本要生成 64 段） | 线上，推荐 |
| C. 用触发器/应用层兜底代替唯一索引 | 无 | 高（性能差、易漏） | 不推荐 |
| D. 不上唯一索引，只修代码 | 无 | 低 | **不可接受**：没有任何机制能证明"再也不会重号" |

选 **B**。

---

## 五、方案 B 的完整步骤

### 5.1 前置：先清洗存量重复

唯一索引建不上去的直接原因是存量 21 万组重复。清洗 SQL 见 [方向 A §4.2](../01-seq发号器并发缺陷修复.md)。**清洗必须先完成**，否则第 3 步会失败。

### 5.2 逐分区并发建（零阻塞）

```sql
-- 对 64 个分区逐个执行；可以用脚本生成
CREATE UNIQUE INDEX CONCURRENTLY uq_p00 ON messages_p00 (conversation_id, seq);
CREATE UNIQUE INDEX CONCURRENTLY uq_p01 ON messages_p01 (conversation_id, seq);
...
CREATE UNIQUE INDEX CONCURRENTLY uq_p63 ON messages_p63 (conversation_id, seq);
```

**注意 `CONCURRENTLY` 不能在事务块里执行**（`BEGIN ... COMMIT` 内会报错）。用 `psql -f` 逐条跑，或用 `psql --single-transaction=false`。

### 5.3 建一个"空壳"父索引

```sql
CREATE UNIQUE INDEX uq_messages_conv_seq ON ONLY messages (conversation_id, seq);
```

`ON ONLY` 是关键：只建父索引的元数据，**不**去建各分区的索引（否则又变成阻塞式全量构建）。此时父索引标记为 `indisvalid = false`。

### 5.4 逐个挂接

```sql
ALTER INDEX uq_messages_conv_seq ATTACH PARTITION uq_p00;
ALTER INDEX uq_messages_conv_seq ATTACH PARTITION uq_p01;
...
```

挂接时 PG 会校验子索引与父索引定义一致，并把子索引标记为"属于该父索引"。全部挂接完成后父索引变为 valid。

### 5.5 验证

```sql
-- 父索引与 64 个子索引都应 valid
SELECT c.relname, i.indisvalid, i.indisunique
FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
WHERE c.relname LIKE '%uq_messages_conv_seq%' OR c.relname LIKE 'uq_p%'
ORDER BY c.relname;
```

期望：65 行，`indisvalid = true`、`indisunique = true`。

## 六、坑点

### 坑 1：`ON ONLY` 漏写就等于没做优化

`CREATE UNIQUE INDEX ... ON messages (...)`（不带 `ONLY`）会对 64 个分区逐个建索引，**持锁数十秒**，与方案 A 没有区别。这是最容易写错的一行。

### 坑 2：`ATTACH` 要求索引定义完全一致

比对项包括：列顺序、排序方向（`DESC`）、操作符类、排序规则（collation）、部分索引的谓词。任一不一致都会报：

```
ERROR: index "uq_p00" is not valid
-- 或
ERROR: cannot attach index ... as it does not match ...
```

**解决**：所有子索引用完全相同的 DDL 模板生成（只换表名），不要手工微调。

### 坑 3：`CONCURRENTLY` 失败会留下 INVALID 索引

并发建索引如果被取消（连接断开、`lock_timeout`、OOM），会残留一个 `indisvalid = false` 的索引，**它会继续被 INSERT 维护（拖慢写入）但不生效**。

```sql
-- 检查
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
-- 清理
DROP INDEX CONCURRENTLY uq_p07;   -- 分区上可以 CONCURRENTLY
```

上线前必须跑一次这个检查。

### 坑 4：`lock_timeout` 与 `statement_timeout`

`ATTACH PARTITION` 需要对子索引加短暂锁。建议：

```sql
SET lock_timeout = '3s';
SET statement_timeout = '60s';
```

超时就重试该条，不要放大到 30 s 以上（否则会排在别人后面，越等越久）。

### 坑 5：不要在同一个 migration 里既清洗又建索引

`golang-migrate` 的 migration 是**单事务**执行的（默认），而 `CONCURRENTLY` 不能被包在事务里。所以：

- 唯一索引**不能写进 migration 文件**；
- 必须作为独立的运维脚本（`biz/scripts/add_uq_messages_conv_seq.sh`）执行，并在应用启动前完成；
- 代码侧要能容忍"索引还没建"的中间态（即冲突重试逻辑不能依赖索引一定存在，见问题 02）。

### 坑 6：分区数量固定，但没有"未来新分区"的兜底

当前是 64 个静态哈希分区，不会有新分区被创建，所以"建完索引后新分区漏建"不会发生。**如果将来改成按时间分区（range），这个方案就要补"新分区自动建索引"的机制**（PG 11+ 的 `CREATE INDEX ON ONLY` + 自动 attach 模板），否则新分区会没有唯一约束。

### 坑 7：唯一索引也会影响 INSERT 性能

冲突检测需要在索引里做**唯一性探测**。分区内 11.7 万行、索引常驻内存时开销很小（微秒级），但会比普通索引略贵。这是必须付的代价——它换来的是"再也不会静默重号"。

## 七、验证

| 项 | 方法 | 通过标准 |
|---|---|---|
| 索引全部有效 | §5.5 的查询 | 65 行全 `valid` |
| 无残留无效索引 | `SELECT ... WHERE NOT indisvalid` | 0 行 |
| 写入未被阻塞 | 建索引期间跑 2000 msg/s，观察 p99 | 无 > 1 s 的尖峰 |
| 约束真的生效 | 手工插入一条重复 `(conversation_id, seq)` | 报 `23505`，`constraint = uq_messages_conv_seq` |
| 冲突可重试 | 应用侧构造重复后重试 | 最终成功，消息不丢（见问题 02） |
