# 问题 03：消息正文长度完全不校验，单条可达 1 MB

> 严重度：**P1（现网缺陷，资源放大 + 稳定性）**
> 状态：已确证（入参校验只覆盖标识字段，不覆盖载荷）
> 关联：[方向 E · 批量写入](../05-组提交批量写入.md)、[方向 I · 边缘层](../09-边缘层背压与流写入串行化.md)

---

## 一、一句话结论

`parseSendMessage` 校验了 `clientMsgId ≤ 64`、`conversationId ≤ 100`、`type ≤ 32`，**但对 `content` 一个字节都不校验**。而链路上唯一的硬限制是"整帧 1 MB"（网关 `SetReadLimit`、gRPC `MaxRecvMsgSize`），所以**一条 1 MB 的文本消息可以合法地写进库、扇出给群里所有人、并被缓存进每个慢消费者的发送缓冲**。

批量写入上线后，这个缺口会从"单条很贵"升级成"整批失败"。

---

## 二、证据

### 2.1 校验函数只看了三个字段

`biz/internal/realtime/handleUplink.go:67-85`：

```go
func parseSendMessage(payload json.RawMessage) (sendMessageInput, bool) {
    var in sendMessageInput
    if err := json.Unmarshal(payload, &in); err != nil { return in, false }
    if in.ClientMsgID == "" || len(in.ClientMsgID) > 64 { return in, false }
    if in.ConversationID == "" || len(in.ConversationID) > 100 { return in, false }
    if in.Type == "" { in.Type = "text" }
    if len(in.Type) > 32 { return in, false }
    return in, true
}
```

`Content`、`Mentions`、`Extra`、`FileInfo` **没有任何长度约束**。

### 2.2 三层限制都是"帧级"，不是"业务级"

| 层 | 限制 | 位置 | 含义 |
|---|---|---|---|
| gateway WS | 单帧 ≤ 1 MB | `gateway/internal/hub/conn.go:105` `SetReadLimit(1<<20)` | 含整个 `{type,data}` 信封 |
| biz gRPC | 单帧 ≤ 1 MB | `biz/internal/realtime/edge.go:40` `MaxRecvMsgSize(1<<20)` | 同上 |
| DB | `content TEXT NOT NULL` | `migrations/0007:11` | **无上限**（TEXT 上限 1 GB） |

也就是说：**只要塞得进 1 MB 的帧，就会原样落库。**

### 2.3 复现

```js
// perf/ 里的客户端协议形态
ws.send(JSON.stringify({
  type: "message.send",
  data: { clientMsgId: "x1", conversationId: "single_1_2", content: "A".repeat(1000 * 1024) }
}));
```

结果：ack 成功、库里多了一行 ~1 MB 的记录、对端收到一条 1 MB 的下行帧。

## 三、影响（按放大倍数排序）

### 3.1 群扇出：一条消息 = N 份内存副本

`FanoutDownlink` 对每个在线成员投一次。帧体（含 1 MB content）在**同一次调用内只 marshal 一次**（`downlink.go:104-106` 的 `frameData` 复用），但：

| 环节 | 放大 |
|---|---|
| gRPC 下行 `stream.Send` | 每帧一次序列化 + 流控窗口占用（1 MB 窗口 ≈ 刚好一帧） |
| fallback pub/sub | **每个网关副本都收到完整 1 MB**，由 Redis 转发 |
| 慢消费者 `send` channel | 单连接可缓冲 256 帧（`GATEWAY_SEND_BUFFER=256`）→ **最坏 256 MB/连接** |

最后一条最危险：一个不读数据的客户端，在收到 256 条 1 MB 消息后才会被逐出，期间网关内存被单条连接吃掉 256 MB。

### 3.2 批量写入：一条毒丸毁掉整批

方向 E 的批大小是 64 条。若 64 条都是 1 MB：

```
单条 INSERT 语句 ≈ 64 MB 参数 + 64 MB WAL
→ 语句执行时间超出批超时 → 整批失败
→ 64 个客户端同时重发 → 再次组成 64 MB 批 → 雪崩
```

这不是理论推演：批量窗口只有 2 ms，只要瞬间来 64 条大消息就会凑成一批。

### 3.3 单条成本

| 维度 | 1 KB 消息 | 1 MB 消息 | 倍数 |
|---|---|---|---|
| 落库字节（含 TOAST） | ~1 KB | ~1 MB | 1000× |
| 下行网络 | ~1 KB | ~1 MB | 1000× |
| JSON 解析/序列化 CPU | ~5 μs | ~2–5 ms | 1000× |
| Redis fallback 流量 | ~1 KB × 副本数 | ~1 MB × 副本数 | 1000× |

**在一台机器上，一条 1 MB 消息的 CPU 成本 ≈ 1000 条正常消息。** 它不需要很多，就能把 p99 打坏。

### 3.4 顺带的风险

- 用户可以拿它当免费对象存储（base64 塞图片），绕过 `/user/uploads/*` 的 S3 计费与审计路径；
- `RETURNING` 会把 1 MB content 原样带回应用层，再 marshal 进 ack 的 `raw_response`（`edge_util.go:83`）——**ack 也变成 1 MB**。

## 四、根因

### 4.1 校验的边界选错了

现有校验集中在"**标识字段**"（用于路由、幂等、日志），因为它们有明确的技术约束（列宽）。而"**载荷字段**"被默认为"用户内容，不该限制"——但工程上必须有上限，否则资源消耗不可控。

### 4.2 限制散落在基础设施层，缺业务层定义

三层限制（WS 1 MB / gRPC 1 MB / TEXT 1 GB）都是**传输与存储的物理上限**，不是**产品与容量的业务上限**。缺的是中间那层：

```
产品语义（一条文本消息应该多大？）
        ↓  ← 缺这一层
传输/存储物理上限（1 MB / 1 GB）
```

## 五、方案

### 5.1 定义业务上限

| 字段 | 建议上限 | 理由 |
|---|---|---|
| `content` | **64 KB**（可配 `MSG_CONTENT_MAX_BYTES`） | 覆盖长文/代码片段/RichText；图片/文件必须走 `fileInfo` + S3 |
| `mentions` | 4 KB / ≤ 200 个 id | 大群 @所有人也够用 |
| `extra` | 8 KB | 富文本元数据 |
| `fileInfo` | 8 KB | 只存元数据与 URL |
| 整帧 | 保持 1 MB（基础设施兜底） | 不依赖它做业务限制 |

### 5.2 校验位置：必须在发号之前

```go
// handleUplink.go handleMessageSend，紧跟 parseSendMessage 之后
if len(in.Content) > cfg.MsgContentMaxBytes {
    metrics.MessageRejectedTotal.WithLabelValues("content_too_large").Inc()
    return UplinkResult{Status: 400, Body: map[string]any{
        "type": "message.error",
        "data": map[string]any{"message": "消息内容过长", "clientMsgId": in.ClientMsgID},
    }}
}
```

**顺序很重要**：限流 → **长度校验** → 幂等 → 发号。放在发号之后会白占号（产生洞），放在限流之前会让超大帧绕过限流计数。

### 5.3 两条上行路径都要加

| 路径 | 位置 |
|---|---|
| gRPC 流（主路径） | `handleMessageSend`（上面这处） |
| HTTP 上行（兼容路径） | `api/internal_routes.go` 复用同一个 `HandleUplink`，自动覆盖 ✅ |

因为两条路径最终都走 `HandleUplink`，只要改这一处即可——**但需要确认 HTTP 路径没有被绕过**（grep `PersistMessage` 的调用点）。

### 5.4 网关侧可以加"更小的帧上限"吗

可以，但要谨慎：

| 做法 | 问题 |
|---|---|
| 把 `SetReadLimit` 降到 128 KB | 会同时限制**上行所有帧类型**（含未来可能的批量帧），且错误表现为"连接被关闭"，客户端拿不到友好提示 |
| 保持 1 MB，业务层拒绝 | 推荐：错误可控、可观测、可灰度 |

## 六、坑点

### 坑 1：`len()` 是字节数，不是字符数

```go
len("你好")        // 6
len("👨‍👩‍👧")     // 可能是 18 甚至更多（ZWJ 组合）
```

前端如果用 `str.length`（UTF-16 码元）限制"2000 字"，中文是 2000 字符 = 6 KB，与 64 KB 的字节上限并不冲突；但**如果按"字符数"实现后端校验，就会与前端不一致**。统一用**字节**，并在错误信息里说清楚。

### 坑 2：拒绝必须在发号前

见 §5.2。放在发号之后会造成两个后果：① `seq` 出现洞（本可避免）；② `seqInitialized` 被污染（虽然无害，但会让监控看不出"到底有多少号被浪费"）。

### 坑 3：历史数据里可能已经有超大消息

上线前先统计，避免"新限制生效后，旧消息仍能被打开展示但无法重新发送"的困惑：

```sql
SELECT count(*), max(length(content)), percentile_cont(0.99) WITHIN GROUP (ORDER BY length(content))
FROM messages WHERE created_at > now() - interval '30 days';
```

如果 p99 已经接近阈值，说明阈值定得太紧，应该先灰度观察（只打日志不拒绝）。

### 坑 4：灰度策略

| 阶段 | 行为 |
|---|---|
| 阶段 1 | 只记 `MessageRejectedTotal{reason="content_too_large"}` + 采样日志，不拒绝 |
| 阶段 2 | 阈值 × 2 处拒绝，观察错误率与客户端重试 |
| 阶段 3 | 收敛到目标阈值 |

一次性硬切会让存量客户端（尤其是粘贴长文本的用户）突然大面积失败。

### 坑 5：图片/文件不能靠"调大阈值"解决

如果产品需要发原图，正确路径是 `fileInfo` + `/user/uploads/*`（S3），而不是把 base64 塞进 `content`。后者会：① 让消息表膨胀；② 让下行变慢；③ 无法 CDN 加速；④ 无法单独清理。

**阈值一旦定死，就等于强制这条路径。**

### 坑 6：`RETURNING` 与 ack 的体积

当前 INSERT 的 `RETURNING` 包含 `content`（`message.go:130-131`），ack 的 `raw_response` 也包含完整消息体（`makeAck` 的 `RawResponse`）。**大消息会让 ack 也变大**，等于把成本再加一倍。

建议在方向 B 改造时顺手裁剪 `RETURNING` 列（只需要 `id/seq`），见[分册 02 §4.3](../02-落库去显式事务.md)。

## 七、验证

| 项 | 方法 | 通过标准 |
|---|---|---|
| 拒绝生效 | 发 65 KB content | `message.error` 带 `clientMsgId`，不落库、不占号 |
| 边界正确 | 发 64 KB / 64 KB+1 B | 前者成功、后者失败 |
| 不占号 | 连续发 10 条超限 | `seq` 不前进 |
| 指标 | `MessageRejectedTotal{reason="content_too_large"}` | 有值 |
| 内存 | 1 万连接 + 每秒 10 条 1 MB（修复前） | 网关 RSS 显著上升，可复现 |
| 批量不受影响 | 方向 E 上线后发 65 KB | 被拒于入队前，不进批 |
