# 08 · 为什么需要 seq：next_seq、conversations 表，以及"为什么不能直接用 id"

> 这篇回答四个连环问题：
> ① `next_seq` 是干什么的？② 为什么要有 `conversations` 表？
> ③ 能不能通过改表结构，让会话内的并发消息不去竞争 `next_seq`？
> ④ 消息记录里已经有 `id` 了，为什么还要 `seq`？不能直接用 id 排序吗？

---

## 〇、一句话结论

- **`next_seq` 是"会话表里的一个计数器"**，它不是消息的一部分，只负责"下一条消息该发几号"。
- **`conversations` 表主要是存会话元数据**（类型、标题、头像），`next_seq` 只是后加的一列。
- **改表结构不能消除竞争**——竞争的根源是"同一会话的所有写都要改同一行"，不是"表太宽"。
- **`id` 能排序，但不能当"会话内游标"**：它全局自增、跨会话交错、洞太大、且不能预分配。

---

## 一、三个东西摆在一起看

### 1.1 真实表结构

`conversations`（`migrations/0001:85-94` + `0002:6` 加的一列）：

```sql
CREATE TABLE conversations (
  id         VARCHAR(100) PRIMARY KEY,   -- 会话 ID，如 single_1_2
  conv_type  "ConvType" NOT NULL,        -- single / group
  title      VARCHAR(100),               -- 群名（单聊为空）
  avatar     VARCHAR(255),               -- 群头像
  created_at TIMESTAMPTZ,
  updated_at TIMESTAMPTZ,
  next_seq   BIGINT NOT NULL DEFAULT 0   -- ← 后加的"发号计数器"
);
```

`messages`（`0007:7-26`，节选）：

```sql
CREATE TABLE messages (
  id              BIGSERIAL,              -- 全局自增，跨会话交错
  conversation_id VARCHAR(100) NOT NULL,  -- 属于哪个会话
  sender_id       BIGINT NOT NULL,        -- 谁发的
  seq             BIGINT NOT NULL,        -- ← 会话内序号
  client_msg_id   VARCHAR(64),            -- 客户端的幂等键
  content         TEXT,
  ...
  PRIMARY KEY (id, conversation_id)       -- 分区表要求主键含分区键
);
```

### 1.2 你的理解是对的

> "每个消息都要先去 conversation 改 next_seq，然后往 message 表写消息记录，这个消息记录里面有自己所在的会话 id 和 seq 号，用来确定自己在会话中的顺序。"

**完全正确。** 用两条语句表示就是：

```sql
-- 第 1 步：拿号（在 conversations 表上）
UPDATE conversations SET next_seq = next_seq + 1
WHERE id = 'single_1_2'
RETURNING next_seq;                       -- 假设返回 106

-- 第 2 步：写消息（把 106 写进 messages）
INSERT INTO messages (conversation_id, sender_id, seq, client_msg_id, content, ...)
VALUES ('single_1_2', 1, 106, 'c-abc', '你好', ...);
```

这两步**必须在一个事务里**，否则会出现"号发了但消息没写"（留下一个洞）或"消息写了但号没发"（重号）。

## 二、`next_seq` 到底是什么

### 2.1 它是"最后发出的号"，不是"下一个号"

名字叫 `next_seq`，但因为 SQL 是**先加一再返回**：

```
初始：next_seq = 0
第 1 条消息：UPDATE → 1，返回 1；列变成 1
第 2 条消息：UPDATE → 2，返回 2；列变成 2
...
```

所以列里存的是"**最后发出的号**"，而"下一个要发的号"是 `next_seq + 1`。

> 这是历史命名留下的坑：**名字叫 next，语义是 last issued**。理解了这一点，后面 Redis 的 `SET init + INCR` 就顺了——初始化成"最后发出的号"，再 `INCR` 得到下一个。

### 2.2 它在代码里只有三个用途

| 用途 | 位置 | 说明 |
|---|---|---|
| **DB 发号（降级路径）** | `seq.go:145` `UPDATE ... RETURNING` | Redis 不可用时用它发号 |
| **Redis 键丢失时的装载值** | `seq.go:133` `GREATEST(next_seq, max(seq))` | 键丢了，从 DB 恢复"发到哪了" |
| **定期 checkpoint 写回** | `seq.go:239` `UPDATE ... SET next_seq = GREATEST(...)` | 每 60 s 把 Redis 的位点写回来兜底 |

还有第四个"顺带"的：`ConversationsByIDs` 会把 `next_seq` 一起查出来返回给客户端（`repo/chat.go:50`），所以它也是 API 字段 `nextSeq`。

**注意：正常路径（Redis 快路径）根本不碰 `next_seq`。** 它只是"灾备值"。

### 2.3 为什么需要它（不用 Redis 的话）

因为"发到几号了"这个状态**必须存在某个地方**。没有它：

- 服务重启后不知道该从几号继续；
- 两个并发请求无法协调（都得先读"到几号了"才能加一）。

**发号器的本质就是"一个被所有写入者共享的计数器"**。`next_seq` 是这个计数器在数据库里的形态；Redis 的 `conv:seq:{conv}` 是它在内存里的形态。**两者是同一个东西的两个副本**（Redis 是主，PG 是兜底）。

## 三、`conversations` 表为什么存在

### 3.1 它首先是"会话元数据表"，不是"发号表"

```
conversations = 会话的档案：类型（单聊/群聊）、群名、群头像、创建时间
next_seq      = 后加的一列，借用这张表存"这个会话发到几号了"
```

之所以放在这张表，是因为**"每个会话一行"这个粒度刚好匹配"每个会话一个计数器"**，不用新建表。

### 3.2 那能不能把 `next_seq` 拆出去？

可以，见 §四的"窄表拆分"。但要先明白：**拆出去只改变"单次更新的成本"，不改变"同一会话必须串行"这件事**。

---

## 四、能不能靠改表结构，消除对 `conversations` 的竞争？

这是你问得最好的一个问题。先给结论，再给六种方案的对比。

### 4.1 竞争的根源不是"表宽"，是"同一行"

```
同一会话的消息 A、消息 B
→ 都要执行 UPDATE conversations SET next_seq = next_seq + 1 WHERE id = 'single_1_2'
→ 改的是**同一行**
→ 数据库必须让它们排队（否则两个都读到 105，都写 106，重号）
```

**只要"计数"存在这一行里，排队就无法避免。** 表宽只影响"每次排队时干活多久"，不影响"必须排队"。

### 4.2 六种 DB 内方案的实测预期

| 方案 | 做法 | 单会话上限 | 为什么 |
|---|---|---|---|
| **现状** | 每消息 `UPDATE conversations` | **~33/s** | 事务 30 ms（含 fsync） |
| **窄表拆分** | 新建 `conv_seq(conv_id PK, next_seq)` | **~50/s（几乎没提升）** | 行本来就只有 100 字节、无二级索引；**省不下 commit 与 fsync** |
| **号段预取** | 一次 `next_seq = next_seq + 100`，内存里发 100 个 | **~3000/s** | 锁频率降到 1/100，但**崩溃会丢段**、洞变大 |
| **计数器分区** | `conv_seq` 按 `conv_id` 哈希分区 | **33/s（对同会话无帮助）** | 不同会话本来就锁不同行；同会话仍是同一行 |
| **advisory lock** | `pg_advisory_xact_lock(conv)` | **更差** | 显式锁 + 事务，成本更高 |
| **`max(seq)+1`** | 不用计数器，现算 | **不可用** | 并发下两个事务读到同一个 max → 重号；且 max 要扫索引 |

**关键结论：**

```
表结构优化最多带来 2–3 倍（号段预取）；
要拿到两个数量级，必须把计数器搬出数据库（Redis / 本地号段 / 雪花）。
```

> 所以你的直觉"压缩表信息"方向对了一半：**减少共享状态的"粒度"或"访问频率"确实有用**（号段预取就是减少频率），但**压缩行宽没用**——成本在事务提交，不在字节数。

### 4.3 为什么"号段预取"能到 3000/s 却不能更高

因为它仍然**每 100 条就要一次事务提交（含 fsync）**：

```
100 条 / 30 ms = 3333 条/秒
```

想再高，就得让"取号"这件事**完全不进数据库**——那就是 Redis。

### 4.4 一张图看清"改表能到什么程度"

```
33/s ──────► 50/s ──────► 3000/s ──────────────► 数十万/s
 现状        窄表         号段预取              Redis / 雪花
             (几乎没用)   (仍受 fsync 限)
```

## 五、既然 `messages` 里已经有 `id`，为什么还要 `seq`？

这是最容易被问住的一题。先把最诚实的部分说清楚：

> **在"单库、单实例、只做排序"这个极窄的场景里，`ORDER BY id` 确实能得到会话内的正确顺序**——因为 id 是全局自增的，全局单调的序列在任意子集上也是单调的。

所以问题不是"id 排不出顺序"，而是"**id 不能当会话内的游标**"。五个原因：

### 5.1 分库 / 多实例后，id 不再全局单调

```
库A 的 BIGSERIAL：1, 2, 3 ...
库B 的 BIGSERIAL：1, 2, 3 ...   ← 与库A 完全重叠
```

一旦分库，`id` 在**跨库范围内**既不唯一也不单调（库内仍各自唯一），`WHERE id > 105` 直接失效。而 `seq` 由**外置的发号器**产生，不依赖某个库的自增序列。

> 这也是[分册 11](../../11-分库分片与Redis集群.md) 说"分库前必须先改全局 ID"的原因。具体怎么改（号段 / 雪花 / 复合 ID，以及 JS 2^53 的坑），见[技术分析 · 09](../09-分库后消息ID重复与全局ID方案.md)。

### 5.2 id 的"洞"太大，无法做断档检测

```
会话 A 的消息 id：5, 12, 19, 31, 88 ...     ← 每条之间隔着别的会话的消息
会话 A 的 seq  ：1, 2,  3,  4,  5  ...     ← 近似连续
```

- 用 `seq`：客户端收到 `1, 2, 4`，立刻知道"3 丢了"，触发补拉；
- 用 `id`：收到 `5, 19, 31`，**无法判断**中间是"漏了"还是"本来就被别的会话占了"。

**洞的大小决定了能不能做 gap 检测。** 这是 seq 存在的最实际的理由之一。

### 5.3 id 不能预分配，而批量写入必须"先定号、再插入"

`id` 是 `BIGSERIAL`，它的值在 **INSERT 执行时**由 `nextval()` 产生。

但批量写入（[分册 05](../../05-组提交批量写入.md)）需要：

```
① 先为这一批 64 条消息分配好号（每个会话一段连续号）
② 再拼成一条多值 INSERT 写进去
③ 用 RETURNING 回映"哪条拿到了哪个 id/seq"
```

第 ① 步发生时还没有执行 INSERT，所以**不可能有 id**。必须有独立的发号器先把号定下来。

同理，"在写库之前就把 seq 回给客户端"（提前 ack 类设计）、"多副本各自服务同一会话"都需要预分配。

### 5.4 语义不同：id 回答"是谁"，seq 回答"排第几"

| 问题 | 用 id | 用 seq |
|---|---|---|
| 这条消息唯一标识是什么 | ✅ `id` | ❌（seq 只在会话内唯一） |
| 它在这个会话里排第几 | ❌ 跨会话交错，无法回答 | ✅ 直接就是 |
| 我读到第几条了 | 只能记"读到 id=88 那条" | ✅ `last_read_seq = 5` |
| 未读多少条 | 要 `count(*) where id > 88` | ✅ `最新 seq − 已读 seq`（设计上支持） |
| 断档检测 | ❌ 洞太大 | ✅ 近似连续，能看出漏 |

一句话：**`id` 是"身份"，`seq` 是"座位号"。** 你当然可以用身份证号排队，但没人这么干。

### 5.5 全局自增序列本身也是一个共享点

`BIGSERIAL` 背后是一个**全局序列**。所有 INSERT 都要向它要号：

- PG 内部对序列有锁与预写（每 32 个一批），所以它不是主要瓶颈；
- 但它把"所有会话的写入"耦合到了同一个计数器上——而 `seq` 是**每会话独立**的，天然分散。

### 5.6 顺带一提：id 的提交乱序问题，seq 也有

两者都是"先分配、后提交"，所以都可能出现"号小的后提交"。这个问题只能靠**同一会话串行提交**（[分册 05](../../05-组提交批量写入.md) 的按会话分片）解决，**不是 seq 独有的缺陷**。

## 六、三种方案的完整写入对照

### 6.1 方案一：DB 行锁（Node 时代）

```sql
BEGIN;
  UPDATE conversations SET next_seq = next_seq + 1 WHERE id = $conv RETURNING next_seq;  -- 行锁
  INSERT INTO messages (conversation_id, seq, ...) VALUES ($conv, $seq, ...);
COMMIT;
```

- 号从 `conversations` 来；
- 同一会话串行在**整个事务**上（~30 ms）；
- 单会话 ~33/s。

### 6.2 方案二：DB 号段预取（未采用）

```sql
-- 每 100 条才执行一次
UPDATE conversations SET next_seq = next_seq + 100 WHERE id = $conv RETURNING next_seq;
-- 内存里把 [end-99, end] 分给 100 条消息
INSERT INTO messages (...) VALUES (...) × N;   -- 与取号解耦
```

- 单会话 ~3000/s；
- 代价：崩溃丢段（洞最多 100）、多副本要各自预占、并发下号段交错。

### 6.3 方案三：Redis 发号（当前）

```bash
INCR conv:seq:{conv}        # 返回 106
```

```sql
INSERT INTO messages (conversation_id, seq, ...) VALUES ($conv, 106, ...)
ON CONFLICT (conversation_id, sender_id, client_msg_id) DO NOTHING
RETURNING id, seq;
```

- 号从 Redis 来，**`conversations` 退出热路径**；
- 同一会话串行在 Redis 的一条命令上（~1 μs）；
- 单会话数千/s；
- `next_seq` 退化为"每 60 s 同步一次的灾备值"。

## 七、常见追问

### Q1：能不能用 `created_at` 排序？

不建议：

- 同一毫秒内的多条消息**无法区分先后**（`TIMESTAMPTZ(0)` 精度到秒，更糟）；
- 系统时钟可能回拨（NTP 校正）；
- 仍然无法回答"这是第几条"，也无法做 gap 检测。

### Q2：能不能用 `(created_at, id)` 复合游标？

能排序，但：

- 游标变成二元组，API 与索引都更复杂；
- 分库后 `id` 不单调，退化成"仅按时间"；
- 仍然解决不了"第几条 / 未读数"。

### Q3：为什么不给每个会话建一个 PG sequence？

`CREATE SEQUENCE` 是**目录对象**，每个都有独立的元数据、锁与 WAL。百万级会话就是百万个序列对象——DDL 会爆炸，`pg_class` 会被撑爆。**PG 的序列是给"少数几个全局计数器"用的，不是给"每行一个计数器"用的。**

### Q4：为什么不用 `SELECT max(seq) + 1`？

并发下两个事务会读到同一个 `max`，都写 `max+1` → 重号（没有唯一索引时静默重号，有索引时一个失败）。而且 `max` 要走索引扫描，比计数器慢得多。

### Q5：`seq` 有洞，客户端排序会不会乱？

不会。客户端按 `seq` 排序只是"比大小"，有没有洞不影响顺序；补拉用 `seq > since`，洞也不影响。**只有"用减法算条数"的逻辑才需要连续**（比如 `未读 = 最大seq − 已读seq`），所以设计上宁可接受洞。

### Q6：那 `next_seq` 现在还有用吗？

有三个用途（§2.2）：DB 降级发号、Redis 键丢失时的装载值、每 60 s checkpoint 兜底。**它不是废字段，但已经不是热路径了。**

## 八、小结

| 问题 | 答案 |
|---|---|
| `next_seq` 是什么 | 会话表里的**发号计数器**，存的是"最后发出的号"（名字叫 next，语义是 last） |
| 为什么需要它 | 发号需要一个"所有写入者共享的计数状态"；没有它就无法协调并发、无法重启恢复 |
| `conversations` 表为什么存在 | 主要是会话元数据（类型/标题/头像）；`next_seq` 只是借用它的"每会话一行"粒度 |
| 改表能消除竞争吗 | **不能**。竞争源于"同一行"，不是"表宽"；DB 内最多 2–3×（号段预取） |
| 为什么不用 id 排序 | id 能排序，但**不能当会话内游标**：分库后不单调、洞太大无法 gap 检测、不能预分配、语义是"全局第几条" |
| id 和 seq 的分工 | **id 是身份，seq 是座位号**；两者都需要 |
| 最快的方案是什么 | 把计数器搬出 DB（Redis），把互斥从 ~30 ms 压到 ~1 μs |
