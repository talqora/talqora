## 一、五个最小必要概念（先懂这五个）

### 1.1 会话（conversation）

**是什么**：一段"聊天窗口"。两个人私聊是一个会话，一个群是一个会话。**消息都属于某个会话。**

**在本项目里**：会话用一个字符串 ID 标识，规则是拼出来的：

| 类型 | ID 形态 | 例子 |
|---|---|---|
| 单聊 | `single_<用户A的ID>_<用户B的ID>` | `single_1_2` |
| 群聊 | `group_<群ID>` | `group_9000002` |

这个 ID 是**可推导的**：给你两个用户 ID，你就能算出他们的会话 ID（不需要查库）。

**为什么和发号器有关**：`seq` 是**会话内**的序号，不是全局的。所以"两个人在同一个窗口里"才需要排队拿号；不同会话之间互不影响。

> 打个比方：会话 = 一个微信群；seq = 这个群里的第几条消息。

### 1.2 seq（会话内序号 / sequence）

**是什么**：一条消息在**它所属的会话里**的编号，从 1 开始，只增不减。

```
single_1_2 会话：  1, 2, 3, 4, ... 105, 106   ← 每个会话各自从 1 开始
single_3_4 会话：  1, 2, 3, ...               ← 另一个会话，也是从 1 开始
```

**它必须满足两条**：

1. **单调递增**：后发的消息号一定比前发的大；
2. **不重复**：同一会话里不会有两个消息拿到同一个号。

**它用来干什么**：客户端断线重连后，会说"我最后看到的是 105 号，把 105 之后的都给我"——服务端就用 `seq > 105` 查出漏掉的消息补给它。这叫**增量同步**。所以 seq 一旦回退或重复，客户端就会**漏消息或重复消息**。

**注意它不是这些**：

| 容易混淆的 | 区别 |
|---|---|
| 数据库主键 `id` | 全局自增，跨会话交错；seq 是每次会话内独立计数 |
| 消息时间戳 | 可能相同、可能乱序；seq 由发号器保证严格递增 |
| 消息条数 | seq 允许有洞（跳号），不等于条数 |

**为什么和发号器有关**：**发号器就是"产生 seq 的组件"**。发号器的全部性能问题，都来自"怎么让两个并发请求拿到不同的、且大的在后"。

### 1.3 事务（transaction）

**是什么**：一组数据库操作，**要么全成功，要么全失败**。

```sql
BEGIN;                              -- 开始
  UPDATE conversations SET next_seq = next_seq + 1;
  INSERT INTO messages (...) VALUES (...);
COMMIT;                             -- 提交：两者一起生效（或者一起回滚）
```

**关键点**：`COMMIT` 不是"告诉数据库我做完了"这么简单——它要让数据**真的落到磁盘**（见 §3 的 WAL / fsync），这一步要花毫秒级时间。

**为什么和发号器有关**：如果发号放在事务里，那么"锁住发号那一行"的时间 = **整个事务的时间**，其中包含等待落盘的时间。这就是"临界区长"的根源。

### 1.4 锁（lock）与行锁

**是什么**：防止两个人同时改同一份数据的机制。**行锁** = 只锁住"某一行"。

```
请求 A：UPDATE conversations SET next_seq=next_seq+1 WHERE id='single_1_2'
        → 数据库把这一行"锁住"，别人改不了

请求 B：UPDATE ... 同一行
        → 发现被锁 → 排队等 A 结束
```

**关键点（最容易误解）**：PG 的行锁**不是一张锁表**，它是写在**这一行数据自己的头部**的一个字段（`xmax`）。所以它跟着这一行走，跨进程、跨机器都有效——**起多少个业务副本都绕不开它**。

**为什么和发号器有关**：只用数据库发号时，"给同一会话发号"这件事天然要求排队，排队就得加锁。**锁的持有时间决定了排队多久。**

### 1.5 连接池（connection pool）

**是什么**：数据库连接是稀缺资源（PG 里一条连接 = 一个操作系统进程）。应用不会每次查询都新建连接，而是从**池子**里借一条，用完还回去。

```
池子容量 32：同时最多 32 个请求在用数据库
第 33 个请求 → 排队等别人还回来
```

**关键点**：**连接是"独占"的**——借出去的那段时间，别人用不了。所以"每条消息占用连接多久"直接决定系统能同时处理多少消息。

**为什么和发号器有关**：只用数据库发号时，请求在**等锁的时候仍然占着连接**。于是"等锁"会连锁成"池被占满"，最终**全站**（不只是那个会话）都拿不到连接——这就是压测里"断崖式失败"的机制。

## 二、业务层术语

| 术语 | 一句话解释 | 在本项目里 |
|---|---|---|
| **消息（message）** | 一条聊天内容 | `messages` 表一行：谁发的、在哪个会话、内容、seq、时间 |
| **clientMsgId** | **客户端自己生成**的消息编号（不是 seq） | 客户端发消息时带一个唯一字符串（≤64 字符），用于"重发去重" |
| **ack** | 服务端的确认回执 | `message.ack { clientMsgId, seq, serverMsgId }`；客户端凭它确认发送成功 |
| **重发** | 客户端 5 秒没收到 ack，就用**同一个 clientMsgId** 再发一次 | 所以服务端必须能识别"这条我处理过了" |
| **幂等** | 同一个操作执行 1 次和执行 N 次，效果一样 | 重发不会产生两条消息 |
| **扇出（fanout）** | 一条消息要投给会话里的多个成员 | 单聊投 2 人，群聊投全部在线成员 |
| **上行 / 下行** | 上行 = 客户端→服务端；下行 = 服务端→客户端 | 上行是 `message.send`，下行是 `receiveMessage` |
| **在线状态（presence）** | 记录"这个用户现在连在哪个网关副本上" | Redis 的 `presence:{userId}` ZSET + `:meta` HASH |
| **已读位点** | 我读到第几条了 | `user_conversations.last_read_seq` |
| **增量同步** | 断线重连后只拉"我漏掉的" | `GET /user/sync?conv=&since=105` → 返回 `seq > 105` 的消息 |
| **跳号 / 空洞** | seq 不连续（如 1,2,5,6） | 允许存在；补拉用 `seq > since`，不受影响 |

> 一个容易混的点：**clientMsgId 是客户端的"这条消息的身份证"，seq 是服务端分配的"这个会话里的第几号"**。前者用于去重，后者用于排序和补拉。

## 三、数据库术语

### 3.1 表结构相关

| 术语 | 解释 |
|---|---|
| **表 / 行 / 列** | 关系数据库的基本单位；一行 = 一条记录 |
| **主键（PRIMARY KEY）** | 唯一标识一行的列（组合） |
| **索引（index）** | 为了"快速找到某行"而额外维护的有序结构（B+tree） |
| **唯一约束 / 唯一索引** | 保证某一列（组合）不重复；插入重复会报错（PG: `23505`） |
| **约束（constraint）** | 数据库强制的规则，如非空、唯一、外键 |

本项目的关键约束：

```sql
messages  PRIMARY KEY (id, conversation_id)                    -- 分区表要求含分区键
messages  UNIQUE (conversation_id, sender_id, client_msg_id)   -- 幂等去重
messages  UNIQUE (conversation_id, seq)                        -- 待加：防重号
```

### 3.2 事务与并发

| 术语 | 解释 | 本项目 |
|---|---|---|
| **BEGIN / COMMIT / ROLLBACK** | 开始 / 提交 / 回滚 | 消息落库原本用 `BEGIN ... COMMIT` |
| **隐式事务（autocommit）** | 不开 BEGIN，单条语句自己就是一个事务 | 优化目标 |
| **隔离级别** | 并发事务之间能"看见"彼此多少 | PG 默认 READ COMMITTED |
| **快照（snapshot）** | 事务开始时"看到的数据版本" | RC 下每条语句一个新快照 |
| **MVCC** | 多版本并发控制：改数据不覆盖原行，而是写新版本 | 旧版本留给 vacuum 回收 |
| **元组（tuple）** | 行在磁盘页里的物理形态 | 行锁就存在元组头的 `xmax` 字段 |
| **死锁（deadlock）** | 两个事务互相等对方的锁 | 数据库会杀掉一个（PG: `40P01`） |

### 3.3 持久化相关（**这是"事务为什么慢"的核心**）

| 术语 | 解释 |
|---|---|
| **WAL（Write-Ahead Log）** | 预写日志：改数据前先记一条"我要改什么"，崩溃后靠它重放 |
| **fsync** | 强制把操作系统缓存里的数据刷到磁盘——**要等硬件确认，毫秒级** |
| **commit record** | 提交时写进 WAL 的一条"这个事务完成了"的记录 |
| **checkpoint** | 定期把内存里的脏页刷盘，并推进 WAL 的回收起点 |
| **组提交（group commit）** | 多个并发事务共享一次 fsync，把 N 次刷盘合并成 1 次 |

**一句话理解事务的成本**：

```
COMMIT 时：写一条 commit record → fsync 等磁盘 → 才算提交成功
              ↑ 这一步 1–10 ms，是"每条消息一个事务"慢的根本原因
```

> 注意：**COMMIT 不等数据页落盘，只等 WAL 落盘**。数据页由后台慢慢刷。

### 3.4 分区（partition）

| 术语 | 解释 | 本项目 |
|---|---|---|
| **分区表** | 一张逻辑表，物理上拆成多张子表 | `messages` 按 `conversation_id` 哈希成 64 片 |
| **分区裁剪** | 查询带分区键时，只扫相关的那一片 | `WHERE conversation_id='x'` → 只扫 1 片 |

## 四、性能术语

| 术语 | 解释 | 怎么看 |
|---|---|---|
| **吞吐（throughput）** | 每秒处理多少条 | msg/s |
| **延迟（latency）** | 一条请求要多久 | ms |
| **p50 / p95 / p99** | 50%/95%/99% 的请求快于这个值 | p99 = "最慢那 1% 的门槛" |
| **并发 / 并行** | 并发 = 同时有很多请求；并行 = 真的同时在跑 | 32 条连接只能并行 32 个 |
| **串行** | 一个做完才做下一个 | 同一会话的发号必须串行 |
| **临界区** | 同一时刻只允许一个执行体进入的区间 | 行锁的持有期就是一个临界区 |
| **互斥** | 保证"同一时刻只有一个"的机制 | 锁、单线程、原子命令 |
| **竞争（contention）** | 多个请求抢同一个资源 | 行锁、连接池、Redis 单线程 |
| **排队** | 抢不到就等 | 等锁、等连接 |
| **利用率** | 资源忙碌时间占比 | 池 89% 就会开始明显排队 |
| **尾延迟放大** | 一个请求要等 N 个资源，最慢的那个决定整体 | 跨 64 片查询时 p99 变成 p53 |
| **RTT** | 一次网络往返的时间 | 同机容器 0.2–1 ms |
| **持有时间** | 占着某个资源多久 | 占连接 9 ms / 0.13 ms |
| **写放大** | 一次业务写触发多次物理写 | 1 条消息写 3 次表 |

## 五、发号器与分布式术语

| 术语 | 解释 | 本项目 |
|---|---|---|
| **发号器** | 产生递增编号的组件 | `NextSeq()` |
| **号段** | 一次取一段连续号（如一次取 64 个） | `INCRBY n` |
| **跳号** | 号不连续 | 失败/重试会产生，可接受 |
| **单调递增** | 后取的号一定更大 | seq 的硬要求 |
| **原子操作** | 不可被打断的操作 | `INCR` 是原子的 |
| **幂等键** | 用来判断"这个操作做过没有"的 key | `msg:idem:{conv}:{sender}:{clientMsgId}` |
| **降级** | 主方案不可用时的退路 | Redis 挂了 → 回 DB 行锁 |
| **副本（replica）** | 数据库的完整拷贝 | 只读副本；**不增加写能力** |
| **分片（sharding）** | 把数据按 key 切到多个物理单元 | 64 个哈希分区 |
| **最终一致** | 短暂不一致，但最终会一致 | 实时下行丢帧 → `/sync` 补 |

## 六、本项目特有名词

| 名词 | 解释 |
|---|---|
| **biz** | Go 写的业务层（无状态、多副本） |
| **gateway** | Go 写的长连接网关（持有 WebSocket 连接） |
| **edge 流** | gateway ↔ biz 之间的 gRPC 双向流，上行帧与 ack 都走它 |
| **定向下行** | 按 `presence` 里记录的副本，把消息**直接**发给持有该用户连接的网关 |
| **pub/sub 兜底** | 直发失败时，改成往 Redis 频道 `gw:downlink` 广播，所有网关都收到、由持有连接的那个投递 |
| **`conv:seq:{conv}`** | Redis 里每个会话一个计数器，`INCR` 就是发号 |
| **checkpoint（发号位点）** | 每 60 s 把 Redis 里的号写回 `conversations.next_seq`，作为灾备兜底 |
| **快路径 / 冷路径 / 降级** | 发号器的三条执行路径（1 次 Redis / 3 次往返 / 回 DB 行锁） |

## 七、用一段人话把所有概念串起来

> 两个人在一个**会话**（`single_1_2`）里聊天。
> 甲发了一条消息，客户端给它编了一个**临时身份证**（`clientMsgId`），发给服务端。
> 服务端要给它分配一个**会话内序号**（`seq`），保证比这个窗口里之前的消息都大——这个分配动作叫**发号**。
> 为了拿到不重复的号，同一会话的并发请求必须**排队**（互斥）。
> 如果排队的地方是**数据库的一行**（**行锁**），那么排队的时长 = 一整个**事务**（因为锁要等 `COMMIT`），而 `COMMIT` 要等 **fsync** 刷盘 → 一次排队几十毫秒。
> 更糟的是：排队的人**占着数据库连接**（**连接池**只有 32 条），等的人一多，池就满了，**整个系统**都拿不到连接。
> 所以把排队的地方挪到 **Redis**——它用**单线程**天然保证互斥，一条 `INCR` 命令只要 1 微秒，而且**不占数据库连接**。
> 号拿到之后，两个请求在数据库里各写各的行，**完全并行**，只共享一次提交（**组提交**）。
>
> 这就是"发号器优化"的全部故事。
