# 08 · 索引瘦身与序列优化（方向 H）

> 归属：[`00-消息吞吐上限分析与提升技术方案.md`](./00-消息吞吐上限分析与提升技术方案.md) §5.5-H
> 优先级：P2/P3（0.5 人日，单语句耗时 −10%~20%；**额度小但零风险**）
> 一句话：`messages` 上挂了 4 个索引，其中 **2 个没有任何查询在消费**，却要为每条 INSERT 支付维护成本。删掉它们不改任何行为，只是让每条写入少做两次 B-tree 插入。

---

## 一、现状分析

### 1.1 四个索引

`migrations/0007_messages_partition.up.sql:102-105`（分区主表上建，自动传播到 64 个分区）：

```sql
CREATE INDEX "idx_messages_conv_seq"  ON messages_partitioned("conversation_id", "seq" DESC);
CREATE INDEX "idx_messages_conv_ts"   ON messages_partitioned("conversation_id", "timestamp" DESC);
CREATE INDEX "idx_messages_sender_ts" ON messages_partitioned("sender_id", "timestamp" DESC);
CREATE UNIQUE INDEX "uniq_msg_idem"   ON messages_partitioned("conversation_id", "sender_id", "client_msg_id");
```

外加主键 `PRIMARY KEY (id, conversation_id)`（`0007:25`）——**共 5 棵 B-tree**，每条 INSERT 要维护 5 处。

### 1.2 谁在消费这些索引

| 索引 | 消费方 | 结论 |
|---|---|---|
| `idx_messages_conv_seq` | `Messages`（`chat.go:75`，`seq DESC LIMIT`）、`MessagesSince`（`chat.go:88`，`seq > ? ASC`）、`loadNextSeqFromPG` 的 `max(seq)`（`seq.go:133`） | **核心索引，保留** |
| `idx_messages_conv_ts` | 仅 `AllMessages`（`chat.go:82`，`timestamp ASC` 无 LIMIT） | 分册 07 修完后**无消费方** → 可删 |
| `idx_messages_sender_ts` | **无** | 全仓 grep `sender_id` 仅出现在 SELECT 列、幂等 WHERE（`message.go:190`，走 `uniq_msg_idem`）与 JSON 输出 → **可删** |
| `uniq_msg_idem` | `ON CONFLICT (conversation_id, sender_id, client_msg_id)` 的冲突目标 | **必需，保留** |
| `PRIMARY KEY (id, conversation_id)` | 分区表强制要求含分区键 | 保留 |

> 核实命令：
> ```bash
> grep -rn "sender_id" biz/internal/repo biz/internal/service biz/internal/api
> ```
> 输出里没有一条 `WHERE sender_id = ?` 或 `ORDER BY sender_id`，也没有按发送者查"我发的消息"的接口。

### 1.3 一条 INSERT 的实际写入量

```
heap tuple（~200 B，含 TOAST 可能性低）
+ PK 索引条目
+ conv_seq 索引条目
+ conv_ts 索引条目
+ sender_ts 索引条目
+ uniq_msg_idem 唯一索引条目（含唯一性探测）
= 1 次堆写 + 5 次索引写
```

索引条目本身不大（十几到几十字节），但每次都是一次**独立的 buffer 修改 + WAL 记录**。按经验，每多一个索引，小行 INSERT 的成本增加 5%–10%——4 个变 2 个，预期 **−10%~20%**（不是翻倍，别期待过高）。

### 1.4 序列的真实情况（一个常见的误判）

`id BIGSERIAL`（`0007:8`）默认 `CACHE 1`。很多资料说"cache=1 时每次 nextval 都写 WAL"，这只说对了一半：

- PG 内部有 `SEQ_LOG_VALS = 32` 的预写机制：即使 `CACHE 1`，也是**每 32 次 nextval 才写一次 WAL**；
- 真正的成本是**每次 nextval 都要更新同一个序列的共享缓冲页**，在极高并发下是一个串行点（同一序列的所有 INSERT 都排队）。

所以：

| 手段 | 真实收益 | 判断 |
|---|---|---|
| `ALTER SEQUENCE ... CACHE 200` | 减少序列页竞争；跳号变多 | **低优先级**，需实测确认有收益再上 |
| 应用侧雪花 id | 彻底移除 nextval | 改动大（`id` 是对外 `serverMsgId`），不推荐现在做 |

**结论：序列不是当前瓶颈，不要为它改表。** 但批量写入（分册 05）会把 nextval 的调用密度提高一个量级，届时值得测一次 `CACHE` 的效果。

## 二、优化原理

### 2.1 索引的写放大

B-tree 索引是**有序结构**，插入一条索引条目意味着：

1. 定位目标叶子页（可能不在内存 → 一次随机读）；
2. 在页内插入并可能分裂；
3. 写 WAL 记录；
4. 若页脏，后续 checkpoint 要落盘。

对本表来说，`conversation_id` 是随机分布的（64 个哈希分区已经把会话打散），所以 `conv_*` 两个索引的插入点**分散**；`uniq_msg_idem` 的前缀也是 `conversation_id`，同样分散。分散的插入点意味着更多的 buffer 命中失败——这是"索引多"比"行大"更伤写入的原因。

### 2.2 删索引的收益不是线性的

| 索引数 | 相对写入成本（示意） |
|---|---|
| 5（现状） | 100% |
| 3（删 conv_ts、sender_ts） | ~80%–90% |

不会减半，因为堆写与 WAL 的固定成本还在。**这也是为什么它是"顺手做"，而不是"核心方案"。**

## 三、具体方案

### 3.1 前置条件（不要提前做）

| 前提 | 原因 |
|---|---|
| 分册 07 上线且 `AllMessages` 无流量 | 否则删掉 `conv_ts` 会让 `/user/messages` 无参路径退化成全表扫 + 排序 |
| 确认无外部报表/BI 直连此库按 `timestamp` 排序 | 生产库可能有离线任务 |

建议先在 `pg_stat_user_indexes` 观察一个周期：

```sql
SELECT indexrelname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
WHERE relname LIKE 'messages_p%'
ORDER BY idx_scan ASC;
```

`idx_scan` 长期为 0 的索引才是安全删除对象。

### 3.2 删除步骤（分区表）

```sql
-- 1) 先在父表删（PG 会自动处理各分区的子索引）
DROP INDEX CONCURRENTLY idx_messages_conv_ts;    -- 分区表不支持 CONCURRENTLY，见坑 1
DROP INDEX idx_messages_sender_ts;
```

实际的推荐姿势：

```sql
-- 逐分区删（每个都是普通索引，支持 CONCURRENTLY）
DROP INDEX CONCURRENTLY messages_p00_sender_ts;  -- × 64
...
-- 最后删父索引的壳
DROP INDEX idx_messages_conv_ts_...
```

> 索引命名规则：`CREATE INDEX idx_x ON parent` 在每个分区上会生成 `messages_pNN_x` 形式的子索引。删父索引会自动删子索引，但**非 CONCURRENTLY 会持锁**。

### 3.3 序列（可选）

```sql
ALTER SEQUENCE messages_id_seq CACHE 200;
```

只在批量写入上线后、且实测确认 nextval 是热点时才做。

## 四、坑点

### 坑 1：分区表不支持 `DROP INDEX CONCURRENTLY`

`DROP INDEX CONCURRENTLY` 对分区**父**索引报 `cannot drop index ... concurrently`（与 `CREATE INDEX CONCURRENTLY` 同源限制）。两条路：

| 方式 | 阻塞 | 做法 |
|---|---|---|
| 直接 `DROP INDEX`（父） | 对父表与各分区持 `ACCESS EXCLUSIVE`，**瞬间完成**（只删元数据） | 推荐。删索引不重写数据，锁窗口是毫秒级 |
| 逐分区 `CONCURRENTLY` 再删父壳 | 零阻塞 | 索引多时更稳妥 |

**注意**：`DROP INDEX` 虽然快，但它要等所有持有该表锁的事务结束。压测中长事务会把它卡住，进而阻塞后续所有查询 → **必须在低峰期做，并设 `lock_timeout`**：

```sql
SET lock_timeout = '3s';
DROP INDEX idx_messages_sender_ts;
```

超时就重试，不要放大到 30 s。

### 坑 2：删索引后"不报错但变慢"是最危险的结果

删错索引不会立刻出错，只会在某个查询上悄悄退化成全表扫。**必须先看 `pg_stat_user_indexes.idx_scan`，再删**，并在删后对比关键查询的 `EXPLAIN (ANALYZE, BUFFERS)`。

### 坑 3：`uniq_msg_idem` 不能顺便"优化"成部分索引

有人会想加 `WHERE client_msg_id IS NOT NULL` 来缩小索引（历史消息的 `client_msg_id` 为 NULL）。但 `ON CONFLICT (conversation_id, sender_id, client_msg_id)` 依赖一个**完整的唯一索引**做冲突仲裁，部分索引会导致 `ON CONFLICT` 找不到匹配的仲裁索引而报错。保持原样。

### 坑 4：序列 CACHE 与主从切换

`CACHE 200` 后，每个会话会缓存 200 个值；主库崩溃切换时，未用完的缓存值丢失 → 更大的 id 空洞。`id` 只作唯一标识（`serverMsgId`），空洞无害。**但如果有任何逻辑假设 "id 连续"，就会坏**——目前没有（`sync`/分页都用 `seq`）。

### 坑 5：不要顺手改主键

`PRIMARY KEY (id, conversation_id)` 是分区表的硬要求（唯一约束必须包含分区键）。改成 `(conversation_id, id)` 会影响现有基于 `id` 的查询计划，属于"看起来等价、实际全表重写"的操作，不在本次范围。

### 坑 6：索引瘦身与唯一索引新增不要混在一次迁移

分册 01 要**新增** `uq_messages_conv_seq`，本册要**删除**两个索引。混在一次 migration 里，一旦失败很难判断是哪一步的问题，也无法单独回滚。分成两个 migration 文件。

## 五、验证方法

| 项 | 方法 | 通过标准 |
|---|---|---|
| 索引确实不再被用 | `pg_stat_user_indexes.idx_scan` | 删除前一个周期内 = 0 |
| 写入变快 | `db_query_duration_seconds{model="messages"}` 均值 | 下降 10%–20% |
| 关键查询不回退 | `EXPLAIN (ANALYZE, BUFFERS)` on `Messages` / `MessagesSince` / `max(seq)` | 仍走 `idx_messages_conv_seq`，行数不变 |
| 存储下降 | `pg_relation_size('messages')` 与各分区索引大小 | 索引总体积下降 ~40% |
| 序列（若做） | 批量场景下 `xact_commit` 与 CPU | nextval 不再是热点 |
