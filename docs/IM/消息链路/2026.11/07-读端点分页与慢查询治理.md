# 07 · 读端点分页与慢查询治理（方向 G）

> 归属：[`00-消息吞吐上限分析与提升技术方案.md`](./00-消息吞吐上限分析与提升技术方案.md) §5.4-G
> 优先级：P1（**0.2 人日**，止血效果最大的一条；不写这一条，后面所有优化都会被它吃掉）
> 一句话：`/user/messages` 不传 `limit` 时会把**整个会话的全部消息**查出来串行化返回。实测同一端点：无 limit 是 **7 rps / p50 1874 ms**，`limit=50` 是 **3964 rps / p50 5 ms**——**558 倍**。修它只需要把无参路径指向已有的分页分支。

---

## 一、现状分析

### 1.1 代码事实

`biz/internal/api/chat_routes.go:78-88`：

```go
limitStr := c.Query("limit")
if limitStr == "" {
    // 旧行为:全量升序(零改动兼容)
    messages, err := chatSvc.AllMessages(c.Request.Context(), conversationID)
    ...
    c.JSON(http.StatusOK, gin.H{"success": true, "data": messages})
    return
}
```

`biz/internal/repo/chat.go:80-83`：

```go
func (chatRepo) AllMessages(ctx context.Context, convID string) ([]Message, error) {
    return queryMessages(ctx, msgColumns, "WHERE conversation_id = $1 ORDER BY timestamp ASC", convID)
}
```

没有 `LIMIT`、没有游标、没有上限。压测账号所在会话有 3.5 万条消息 → 单请求要扫描 + 序列化 + 传输 3.5 万行。

### 1.2 已有分页分支完全可用

同一文件的 `limit` 分支（`chat_routes.go:90-120`）已经实现了完整的键集分页：

| 参数 | 语义 |
|---|---|
| `limit` | 1–200，返回 `seq DESC` 一页 |
| `beforeSeq` | 上一页最后一条的 `seq`（第一页不传） |
| 响应 | `{data, hasMore}`，`hasMore` 由"多取一条"判定 |

底层 SQL（`repo/chat.go:69-77`）：

```sql
WHERE conversation_id = $1 [AND seq < $2] ORDER BY seq DESC LIMIT $3
```

走 `idx_messages_conv_seq (conversation_id, seq DESC)`，单页 5 ms。

也就是说：**能力早就有了，只是默认路径没走它。**

### 1.3 第二个慢端点：`/user/lastMessages`

`repo/chat.go:92-95`：

```sql
SELECT DISTINCT ON (conversation_id) <17 列>
FROM messages
WHERE conversation_id = ANY($1::text[])
ORDER BY conversation_id, timestamp DESC
```

成本来自两处，且都与"会话数"成正比：

1. **每个会话一次索引扫描**：`DISTINCT ON` 需要对每个会话取"最新一条"，即便 `(conversation_id, timestamp DESC)` 索引能让每次只读一行，也是 **N 个会话 → N 次索引查找**；
2. **多分区归并**：`ANY($1)` 会让计划变成多分区的 `Append`/`MergeAppend`（数组参数下裁剪能力弱于单值常量），再叠加 `DISTINCT ON` 的排序/去重。

实测 52 ms 的量级与此吻合：约 40 个分区 × 每分区一次索引查找（0.5–1 ms 随机 IO）+ 归并。**注意这不是"扫了全表"——所以优化方向不是"减少分区扫描"，而是"减少每个会话的查询次数"**（缓存最新一条，或改为按会话点查）。

实测 p50 **52 ms**，是 `/user/sync` 的 10 倍。每 100 rps 就占 5.2 条连接（16%）。

## 二、优化原理

### 2.1 池的账要按"连接·秒"算

```
某端点的连接占用 = rps × 单请求耗时
```

`/user/messages` 无 limit：`7 rps × 1.874 s = 13.1 连接·秒/秒`，池总共只有 32 连接·秒/秒 → **7 个并发就把 41% 的池吃掉了**。

对比分页版：`3964 × 0.005 = 19.8`——注意这个 3964 是**池被打满时的极限 rps**，不是它的正常成本。真正该看的是"单请求连接·秒"：

| 端点 | 单请求连接·秒 | 相对成本 |
|---|---|---|
| `/user/messages`（无 limit） | **1.874** | **375×** |
| `/user/messages?limit=50` | 0.005 | 1× |
| `/user/lastMessages` | 0.052 | 10× |
| `/user/sync` | 0.005 | 1× |

**结论：不是"读接口太多"，而是"少数几个读接口特别贵"。** 降低单请求成本比限制 QPS 有效得多。

### 2.2 分页为什么能快 558 倍

| 维度 | 全量 | 分页 |
|---|---|---|
| 扫描行数 | 3.5 万 | 51（limit+1） |
| 排序 | 需要（`ORDER BY timestamp`） | 无（索引有序） |
| 序列化 | 3.5 万 × 17 列 → 数 MB JSON | 50 × 17 列 → 几十 KB |
| 网络传输 | 数 MB | 几十 KB |
| 连接持有 | 1.8 s | 5 ms |

不是"SQL 优化"带来的，而是**根本不需要查那么多**。

## 三、具体方案

### 3.1 `/user/messages` 改默认分页（必做，0.2 d）

```go
const (
    msgDefaultLimit = 50
    msgMaxLimit     = 200
)

limitStr := c.Query("limit")
limit := msgDefaultLimit
if limitStr != "" {
    n, err := strconv.Atoi(limitStr)
    if err != nil || n <= 0 || n > msgMaxLimit {
        c.JSON(400, ...); return
    }
    limit = n
}
// 之后统一走已有的 beforeSeq 分支
```

### 3.2 兼容性处理（关键，见坑 1）

无参路径与分页路径**语义不同**，不能直接替换：

| 维度 | 无参（旧） | 分页（新） |
|---|---|---|
| 排序 | `timestamp ASC`（正序） | `seq DESC`（倒序，最新在前） |
| 数量 | 全部 | 50 |
| 响应 | `{data}` | `{data, hasMore}` |

推荐做法：**保留"正序"语义，只加数量上限**。

```go
// 新分支：默认返回"最近 N 条，按时间正序"
if limitStr == "" && c.Query("beforeSeq") == "" {
    msgs, err := chatSvc.Messages(ctx, convID, 0, msgDefaultLimit)  // seq DESC LIMIT 51
    // 反转成正序后再返回
    slices.Reverse(msgs)
    c.JSON(200, gin.H{"data": msgs, "hasMore": len(msgs) == msgDefaultLimit})
}
```

这样老客户端拿到的仍是"正序、最后 50 条"，只是**不再返回全量**。这是唯一兼顾兼容与止血的选项。

### 3.3 `/user/lastMessages` 的三种改法

| 方案 | 做法 | 成本 | 评价 |
|---|---|---|---|
| A. 逐会话单点查询 | `for convID { SELECT ... WHERE conversation_id=$1 ORDER BY seq DESC LIMIT 1 }` | 低 | 可裁剪到单分区，N 次点查；N 通常 < 50，仍比全分区扫快 |
| B. Redis 缓存 | 写入时把"会话最后一条"写进 `conv:last:{conv}`（HSET 或 String） | 中 | **最快**（O(1)），但要维护一致性（删除/编辑消息时要更新） |
| C. 反范式表 | 建 `conversation_last(conv_id PK, msg_id, seq, ts, preview)`，写消息时 UPSERT | 中 | 与 B 类似，但落在 PG，事务内可保证一致 |

推荐 **A 先上线（零风险）→ 观察 → 再评估 B/C**。A 的改动只在一个 repo 方法内，不动表结构。

```sql
-- A 的形态：UNNEST + LATERAL，仍是一次往返
SELECT m.*
FROM unnest($1::text[]) AS c(conv_id)
CROSS JOIN LATERAL (
  SELECT * FROM messages WHERE conversation_id = c.conv_id ORDER BY seq DESC LIMIT 1
) m;
```

### 3.4 顺手做掉：授权缺口

`/user/messages` 与 `/user/lastMessages` **有认证（`AuthenticateToken`）但没有成员授权**——对比 `/user/sync` 有 `IsConversationMember`（`sync_routes.go:72`）。而 `conversationId` 形如 `single_<uid1>_<uid2>`、`group_<id>`，可枚举，因此任何登录用户都能读任意会话。这是独立的**安全缺陷**，已单列：[问题 08](./问题分析/08-读接口缺成员授权.md)。

> 建议与分页改造同批做，但注意顺序：**先分页降成本，再加授权**。加了校验就多一次 PG 查询（`read.go:15-24`），会把单请求从 5 ms 抬到 ~8 ms；单聊可用"从 ID 推导参与者"做到**零查询**。

## 四、坑点

### 坑 1：排序方向变了会让前端首屏倒过来

旧路径 `ORDER BY timestamp ASC`，新路径（若直接走分页分支）是 `seq DESC`。前端如果是"直接渲染返回数组"，会看到最新消息排在最上面。

**上线前必须核对 web 端调用点**：

```bash
grep -rn "user/messages" web/src | head
```

如果前端已经在用 `limit`（可能已经在分页），那无参路径可能只有旧版本客户端/脚本在用，可以直接切；否则按 §3.2 保留正序。

### 坑 2：`hasMore` 的语义与旧响应不同

旧响应没有 `hasMore`，前端可能用 `data.length` 判断"还有没有"。新响应加了 `hasMore` 但 `data` 变短了，如果前端用 `data.length < 期望` 判断"到底了"，会误判。

**建议**：`hasMore` 与 `data` 同时返回，但保留一个开关 `MSG_LIST_LEGACY_FULL=1` 可回滚（默认 0）。灰度一轮后再删开关。

### 坑 3：不能只改默认值不做上限

只把默认值改成 50、但仍允许 `limit=100000`，等于给攻击者留了一个 OOM 入口。当前分页分支已限制 `limit ≤ 200`（`chat_routes.go:91`），保持。

### 坑 4：`/user/lastMessages` 的输出是 snake_case

`handleLastMessages` 的注释明确写着"输出 snake_case 列名（`$queryRaw` 原始行形态，web 前端依赖）"（`chat_routes.go:143`）。改 SQL 时**不要顺手把列别名改成 camelCase**，前端会解析失败。

### 坑 5：`AllMessages` 不要立刻删

留一个版本周期，观察调用量（加一个 `metrics.AllMessagesCalled` 计数器）。确认无流量后再删函数与 `idx_messages_conv_ts` 索引（分册 08 依赖这个前提）。

### 坑 6：慢查询熔断不要做成"静默降级"

若给慢端点加超时/熔断，返回的必须是**显式错误**（503 + `Retry-After`），不能返回空数组——空数组在 IM 里意味着"这个会话没有任何消息"，客户端会据此清空本地缓存，造成用户可见的数据丢失。

## 五、验证方法

| 项 | 方法 | 通过标准 |
|---|---|---|
| 无参路径 | `node perf/http-bench.mjs`（不加 limit 的场景） | 从 7 rps 提到 **≥ 1500 rps**，p50 ≤ 20 ms |
| 分页路径不回退 | 同一脚本带 `limit=50` | 保持 ≈3964 rps |
| 首屏兼容 | 手工调无参接口 | 返回最近 50 条、正序、带 `hasMore` |
| 池占用 | 注入 7 rps 无参请求 + WS 2000 msg/s | 消息侧 p99 劣化 ≤ 10% |
| `lastMessages` | `http-bench` 单端点 | p50 从 52 ms 降到 ≤ 15 ms |
